# Ось: performance

**Владелец:** Agent tool, `subagent_type=Performance Benchmarker`. Этот файл
целиком идёт в промпт субагенту вместе с путями/hunks из шага 1 диспетчера.
Если тип недоступен в runtime — пройти чек-лист инлайн, пометив в отчёте
`(inline, agent-тип недоступен)`.
**Не трогает:** корректность SQL и транзакции — это ось persistence.
Здесь только стоимость: время, память, число запросов, внешние вызовы.

## Чек-лист

- Число SQL-запросов на запрос/задачу растёт с числом объектов (N+1).
  Ось persistence ловит это как дефект, здесь — как стоимость: оценить N.
- Синхронный внешний HTTP в обработчике вебхука/запроса — таймаут наружу.
  Должно уходить в очередь.
- Загрузка всего queryset в память вместо `.iterator()` / пагинации.
- Регулярка компилируется на каждый вызов вместо модульного уровня.
- Celery/периодическая задача без лимита батча — растёт вместе с БД.
- Кеш: ключ включает тенанта; TTL задан; инвалидация есть.
- LLM-вызовы: лишний round-trip, раздутый промпт, отсутствие короткого пути
  для детерминированных случаев.

## Формат находки

Указать порядок величины («1 + N запросов, N = число записей пользователя»),
а не «может тормозить». Без оценки — `NICE_TO_HAVE`.
