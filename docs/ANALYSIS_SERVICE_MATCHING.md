Статус: **разбор закрыт, шесть вопросов владельцу открыты** (см. §5).

## 1. Путь от фразы человека до списка мастеров

**Шаг 0.** `apps/orchestrator/fast_path.py:378` `claims_direct_show_masters()` — детерминированная
ветка берёт ход, только если фраза разбирается ровно как «покажи мастеров по услуге».
Всё остальное — консьержу с моделью.

**Шаг 1a. Детерминированная ветка.** `apps/orchestrator/concierge.py:2255` —
`discover_masters(specialization=message_text, limit=5)`. Сырая реплика уходит в каталог
строкой поиска. Ноль результатов → `return None`, ход отдаётся консьержу (`:2265`).

**Шаг 1b. Ветка с моделью.** Инструмент `show_masters` (`apps/orchestrator/discovery.py:236`).
Роль модели — **только разбор языка**: заполнить `city`, `specialization`, `services[]`. Далее:

- `concierge.py:2243` `reground_specialization()` — если человек назвал услугу дословно,
  ищем по ней, а не по донесённому из прошлых ходов (DRF-968);
- `concierge.py:2262` `has_discovery_criteria()` — вызов без города и без услуги отбивается
  вопросом, а не каталогом;
- `concierge.py:2272` → `discover_masters(..., limit=5, resolve_service=True)`.

**Шаг 2. Разбор запроса** — `apps/marketplace/discovery.py:739` `_parse_query()`, единственная
точка разбора:

| строка | что делает |
| -- | -- |
| `:373` `_content_tokens()` | снять приветствие, выкинуть филлеры, взять слова длиной ≥2 |
| `:397` `_query_tokens()` | оставить **последние 5** токенов (`_MAX_TOKENS = 5`, `:64`) |
| `:544` `_split_known_cities()` | токен-город уходит в фильтр по городу |
| `:463` `_attested_tokens()` | короткий токен (<4) остаётся, только если каталог использует его как целое слово (DRF-1352) |
| `:709` `_match_goal_keys()` | если **все** токены покрыты одной курируемой целью — запрос «целевой», `stems` **обнуляется** |
| `:102` `_STEM_LEN` | иначе каждый токен режется до 6 символов — это «основа» |

**Шаг 3. Отбор** — `:1200` `_bookable_qs()`:

- `:1256` база: `is_active` + `invite_status=accepted` + `archived_at IS NULL`, через
  единственную санкционированную межтенантную дыру `CatalogMaster.all_tenants`;
  сортировка по умолчанию `:1260` — **`("name", "id")`, алфавит**;
- `:1262` город: `tenant__city__iexact`; `:1270` `tenant_id` — тап по чипу салона;
- `:1286` **fail closed**: запрос был, но не разобрался («я», эмодзи) → `qs.none()`;
- `:1311` **целевая ветка**: `.filter(_goal_row_q(...)).distinct()` — **без всякого ранжирования**,
  порядок остаётся алфавитным;
- `:1318` **только город**: весь город, алфавитом;
- `:1320-1333` **основная ветка**: `filter(service_match | specialization_match)` →
  `annotate(match_score=...)` → `order_by("-match_score", "name", "id")`.

**Шаг 4. Что такое `match_score`** — `:1074` `_match_score()`. Для каждой основы `CASE WHEN` (1/0),
сумма по **одной** строке `MasterService`, затем `MAX` по строкам, затем `COALESCE(...,0)`.
То есть: **сколько основ запроса совпало с названием одной лучшей услуги мастера**.

- `MAX`, а не `SUM`, — намеренно (`:1009`): мастер со «Спортивным маникюром» и отдельным
  «Тайским массажем» на «спортивный массаж» получает 1, а не 2.
- `COALESCE` тоже нагружен: мастер, найденный только по свободному тексту `specialization`,
  строк услуг не имеет, `MAX` вернул бы NULL, а NULL в Postgres при `DESC` идёт первым.

**Шаг 5. Срез.** `:1364` `masters = list(qs[:limit])`. Лимит с разговорного пути **всегда ≤ 5**
(`_MAX_MASTER_CARDS = 5`, `apps/orchestrator/discovery.py:65`).

**Шаг 6. Привязка услуги** — `:1108` `_matched_services()`: услуга проставляется на карточку,
только если совпавшие услуги мастера в его верхнем ярусе сводятся ровно к одной, и только при
`BOOKING_VIA_AYLA_REST` с непустым `ayla_service_id`.

**Шаг 7. Отрисовка** — `apps/orchestrator/discovery.py:~975-1020`:
`• Имя — спец · услуга · ★ рейтинг · город` + кнопка «Записаться к …».
Рейтинг печатается **только при `>= 1`** (`:985`) — нули читаются как «плохой мастер» (DRF-1224).

**Пустой результат.** `concierge.py:~2277` `remember_refusal(...)` пишет факт в
`Conversation.skill_state`; деградированные пути идут в `discovery.py:663` `render_no_match()`
с альтернативами из `marketplace/discovery.py:1396` `city_service_samples()`.
Повтор того же запроса перехватывается детерминированно — `concierge.py:1417` `_repeats_a_refusal()`.

**Другие поверхности с сортировкой:**

| поверхность | строка | порядок |
| -- | -- | -- |
| салоны | `discovery.py:1660` | `(tenant.name, id)` — чистый алфавит |
| услуги | `:1777` `discover_services()` | текстовый запрос — `("-match_score","name","id")` (`:1849`); целевой — `("tenant__name","name","id")` |
| меню услуг мастера после тапа | `apps/orchestrator/handoff.py:449` | `menu_score`, тот же счётчик; ветка `else` на `:453` — алфавит |
| поиск по имени мастера | `:1550` | наследует алфавит |

## 2. Что подтвердилось и что опровергнуто

**Подтверждено:**

- единственная сортировка выдачи мастеров — `discovery.py:1333` `("-match_score","name","id")`;
- `match_score` — счётчик совпавших основ по лучшей одной строке (`:1074`, `:1009`);
- рейтинг, отзывы, свободное время, цена, история клиента в отборе **не участвуют**;
- цель только сужает набор.

**Опровергнуто / уточнено — четыре находки:**

**(1) Целевой запрос не ранжируется вообще.** `:1311` возвращает `.distinct()` над алфавитной
базой. При «хочу расслабиться» порядок на 100% алфавитный, и это записано в коде как осознанное
решение («ordering carriers against each other would be recommendation»). `self_care` покрывает
120 услуг — размер ничьей равен всему набору.

**(2) Срез в 5 происходит в SQL, до всякой возможности переупорядочить.** На «массаж» найдено
8 мастеров — **троих человек не увидит никогда, и кто именно выпал, решает их фамилия.**
Это не «Анна выше Ольги», это «Ольги нет».

**(3) Есть ещё две точки сортировки** — `handoff.py:449` и `discover_services():1849`.
Обе унаследуют любое решение по критериям.

**(4) Рейтинг участвует — но другой.** `apps/booking/services/feedback.py:128`: оценка визита
клиентом 1-5, при `<= 3` создаётся HUMAN-эскалация, при `<= 2` приоритет HIGH (`:166`).
Платформа умеет действовать по оценке — просто `CatalogMaster.rating` в этой роли не используется
нигде. `review_count`: писатель есть (`catalog/services/upserter.py:202`), читателей вне тестов нет;
докстринг `catalog/models.py:240` обещает байесовскую оценку доверия (#1060), реализации нет.

**Ещё два поля-обещания:** `CatalogService.is_popular` (`models.py:118`) синхронизацией
**никогда не заполняется** (`upserter.py:128`: «keep their model defaults»), в ранжировании
не читается. `CatalogService.requires_health_check` / `contraindications` (`models.py:122-123`)
заполняются из фида — готовый крючок для гейта безопасности §9, к отбору не подключены.

## 3. Замеры (пилот, 06.09.2026)

**Алфавит — не тайбрейк, а основной механизм ранжирования:**

| Запрос | Найдено | Верхний счёт | В верхнем ярусе | Разброс |
| -- | -- | -- | -- | -- |
| массаж | 8 | 1 | **8** | 0 |
| маникюр | 6 | 1 | **6** | 0 |
| стрижка | 5 | 1 | **5** | 0 |
| эпиляция | 5 | 1 | **5** | 0 |
| лимфодренаж | 3 | 1 | **3** | 0 |
| спортивный массаж | 8 | 2 | 3 | 1 |

Это **структурное свойство**: при однословном запросе `match_score` принимает только два значения —
1 у найденных через связь с услугой и 0 у найденных лишь по свободному тексту `specialization`.
Различить внутри яруса он не способен в принципе. Однословных запросов после снятия филлеров —
подавляющее большинство.

Прочее: 31 бронируемый мастер, рейтинг ≥1 у 22, **отзывов нет ни у одного**;
387 связок мастер×услуга (12.5 на мастера), 265 активных услуг, все с `ayla_service_id`;
233 услуги с целями (`self_care` 120 … `relax` 10);
`WorkingHours` у **4 из 31**, `SlotConfig` **0 строк**, `BookingRequest` 9 штук.

## 4. Предложение по критериям

### Главный вывод

Бот не может отранжировать «массаж» не потому, что формула плоха, а потому, что **запрос не
содержит того, чем восемь мастеров различаются**. Честный ответ на неразличимый ярус — не
отсортировать его, а **задать различающий вопрос словами самого каталога**. Материал уже
посчитан: `_matched_services()` знает, какие услуги совпали у каждого мастера.
«Массаж» → чипы «Классический / Спортивный / Лимфодренажный / Массаж головы» — прогрессивное
раскрытие по §7, ярус из восьми превращается в ярус из двух-трёх.

**Порядок работ: сначала научиться различать, потом рекомендовать.** Ввести §13 («одна главная
рекомендация») до фактора A — значит выдавать первого по алфавиту уверенным тоном.
Это хуже сегодняшнего списка.

### Таблица факторов

### F. Свободное время — три ветки, а не две

1. **Сейчас через Ayla REST.** `apps/integrations/ayla/booking_client.py:919`
   `get_available_times(specialist_id, service_id, date)` — один день за вызов, `service_id`
   обязателен, кэш 60 с, календарь веером по 14 дням. На поиск: 5 × 14 = **70 HTTP-вызовов**,
   плюс требование активного тенанта (`_require_tenant_id`), которого у межтенантного поиска нет.
   **~13 SP и упирается в чужой эндпоинт** («ближайший свободный слот», желательно пакетный).
2. **Сейчас через локальный резолвер.** `apps/scheduling/services/resolver.py` считает слоты
   чистым SQL. Но `WorkingHours` у **4 из 31**, `SlotConfig` пуст. Для остальных 27 фактор
   вернёт «свободен всегда» или «занят всегда» — **хуже, чем не делать**.
3. **Позже через тот же резолвер.** Он пуст не потому, что плох, а потому, что мастера ещё
   не подключены — это работа DRF-1505 / DRF-1508 / эпик DRF-1503. Когда мастера зайдут и
   заведут расписание, резолвер наполнится сам, и фактор станет **~3 SP чистого SQL**.

**Предложение: не «строить или нет», а «включить, когда наполнится».** Условие перехода в задачу:
**фактор доступности включается, когда расписание ведут ≥ 80% бронируемых мастеров**
(сегодня 13%) **и заведён `SlotConfig` хотя бы на уровне тенанта** (сегодня 0 строк).

### Четыре порога §8 на существующих данных

| Порог §8 | Сегодня выразим? | Чем выразить после A + D |
| -- | -- | -- |
| HIGH → рекомендовать | нет | `separation ≥ τ₁` и контекст полон и конфликтов нет |

## 5. Шесть вопросов владельцу

**В1. Что делает мастера более подходящим и в каком порядке важности?**
Ответ одной фразой — перестановка из списка: точность совпадения / свободное время / цена /
город / прошлый опыт клиента / рейтинг.
*Последствия:* «точность» первой → работа начинается сразу, 5 SP на существующих данных.
«Свободное время» → откладывается до подключения мастеров, до тех пор выдача остаётся алфавитной.
«Рейтинг» → 0 отзывов делает фактор пустым, вопрос вернётся.

**В2. Как меряется различимость кандидатов?**
«Разрыв между первым и вторым; меньше порога — спрашивать, а не сортировать».
*Последствия:* да → фактор D, 3 SP, §8 получает вход. Нет → §8 неисполним, DRF-1519 лишается
входных величин.

**В3. Одна рекомендация или список?**
«Одна главная + „показать ещё“» / «три» / «оставить пять».
*Последствия:* «одна» → 3 SP, **но только после A и D**; без них это уверенно поданная
случайность. «Список» → канон §13 остаётся расхождением, записать как осознанное отступление.

**В4. Что делать с рейтингом и отзывами?**
«Убрать обещание из кода и вернуться, когда появятся отзывы» / «включить рейтинг последним
тайбрейком сейчас».
*Последствия:* «убрать» → 0.5 SP на правку докстринга `models.py:240`. «Включить» → 2 SP,
но у 9 из 31 рейтинг 0.00 — это не рейтинг, а пустое поле, и они уедут в конец без основания.

**В5. Свободное время как фактор?**
«Да, включаем при 80% расписаний» / «Да, просим у Ayla эндпоинт ближайшего слота сейчас» / «Нет».
*Последствия:* «когда наполнится» → 0 SP сегодня, ~3 SP при включении, фактор появляется как
побочный эффект DRF-1503. «Просить эндпоинт» → срок не наш, у нас ~5 SP на кэш поверх.
«Нет» → человек продолжает выбирать мастера, к которому нельзя записаться.

**В6. Что происходит при равенстве?**
«Ротация» / «алфавит осознанно» / «содержательно (цена / время / популярность)».
*Последствия:* это **не редкий случай, а норма**: в 5 запросах из 6 весь результат в одном ярусе,
и на «массаж» трое из восьми не показываются из-за среза. «Ротация» → 2 SP, равные доли показов.
«Алфавит осознанно» → нужно уметь объяснить салонам, чьи мастера на «С» и «Ш».
«Содержательно» → возвращает в В1 и требует сначала A.

## 6. Границы со смежными задачами

**DRF-1519 (пороги остановки).** DRF-1526 производит **величины**: оценку кандидата (A),
`separation`, `completeness`, `conflicts` (D), порядок выдачи. DRF-1519 **потребляет** их и решает:
рекомендовать / дать альтернативы / задать вопрос / остановиться. Граница: вычисление числа —
здесь; сравнение с порогом и изменение поведения диалога — там.
**Следствие: DRF-1519 не может быть выполнена осмысленно до фактора A** — сегодня `separation ≡ 0`,
и любой порог даёт один ответ «спрашивать».

**DRF-227** («RecommendationEngine — real availability scoring», Todo, 3 SP). Пересечения нет:
DRF-1526 отвечает, **какие факторы должны участвовать**, DRF-227 — **как считать один конкретный**.
Если по В5 ответ «да» — доступность становится продолжением DRF-227: туда уезжает требование к
сигналу (один `next_free_at` на мастера, ≤1 SQL-запрос в момент поиска) и условие включения.

**Граница модель/код не сдвинута.** Всё предложенное детерминировано: A считается из названий
