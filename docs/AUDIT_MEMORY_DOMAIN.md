# Аудит домена памяти: что построено и что из этого работает

**Дата:** 2026-08-19
**Основание:** целевая архитектура из `Ayla - Архитектура памяти Ayla.md`
**Метод:** чтение кода обоих репозиториев плюс запросы к пилотной БД. Три ключевые находки перепроверены главным окном лично.

Классы: **VERIFIED** — прочитано в коде или замерено · **INFERRED** — вывод · **UNKNOWN** — не проверялось.

---

## 0. Короткий вывод

Домен памяти **построен основательно и почти целиком не исполняется**.

Схема, шифрование, зоны доступа, политика на уровне БД, журнал доступа с семилетним хранением, AST-линтер, стирание по 152-ФЗ — всё написано и покрыто тестами. И при этом:

- запись в жёлтую и красную зоны **отбрасывается в 100% случаев** — по замыслу, до реализации проверки возраста;
- согласий на пилоте — **ноль записей**, а ветка декларированных предпочтений требует согласия, которое продовый код **не выдаёт нигде**;
- единственный живой путь записи — **три регулярных выражения про диету**.

Это не небрежность. Это система, у которой построен низ и не подключён верх. Для планирования это меняет всё: **строить поверх нерабочего слоя значит закрепить его нерабочим.**

## 2. Четыре находки, каждая проверена лично

### 2.1. Защита работает вхолостую

`apps/identity/services/memory_writer.py:57` — `_check_minor_protection()` **всегда бросает** `MinorProtectionLookupFailed`. Эндпоинт проверки возраста в Ayla не реализован (#597), и это намеренное поведение «отказ по умолчанию».

**Следствие:** любая запись в жёлтую и красную зоны молча отбрасывается, всегда.

Вокруг этих зон построено: RLS-политика, отдельный читатель с обязательной целью, журнал доступа с семилетним хранением, три ограничения целостности, AST-линтер. **Аппарат защищает таблицу, в которую физически нечего положить.**

VERIFIED — прочитан код функции.

### 2.2. На пилоте ноль согласий

```
select count(*) from consent_consentrecord  →  0
```

Не «мало» — **ни одного**.

При этом чтение декларированных предпочтений требует согласия `memory_green`, а продовый код его **не выдаёт нигде**: упоминания есть в перечислении, в миграции и в тестах. Онбординг выдаёт только `personal_data`.

**Следствие:** ветка «декларированные предпочтения Ayla + уточняющий вопрос» мертва в проде. `memory_ask.py` — 293 строки разбора ответов — выходит на первом гейте.

VERIFIED — запрос к пилотной БД и поиск по репозиторию.

### 2.3. Единственный живой путь записи — три регулярки

`record_inferred_green_facts()` — 147 строк, полный набор проверок, десять тестов, **один вызывающий вне тестов**.

Реально работает детерминированный разбор трёх фраз: «веган», «вегетарианец», «я не ем мясо».

VERIFIED.

### 2.4. Противоречия накапливаются — это действующий баг

Значение не обновляется: новое пишется новой строкой, старая **остаётся живой**. Чтение сортирует по возрастанию даты создания и берёт **первое** вхождение ключа; поверхность выводит **все** факты подряд.

Практически: человек был веганом, стал кето — в подсказку модели попадает «веган» из блока памяти и «веган; кето» из блока поверхности одновременно.

VERIFIED — прослежена логика в трёх файлах.

## 3. Главная склейка

`users.UserPersonalContext` в бэкенде Ayla — плоская широкая таблица с перезаписью на месте, без истории.

**Ночной вывод модели пишет в те же колонки, что и человек.** Различает их словарь `data_sources`, который сам перезаписывается.

То есть догадка и подтверждённый факт лежат **в одной ячейке** — прямое нарушение первого принципа целевой схемы.

Поверх есть публичный REST-контракт, внутренний API, мобильный клиент и фронт. **Глубина переделки: глубокая.**

### 3.1. Граница между репозиториями проведена по той же линии

В докстринге модели бота зафиксировано прямо: **declared в Ayla, inferred в боте.**

То есть черта между хранилищами проведена ровно по «подтверждённое против выведенного» — но **между сервисами**, а не между типами записей. Целевая схема требует держать оба типа в одном домене как разные сущности.

**Значит расклейка — не рефакторинг одной таблицы, а пересмотр границы двух репозиториев.**

## 4. Кто читает память

**Четыре независимых пути, ни один не принимает цель использования:**

| Путь | Источник |
|---|---|
| `read_personal_context()` | `MemoryEntry` green + сводка, прямой ORM |
| `build_concierge_memory_block()` | HTTP в Ayla |
| `memory/coordinator.load_snapshot()` | Redis + профиль + состояние слотов — **про `MemoryEntry` не знает вообще** |
| `_build_personal_context_hint()` | прямой ORM уже в бэкенде |

Контролируемый доступ существует **ровно для красной зоны** — `RedZoneReader` с обязательной целью, субъектом, идентификатором запроса и атомарным аудитом.

**Это готовый образец того, чем должен стать единый вход для всех зон.**

## 5. Три списка

### Есть и годится — строить поверх

1. **`ConsentRecord` и сервисы согласий** — append-only, отзыв, версия документа, аудит, каскад. Единственная подсистема, уже соответствующая целевой схеме.
2. **Схема `MemoryEntry` как контейнер факта** — зоны, источник, шифрование, TTL, мягкое удаление, ограничения, RLS. Реализованная спецификация, а не набросок.
3. **`RedZoneReader` и журнал доступа** — прототип будущего `resolve_context`.
4. **Session memory** — изолирована, TTL, не смешана с долговременной.
5. **Стирание по 152-ФЗ** — выгрузка и каскадное удаление, флаг «забыть всё» учитывается мгновенно, до асинхронной уборки.

### Есть, но склеено или без нужных свойств

1. **`UserPersonalContext`** — вывод и факт в одной ячейке. *Глубоко.*
2. **Два несогласованных основания согласия** для одной и той же зелёной памяти. Задокументировано как осознанное расхождение. *Средне, решение уровня владельца.*
3. **`MemoryEntry` без цели и без уверенности.** Цель существует как аргумент функции и умирает в ней. Уверенность подставляется **на этапе рендера промпта** константами — то есть это свойство места, откуда факт достали, а не свойство факта. *Средне.*
4. **Накопление противоречий** — см. 2.4. *Средне, действующий баг.*
5. **Аудит только для красной зоны.** Успешная запись зелёного факта не создаёт аудит-строки; чтение зелёного не аудируется вообще.
6. **`NutritionProfile`** — пол, возраст, вес, флаги здоровья включая беременность и РПП. Не зашифрован, без зоны, вне системы согласий, читается напрямую своим доменом. **Фактически красная зона вне контура памяти.** *Глубоко.*

### Нет вовсе — писать с нуля

1. `MemoryProposal` и цикл «предложение — подтверждение».
2. `DecisionRecord`.
3. `ConsentScope` — цель использования как ограничение.
4. `resolve_context()` и запрет прямого чтения.
5. **Реестр согласий на стороне Ayla** — согласия физически живут только в БД бота, привязанные к `BotUser`, тогда как данные в БД Ayla привязаны к `User`.
6. Semantic recall — в MVP не требуется.

## 6. Что удивило

**Согласие `memory_green` не выдаётся нигде** — только в тестах. По названиям файлов ветка выглядит работающей фичей.

**`confidence` принимается по проводу и выбрасывается** — сериализатор внутреннего API валидирует значение от 0 до 1, обработчик его игнорирует.

**Защита от самострела при стирании:** если реплика была командой «забудь, что я веган», экстрактор на этом ходу не запускается — иначе подстрока «я веган» мгновенно воссоздала бы только что удалённый факт. Признак того, что путь стирания проверяли на живом сценарии, а не писали по спецификации.

## 7. Что это меняет в плане

Документ целевой архитектуры предлагает этап 0 «закрыть governance-блокеры», затем этап 1 «схема».

**Замер показывает, что схема уже есть, а исполнение нет.** Значит порядок другой:

1. **Решить, что из построенного оживлять, а что списать.** Проверка возраста (#597) — блокер, из-за которого мертвы две зоны из трёх. Согласие `memory_green` — одна строка в онбординге. Это решения продукта, не разработки.
2. **Закрыть действующий баг с противоречиями** — он влияет на подсказки модели уже сегодня, независимо от любых планов.
3. **Governance-блокеры** — как в документе, но теперь со знанием, что именно регулируем.
4. **Только потом** — новые сущности: предложение, решение пользователя, цель использования, единый вход.

**Строить поверх слоя, который не исполняется, значит закрепить его нерабочим.**
