## 0-тер. Вывод, ради которого стоило считать: снятое число вернулось вычисленным

Не иллюстрация к §7, а самостоятельный вывод аудита.

Восьмёрку («8 стаканов воды в день») из клиента **уже выбрасывали** — со словами
«норму воды не придумываем, восемь — число ниоткуда». Потом убрали и константу
`NUTRITION_DEFAULT_WATER_GOAL_ML = 2000` (§0). А на пилоте 09.09 двое из шести видят
ориентир по воде **ровно в восемь стаканов**:

```
weight_kg IS NULL  →  DEFAULT_WEIGHT_KG = 70.0        (nutrition_profile_service.py:37)
70 × WATER_ML_PER_KG (30)  =  2100 мл                 (:263-270)
round(2100 / 250)  =  8 стаканов                      (views.py:2688-2692)
```

**То же число, другим путём, и теперь оно носит вид расчёта.** Константу можно найти
`grep`-ом и удалить; вычисленную фикцию — нельзя: она приходит по той же трубе, что и
честный ответ, и на экране от него неотличима.

Отсюда правило, которое дороже самой правки:

* **удаление литерала — не удаление числа.** Сняв фиктивное значение, спрашивать надо
  не «убран ли литерал», а **может ли это число возникнуть заново из умолчания входа**;
* **фикция в пути чтения снимается удалением, фикция в пути записи — только контрактом
  отказа считать.** Убрать `DEFAULT_*` без такого контракта значит получить `None` в
  арифметике либо новый ноль на месте старого;
* **пока фикцию нельзя снять, её надо уметь пересчитать.** Пометка подстановки
  существует (`assumed_inputs`), покрывает одно поле из четырёх и не читается никем —
  то есть её как бы нет. Счётчик носителей и есть то, что превратило «может
  случиться» в «двое из шести».

## 1. Где рождается ориентир калорий — нигде

Точек рождения калорийного ориентира на `dev` **ноль**. Есть три места, где его
можно было бы ждать, и ни одно его не даёт.

**1.1. Сводка дня отдаёт жёсткий ноль всем.**
`nutrition/services/nutrition_summary_service.py:152` — `calories_goal = 0`,
литерал, без чтения профиля. Профиль в этой функции не открывается вовсе.
Человек, прошедший анкету и имеющий `NutritionProfile.daily_kcal = 1850`,
получает из `internal/summary/` `calories_goal = 0`.

**1.2. Расчёт существует, но в сводку не доезжает.**
`nutrition/services/nutrition_profile_service.py:123` `compute_norms()` считает
`daily_kcal` и кладёт в `NutritionProfile.daily_kcal`. Его читает **только**
карточка завершения анкеты в боте (`apps/skills/nutrition_anketa/skill.py:374`).

**1.3. Отсюда — расхождение двух поверхностей на одном человеке.**
Бот после анкеты говорит `🔥 Калории: 1850 ккал/день`. Экран «Сегодня» в тот же
день показывает `1200 ккал сегодня` без цели и без шкалы, потому что источник
у него другой и он ноль. Два ответа про одно число.

**1.4. Та же асимметрия внутри одного сообщения.**
`apps/nutrition_proactive/render.py:137-140`: строка «Калории» берёт цель из
`summary.calories_goal` (всегда 0 → цель не печатается), строки «Белки/Жиры/Углеводы»
берут цель из профиля (`_target`, `render.py:261`) → печатаются. Итог дня выглядит
так: `Калории: 1240 ккал.` / `Белки: 80 из 95 г.` В одном сообщении у БЖУ ориентир
есть, у калорий нет.

Наружу уходит одно имя на три причины. Это ровно §78 (у отсутствия должно быть имя)
