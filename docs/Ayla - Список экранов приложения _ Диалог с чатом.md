# Главное продуктовое решение

Ayla не стоит проектировать как:

```
Главная
Мастера
Услуги
Записи
Профиль
```

Это получится ещё один YClients/Dikidi/маркетплейс.

Правильнее:

```
              МОЯ ЦЕЛЬ
                 │
                 ▼
             ┌───────┐
             │ AYLA  │
             └───┬───┘
                 │
       понимает мой контекст
                 │
                 ▼
          рекомендует шаг
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    действие   запись    наблюдение
       │         │         │
       └─────────┼─────────┘
                 ▼
              РЕЗУЛЬТАТ
                 │
                 ▼
              ПРОГРЕСС
                 │
                 ▼
        следующий шаг Ayla
```

Поэтому **мастер, салон, услуга и слот — это не центр клиентского приложения. Это ресурсы, которые Ayla использует для достижения цели клиента.**

В старом MVP действительно были заложены базовые клиентские функции — регистрация, просмотр мастеров, карточка мастера, бронирование, оплата и уведомления. Но текущая продуктовая модель уже существенно шире: обязательным считается путь через цель, Twin, объяснимую рекомендацию и прогресс, а сама запись — лишь одна из downstream-опций.

Отдельно я бы зафиксировал важный принцип для следующего этапа проектирования: **115 пунктов выше — это не 115 экранов, которые надо сразу рисовать и разрабатывать.** Многие из них будут состояниями, bottom sheet, modal или вложенными surface. Следующий рациональный шаг — превратить эту карту в **Customer App Information Architecture** и сократить её примерно до **12–15 P0 экранов MVP + P1 + P2**, после чего уже рисовать navigation flow.

### Что должно войти в P0 MVP

| # | Экран | Зачем он нужен |
| --- | --- | --- |
| 1 | **Welcome** | Вход в продукт / начало onboarding |
| 2 | **Goal Creation** | Создание `Transformation Goal`: чего человек хочет добиться |
| 3 | **Photo & Video Capture** | Исходная фиксация состояния |
| 4 | **Current Model** | Показ baseline / текущего состояния пользователя |
| 5 | **Desired Outcome** | Какого результата хочет пользователь |
| 6 | **Forecast & Confidence** | Прогноз результата + честное отображение уверенности |
| 7 | **Personal Plan** | Персональный план достижения цели |
| 8 | **Today / Home** | Главный ежедневный экран: что делать сегодня |
| 9 | **Schedule** | Расписание действий и процедур |
| 10 | **Food Scanner** | Фиксация питания |
| 11 | **Water Quick Add** | Быстрая фиксация воды |
| 12 | **Fitness Action** | Фиксация/выполнение активности |
| 13 | **Weekly Check-in** | Повторная оценка состояния |
| 14 | **Progress Comparison** | Сравнение «старт → сейчас → цель» |
| 15 | **Procedure Recommendation** | Ayla предлагает подходящую процедуру и связывает её с целью |
| 16 | **Specialist Selection** | Выбор подходящего специалиста |
| 17 | **Booking Confirmation** | Завершение записи |
| 18 | **Data & Consent** | Согласия и управление использованием данных |

Это не моя реконструкция — именно эти 18 экранов перечислены в разделе **«Минимальный набор экранов»** Reset Roadmap.

При этом весь P0 journey выглядит так:

```
Регистрация    ↓Transformation Goal    ↓Фото / видео    ↓Baseline / Current Model    ↓Desired Outcome    ↓Forecast    ↓Personal Plan    ↓Today ┌──┼────┐ ↓  ↓    ↓еда вода активность └──┼────┘    ↓Procedure Recommendation    ↓Specialist    ↓Booking    ↓Weekly Check-in    ↓Progress    ↓корректировка плана    ↓новый цикл
```

Именно такой основной путь прямо зафиксирован в Roadmap.

Есть ещё важный нюанс. **P0 MVP ≠ только эти 18 визуальных экранов.** Под ними должны существовать обязательные продуктовые контуры: Auth, Profile, Chat, Memory, Goals, Media, Visual Model, Plan, Schedule, Food, Water, Fitness, Procedures, Specialists, Booking, Notifications, Consent и Analytics. # 11. Авторизация

Дизайнеру не надо заставлять пользователя авторизоваться **до того, как он понял ценность Ayla**, если технический/security-контракт этого не требует.

**C01-A — пользователь не авторизован**

Визуально они могут практически не отличаться.

# 2. Почему нельзя сразу рекомендовать услугу

Допустим, три человека выбрали:

**«Улучшить фигуру»**

Но один имеет в виду:

> «Хочу уменьшить отёчность».

Второй:

> «Меня беспокоит внешний вид кожи».

Третий:

> «Хочу визуально скорректировать проблемные зоны».

Если после `goal=improve_body` мы сразу покажем всем одну процедуру, наша новая система окажется обычным:

```
goal ↓service category
```

Нам нужен хотя бы минимальный слой понимания намерения.

---

# 3. Основная идея C02

Верх:

**Твоя цель**

### Улучшить фигуру

И дальше Ayla:

> **Что именно ты хочешь изменить?**

Подзаголовок:

> Выбери то, что сейчас для тебя важнее всего.

Дальше — варианты.

```

○ Сделать контуры тела более выраженными
○ Улучшить внешний вид кожи
○ Почувствовать лёгкость в теле
○ Подготовиться к событию или отпуску
○ Другое
```

Это пока **пример структуры**, а не утверждённая taxonomy.

---

# 4. Один выбор или несколько?

Здесь я предлагаю **разрешить несколько**, но попросить определить главный.

Например пользователь выбирает:

```
✓ Уменьшить отёчность
✓ Улучшить внешний вид кожи
```

После второго выбора появляется:

> **Что для тебя сейчас важнее?**

И одна цель получает `primary`.

Почему это полезно?

Потому что реальный человек редко думает строго одной категорией.

Но recommendation engine должен понимать приоритет.

В домене получится условно:

```
Goal:  improve_body
Desired outcomes:  - reduce_swelling [PRIMARY]  - improve_skin_appearance
```

Точные названия полей пока не канонизируем.

---

# 5. Не использовать медицинские обещания

Это особенно важно для дизайнера и копирайтинга.

Не писать:

**«Избавиться от целлюлита»**

Лучше:

**«Улучшить внешний вид кожи»**

Не:

**«Вылечить боль в спине»**

А:

**«Уменьшить дискомфорт»**

Мы собираем **желаемый outcome пользователя**, а не ставим диагноз и не обещаем медицинский результат.

# 7. Но здесь появляется важная возможность

Я бы не превращал весь дальнейший onboarding в набор анкет.

После первого выбора C02 Ayla может **сама начать уточнять контекст**.

Например пользователь выбирает:

> **Уменьшить отёчность**

Следующий экран уже выглядит не как форма:

> Возраст: ___  
> Вес: ___  
> Активность: ___

А как Ayla:

> **Поняла. Задам ещё пару вопросов, чтобы не советовать тебе наугад.**

И далее один вопрос за раз.

Это гораздо ближе к продуктовой концепции.

# 8. Поэтому архитектура C02

Я предлагаю сделать C02 **последним классическим selection screen**.

Дальше интерфейс становится conversational/progressive:

```
C01Широкая цель     ↓C02Желаемый результат     ↓C03Ayla уточняет контекст     ↓C04Рекомендация
```

Получается хороший баланс:

**C01** — быстро понять направление.

**C02** — структурировать intent.

**C03** — персонализировать.

**C04** — показать ценность Ayla.

---

# 9. Что делать с «Другая цель»

На C01 у нас есть:

**«Другая цель / Не знаю, что мне подходит»**

Этот пользователь **не должен попадать на C02**.

Его путь:

```
C01«Не знаю»   ↓Conversation with Ayla   ↓Ayla определяет candidate Goal   ↓подтверждение   ↓C02 или сразу C03
```

То есть C02 предназначен прежде всего для пользователя, выбравшего одну из структурированных целей.

# 10. Returning / Back

Пользователь должен иметь возможность нажать назад и поменять широкую цель.

```

```

Если поменял:

```
Improve Body→ Relax
```

старые C02 selections должны быть сброшены, если они несовместимы с новой целью.

# 11. Состояния C02 для дизайнера

Здесь уже не нужно пять совершенно разных экранов. Нужны **4 состояния одного экрана**:

**C02.1 — Default**

Цель известна, ничего не выбрано.

**C02.2 — One outcome selected**

Например:

`✓ Уменьшить отёчность`

Кнопка `Продолжить` активируется.

**C02.3 — Multiple outcomes selected**

Например два outcome + понятное указание приоритета.

**C02.4 — Other**

Появляется короткое поле:

> **Расскажи своими словами**

Но это не полноценный чат.

# 12. Что НЕ должно появиться здесь

На C02 пока не нужны:

* процедуры;
* мастера;
* цены;
* рейтинг;
* свободные слоты;
* диагнозы;
* фотографии тела;
* вес и рост;
* длинная анкета;
* прогноз результата;
* план;
* AI-рекомендация.

И особенно:

> **«Для вашей цели подходит LPG-массаж»**

Это преждевременно.

# 13. Что должен дать C02 системе

# 15. Главный UX-критерий

После C02 пользователь должен думать:

> **«Ayla начинает понимать, чего конкретно я хочу».**

Не:

> «Я прохожу анкету салона».

И не:

> «Я настраиваю фильтры поиска».

## Definition of Done C02

Экран принимаем, если:

1. Видно, какую широкую цель пользователь выбрал на C01.
2. Ayla уточняет **желаемый результат**, а не услугу.
3. Пользователь проходит экран примерно за 5–10 секунд.
4. Нет медицинских обещаний.
5. Полученные данные действительно способны повлиять на следующую рекомендацию.
6. После C02 пользователь ещё не видит каталог.
7. Следующий шаг естественно воспринимается как **«Ayla хочет немного лучше меня понять»**.

### Итоговый flow теперь

```
C01 — Чего хочешь добиться?          ↓C02 — Что именно хочешь изменить?          ↓C03 — Что Ayla нужно знать о тебе?          ↓C04 — Что Ayla рекомендует и почему?          ↓существующий fulfillmentProcedure → Master → Slot → Booking

## C03 — Ayla уточняет контекст

После C02 у нас уже есть:

```

### 1. Главная задача C03

C03 отвечает не на вопрос:

> «Давайте соберём профиль пользователя».

А на гораздо более узкий:

> **«Каких данных Ayla не хватает, чтобы выбрать между возможными следующими действиями?»**

Это важнейший принцип.

Если ответ пользователя **не способен изменить рекомендацию**, вопрос вообще не должен появляться в C03.

Например, если Ayla одинаково порекомендует одно и то же независимо от ответа — вопрос лишний.

```

Но конкретные вопросы **ещё нельзя считать утверждёнными**.

Для дизайнера сейчас важен **паттерн взаимодействия**.

# 5. Третий тип вопроса — временной горизонт

Для некоторых целей это действительно может менять рекомендацию:

> **Есть ли дата, к которой ты хочешь увидеть результат?**

```
○ Нет конкретной даты
○ В ближайший месяц
○ Через 1–3 месяца
○ Через 3+ месяца
○ Указать дату
```

Если человек говорит:

> «Через две недели свадьба»

и:

> «Просто хочу постепенно улучшить форму»

это потенциально разные recommendation contexts.

---

# 6. Safety gate

Перед рекомендацией нам может потребоваться отдельный вопрос безопасности.

Но я бы **визуально отделил его от персонализации**.

Не:

> «Есть ли у вас противопоказания?»

с огромным медицинским списком.

А отдельный state:

### Перед рекомендацией

> **Есть ли что-то важное о здоровье, что Ayla должна учитывать?**

Например:

```
○ Нет
○ Беременность
○ Недавняя операция или травма
○ Есть хроническое заболевание
○ Есть ограничения от врача
○ Не уверен(а)
```

Но **конкретный перечень должен прийти из safety/eligibility contract**, а не от дизайнера и не из этого примера.

---

# 7. Очень важное поведение

Если человек выбирает safety-sensitive вариант:

```
«Недавняя операция или травма»
```

мы **не продолжаем обычный recommendation flow как ни в чём не бывало**.

Возможный UI:

```
Спасибо, что сказала.
Для некоторых процедур этоважно учитывать.
Я не буду рекомендовать ихбез дополнительной проверки.
[Продолжить безопасный подбор]
```

Дальше recommendation engine должен исключить или ограничить соответствующие варианты согласно policy.

Это уже не просто дизайн — backend обязан поддержать это поведение.

---

# 8. Сколько вопросов?

Для Controlled Pilot я бы поставил жёсткое UX-ограничение:

### **2–4 вопроса максимум до первой рекомендации.**

Не:

```
Goal→ 14 вопросов→ Recommendation
```

А:

```
Goal→ Outcome→ Q1→ Q2→ возможно Q3→ Safety gate при необходимости→ Recommendation
```

Мы должны как можно быстрее довести пользователя до:

> **«Вот что Ayla советует тебе и почему».**

---

# 9. Adaptive questioning

Это особенно важно.

Не все пользователи должны получать одинаковые вопросы.

Например:

```
GoalУлучшить фигуру
OutcomeУменьшить отёчность       ↓Q1 lifestyle       ↓Q2 symptoms/context       ↓Recommendation
```

Но:

```
GoalРасслабиться
OutcomeСнять напряжение       ↓Q1 где ощущается напряжение       ↓Q2 интенсивность/контекст       ↓Recommendation
```

То есть C03 — это **не конкретная анкета**.

C03 — это UI-engine для короткого adaptive clarification flow.

---

# 10. Свободный ответ

Иногда варианты не подходят.

Поэтому снизу можно иметь:

**«Расскажу своими словами»**

Тогда:

```
┌─────────────────────────────┐│ Напиши, что важно учесть…   ││                             │└─────────────────────────────┘
            Отправить
```

Но structured options должны оставаться основным способом ввода для Controlled Pilot.

Это позволит получать нормальную статистику.

---

# 11. Что Ayla должна объяснять

После каждого ответа не нужен бессмысленный:

> «Спасибо!»

Лучше иногда давать короткий acknowledgement:

> **«Поняла. Это поможет мне точнее выбрать следующий шаг.»**

Но не после каждого клика.

Иначе onboarding становится медленным и искусственным.

---

# 12. Progress

На C03 я бы **не показывал `Вопрос 2 из 7`**.

Потому что flow adaptive и количество вопросов может различаться.

Лучше использовать абстрактный progress:

```
● ● ━━━ ○
```

или:

> **Почти готово**

на последнем уточнении.

Это не создаёт обещание фиксированного количества вопросов.

---

# 13. Возможные состояния C03

Дизайнеру я бы заказал **5 макетов**.

### C03.1 — Intro + first question

Ayla объясняет:

> «Чтобы не советовать наугад, задам несколько коротких вопросов».

И сразу первый вопрос.

### C03.2 — Standard question

Чистый single-choice question.

### C03.3 — Adaptive follow-up

Показываем, что следующий вопрос возник из предыдущего ответа:

> «Поняла. Тогда уточню ещё одну вещь…»

### C03.4 — Free text

`Расскажу своими словами`.

### C03.5 — Safety gate

Отдельно визуально спокойный вопрос о факторах, которые необходимо учитывать перед рекомендацией.

          [Ayla]

```

Это может быть loading state, а не отдельный canonical screen.

# 15. Что НЕ должно быть в C03

Не показываем:

* услуги;
* мастеров;
* цены;
* рейтинги;
* availability;
* акции;
* длинную анкету;
* полный медицинский опросник;
* диагнозы;
* прогноз;
* фотографии;
* recommendation score;
* внутренние AI confidence numbers.

И самое главное — **не спрашиваем данные просто потому, что «когда-нибудь пригодятся»**.

# 16. Privacy

Если задаётся чувствительный вопрос, пользователь должен понимать **зачем**.

Можно использовать небольшой элемент:

**Почему Ayla спрашивает?**

По нажатию:

> Этот ответ помогает исключить неподходящие варианты и сделать рекомендацию безопаснее.

Для обычных вопросов такие пояснения не нужны.

# 18. Главный критерий C03

После прохождения пользователь должен думать:

> **«Она задала ровно те вопросы, которые нужны, чтобы понять мою ситуацию».**

Если ощущение:

> «Зачем им вообще всё это знать?»

— экран провален.

Если:

> «Я заполняю медицинскую карту»

— тоже провален.

## Definition of Done C03

Принимаем дизайн, если:

1. Один вопрос = один простой decision.
2. Ответ занимает несколько секунд.

# C05 — Recommended Procedure / «Как это сделать»

## 1. Место C05 в архитектуре

До C05 пользователь ещё ничего не покупал и не искал.

Ayla сначала поняла:

```

```

Например:

```

↓
Главное:Уменьшить отёчность
↓
Контекст:...
↓
C04:«Я рекомендую начатьс работы над отёчностью»
↓
C05:«Для этого я подобралалимфодренажный массаж»

```

C05 — **не каталог**.

Это принципиально.

---

# 2. Задача экрана

C05 должен ответить:

> **«Как конкретно выполнить то, что Ayla рекомендовала мне на C04?»**

На C04:

> **Что делать?**

На C05:

> **Какая конкретная услуга поможет это сделать?**

А следующий существующий экран отвечает:

> **У кого это сделать?**

Получается очень чистое разделение:

```
C04 → ЧТО ДЕЛАТЬC05 → КАКОЙ ПРОЦЕДУРОЙExisting → У КОГОExisting → КОГДАExisting → ЗАПИСАТЬСЯ
```

---

# 3. Верхняя часть

Сохраняем контекст предыдущего решения.

Например:

**Рекомендация Ayla**

### Начать с уменьшения отёчности

Ниже короткая связка:

> Для этого я подобрала процедуру, которая лучше всего подходит под твою цель и ответы.

Не надо снова повторять весь reasoning C04.

---

# 4. Главная карточка процедуры

На экране должна доминировать **одна primary recommendation**.

Например:

```
┌──────────────────────────────┐│                              ││       [фото процедуры]       ││                              ││  РЕКОМЕНДАЦИЯ AYLA           ││                              ││  Лимфодренажный массаж       ││                              ││  60 минут                    ││                              ││  от 2 500 ₽                  ││                              ││  Подходит для твоего         ││  следующего шага             ││                              ││  [ Выбрать специалиста ]     ││                              │└──────────────────────────────┘
```

Главный CTA:

### **Выбрать специалиста**

Не:

**Купить**

Не:

**Заказать**

Не обязательно даже:

**Записаться**

Потому что следующим шагом ещё будет выбор специалиста и слота.

---

# 5. Почему эта процедура

Под основной карточкой нужен компактный explanation block.

Например:

### Почему Ayla выбрала её

```
✓ соответствует твоей текущей цели
✓ подходит под выбранный результат
✓ доступна у специалистов рядом
✓ есть подходящие варианты записи
```

Но здесь есть важное архитектурное правило.

**Reasoning должен исходить из фактических данных recommendation engine.**

Нельзя позволять дизайнеру придумать красивые причины, которых система технически не умеет доказать.

# 7. Нужны ли альтернативы?

**Да. Но primary recommendation должна оставаться очевидной.**

Не надо делать:

Это снова каталог.

То есть:

> **1 primary + 1–2 alternatives**

Для пилота этого достаточно.

---

# 8. Почему альтернативы важны

Ayla не должна создавать ощущение:

> «AI сказал — значит другого варианта нет».

Пользователь должен иметь agency.

Например:

**Посмотреть другой вариант**

или:

**Мне это не подходит**

Это ещё и крайне ценный сигнал для recommendation engine.

# 9. «Не подходит»

Я обязательно добавил бы:

### **Мне это не подходит**

По нажатию — компактный bottom sheet:

> Что именно не подходит?

```
○ Цена
○ Не хочу эту процедуру
○ Не подходит время/длительность
○ Уже пробовал(а)
○ Хочу другой вариант
○ Другое
```

Это очень ценные данные.

Вместо тупого:

```

мы получаем:

```

# 10. Цена

На C05 цену уже надо показывать.

Потому что recommendation становится **реально исполнимым предложением**.

Например:

**от 2 500 ₽**

Если цена зависит от мастера:

> **от 2 500 ₽**

а не фиктивная точная цена.

Если цена фиксирована:

> **2 500 ₽**

# 11. Длительность

Тоже показываем:

**60 минут**

Пользователь должен понимать стоимость действия не только в деньгах, но и во времени.

# 12. Availability

Не надо показывать весь календарь на C05.

Но полезно дать availability hint, если backend действительно умеет его получить:

> **Есть запись завтра**

или:

> **Ближайшее время — сегодня 18:30**

Это повышает actionable value рекомендации.

Но только если это **реальная authoritative availability**.

Не кешированный декоративный текст.

Именно его надо переиспользовать.

# 18. Состояния C05

Для дизайнера я бы запросил **5 состояний**.

### C05.1 — Primary recommendation

Основной happy path.

### C05.2 — Alternatives expanded

Основная рекомендация + альтернативы.

### C05.3 — Why this procedure

Раскрытый explanation.

Можно bottom sheet, а не отдельный экран.

### C05.4 — Not suitable

Bottom sheet причины отказа.

### C05.5 — No eligible recommendation

Очень важный state.

Например safety rules исключили все доступные процедуры.

Не писать:

> «Мы ничего не нашли».

Лучше:

> **Сейчас я не могу уверенно рекомендовать процедуру из доступных вариантов.**

И предложить безопасный следующий шаг согласно будущему policy contract.

# 19. Что НЕ должно быть на C05

Не нужны:

* десятки услуг;
* категории;
* сортировка;
* фильтры;
* рекламные баннеры;
* «популярное»;
* sponsored recommendation;
* акции, влияющие на ranking;
* скрытое повышение коммерчески выгодной услуги;
* огромный текст от AI.

C05 должен ощущаться как **решение**, а не поисковая выдача.

---

# 20. Очень важное правило neutrality

Если две процедуры подходят:

```
A — лучше для пользователяB — выгоднее салону
```

Ayla должна выбрать **A**.

Не B.

Коммерческие условия салона не должны незаметно менять recommendation ranking.

Это особенно важно, потому что Controlled Pilot проходит внутри одного салона: иначе очень легко построить не AI-проводника, а красивый upsell engine.

---

# 21. Главная метрика C05

Не просто:

> сколько нажали «Записаться».

Нам нужна цепочка:

```
recommendation_shown        ↓why_opened        ↓recommendation_accepted     ↙        ↘ accepted    rejected               ↓          reject_reason        ↓specialist_selected        ↓booking_started        ↓booking_confirmed        ↓visit_completed        ↓feedback
```

Это позволит проверить исходную гипотезу пилота:

> **считает ли человек рекомендацию Ayla осмысленной настолько, чтобы действовать по ней.**

# Definition of Done C05

Принимаем экран, если:

1. Есть одна очевидная primary recommendation.
2. Понятна связь с целью пользователя.
3. Есть доступное объяснение «почему».
4. Цена и длительность прозрачны.
5. Есть максимум несколько альтернатив, а не каталог.
6. Пользователь может отказаться.
7. Причину отказа можно собрать.
8. Safety может полностью заблокировать procedure recommendation.
9. Availability показывается только из authoritative источника.
10. CTA ведёт в уже существующий specialist/booking flow.
11. `recommendation_id` сохраняется через booking journey.
12. Коммерческая выгода салона не влияет скрыто на рекомендацию.
13. Пользователь ощущает: **«Ayla подобрала это для моей ситуации»**, а не «мне показали рекламу услуги».

Таким образом после C05 **мы перестаём проектировать новый booking UI**:

```
C01 Цель ↓C02 Outcome ↓C03 Context ↓C04 Next Best Action + WHY ↓C05 Procedure + WHY ═══════════════════════ ↓СУЩЕСТВУЮЩИЙ КОНТУР ↓Specialist recommendation ↓Master ↓Availability ↓Booking
```

А после завершённого визита мы снова возвращаемся в новый продуктовый слой — **feedback/result → goal-centric Home**, потому что именно там должен замкнуться первый цикл Ayla.
