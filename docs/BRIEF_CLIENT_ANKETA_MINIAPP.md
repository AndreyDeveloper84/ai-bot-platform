# Бриф: клиентская анкета как первый вход в мини-приложении

**Заказчик:** владелец Ayla. Решение принято 03.09.2026, в диалоге, дважды подтверждено.
**Репозиторий:** `ai-bot-platform`. PR **против `dev`**, не против `main`.

---

## 1. Что просят

Клиент, открывающий мини-приложение впервые, попадает **на анкету**. После её
заполнения **формируется цель**, и клиент идёт дальше уже с целью.

## 2. Это переопределяет канон. Правка канона входит в задачу

`ayla-knowledge/01 Product/BOT-001 First Contact Specification.md` запрещает
ровно это в четырёх местах:

| Место | Что сказано |
| -- | -- |
| `:338` | MUST NOT: standalone «Анкета» object or button |
| `:554` п.1 | No mandatory onboarding — Ayla MUST NOT require a guided onboarding sequence before useful action |
| `:554` п.2 | No standalone questionnaire |
| `:597` AC-5.1 | No standalone questionnaire appears in First Contact |

**Задача DRF-1199 уже удаляла эту кнопку** именно по этим основаниям. Если
вернуть её, не поправив канон, следующий аудит снесёт её снова — и работа
пропадёт. Поэтому:

**Обязательный пункт объёма:** внести в BOT-001 явную поправку — датированную,
со ссылкой на решение владельца от 03.09.2026, — которая описывает новый вход
и снимает противоречие в **каждом из четырёх** мест. Не удалять историю запрета:
дописать, что и почему изменено. Заодно дописать строку в
`Ayla/docs/OPEN_DECISIONS.md`.

Канон, который молча нарушен, хуже канона, который открыто изменён.

## 3. Как это устроено сейчас — не сломать

Цель уже формируется **на сервере**. Читать:

- `apps/miniapp/src/screens/GoalSelectScreen.tsx` — экран является «глупым
  отрисовщиком» серверного документа решения. В шапке файла записано прямо:
  «The screen takes NO decisions: no hardcoded chip lists, no local
  "what to show next" computation, no next-screen branching».
- `apps/miniapp/src/lib/customer-goals.ts` — `POST /goals/select`, три варианта
  тела: `{goal_key}`, `{goal_text}`, `{intent: "need_guidance"}`. Ответ —
  документ, который **заменяет состояние целиком**.
- `MissingKind = "goal" | "goal_clarification" | "goal_guidance"` — механизм
  «чего не хватает» уже существует и уже умеет задавать уточняющие вопросы.

**Отсюда главное требование к решению.** Анкета — это **не новый клиентский
мастер с зашитыми вопросами**. Это продолжение того же серверного механизма:
вопросы приходят с сервера как элементы `missing`, ответы уходят тем же
`POST /goals/select`, а по завершении сервер возвращает документ с
заполненным `known.goal`.

Клиентский мастер с зашитой последовательностью вопросов нарушит и текущую
архитектуру, и пункт канона «No independent Mini App conversational
implementation» — тот пункт владелец **не** отменял.

## 4. Объём

1. **Сервер.** Расширить документ решения так, чтобы для клиента без цели
   выдавалась последовательность вопросов анкеты, а по её завершении
   формировалась цель (`known.goal` заполнен). Существующие варианты
   (подсказки-чипы, свободный ввод, «нужна помощь») **сохранить** — они не
   отменяются, анкета становится путём по умолчанию для новичка.

   **На той же поверхности — запрос уже известной услуги** (уточнение
   владельца, 03.09.2026). Человек, который пришёл со словами «хочу маникюр»,
   называет услугу прямо здесь и идёт к записи, не проходя вопросов. Это
   **не отдельный экран и не ссылка «пропустить»**, а равноправная часть той же
   поверхности, рядом с вопросами.

   Отдельной механики под это заводить не нужно: свободный ввод
   (`{goal_text}`) и подсказки (`{goal_key}`) уже существуют и делают ровно
   это. Задача — расположить их на поверхности анкеты так, чтобы названная
   услуга распознавалась как готовая цель и вела к подбору, а не роняла
   человека обратно в вопросы.
2. **Мини-приложение.** Первый вход клиента ведёт на эту поверхность.
   Отрисовка — существующим механизмом `missing`, без новых решений на клиенте.
3. **Повторный проход.** Владелец ранее распорядился (DRF-1225): человек должен
   иметь возможность пройти анкету **сколько угодно раз**. Предусмотреть вход
   для того, кто уже с целью.
4. **Канон и реестр решений** — пункт 2 этого брифа.
5. **Тесты.** На сервере — что цель формируется по завершении и что прежние три
   пути живы. На клиенте — что первый вход ведёт на анкету и что экран не
   принимает решений сам.

## 5. Чего делать нельзя

- Не зашивать вопросы в клиент.
- Не делать анкету **воротами**. Владелец уточнил это прямо: рядом с вопросами
  должен быть запрос уже известной услуги. Незаполненная анкета не блокирует
  человека, который знает, чего хочет. Проверить это отдельным тестом: путь
  «назвал услугу → попал к подбору» проходится **не отвечая ни на один вопрос
  анкеты**.
- Не трогать нутриционный навык `apps/skills/nutrition_anketa/` — это **другая**
  анкета, про питание. Наша — клиентская, про бьюти-цель.
- Не передавать телефон клиента куда-либо (DRF-1039).
- Не менять статусы визитов и не ходить в Django-админку.

## 6. Порядок работы

- Своё рабочее дерево, не занимать чужое.
- Коммитить промежуточное, не копить один большой коммит.
- Секреты не печатать.
- Перед PR прогнать локально: `ruff format --check`, `ruff check`, `mypy`,
  затронутые тесты, `npm run build` в `apps/miniapp`. Версия `ruff` — из
  `uv.lock`, ставится через `uvx ruff@<версия>`.
- Длина строки в репозитории **100**, не 88.

## 7. Убрать за собой

По завершении:

- снять своё рабочее дерево (`git worktree remove`), если оно больше не нужно;
- удалить временные контейнеры и одноразовые базы, поднятые для работы;
- удалить временные файлы и черновики вне репозитория;
- **в отчёте перечислить поимённо**, что именно снято.
