# Общие правила для треков A / B / C / D (спецификации мозга Ayla)

Читается **всеми** исполнителями треков. Свой трек — отдельным брифом.

## Что это за этап

Мы **не строим** «мозг Ayla» одной задачей. Сейчас нужны **implementation-ready
контракты**, а не код. Ваш результат — документ, по которому другой разработчик
напишет код, **не принимая ни одного нового продуктового решения**.

**Код не менять.** Задача read-only, пока владелец явно не переведёт её
в реализацию.

## Порядок работы, обязательный

1. **read-only discovery** — что есть на самом деле;
2. **gap analysis** — чего нет;
3. **specification** — контракт.

Не начинайте с третьего.

## Источники канона (проверить, не принимать на слово)

* `docs/ayla-conversation-state-v1.1-reconciled.md` — **Working Canon**, 14 решений.
  Отменяет v1.0. Читать его, а не v1.0.
* `docs/OPEN_DECISIONS.md` — решения владельца, §40 разбор канона v1.1,
  §41 замер скорера, §42 замер завершения визитов, §45 адреса, §47 пакет 07.09.
* `docs/OPEN_QUESTIONS_OWNER.md` — что ещё не решено.
* `docs/SYSTEM_GOALS.md` — как устроены цели.

**Правило приоритета при конфликте:**

```
принятое каноническое решение  >  реализация  >  устаревший handoff/комментарий
```

* Если **два канонических документа противоречат друг другу** — СТОП, вопрос владельцу.
* Если **реализация расходится с каноном** — зафиксировать расхождение;
  **не переписывать канон под код молча**.
* **Код не является каноном** только потому, что он существует.
* **Документ не является каноном** только по названию файла.

## Требования к доказательствам

* Каждое утверждение «есть / нет / работает» обязано иметь **evidence**.
* Ссылаться на **repo/path/symbol/API/тест**, когда утверждение основано на коде.
* **Не доверять именам функций и комментариям** — проверять фактический путь
  вызова и данных. За сутки 06–07.09 восемь раз комментарий говорил одно,
  а код делал другое.
* **Зелёный CI не есть доказательство лечения дефекта** — нужен targeted proof
  (краснеет до правки, зеленеет после) или живая проверка причины.
* **У боевых замеров есть срок годности.** Старый production measurement нельзя
  выдавать за текущий без повторной проверки.
* `pytest` через конвейер отдаёт код выхода **последней** команды — «exit 0»
  может прийти от `tail`. Верить только строке `N passed / M failed`.

## Что нельзя

* Расширять scope «заодно».
* Молча чинить посторонние дефекты — найденный P0/P1 **документировать отдельно**.
* Принимать решения владельца самостоятельно.
* Создавать новые продуктовые семантики ради удобства реализации.
* Заменять **UNKNOWN** догадкой. `UNKNOWN ≠ 0 ≠ false ≠ произвольное умолчание`.
* Любые разрушительные действия на боевом контуре.

## Обязательная классификация действий

В **каждом** документе каждое действие классифицировать как одно из:

```
DETERMINISTIC
CONTROLLED_POLICY
AUTHORITATIVE_DOMAIN
LLM_ALLOWED
LLM_FORBIDDEN
```

**LLM разрешено:** понимание естественного языка, семантическое извлечение,
контролируемая отрисовка, обоснованное объяснение.

**LLM запрещено как источник истины:** решение о безопасности, DecisionReadiness,
каноническое сопоставление каталога, доступность, цена, способности исполнителя,
сохранение Goal, правила времени в плане, совместимость, политика ранжирования,
правда о записи, происхождение свидетельств.

Если предлагаете «попросим модель решить» — **обязаны доказать**, почему это
`LLM_ALLOWED`. Иначе это архитектурный дефект.

## Новые инварианты, которые обязан учитывать каждый трек

**EVIDENCE ORIGIN.** Утверждение, порождённое **моделью**, никогда не становится
свидетельством **пользователя** только потому, что лежит в истории диалога.
Свидетельство пользователя — только: явный текст человека, явный клик,
авторитетный доменный факт, подтверждённая память/цель (если данный потребитель
вправе их использовать в этом решении). Происхождение не смешивать.

**QUESTION LOOP.** Каждый семантический вопрос обязан иметь **stable `question_id`**.
Состояние должно позволять определить: вопрос задавался / отвечен / остаётся
неотвеченным / политика разрешает или запрещает повтор. Повтор разрешён **только
по явному controlled rule с причиной**. Модель не запускает re-ask сама.

**SURFACE-INDEPENDENT RECOMMENDATION.** Представление может отличаться,
**политика рекомендации — нет**. Один и тот же семантический контекст не может
обслуживаться двумя противоречащими политиками.

**EVIDENCE STRENGTH.** При `review_count = 0` потребитель **не вправе** превращать
недоказанный рейтинг в обоснованное WHY. `Unknown ≠ false ≠ true`.

## Review gates — документ не готов, пока не пройдены все пять

1. **Canon reconciliation** — против принятых Decisions 1–14.
2. **Code reality** — не предполагает ли документ существование API/данных,
   которых нет.
3. **Cross-contract consistency** — идентификаторы, владение, статусы,
   provenance, жизненные циклы, границы против остальных четырёх документов.
4. **Failure behavior** — UNKNOWN, устаревшее, недоступное, конфликтующее,
   заблокированное безопасностью, отсутствующий маппинг, отсутствующее
   свидетельство.
5. **Implementability** — другой разработчик пишет код **без новых продуктовых
   решений**. Если невозможно — документ остаётся **DRAFT**.

## Формат вопроса владельцу

Не носить владельцу десятки мелочей. Разрешайте сами, если ответ однозначно
следует из канона, доменной модели или доказанного контракта API.

Выносить, **только** если есть настоящая продуктовая развилка, где два варианта
совместимы с каноном и выбор меняет поведение для человека или бизнеса.

```
1. Что именно не определено.
2. Почему канон не даёт ответа.
3. Вариант A.
4. Вариант B.
5. Последствия каждого.
6. Ваша рекомендация.
7. Что заблокировано до решения.
```

**Один вопрос — одно решение.**

## Linear

**Не заводить дубликаты.** Сначала найдите существующие задачи по теме,
обновите или декомпозируйте их. Кириллица в GraphQL-мутациях — только
ASCII-escaped (`\uXXXX`), после записи верифицировать чтением.
**Статусы в Linear меняет главное окно** — вы приносите предложение, не правите.
