## §2. Создание записи

`POST /api/v1/tenants/me/appointments/` → **201**, тело `AppointmentDetailSerializer`.

### Поля запроса

| Поле | Тип | Обяз. |
|---|---|---|
| `specialist_id` | UUID | **да** |
| `service_id` | UUID | **да** |
| `start_datetime` | DateTime | **да** |
| `client_id` | UUID | ровно одно из двух |
| `client_name` | str ≤150 | ровно одно из двух |
| `client_phone` | str ≤20 | **обязателен вместе с `client_name`** |

### Правило, ради которого стоит читать исходник

`service_id` — **обязательный вход, никогда не выводится и не подставляется по умолчанию.** Комментарий в коде (строки 104-110) объясняет почему, и это прямая ссылка на твой UX-контракт:

> Master Schedule UX Contract (15.08) фиксирует порядок Клиент → Услуга → Дата/время → доступность → обзор → создание именно потому, что длительность услуги решает, какие интервалы вообще пригодны. Ручка, которая угадала бы услугу, отвечала бы не на тот вопрос, который задала консоль.

**То есть порядок шагов в твоём экране — не UX-предпочтение, а требование ручки.** Собрать форму в другом порядке нельзя.

### Идентификация клиента — строго XOR

```python
if has_id == has_name:
    raise ValidationError(
        "Provide exactly one of client_id … or client_name (a new guest)."
    )
if has_name and not client_phone:
    raise ValidationError({"client_phone": "A new guest needs a name and a phone."})
```

Ни оба, ни ни одного. Новый гость — **имя и телефон обязательны вместе**.

`client_phone` канонизируется к тому же виду `+7…`, в котором хранится зарегистрированный аккаунт, — чтобы проверка «а это не существующий ли клиент» сравнивала одинаковое с одинаковым. Значение, не похожее на российское, **чистится, но принимается**.

## §3. Поиск клиента

`GET /api/v1/tenants/me/customers/?q=…`

**Совпадение по телефону — точное.** Из кода: префиксный поиск по цифрам превратил бы ручку в способ вычерпать список клиентов салона по несколько нажатий за раз.

Значит в интерфейсе **нельзя делать поиск-по-мере-ввода по телефону** — он не будет находить, и это не баг. По имени поведение мягче, но проверь сам, я снял только правило про телефон.

## §4. Перенос

`POST …/appointments/<uuid>/reschedule/`

| Поле | Тип | Обяз. |
|---|---|---|
| `new_start_datetime` | DateTime | да |
| `expected_version` | int ≥1 | **да** |

`expected_version` **обязателен именно здесь**, хотя на мобильном пути он опционален. Обоснование из кода:

> У салонной консоли нет легаси: она читает журнал дня — где у каждой брони есть `version` — непосредственно перед тем, как предложить кнопку. Перенос без версии это ошибка вызывающего, а не случай совместимости, который стоит поддерживать.

**Практическое следствие для тебя:** твоя проекция дня **обязана нести `version` каждой записи**, иначе перенос невозможен. Проверь, что зеркало его отдаёт, — если нет, это находка, и её надо назвать до начала работы.

## §5. Отмена

`POST …/appointments/<uuid>/cancel/`

| Поле | Тип | Обяз. |
|---|---|---|
| `reason` | str ≤500 | нет |
| `reason_code` | choice | нет |

Допустимые `reason_code` (`appointments/domain/value_objects.py:236`):

```
master_unavailable
tenant_closed_slot
other
```

Закрытый список: салон вправе утверждать только то, что действительно знает. Пропущен — берётся умолчание роли (`other`).

**Не подставляй `other` сам.** Разница между «салон сказал: мастер заболел» и «салон не сказал ничего» доходит до клиента, и затирать её на своей стороне нельзя.
