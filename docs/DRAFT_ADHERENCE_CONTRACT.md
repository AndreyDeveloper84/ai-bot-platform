# ДРАФТ — Adherence Contract (DRF-1334, эпик DRF-1331)

**Подготовлено окном goals 25.08.2026.** Дочерняя задача эпика
(3afc3078): пробел, найденный владельцем при чтении SPEC_CARE_CONTRACT —
**Plan Adherence нельзя считать по любому факту активности**; факт
становится adherence только если Personal Plan заранее содержал
соответствующее обязательство.

**Статус: принято с правкой (вердикт главного окна 25.08), доведён до
спеки.** Правка вердикта внесена в §4 и §5. Реализация разрешена.

---

## 1. Граница (та же линия, что В-2, с другой стороны)

> **Поставщики поставляют факты. Домен Personal Plan вычисляет adherence.**

- Nutrition (и позже другие) сообщает: «запись воды за такую-то дату
  состоялась». Слова «выполнено» в контракте поставщика **нет**.
- Personal Plan решает, был ли план выполнен, — потому что только он знает,
  что было обещано.
- Nutrition не хранит наблюдения (В-2) и не судит о выполнении плана (эта
  задача). Иначе nutrition-домен становится владельцем всей системы заботы
  (OD_CARE_PLAN_BOUNDARY п.1).

## 2. Модель планового действия (место в `wellness`)

`PlanAction` — обязательство внутри Personal Plan. **Не engine**: ни
расписания, ни напоминаний, ни пересчёта — только запись «что обещано».

```
plan         FK -> PersonalPlan
action_type  курируемый ключ (первый срез: log_food, log_water)
cadence      per_day | per_week
target_count PositiveSmallInteger   (сколько раз за период)
created_at
```

Ключи `action_type` — курируемые данные (как Evidence Registry): новый ключ —
owner approval, не свободный ввод. Первый срез — два ключа выше, ровно под
факты, которые Nutrition уже умеет сообщать.

## 3. Контракт поставщика факта

```
FactSupply:
  provider      nutrition | ...       (кто сообщает)
  fact_type     water_logged | food_logged | ...
  subject_date  date                   (за какой день факт)
```

Поставщик отвечает на вопрос «был ли факт типа T за дату D для человека» —
да/нет, без интерпретации. Adherence-сопоставление спрашивает поставщика
по периоду и считает само.

## 4. Сопоставление (единственная операция)

**Счёт идёт по ведру каденса, не по периоду** (правка вердикта 25.08):
`per_day` — это про распределение, и счёт по всему периоду распределение
стирает — семь записей в понедельник иначе давали бы «полное выполнение»
недели.

```
adherence(plan, period):
  для каждого PlanAction:
    для каждого ведра каденса внутри period:    # день для per_day,
                                                # неделя для per_week
      facts_в_ведре = поставщик(action_type, ведро)
      fulfilled += min(count(facts_в_ведре), target_на_ведро)
    target_total = target_на_ведро * число_вёдер_в_period
```

Это по-прежнему **арифметика, а не суждение**: ни мнения о времени суток,
ни оценки человека — счёт ведётся в той единице, в которой сформулировано
обязательство. Форма `PlanAction` при этом остаётся минимальной; богатый
каденс (конкретные дни, время суток) в первый срез **не берём** по двум
причинам из вердикта: движка планов нет (OD_CARE_PLAN_BOUNDARY п.7), и
«по понедельникам» — уже суждение о том, *когда* человек что-то сделал, шаг
за рубеж «утверждение о плане, не о человеке».

Результат — структура: `{action_type, target_total, fulfilled_count}` на
действие. **Никогда не сходится с Outcome Progress в одно число, цвет или
шкалу** (AYLA-DEC-0082, LDT §9 v1.2). Оценочных формулировок нет;
разрешённая форма — утверждение о плане, не о человеке (SPEC §3.2):
«выполнены 3 запланированных действия из 4» + приглашение, не оценка.

## 5. Приёмочные случаи (из задачи + вердикт)

- Человек **один раз** записал воду, планового обязательства про воду
  **нет** → adherence не растёт ни на сколько (нет PlanAction — нечему
  сопоставляться; факт поставщика остаётся фактом, не выполнением).
- То же действие **при наличии** PlanAction(log_water, per_day) →
  засчитывается.
- **Семь записей в один день при `per_day` за неделю → `1/7`, а не `7/7`**
  (правка вердикта: счёт по вёдрам; без этого случая правку тихо потеряют
  при первом рефакторинге).

## 6. Границы

- Personal Plan engine не строится (OD_CARE_PLAN_BOUNDARY п.7 — до первого
  работающего вертикального среза).
- Outcome Progress не трогаем (DRF-1343, отдельная линия).
- Посещённые процедуры (`booking.completed`) в первый срез не входят —
  ноль фактов за историю пилота и ловушка с часами (SPEC О-7); возвращаются
  после DRF-1048.
- Правка nutrition/ здесь не нужна: поставщик фактов — чтение существующих
  журналов (WaterEntry/FoodLog) через контракт §3.

## 7. Вердикт главного окна (25.08) по обоим вопросам

1. **Каденс — форма достаточна.** Богаче не брать (причины — в §4).
2. **Синхронный вызов — подтверждён, довод усилен:** событийный вариант
   означал бы копию фактов, а копия — та самая «производная, ставшая
   источником истины», которую контракт запрещает. Оба домена в одном
   репозитории — синхронный вызов.
