# Правила исполнителя — общий свод

Ссылка на этот файл заменяет повторение правил в каждом брифе.
**Каждое правило здесь стоило нам суток.** Ни одно не формальность.

## 1. Источник

**Пересказ источника — не источник, даже собственный.** Открывай файл,
`git show`, ответ ручки — а не свою формулировку о нём. Свой прежний вывод
опаснее чужого: он читается как память, а не как непроверенное утверждение.

**Не доверять именам функций и комментариям.** За трое суток двенадцать раз
комментарий говорил одно, а код делал другое.

**«В каком репозитории» — часть утверждения, а не контекст.** У нас два
репозитория с разными конвейерами. «Голова `dev`», «в коде», «T6» звучат полно
и не содержат, где. Признак верный, предмет чужой — три случая за сутки.

## 2. Проверки

**Состав локальных проверок выписывается из `.github/workflows/ci.yml` ТОГО
репозитория, где правишь.** Не из привычки. Аргументы копировать **дословно**:
`ruff check .` ≠ `ruff check apps/`; `guard apps/` ≠ `guard apps/ tests/`
(разница — 49 непроверенных мест). Бот — `ruff` + `mypy`; каталог — `flake8` +
`detect-secrets`. Подробно: `MAIN-note-local-checks-come-from-ci-yml.md`.

**Числа из `--junitxml`, не из текста.** Строку `N passed` среда обрезает.
`errors` — про стенд, `failures` — про предмет; **складывать в «упало N» нельзя**.

**Пустой вывод — не доказательство успеха** ни при каком коде выхода.

**Подмену для targeted proof проверяй на применение.** `str.replace`, `sed`,
копирование — все «успешны» при нуле совпадений и дают доказательство
несуществующего свойства.

**Зелёный CI доказывает отсутствие обнаруженной регрессии, а не исправление.**
Targeted proof обеими строками: краснеет до, зеленеет после.

**Тест, где обе стороны данных построил один автор, проверяет согласованность
фикстуры, а не системы.** Когда предмет — стык двух систем, доказательство —
замер на стыке.

## 3. Ловушки этого кода

**Тенантные менеджеры вне контекста запроса.** `Model.objects` при
`STRICT_TENANT_SCOPE=audit` **молча возвращает `.none()`**, при `strict` бросает.
На пилоте стоит `strict`. Нужен межсалонный доступ — `all_tenants`
**с явным объяснением в докстринге**, не молчаливым обходом.

**Ноль обязан иметь положительную стражу.** `>= before` зеленеет на нуле.
Проверяй `== before + 1`.

**PEP 660 editable-finder** подставляет `apps`/`config` из общего чекаута —
тесты из worktree молча идут по чужому дереву. Отключать перед прогоном.

**`pytest` врёт кодом выхода** через конвейер (ноль при падениях) и при нехватке
памяти (ненуль без итоговой строки). `uv run pytest` берёт системный pytest и
возвращает **ноль** — запускать `uv run python -m pytest`.

## 4. Дисциплина отсутствия

**Отсутствие доезжает отсутствием.** Не подставлять умолчание, не подставлять
«настоящее значение», не рисовать прочерк вместо значения. Умолчание колонки,
равное осмысленному значению, делает «человек молчал» неотличимым от
«человек выбрал» — и через день это уже не снять.

**У каждого пропуска должно быть имя.** Молчаливая пустота — отказ без имени.

**Имя состояния по умолчанию обвиняет источник**, потому что потребитель видит
только вход. Наружу — одно грубое имя, внутрь — раздельные счётчики причин.

**Проверяемый инвариант не живёт в комментарии.** Нужен сторож.

**Сторож не ослабляется.** Если краснеет — он работает; правь предмет, а не
проверку. Место, где хочется снять проверку, — назови главному окну строкой.

## 5. Порядок работы

* **Объявить пакет файлов главному окну ДО первого коммита.** Понадобился файл
  вне списка — сказать строкой в момент, не в отчёте.
* **Свой worktree.** Общий чекаут читать можно, писать нельзя. Два исполнителя
  в одном worktree недопустимы.
* **Коммитить промежуточное.** У нас пропадали 686 строк в незакоммиченном
  worktree, и ещё 1235 нашлись брошенными в трёх копиях.
* **Ветка `dev` защищена** (09.09): PR обязателен, нужны зелёные
  `pytest + ruff + mypy`, `miniapp (typecheck + vitest)`,
  `replay fixtures (golden + adversarial + voice)`, **база должна быть свежей**.
  Держать ветку перебазированной, иначе PR не сольётся даже зелёным.
* **Не мержить.** Слияние решает владелец: merge в `dev` = выкладка на пилот.
* **Не сливать ничего, пока идёт прогон предыдущего слияния** — вытеснение по
  concurrency отменяет прогон, и выкладка не состоится молча.
* Настоящий `ci` = **274201556**, `replay` = **274201559**. Цитировать **id
  прогона**, не id воркфлоу. Пары `*-docs-skip` — механизм, не подделка.
* **Секреты не печатать.**
* **Убрать за собой**: worktree, `node_modules`, ветки, временные файлы,
  разовые контейнеры. Перечислить снятое в отчёте.

## 6. Отчёт

Сообщением главному окну, не только файлом: пакет; что сделано; targeted proof
**обеими** строками с числами; id прогона; номер PR; что снял за собой.
**Замер без даты и без «чем снято» не существует.**

## 7. Перезапуск прогона — сверять SHA, а не память

**Перед `gh run rerun` сверь SHA прогона с ГОЛОВОЙ ветки, а не с тем, что помнишь.**

09.09: исполнитель увидел отменённый прогон и перезапустил его. За это время
ветку обновили на свежий `dev`, голова уехала. **Перезапуск на устаревшем SHA
вытеснил прогон на голове**, и второй «cancelled» стал следствием первого.

Опаснее самого случая — как он читался бы в отчёте: «`ci` отменён, вытеснение
по concurrency» — **правда по форме и ложь по причине**. Вытеснил его сам
исполнитель. Исполнитель назвал это сам, до отчёта.

**Проверка одной строкой:**
```
gh run view <id> --json headSha --jq .headSha
gh pr view <n> --json headRefOid --jq .headRefOid
```
Не совпало — не перезапускай, а запускай на голове.

Родственное: `production-facts-have-freshness`, раздел 2 про числа из junit.

## 8. Влили чужое в твою ветку — проверяй содержимое, а не родство

Обновление ветки чужой рукой (кнопка «Update branch», merge `dev` в ветку)
**не доказывается ancestry**: слияния squash рвут родство, а merge-коммит
его создаёт, ничего не гарантируя про твои файлы.

**Проверять побайтово свои файлы против своего же коммита**, а не «выглядит на
месте». 09.09 исполнитель так и сделал — и смог сказать «ничего не потеряно»
как факт, а не как надежду.

## 9. Файл в твоём же выводе grep, который ты не открыл, — не проверен

**Список — доказательство того, что тебе сказали, а не того, что ты посмотрел.**

09.09: исполнитель прогнал «широкий набор затронутых модулей», выбранный
**на глаз**. Файл `test_food_memory_flow.py` **был в его собственном выводе
`grep`** по потребителям шагов анкеты — он увидел его в списке и не открыл.
Отчитался «125 passed» и назвал это широкой проверкой.

**Числа были верные. Набор — угаданный.** Прогон конвейера дал падение.

**Правило:** если твоя проверка — подмножество конвейера, ты обязан назвать
**правило отбора**, а не перечень. «Затронутые модули» правилом не является:
его нельзя проверить и нельзя опровергнуть. Правило звучит так — *«весь `apps/`
с теми же `-n` и тем же списком `--deselect`, что у конвейера»*, и тогда любой
может повторить.

Формулировка исполнителя, дословно: **«числа были верные, а набор — угаданный»**.

## 10. Свои падения не выдавать за чужие, но и «похоже на среду» доказательством не считать

Тот же день: полный локальный прогон дал **35 красных** — таймауты, `p95=8434ms`
при бюджете 4000, `100 turns took 899.5s` при бюджете 60. Пятнадцатикратный
перелёт выглядит как перегруженная машина.

**Но «выглядит как среда» — не доказательство.** Исполнитель проверил по
конвейеру: тот же коммит на чистом раннере дал **ровно одно** падение — то,
которое он и чинил. Значит 35 — свойство машины, а не ветки.

**Приём:** совпадение по коммиту между локальным прогоном и прогоном конвейера
превращает догадку «это среда» в вывод. Без него — `UNKNOWN`, а не «не наше».

## 11. Опрос GitHub API — не чаще раза в 90 секунд

Токен **общий на все окна**. Опрос каждые 45 секунд упёр одно окно в лимит
GitHub API и, возможно, задел соседей.

Цикл ожидания: **интервал 90 с и выше**, и на каждой итерации **сверять SHA
головы PR** (см. §7) — иначе дождёшься прогона, который уже никому не нужен.

## 12. Умолчание, прочитанное у `getattr`, — не умолчание системы

Замер утверждал: «`DISCOVERY_CLARIFY_MIN_TIER` по умолчанию 0, значит различающий
вопрос фактически отключён». **Неверно на обеих базах.**

`config/settings/base.py` задаёт `os.environ.get("DISCOVERY_CLARIFY_MIN_TIER", "4")`.
Ноль — это фолбэк внутри `getattr(settings, ..., 0)` в самой функции, и он
**недостижим, пока настройка объявлена**. Живое значение — **4**, механизм работает.

**Правило:** умолчание надо читать **там, где значение рождается** (настройки,
переменная окружения, схема БД), а не там, где его читают. Фолбэк у читателя
описывает поведение при отсутствии настройки, а не текущее состояние системы.

Родственное: §7 (сверять SHA, а не память), «пересказ источника — не источник».

## 13. Имя файла — это данные, а не строка

`git diff --name-only` **берёт путь в кавычки и переводит не-ASCII в октальные
escape'ы**, пока включён `core.quotePath` (умолчание). Кириллическое имя приходит
как `"docs/Ayla - \320\236….md"`, и фильтр `grep -vE '^docs/|\.md$'` промахивается
дважды: строка начинается с кавычки и кончается кавычкой.

09.09 это стоило дороже, чем выглядит. Двойник `ci-docs-skip` прочитал документный
PR #1504 (377 файлов, все под `docs/`) как смешанный и самоотменился «пусть решает
настоящий `ci`». Настоящий `ci` на своём `paths-ignore: docs/**` не запустился.
Обязательная проверка осталась **без единого авторитета** — и так навсегда.

Целевое доказательство: старый фильтр находит 13 «не-документных» файлов, все
тринадцать это `docs/*.md` и `docs/*.png`; новый (`-z`, разбор по NUL) — ноль.

Тот же корень 09.09 съел мой собственный скрипт спасения: имена с пробелами
считались по словам, отсюда строки «НЕТ В РЕПО: Ayla» и «модель».

**Правило:** любой перечень путей читать в машинной форме — `-z` и NUL, `--porcelain`,
JSON, — а не как текст, разбитый по пробелам и переводам строки. Проверять на живом
наборе имён проекта, а не на `test.py`: у нас почти все документы названы кириллицей.

## 14. Проверка может не докладывать вовсе — это не «красный»

`BLOCKED` бывает трёх разных состояний, и различать их обязательно: проверка
**упала**, проверка **не завершилась**, проверка **не запускалась ни в каком виде**.
Третье в списке `gh pr checks` выглядит как первое, а лечится противоположно.

Опаснее всего **взаимная уступка**: двойник отменяет себя в пользу настоящего,
настоящий молчит по `paths-ignore`. Каждый вежливо уступил, суммарный авторитет — ноль.

**Правило:** увидев `BLOCKED`, спросить не «почему упало», а «кто вынес вердикт».
Перечислить прогоны по головному SHA (`actions/runs?head_sha=…`) и сверить
`workflow_id` — пустой перечень и красный перечень это разные болезни.

## 15. Защита за вычислителем не ловит вычисленное

У бота есть честный fail-closed: `NULL` в признаке скрининга читается как
«скрининг нужен». За 09.09 он сработал **на нуле рёбер из 387**.

Не потому, что данные хороши. Каталог вычисляет `False` из отсутствующего шаблона
**до границы** и отдаёт боту уверенное отрицание там, где источник не знал ответа.
`NULL` до сторожа не доходит: его съел вычислитель выше по течению.

**Правило:** сторож ловит только то, что до него доезжает. Прежде чем засчитывать
защиту, посчитать её **срабатывания**, а не наличие. Ноль срабатываний означает либо
«ловить нечего», либо «стоит не там», и различить это можно только замером выше по
течению — у того, кто превращает незнание в утверждение.

Родственное: §12 (умолчание у читателя), «ноль обязан иметь положительную стражу».
## 16. Пустой прогон — не доказательство. И у нуля тестов тоже

Окно снимало targeted proof десятью подменами. Случай G дал `tests: 0, failures: 0`
и едва не был зачтён за «сторож молчит, значит правка нужна». На деле сторож
не молчал — **прогон не содержал ни одного теста.**

Причина названа исполнителем точнее, чем следствие: тест дописывался в файл через
`cat >>` и приклеился к последнему классу в файле, а подмена целилась в тот класс,
которому тест принадлежит по смыслу. **Между «где тест лежит» и «о чём тест»
появился зазор**, и подмена промахнулась мимо обоих.

**Правило:** в скрипт подмен обязателен предварительный шаг «прогон пустой —
доказывать нечего»: если выбранный узел даёт ноль собранных тестов, это отказ
инструмента, а не результат. И дописывать тест в конец файла нельзя — класс
выбирается по смыслу, а не по тому, где кончился текст.

Родственное: «код выхода pytest врёт», «ноль обязан иметь положительную стражу».
Один и тот же зверь: ноль получен не тем механизмом, о котором думаешь.

## 17. Утверждение, которое станет ложью без единой правки, обязано нести дату

Класс Б («читается как вечно истинное, возраста не имеет») опаснее всего там, где
факт меняется **вне кода**: переменная окружения, флаг, состав аллоулиста,
конфигурация хоста. Такое утверждение станет неверным, не изменившись ни буквой,
и в диффе этого не увидит никто.

09.09 окно само поймало у себя такую фразу — «другого работающего пути инвалидации
сегодня нет вовсе» — и приделало к ней дату и два способа перепроверки, не меняя
содержания. Правильный ход: содержание правится, когда факт изменился; возраст
приделывается сразу.

**Дешёвая замена памяти — машинный сторож.** На пилоте такой уже есть и был найден
случайно:

```
WARNING apps.observability.checks
env_file_drift: EVENT_INGEST_ALLOWED_EVENTS declared in .env.staging
did not reach the process (differs)
```

Он ловит ровно тот разрыв, который иначе держится на памяти двух окон: файл правлен,
процесс держит старое. Прежде чем договариваться «я скажу, когда факт изменится»,
поискать, нет ли на этот факт счётчика — он не забудет и не закроется.

Родственное: §12 (умолчание у читателя), «у боевых замеров есть срок годности».
## 18. Соблюдаемое правило без сторожа — это совпадение, а не выполненное требование

09.09 за одну сессию четыре раза повторилось одно и то же: код вёл себя правильно,
и именно поэтому дыра доживала. Зелень вокруг ничего не значила — она подтверждала
согласие с текущим поведением, а не наличие требования.

Случай окна расписания, названный им же точнее всего: два теста проверяли, что строк
расписания **нет**, и ни одного — что есть **нерабочие**. `has_working_day` считал
истинные и был верен. Подмени его на `bool(self.rows)` — «подтверждать можно» стало бы
у всякого, кому завели семь выходных, **и оба теста остались бы зелёными.**

**Правило:** отличить «требование выполнено» от «сегодня совпало» можно только подменой.
Сломать правило и посмотреть, кто закричит. Никто не закричал — сторожа нет, сколько бы
зелени ни было вокруг. Формулировка исполнителя: **верен без доказательства.**

**Дополнено 10.09.2026.** У подмены обязан быть **свой** контроль: печатать число
совпадений, которое она сделала. `str.replace`, `sed` и копирование «успешны» при нуле
совпадений, и тогда зелёный прогон после пробы доказывает не сторожа, а то, что пробы не
было. Без этого числа «подмена применилась» — утверждение, а не наблюдение, и отличить
«сторож молчит» от «предмет не подменён» нечем. Случай, на котором это выяснилось,
записан в §36.

Родственное: §16 (пустой прогон), «проверяемый инвариант не живёт в комментарии».

## 19. Считая только истинные строки, не отличишь «не пришло» от «пришло пустым»

Пять мастеров имели в зеркале ноль рабочих дней. По `is_working=True` это один ноль.
По `COUNT(*)` — два разных состояния с противоположным лечением:

```
COUNT(*) = 0                 синхронизации не было вовсе — сломан путь
COUNT(*) = 7, истинных 0     синхронизация прошла, источник отдал неделю выходных
```

**Правило:** там, где отсутствие может означать и «не доехало», и «доехало пустым»,
снимать **два** числа: сколько строк всего и сколько удовлетворяют условию. Один
агрегат по условию склеивает сломанный механизм с работающим механизмом на других
данных.

То же и наружу: у гейта, отвечающего «нет», должны быть раздельные внутренние
счётчики причин, даже когда наружное имя одно.

Родственное: §15 (защита за вычислителем), «имя состояния обвиняет источник»,
«гейту нужен счётчик».

## 20. Греп без исключения `node_modules` находит чужой код и выдаёт за свой

Окно матрицы искало поверхности гейтов во `frontAyla` и получало совпадения. Все они
жили в `node_modules/@react-native/debugger-frontend` — отладочные бандлы Chrome
DevTools. В собственном коде (`apps/`, `packages/`) совпадений ноль.

**Правило:** любой греп по репозиторию с фронтендом исключает `node_modules`,
`dist`, `.venv`, `site-packages` — иначе замер описывает чужую библиотеку. Проверять
не по числу совпадений, а по путям, в которых они найдены.
## 21. Отсутствие журнала не означает отсутствие свидетеля

У профиля мастера нет ни аудита, ни истории версий — история назад не читается.
Но `updated_at` с `auto_now` даёт **границу сверху**: любая правка сдвинула бы отметку.
Ноль сдвигов у 31 профиля за 50 суток = ноль правок. Утверждение о прошлом получено
у механизма, который прошлого не хранит.

Та же семья: 28 строк, созданных за 0,2 секунды, — это один пакет, а не работа людей;
две волны с разными умолчаниями (7 рабочих дней против 6) — это две загрузки, а не
расписания живых людей.

**Предостережение, чтобы приём не доказывал больше, чем может** (формулировка окна
матрицы): `auto_now` даёт границу сверху, а не историю. Правка с откатом в одной
транзакции, `bulk_update` без `updated_at` в `update_fields` и сырой SQL отметку
**не двигают**. Прежде чем опираться на ноль сдвигов, убедиться, что все писатели
проходят через ORM.

## 22. У беды должно быть точное имя, иначе она подменяется другой

Тринадцать застрявших `customer.consent.changed` я подал как «у согласий другой вес» —
формулировка верная и читающаяся как утечка прав. Исполнитель проверил прежде, чем
она ушла дальше: согласие пишет **три независимые копии до шины** (строка
`ConsentRecord`, аналитическое событие, аудит), отзыв исполняется по строке, а не по
событию, и в коде прямо сказано, что для пилота доказательством служат аудит плюс
аналитическое событие, а зеркало доменной шины — после пилота. Застряла четвёртая копия.

**Правило:** прежде чем назвать находку тревогой, проверить, что первичная запись цела.
Это то же «у отсутствия должно быть имя», применённое к самой тревоге. Неточная тревога
не осторожнее точной — она дороже: она тратит внимание владельца на беду, которой нет,
и прячет ту, которая есть (здесь настоящая цена — не сегодня, а у будущего потребителя
согласий, который получит пустую историю и не узнает, что она была непустой).

## 23. Тревога внутри предмета — не тревога

`_emit_dlq_alert` зовётся ровно из одного места — из тела `dispatch_pending_events`.
Диспетчер не запускается, значит тревога не звучит, значит молчание читается как
здоровье.

Это третья форма одного и того же за день, и все три дают неотличимую тишину:

| форма | пример |
|---|---|
| сторож **за** вычислителем | fail-closed бота на `NULL`, ноль срабатываний из 387 |
| сторож **не в том процессе** | system check, который `uvicorn` не прогоняет |
| сторож **внутри** предмета | тревога о застрявшем ящике внутри разборщика ящика |

**Правило:** счётчик ставится **снаружи** того, за чем следит, и в том процессе,
который может сломаться. Образец на пилоте — `env_file_drift` (`observability.W010`):
считает снаружи и логируется из `ready()` именно потому, что `uvicorn config.asgi`
системные проверки не прогоняет, «so a check alone would have stayed invisible in
exactly the process that mattered».

Проверка: **если предмет мёртв, мой сторож закричит?** Нет — сторожа нет.
## 24. Печатать идентификатор предмета в тот же лог, что и результат

Три случая за одни сутки, и все три — **прогон, который отработал успешно и измерил не то**:

| что случилось | что показал инструмент |
|---|---|
| подмена целилась в несуществующий узел | `tests: 0, failures: 0` — читается как «сторож молчит» |
| зелень получена на старой голове | `2441 passed` — число настоящее, предмет чужой |
| монитор доложил `mergeStateStatus: CLEAN` у черновика | «готов к слиянию» — а слить нельзя |

Общее у всех трёх: **«успех команды» и «предмет измерения» — независимые вещи.**
Инструмент не соврал ни разу. Он ответил на свой вопрос, а прочитан был как ответ на другой.

**Правило:** рядом с результатом печатать то, что доказывает предмет.

* прогон тестов — `git rev-parse --short HEAD` и число **собранных** тестов;
* targeted proof — имя узла и подтверждение, что подмена применилась;
* состояние PR — `isDraft` рядом с `mergeStateStatus`;
* замер на контуре — имя контейнера и время старта процесса.

Исполнителя, поймавшего у себя зелень на старой голове, спасло не внимание, а то, что
он вывел SHA в тот же лог рядом с числом и увидел `9c0ce1db` там, где ждал `c2697a9b`.

**Без идентификатора предмета отчёт неотличим от правды.**

Родственное: §16 (пустой прогон), §23 (тревога внутри предмета), «код выхода pytest врёт».

## 25. `CLEAN` отвечает на «сойдётся ли текстом», а не «переживёт ли предмет»

Мержибельность — свойство текста. Git сливает без конфликта и там, где семантически
**откатывает**: ветка, заведённая до чужого слияния и правящая те же файлы, наложится
чисто и вернёт прежнее поведение.

Проверка стоит секунды и делается **по содержимому, а не по статусу**: грепнуть три-четыре
опорные строки чужой уже слитой работы в голове сливаемой ветки. Так исполнитель убедился,
что PR из чужой ветки не откатывает его стоп-гейты и обёртку конверта, прежде чем дать
согласие на слияние.

Родственное: §8 (содержимое, а не родство), «влили чужое в твою ветку — проверяй содержимое».
## 26. Полный локальный `pytest apps/` требует поднятого Redis

**Практическое.** Без него 35 тестов в `apps/orchestrator/` красные на **чистом** `origin/dev`:

```
redis.exceptions.ConnectionError: Error 10061 connecting to localhost:6379
pipeline.turn → _run_under_tenant → _update_short_term
              → memory/short_term.py:120 pipe.execute()
```

Конвейер валится на записи краткосрочной памяти и не доживает до собственных утверждений.
Отсюда разнородность имён — `test_intent_captured`, `test_skill_response_composed`,
`test_p95_under_4000ms_over_50_runs` падают **по одной причине**, а выглядят как три разные.

В `ci.yml` Redis объявлен сервисом, поэтому CI зелёный. Локально: `docker run -p 6379:6379 redis`.

**Это не чужой дефект и не отселектированные тесты.** Разница важна: «чужой дефект» идут
искать в чужом коде, а искать тут нечего.

## 27. Трассировка дешевле трёх гипотез

К этим тридцати пяти было предложено **три правдоподобных объяснения, и все три неверны**:

| гипотеза | чем опровергнута |
|---|---|
| «отселектированы в `ci.yml`» | 64 деселекта, про orchestrator — ноль |
| «блокер круга, чужой дефект» | CI зелёный, тесты выполняются |
| «классика среды: замеры скорости» | ближе всех и всё равно мимо — `test_p95_*` падает от Redis, а не от медленности |

Верное лежало **в первой трассировке**. Один прогон против трёх рассуждений.

**Правило:** увидев набор падений, сначала открыть трассировку **одного** из них,
и только потом строить объяснение. Разнородные имена в списке падений — не признак
разных причин; чаще это одна причина выше по стеку, чем все они пользуются.

Родственное: §24 (печатать идентификатор предмета), «пересказ источника — не источник».
## 28. Сторож обязан проверять, что предмет охраны ещё существует

Сторож «у поля читателей ноль» остаётся зелёным и в тот день, когда поле удалили или
перестали различать. Предмет исчез, охрана осталась и **рапортует об успехе**.

Поэтому рядом с проверкой запрета ставится проверка предмета: `test_the_field_still_exists`
у сторожа `CatalogMaster.address` держит `null=True` и ловит два случая — колонку удалили
(`FieldDoesNotExist`) и колонку сделали двузначной.

**Границу покрытия называть вслух.** Тот же сторож НЕ ловит третий случай: поле переименовали,
а старое имя оставили живым синонимом — регулярка ищет `.address`, тест смотрит на имя поля.
Формулировка исполнителя, и она обязательна к повторению:

> Правило верное, но сторож покрывает предмет не целиком, и это стоит назвать явно.
> Иначе через месяц кто-то сошлётся на эту строку как на полную гарантию — а это ровно
> тот же зверь: **имя, которое обещает больше, чем механизм даёт.**

## 29. Зелёная строка рядом с тестом не доказывает, что тест исполнялся

`-q` печатает точки, а не имена. Отсутствие имени в логе выглядит одинаково и когда тест
прошёл, и когда файл **не был собран вовсе**.

Проверять двумя шагами:

1. открыть `ci.yml` и убедиться, что путь попадает в шаг (`tests/contracts/` собирается,
   исключён один именованный тест);
2. **сверить счётчик с базой.** Последний зелёный прогон на `dev` — 752 passed, 11 skipped,
   38 deselected. Прогон с новым сторожем — **756 passed**, те же 11 и 38. Ровно +4:
   столько тестов и добавлено, ни больше ни меньше.

Дельта счётчика — доказательство исполнения. Зелёная галочка — нет.

Родственное: §16 (пустой прогон), §24 (печатать идентификатор предмета).

## 30. У базы ветки тоже есть содержимое, и `CLEAN` о нём ничего не говорит

Правило 25 отвечает на «сойдётся ли текстом». Оно ничего не говорит о том, **видит ли ветка
то, что уже слито в её базу**.

Устаревшая база невидима всеми обычными способами: PR показывает `CLEAN`, тесты зелёные,
конфликтов нет. Проявляется она только когда полезешь в файл **за конкретной вещью, которая
должна была там быть, и не найдёшь её**.

*Случай (10.09.2026):* цепочка из трёх PR каталога стояла на базе, не содержавшей уже
слитого #309. Все три правили один и тот же `services/admin.py`, не видя чужих правок в нём.
Слияние прошло бы автоматически — «скорее всего», а это ровно то место, где правки теряются
тихо. Нашёл исполнитель, начав следующий срез и не обнаружив формы из #309.

**Проверять базу тем же приёмом, что и слияние (правило 8): содержимым.** `git merge-base`
с `origin/dev` — одна строка, и она обязана равняться голове `dev`.

**Следствие:** зелень снимается на конкретном коммите. Ветку перебазировали — прежняя зелень
относится к коммиту, которого больше нет. Она была честной; она про другое.

## 31. Предусловие, выданное тесту, обязано быть объявленным, напечатанным и живым

Гейт, поставленный в код, красит тесты, которые описывали мир без него. Чинить их подгонкой
нельзя — но и «тест сам себе что-то настроил» не годится.

Три требования:

* **объявленным** — в общем списке, а не в теле теста;
* **напечатанным** — в отчёт покрытия, чтобы было видно, что гейт раздал системе бесплатно;
* **живым** — настоящим вызовом, а не подменой предиката. Подменённый предикат проверяет
  вашу заглушку вместо обработчика.

*Образец в этом репозитории:* `GRANTED_PRECONDITIONS` в `apps/replay` — кортеж объявленных
предусловий со встроенной оговоркой о собственном сроке годности: «ни одно из них не является
веткой, которую документирует golden-фикстура; если фикстура для такой ветки появится, её
надо перестать выдавать здесь».

*Случай (10.09.2026):* гейт согласия покрасил 11 тестов анкеты и 4 replay-фикстуры.
Починены выдачей настоящего `grant()` и записью в тот же кортеж теми же словами.

## 32. Правило, перенесённое без поведения, — не то же правило

Переносить проверку из одного контура в другой можно; переносить её **вместе с тем, что
происходит после отказа**, — обязательно. Иначе получится правило с чужими последствиями.

*Случай (10.09.2026):* медицинский гейт в боте на `True` **не отказывает** — он вызывает
`_handoff` и отдаёт человеку текст про консультацию; над кодом это прямо написано. Перенос
того же правила в каталог поднял исключение и вернул `400`. Правило то же, поведение другое —
и из этой разницы родились 104 жёстких падения тестов, которые сначала прочли как «фикстуры
не отвечают».

## 33. Довод живёт у правила, а не в докстринге файла

Читают у правила. Объяснение, стоящее на сто девяносто строк выше, через полгода не
прочитают вовсе — и свойство пилота примут за свойство системы.

## 34. «Неприменимо» — не «неизвестно»

`UNKNOWN` обвиняет данные в том, что они не ответили. Но если в модели **нет колонки**, куда
лёг бы ответ, — отвечать было негде, и это другое состояние.

Разница не стилистическая, а операционная: у «неизвестно» есть работа (спросить, разметить,
дозаполнить), у «неприменимо» работы нет вовсе. Слитые в одно, они дают очередь задач, в
которую валится слой, размечать который никто не собирается.

*Случай (10.09.2026):* у легаси-модели `Service` нет признака медицинского скрининга.
Отвечать `False` — фикция; отвечать `UNKNOWN` — ложная работа. Заведён третий код,
`HEALTH_CHECK_NOT_APPLICABLE`.

**Заводить порознь с первой строки, а не разделять потом.**

## 35. Значение, проставленное пачкой, отвечает не на тот вопрос

Провенанс, выставленный оптом, отвечает на «кто нажал», а не «кто решил». Фикстура, залитая
одним значением по всему файлу, отвечает на «как позеленить», а не «что здесь за предмет».

*Случай:* 56 связей каталога — это 56 решений, и массового подтверждения у них не будет.
*Случай:* в тесте про оплату услуга скорее не требует скрининга, в тесте про медицинский
педикюр — требует; одинаковое значение в обоих означает, что вопрос не задавали.

## 36. Несработавший сторож при сработавшей подмене — находка, а не шум

Подмена вернула в код **две** запрещённые вещи сразу — объяснения персональной
пригодности и передачу клиента в движок. Покраснели **два теста из трёх**.

Соблазн прочитать это как «подмена применилась частично» велик, и он неверен. Проба
печатала собственные совпадения (`match_reasons 1`, `client_id 1`) — применилась целиком.
Значит молчал сторож, и молчал он не случайно: он искал подстроку `client_id=None`
в исходнике и **находил её в комментарии**, который объяснял правку.

**Правило:** проверять надо не «покраснело ли», а **«покраснело ли ВСЁ, что обязано»**.
Список того, что обязано, составляется **до** пробы, иначе после неё он подгонится под
результат.

Родственное: §18 (подмена как способ отличить требование от совпадения) — здесь тот же
приём, повёрнутый на самого сторожа.

## 37. Сторож, читающий исходник как текст, проверяет документацию, а не программу

Три случая за один день, у трёх разных окон:

* тест искал `"client_id=None"` в исходнике метода — и нашёл в комментарии, объясняющем,
  почему там стоит `None`. Зеленел на подменённом коде;
* текстовый гард поймал **докстринг**, который перечисляет запрещённые конструкции,
  чтобы их запретить, — и объявил документацию нарушением;
* фильтр по логу поймал имя собственного задания и отчитался чужой строкой.

Общее: **упоминание предмета и предмет неотличимы для поиска по тексту.** Комментарий,
докстринг и имя задачи живут в том же файле, что код, и написаны теми же словами —
особенно если написаны хорошо.

**Правило:** сторож, чей предмет — код, читает **дерево разбора**, а не строки.
`ast.walk` вместо `in source`, именованный аргумент вместо подстроки. Где разбор
невозможен, сторож обязан **краснеть при неразбираемом входе**, а не пропускать его.

И вторая половина, без которой первая недостаточна: **сторож, потерявший предмет, обязан
кричать.** Нет вызова с таким аргументом — падать с «смотрю не туда», а не зеленеть.
Иначе он превращается ровно в то, чем был.

## 38. Между записью подмены и `finally` не должно быть ни одной строки, способной бросить

Проба подменой оставляет систему изменённой, и восстановление обычно стоит в `finally`.
Ассерт, поставленный **до** `try`, обрывает исполнение раньше, чем `finally` появится в
кадре, — и дерево остаётся отравленным. Следующая проба мерит на нём и получает число,
которое ничего не значит.

**Правило:** записал подмену — следующей строкой `try`. Всё, что способно бросить, —
внутрь. И **печатать базовое состояние** до пробы: без него «восстановилось» есть
утверждение, а не наблюдение.

## 39. `head` запрещён на перечне, полнота которого и есть предмет проверки

Обрезка вывода — привычка экономить экран, и она безвредна, пока вопрос звучит «есть ли
хоть один». Когда вопрос звучит **«все ли»**, `head` превращает ответ в противоположный:
перечень, обрезанный на десятом, доказывает наличие десяти и молчит про одиннадцатый.

Отличать от §9 (угаданный набор) по лечению: там требуется **назвать правило отбора**,
здесь — **не резать вывод**. Правило отбора может быть безупречным, а вывод всё равно
обрезанным.

## 40. Метрика может быть верной и отвечать не на тот вопрос

Три случая за день, и во всех число было **настоящим**:

* `ruff check` честно ответил «All checks passed» — на свой вопрос. Прочитали как ответ
  про проверки конвейера;
* «20 узлов» оказались одним тестом, разложенным параметризацией;
* «756 passed» было точным числом — чужого набора.

Ни в одном случае измерение не сломалось. Сломалось **соответствие вопроса и метрики**, и
именно поэтому такие случаи не ловятся перепроверкой числа: число сойдётся снова.

**Правило:** рядом с числом печатать **вопрос, на который оно отвечает**, и предмет, на
котором снято (§24). «Прошло 756» и «прошло 756 в наборе X на коммите Y» — разные
утверждения, и второе невозможно прочитать не так.

## 41. Зелень в N раскладках доказывает, что эти N не поймали

Прогон, зелёный на нескольких порядках выполнения, читается как «порядок не влияет». Он
означает ровно то, что сказано: **эти конкретные раскладки дефекта не нашли.**

И отдельно: **на детерминированном планировщике повтор — не независимое испытание.** Сто
одинаковых прогонов дают одно наблюдение, а не сто.

**Правило:** формулировать как «не поймали на N раскладках», а не «не зависит от
порядка». Первое — измерение, второе — вывод, которого измерение не даёт.

## 42. Флаг, который никто не может прочитать, не должен быть тем, что что-то включает

`bool("false")` есть `True`. Строка из окружения, попавшая в условие без разбора,
включает то, что человек выключал, и делает это молча — потому что и «включено», и
«выключено» приходят непустой строкой.

**Правило:** значение, управляющее поведением, обязано **разбираться явно**, а результат
разбора — печататься при старте. Флаг, чьё значение нельзя увидеть в логе, отличается от
константы только тем, что все верят, будто им можно управлять.

## 43. Имя worktree берётся от окна, а не от предмета

Общая временная директория — **общее пространство имён**. Имя, взятое от предмета
(`wt-provenance`, `wt-schedule`), у соседнего окна возьмётся из того же словаря, потому
что предметы у окон пересекаются.

Случай: `git worktree add` отказал по «директория уже существует», исполнитель сделал
`cd` туда и прочитал головой **чужую ветку**, приняв её за свою. Спасло несовпадение SHA
с тем, что он сам пушил минуту назад.

**Правило:** `wt-<окно>-<предмет>`.

И второе, важнее первого: **`cd` в существующую директорию после отказа
`git worktree add` — это молчаливая смена предмета.** Отказ инструмента был единственным
сигналом, и он был обойдён рукой. Тот же зверь, что §39: инструмент ответил верно, ответ
обойдён.

## 44. Подмена возвращает своё имя, но не своё потомство

Формулировка окна питания, 10.09.2026, дословно. Зонд поставлен, снят, дерево чисто:

```
                                 один прогон   после соседей
httpx.AsyncClient                    нет            нет
openai.AsyncOpenAI                   нет            нет
openai.DefaultAsyncHttpxClient       нет           ДА      ← никто не патчил
```

Класс достраивается от текущего `httpx.AsyncClient` **на импорте модуля**. Импорт
случился **внутри** `with patch("httpx.AsyncClient")`. Выйдя, `with` восстановил
родителя — **но не то, что от него успели произвести.** Испорченным остался объект,
которого в подмене никто не называл.

**Момент рождения — импорт, а не первое обращение**, и это выяснено опытом, а не
рассуждением. Первая гипотеза автора была «при первом обращении»; он же её и снял,
соседнее окно закрыло вопрос тремя опытами:

```
module __getattr__ у вендора             НЕТ
импорт ВНЕ патча, обращение ВНУТРИ       класс цел
импорт ВНУТРИ патча                      отравлен
```

Разница не академическая, она **меняет лечение**. Из «при первом обращении» следовало бы
«тронуть имя пораньше» — и не вылечило бы ничего. Из «на импорте» следует
**eager-import до патчей**.

**Почему это не §36 и не §37.** Три инструмента ответили бы **верно**:

```
обход AST                плохих форм нет
сторож на имя            имя восстановлено
сторож на кэш роутера    тест строит провайдера свой, локальный
```

Формулировка автора: **три верных ответа, и все не на тот вопрос.**

§37 — про то, **чем** смотрит сторож: текстом или деревом. Здесь смотреть можно чем
угодно: вопрос в том, **на что** он смотрит. Ответ инструмента про **механизм** не
заменяет **наблюдения за состоянием**.

**Правило:** стеречь снимком `{имя: id(объект)}` по вендорскому модулю до и после теста.
Он ловит все каналы разом и **не спрашивает, кто чем их испортил** — а значит ловит и
тот канал, о котором никто не знал.

**Покрывать обоих вендоров и общий корень.** Таких ленивых импортов найдено **три**, и
один из них — другой вендор, устроенный буква в букву. Сторож, снимающий один модуль,
зелен ровно тогда, когда сломается непокрытый.

**И запрет, названный автором находки:** не «чинить» это сбросом синглтона первой
правкой. Сброс сделает прогон зелёным и **спрячет измеренный канал** — это зелень из
соседства, полученная своей же рукой (§8, §41).

## 45. Команда, которая умеет отказать, отделяется проверкой исхода, а не разделителем

Два случая одного рода, разные концы последствий.

**Разрушительный.** Сцепка была такой:

```
git add … && git commit -F - <<EOF … EOF
git log --oneline -1; git branch -f новая HEAD && git reset --hard origin/другая
```

Хук отклонил коммит. `&&` защищал только `add → commit`; дальше стояла `;`, и
`reset --hard` снёс **девять файлов**, включая два новых модуля. Восстанавливали из
висячих блобов.

**Публикующий.** Скрипт, готовивший тело PR, упал — не нашёл файл (путь в MSYS-форме
невалиден для питона на Windows). Следом в той же строке стоял `gh pr edit`: он
отработал и **залил старое описание**, отрапортовав успехом.

**Второй тише и потому опаснее.** Разрушение замечают: файлов нет. Публикацию
устаревшего не замечает никто — снаружи всё на месте, просто не то.

**Правило:** `git commit` умеет отказать **штатно** — любой хук делает это нормальным
исходом, а не аварией. Скрипт, не нашедший файл, — тоже. Поэтому между «умеющей
отказать» и «делающей необратимое или публикующее» стоит **проверка исхода**, а не `;`.

Признак, который ловится глазами: в одной строке после `commit`, `push` или генерации
файла стоит `reset --hard`, `checkout`, `clean`, `branch -f`, `gh pr edit`,
`gh pr create`.

**И проверять результат содержимым, а не кодом возврата.** Во втором случае код возврата
сказал «успех» и был **прав**: `gh pr edit` действительно отработал. Вопроса «то ли
содержимое там лежит» он не задавал — его задал
`gh pr view --json body | grep -c <маркер нового текста>`, давший четыре совпадения.
Это §40 в чистом виде: метрика верна и отвечает не на тот вопрос.

Родственное: §38 — там про порядок **внутри** пробы, здесь про **сцепку двух команд**.
Предмет разный, лечение разное.

## 46. Построено и выключено — третье состояние, а не одно из двух

Сверяя макет с рантаймом, естественно разложить на две графы: сделано и не сделано. Обе
солгут про построенный механизм, у которого закрыт рубильник.

```
ИСПОЛНЕНО   человек это видит
ЗАПЕРТО     построено, рубильник закрыт — человек НЕ видит
ОТМЕНЕНО    решением, со ссылкой на него
ПОДЛЕЖИТ    не сделано, с номером задачи
```

`ИСПОЛНЕНО` обещает, что человек это видит, — а он не видит ни разу. `ПОДЛЕЖИТ` заводит
работу, которая уже сделана, и следующий исполнитель напишет её второй раз.

**Вердикт `ЗАПЕРТО` обязан называть рубильник и его значение.** Без имени рубильника это не
вердикт, а впечатление: проверить его нельзя, открыть — тоже, потому что неизвестно что
открывать. Значение нужно отдельно от имени: флаг, упомянутый в коде и не заданный нигде,
выглядит как выключенный, а на деле у него нет выключателя (см. правило о ветке без
установщика).

*Случай (11.09.2026):* пост-визитный отклик «как прошёл визит?» построен целиком и **не
уходил ни разу** — `POST_VISIT_FOLLOWUP_ENABLED=false`, `POST_VISIT_FOLLOWUP_DRY_RUN=true`.
По прежней двухграфной разметке он попал бы либо в «исполнено» (ложь про человека), либо в
«подлежит» (ложь про работу).

**Проверять значение на своей базе, а не по аудиту.** Рубильник — самая изменчивая часть
системы: аудит двухнедельной давности говорит о нём в настоящем времени, а истина в
`settings` на сегодняшнем `dev`.

## 47. Назови, где живёт предмет, прежде чем рассуждать о нём

Номер 46 оставлен соседнему окну по разводке.

Четыре случая за сутки, и общее у них **не ошибка в рассуждении**. Рассуждение каждый
раз было безупречным — оно прикладывалось не туда, потому что **место предмета не было
названо**.

```
§37  где живёт предмет?  в коде или в комментарии о коде
     сторож искал строку в исходнике и нашёл её в объяснении правки

§40  чей это вопрос?     ruff ответил на свой, прочитали как ответ про конвейер
     «756 passed» было точным числом — чужого набора

§44  какой это объект?   подмена вернула имя, но не произведённое от него
     испорченным остался тот, кого никто не называл

+    в какой базе?       потребован тест, который стерёг бы ЧУЖУЮ базу;
     (11.09)             тест задаёт себе данные и с тем предметом не связан вовсе
```

К ним примыкает пятый, из другого дня того же набора: **в какой сборке?** — три разные
`ayla_ai_core` под одним номером версии, и процедура сверки, сравнивающая ровно тот
признак, который у всех трёх одинаков.

**Почему это отдельное правило, а не сумма тех четырёх.** Каждое из них лечит **свой
канал**: читай дерево, печатай вопрос рядом с числом, стереги снимком состояния. Общего
лечения ни одно не даёт, а канал всякий раз оказывается новый — пятый мы нашли сегодня,
шестой найдём завтра.

**Правило:** прежде чем рассуждать о предмете, **назови его место** — в каком файле, от
чьего имени, в какой сборке, в какой базе, на чьей ветке. Не «проверь предпосылки»:
предпосылки обычно верны. Именно **место** оказывается тем, что никто не назвал вслух,
потому что оно кажется очевидным.

**Признак, по которому ловится у себя.** Вывод получился убедительным, и при этом
где-то в цепочке стоит слово без адреса: «в коде», «в базе», «в пакете», «в тесте».
Каждое из них молча означает «в том, о котором я думаю», — а думают о разных.

Родственное: §24 (печатать идентификатор предмета рядом с результатом) — это то же
требование, суженное до одного лога.

## 48. Сверка с живым документом обязана называть его версию

Сверить реализацию с каноном, спецификацией или реестром решений — обычная работа. Она
становится невыполнимой, если документ меняется быстрее, чем читается: сверка, начатая в
понедельник, к пятнице сверяется **не с тем документом**, с которого начиналась.

Это **не то же самое**, что сверка без признака завершённости. Там конец **не определён** —
и лечится тем, что его определяют заранее. Здесь конец **недостижим**, и никакой критерий
изнутри задачи не помогает: причина снаружи.

**Постановка обязана звучать «сверить с `<файл>` на SHA X», а не «сверить с каноном».**
Принятое после X идёт следующим заходом, и это не потеря: заход, который нельзя закрыть,
не даёт ничего вообще, а закрытый заход плюс остаток дают всё.

*Случай (11.09.2026):* DRF-1322 сверяет клиентский UX с каноном. Замер канона — **111
решений, 12 коммитов за трое суток**, около четырёх решений в сутки. Оценить задачу было
нельзя до тех пор, пока владелец не закрепил версию; после закрепления объём считается по
числу разделов за час.

**Признак, по которому это распознаётся заранее:** в постановке стоит имя документа без
версии, а документ живой. Если непонятно, живой ли, — посчитайте коммиты в него за
последнюю неделю. Это один запрос.

## 49. Путь не есть адрес: две машины, один путь

Замер «3315 объектов в дереве выкладки принадлежат root» был снят на
`/home/taximeter/ai-bot-platform-dev` — и **не на той машине**. Второй хост несёт
тот же путь, ту же учётку и те же имена compose-проектов, и его копия контура
заброшена с 03.09: дерево заморожено, прикладные контейнеры вышли, на порту пробы
никто не слушает. Число было правдоподобным, разбивка осмысленной, и на нём успели
завести храповик.

Поймалось только противоречием: одно окно видело зелёную выкладку сегодня, другое —
HEAD восьмидневной давности. **Оба были правы — про разные машины.**

§47 требует назвать место предмета. Здесь место было названо — путём — и этого не
хватило, потому что путь есть на обеих. Различает только **адрес**, а адрес называет
тот, кто предметом пользуется, а не тот, кто его ищет:

```
docker inspect <контейнер> --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'
nslookup api-dev.gobeauty.site
```

**Правило:** hostname и адрес печатаются рядом с числом всегда, не только когда
машин заведомо несколько. Противоречие между двумя верными замерами — сначала
вопрос «об одном ли предмете они», и чаще всего нет. В базовой линии машина
называется именем и адресом; первая редакция писала «on the dev box», и именно эта
неназванность позволила поверить чужому дереву.

Родственное: §1 («в каком репозитории» — часть утверждения), §47.

## 50. Владелец файла говорит о способе записи, не о писавшем

Двое суток считали, что в дерево выкладки пишут **три** учётки — по владельцам
файлов, записанных в одну секунду:

```
.git/FETCH_HEAD     taximeter   05:04:36.443
.git/index          root        05:04:36.467
apps/miniapp/dist   uid 1001    05:05:41      ← такого пользователя на машине НЕТ
```

Актор был один — root. Отличались не писавшие, а **способ записи**:

```
на месте (открыть-обрезать)   владелец НЕ меняется — root пишет любой файл
lock + rename (новый файл)    владельцем становится писавший
tar под root                  ВОССТАНАВЛИВАЕТ владельцев из архива;
                              под обычным пользователем — игнорирует их
```

Несуществующий uid 1001 сперва прочли как след раннера. Это след **прав
распаковывавшего**: из одного наблюдения следуют противоположные выводы, и решает,
кем был процесс.

**Правило:** владелец — свойство inode, а не события записи. Перед тем как считать
акторов по владельцам, спросить: файл создавался заново или переписывался?
`git`, `tar`, редакторы делают и так, и так. Чей euid был у процесса — выводить
**поведением**: `sudo -n -l` у пользователя пуст, а шаг исполняет `sudo` и зелёный ⇒
шаг идёт не от него. Такой вывод не требует прав, которых нет.

## 51. Право удалить и заменить файл — у каталога, не у владельца файла

Доложено как находка: «loose-объекты `.git` принадлежат root, значит `git gc` от
владельца дерева не сможет их удалить». Принято как лучшее в отчёте, вписано в
тикет третьим взведённым каналом. **Неверно.**

```
.git/objects        taximeter 775     ← решает ЭТО
объекты внутри      root 644          ← а не это
sticky-бита нет; touch в каталог — РАЗРЕШЁН
```

В POSIX удаление и создание — операции над каталогом. Отсюда практический
разворот: чужие файлы в своём каталоге почти безвредны, а свой файл в чужом
каталоге останавливает всё. Из 434 чужих объектов настоящим препятствием оказались
**8 каталогов**; остальное лечится само при перезаписи — если инструмент
**удаляет и создаёт** (git через rename, `collectstatic` через
`storage.delete` перед копией), а не переписывает на месте (`open(..., "w")` по
существующему пути упрётся в права файла).

**Правило:** прежде чем говорить «не сможет удалить» — померить каталог: владельца,
режим, sticky-бит, и пробой (`touch` + `rm`), а не рассуждением. Удаляет инструмент
или переписывает — смотреть в исходник. Объём починки считать в каталогах, а не в
объектах.

## 52. Мера, которая работает ровно так, как написана, и не делает ничего

`--user "$(id -u):$(id -g)"` был поставлен на `docker compose run`, чтобы
контейнер перестал писать в дерево от root. Флаг заэкранирован верно, стоит в
правильном месте, доезжает до docker и честно передаёт «работай от того, кто меня
позвал». Позвал root: выкладка входит по ssh под root, и `$(id -u)` разворачивается
в `0:0`. Замер после правки: те же 154 root-овых файла.

`id -u` был **прокси** для «владелец дерева», верный ровно в предположении, что
зовущий и есть владелец. Предположение ложно, и мера, целиком исправная по форме,
пуста по действию.

**Правило:** сторож «флаг присутствует» такого не ловит — флаг присутствует.
Ловит только проверка **результата**: владелец записанного файла. И у каждого
прокси-значения спрашивать, при каком допущении оно равно настоящему, и верно ли
допущение **на той машине**, где мера исполняется. Лечение здесь — брать значение у
предмета (`stat -c %u "$DEV_DEPLOY_PATH"`), а не у зовущего.

Родственное: §12 (умолчание `getattr` — не умолчание системы): там значение брали не
из того контейнера, здесь — не у того субъекта.

## 53. Носитель факта существует, самого факта в нём нет

Шаг выкладки печатал актора, чтобы снять догадку, кто пишет файлы:

```
##[notice]шаг идёт от пользователя ***
```

Имя совпадает с секретом `DEV_USER`, и GitHub его вычёркивает. Строка, заведённая
ради снятия догадки, догадку не снимает — и хуже отсутствия строки: отсутствие
заметно, а `***` читается как «сработало».

**Правило:** заводя диагностическую печать, спросить, не совпадает ли значение с
секретом. Лечить сменой **носителя**, не формулировки: `id -u` — число, ноль против
1000 отвечает целиком и секретом не является.

Родственное: §24 (печатать идентификатор предмета в тот же лог) — это условие, при
котором §24 вообще выполнимо.

## 54. Стеречь класс, а не сегодняшнее написание — и печатать субъектов отдельно от нарушений

Правка чинила нераскрытую подстановку `$(id -un)` внутри ssh-строки и ставила сторож
**на `$(...)`**. Класс дефекта — «подстановка, раскрываемая оболочкой раннера», и в
него входит обратная кавычка `` `...` ``, которую сторож не видел. Следующая выкладка
упала на голой обратной кавычке **в комментарии**.

Сторож второго захода (голые кавычки внутри `bash -lc "`) был обойдён двумя
способами: `bash -l -c "` — блоков найдено 0, зелено; одинокая `"` в теле — блок
закрылся рано. Открывающая форма была **литералом**, и любая другая запись того же
самого проходила мимо.

Третий заход шёл по YAML: каждый шаг, в чьём `run` есть `ssh`. И тут дыра нашлась не
в правиле, а в **области**:

```
старая редакция   3 блока  / 14 нарушений
новая редакция    4 шага   / 14 нарушений
```

Нарушений поровну — редакции выглядят эквивалентными. Субъектов разошлось на
единицу, и это указало на шаг, который старая редакция не проверяла **никогда**: он
собирал вызов в переменную (`SSH="ssh …"`) и литерала не содержал.

**Правило:** написав сторож, спросить «как записать то же самое иначе» и проверить
**опытом**, а не перечитыванием. И печатать два счёта рядом — сколько нарушений и
сколько субъектов проверено. Расхождение второго — сигнал, даже когда первый совпал:
неполное покрытие неотличимо от полного, если печатать только нарушения.

Родственное: §37 (сторож читает дерево, а не строки), §28 (сторож проверяет, что
предмет ещё существует).

## 55. Пересечение сторожей недоказуемо

Две проверки в `check_distance_readiness`: «новейшая запись старше порога» и
«свежих опор меньше одной». Это **одно условие** (нет записи в пределах порога ⟺
свежих нуль). Тесты зелёные, логика верная, покрытие «двойное» — и выключить можно
было любой из двух: второй ловит ту же пробу.

Увидела это подмена, не чтение: в отчёте пробы стояло `1 failed, 1 passed` там, где
раньше было `2 failed`.

**Правило:** два сторожа на одно условие делают каждого недоказуемым. Ветки
разводить так, чтобы области не пересекались (`if not alive` / `elif len(alive) < N`).
Признак в отчёте подмен — проба, которая краснит **меньше** тестов, чем раньше, при
том что кода стало больше. Число покрасневших — часть результата пробы, а не её
оформление.

Родственное: §18, §36.

## 56. Наблюдаемая устойчивость — не гарантия; ключ сортировки — не порядок

`order_by("-last_seen").first()` при равном `last_seen` отдаёт произвольную строку,
и один человек разрешается в разные тенанты на двух одинаковых запросах. Тест на это
был написан: позвать резолвер дважды, утвердить совпадение. **Он проходил и со снятым
тай-брейком** — на обоих сломанных местах.

Postgres при ничьей **волен** вернуть любую строку, но «волен» не значит «каждый раз
другую»: на одном плане, с холодной таблицей и без перемещений он отдаёт одну и ту
же, сколько ни спрашивай. Возмущение `UPDATE`-ом, на которое рассчитывали, ответ
тоже не переворачивало — проверено.

Утверждение было про **гарантию** («порядок полный»), а проверялось
**наблюдение** («сегодня совпало»). Неопределённое поведение почти всегда
воспроизводимо в узких условиях теста — на том и держится иллюзия.

**Правило:** гарантию проверять по её носителю, не по исходу. Для порядка носитель —
настоящий SQL: `CaptureQueriesContext`, и в `ORDER BY` обязано стоять уникальное по
строке поле. Наблюдательный тест можно оставить рядом, назвав слабым и сказав, что
именно он проверяет.

Вторая половина того же случая: `auto_now=True` молча выбрасывает `last_seen`,
переданное фикстуре, и тест превращается в гонку с часами — «плавающий отказ» был
не состоянием и не кешем, а **скоростью**: прогретый интерпретатор укладывал две
вставки в один тик. Задавать такое поле честно можно только `QuerySet.update()`.

Родственное: §18 — сторож, зелёный на сломанном коде, опаснее неверного числа: число
заметно при сверке, а зелёный сторож выглядит доказательством.

## 57. Проба, которая ничего не ломает, находит окно

Привычная проба снимает предмет и ждёт красноты — это **проба про значение**. Она
слепа к промежуточному состоянию, потому что итог не меняется.

Инвариант «сорт ключа пишется в том же `save()`, что и ключ». Проба: разнести один
`save()` на два, **оставив значения прежними**. Всё дописано, все прочие тесты
зелены, и покраснел ровно один сторож — на строку, у которой ключ уже стоит, а сорт
ещё `NULL`.

**Правило:** инвариант «эти поля меняются вместе» проверяется не снятием поля, а
разнесением записей во времени. Сторож ставится на границу записи
(`Model.save`, транзакция), а **не на порядок строк в исходнике**: текстовый сторож
переживает перестановку кода и умирает от неё же. И сторож обязан сначала
утвердить, что он что-то видел: пустой список перехватов проходит любую проверку
«все записи хороши» молча.

Родственное: §18, §36.

## 58. Fail-closed значение прячет своё происхождение

Кодек состояния: отсутствие ключа `safety` даёт `UNKNOWN`, а не `NORMAL` — верно и
недостаточно. Раз отсутствие ключа **уже** означает «не оценивали», `UNKNOWN` не
нужно хранить никогда. А если его можно записать, у одного состояния появляется
второе происхождение: «движок не запускался» и «адаптер проглотил ошибку и вернул
fail-closed значение» приезжают в хранилище одинаковыми.

```
неверный NORMAL    заметят — он пропустит то, что должно было остановиться
неверный UNKNOWN   выглядит осторожностью, блокирует по правдоподобной причине,
                   и снаружи девять правильных блокировок и одна проглоченная
                   ошибка — одно событие
```

`__post_init__` этого не ловит и не по слабости: `UNKNOWN` без ревизии — его
разрешённая пара. Происхождение из значения не видно; удержать его может только
**формат** — тем, что не умеет это сказать.

**Правило:** одно представление на факт. Если отсутствие ключа уже что-то значит,
писать то же значение объектом — заводить второй источник состояния; записанное
fail-closed значение при чтении **отвергать**. Различать терпимость к **форме**
(нечитаемый ключ имеет невиноватое происхождение — раскатка) и строгость к
**значению** (у записанного отказа невиноватого происхождения нет). И спрашивать не
только «что будет, если подставят разрешение», но и «что будет, если подставят
отказ» — второй вопрос почти никогда не задают.

Родственное: §34 («неприменимо» — не «неизвестно»).

## 59. Зелено, потому что среда совпала

Экран салона печатал часы через `new Date` — в поясе **браузера**, хотя рядом лежала
`wireTime` с докстрингом «провод несёт смещение салона». Локальные прогоны идут в
MSK, провод в тестах несёт `+03:00`, пересчёт совпадал со срезом — **807 тестов
зелёные**. Красноту нашёл CI, потому что он идёт в UTC: «14:00 салона» стало «11:00».

**Правило:** «у меня зелено» — утверждение о моей среде, а не о коде, и перезапуск
это только подтвердит. Случай строить так, чтобы он расходился при **любом** едином
пересчёте, а не при конкретном: два визита на одно стенное время с разными
смещениями — правильный код даёт один заголовок, любой пересчёт два. И считать
**носители**, а не одно значение: `getAllByText("14:00")).toHaveLength(1)` было
зелёным при обеих реализациях, потому что сломанный код уводил второй визит в
«08:00», и «14:00» по-прежнему был один.

Родственное: §41 (зелень в N раскладках доказывает, что эти N не поймали) — здесь
раскладка не тестов, а среды.

## 60. Замер пишет в свою же опору

`events.Event` получает строку `worker.subscriber_audit` при **каждом** старте
процесса — включая старт `manage.py surface_state`, который этот пульс и измеряет.
Опора «события» читалась как «возраст 0 мин» на пустой базе: замороженная копия с
живым контейнером БД выглядит живой ровно потому, что к ней подключились. Тот же
boot-след, оставленный ручным прогоном в переиспользуемой тестовой базе, уронил
6 чужих тестов, ждавших чистую таблицу.

**Правило:** у каждой опоры пульса спросить «кто пишет сюда при старте *моего*
процесса?» — ready-хуки `AppConfig`, warmup, health-probe, audit-emit. Такие строки
вычитать явно и держать тест «один boot-след пульсом не считается». После ручного
прогона команды на `--reuse-db` — `--create-db` для соседей, иначе их краснота будет
по чужой причине.

Родственное: §23 (тревога внутри предмета — не тревога): там сторож стоял внутри
измеряемого, здесь измеритель пишет в измеряемое.

## 61. Красный при зелёном имеет четыре класса, различимых по API

Два PR шесть часов стояли `BLOCKED` при `mergeable=true` и **всех четырёх
обязательных `success`**. Гипотезы «устаревшая проверка» и «нужно ревью» не
подтвердились. На голове каждого workflow стартовал дважды в одну секунду, и
`cancel-in-progress` погасил один — у каждого обязательного имени два check-run'а,
`cancelled` и `success`. У проходящих PR каждое имя ровно один раз. `gh run rerun`
отменённого → `clean` через минуты.

Третий PR был красен дважды с одним текстом, включая перезапуск, при верном теле.
Регулярка **из лога** объясняла падение; регулярка **на `dev`** была расширена
сутками раньше и тело пропускала. На `pull_request` workflow берётся из головы PR:
починка сторожа не доезжает до неперебазированного PR, и перезапуск перечитывает то
же тело тем же старым сторожем.

```
1  cancelled рядом с success на голове   rerun отменённого
2  failure дважды, один текст            прогон прав: тело/код неправ
3  прогон устарел от головы (§7)         push/rebase
4  PR несёт старую копию сторожа         rebase; rerun бесполезен  ← маскируется под 2
```

**Правило:** «все обязательные зелёные» и «на голове нет ни одного отменённого» —
разные утверждения, кнопка показывает первое. `BLOCKED` при зелёных обязательных →
`gh api …/commits/<head>/check-runs` и считать дубли имён. Читая правило из лога,
помнить: это правило **той головы**, не репозитория; класс 4 от класса 2 отличает
только сверка с `dev`. Первый `gh api …/pulls/N` отдаёт `mergeable_state=unknown` —
GitHub считает лениво, повторить. Лечить перезапуском отменённых, не пустым
коммитом: коммит двигает голову и запускает всё заново.

Родственное: §7 (перезапуск — сверять SHA), §14 (проверка может не докладывать вовсе).

## 62. Пример связывающей формы — связывающая форма; объяснение дефекта воспроизводит дефект

PR, объясняющий, почему сторож ссылки на задачу упал на `**Задача: DRF-NNNN**` (с настоящим номером),
привёл эту строку в теле как пример. Прогон:

```
##[notice] Ссылка на задачу найдена: Задача: DRF-NNNN   ← здесь стоял настоящий номер
```

Сторож нашёл пример и счёл его связывающей формой — интеграция привязала бы PR к
чужой задаче реестра. Ровно случай из шапки самого сторожа («PR про бэкап пилота
ссылался на чужую задачу как на образец»), который тот же PR цитировал.

Это вторая форма одного явления за день: §37 описывает докстринг, перечисляющий
запрещённые конструкции, который текстовый гард объявил нарушением. Там лечение —
сторож читает дерево разбора. Здесь предмет — прозу — разобрать нельзя, и лечение
на стороне **автора**.

**Правило:** сторож различает **место**, а не намерение, и это верно по замыслу.
Поэтому объяснение дефекта не должно содержать дефект: цитировать связывающую форму
можно только с выхолощенным номером (`DRF-NNNN`), запрещённую конструкцию — в
неразбираемом виде. Перед пушем прогнать регулярку сторожа по своему же телу:
«объяснил, почему падало» и «воспроизвёл, отчего падало» на письме неотличимы.

Родственное: §37.

## 63. Слитый PR — не закрытая задача

Сторож «работа без записи» дал 28 задач со слитым PR и открытым состоянием. Разметка
**по номерам** предложила бы закрыть все. Чтение обоих тел — задачи и PR — дало
другое: девять из шестнадцати закрывать было нельзя.

```
срез, не задача          задача разбита на B-2.1…B-2.4, PR — один из них
разбор, не постройка     задача «Разбор: …», PR — другой предмет, лишь ссылается
временное ≠ сделанное    PR говорит «временное правило периметра»
чужой номер              PR в теле пишет DRF-1411, сторож связал с 1409
часть предмета           задача про набор, PR — «только цвет»
ops-половина             задача про переменную на пилоте; PR чинит подсказку в коде,
                         задана ли переменная — из кода не видно
```

**Правило:** упоминание номера в PR — это связь, а не покрытие. Сторож видит связь;
покрытие видно только чтением обоих тел. Исполнителю не предлагать список «закрыть»
по номерам — предлагать список **проверить**, с признаком расхождения у каждого.

Родственное: §40, тем же днём: DRF-1092 был сформулирован именем переменной,
которого код не читает (`git grep` — ноль читателей); замер «отсутствует» был
методически исправен и отвечал не на тот вопрос (§40). Перед «задана ли настройка»
— grep, кто читает имя. Ноль читателей значит «мерить нечего», а не «настройка
отсутствует».

## 64. Linear отвечает шире вопроса

Два расхождения между вопросом и ответом GraphQL, и оба дали правдоподобный счётчик
(220 из 222):

1. `comments(last: 1)` возвращает **первый** комментарий, не последний. Три задачи
   показали чужой текст под видом свежего.
2. `issues(filter: {number: {in: [...]}})` без `team: {id: {eq: …}}` возвращает
   задачи **других команд** с теми же номерами.

**Правило:** каждая мутация — чтение обратно по идентификатору или тексту; каждый
запрос по номерам — с ограничением команды. Счётчик «почти всё записано» без чтения
обратно — утверждение о запросе, а не о данных.

Родственное: §19 (считая только истинные строки, не отличишь «не пришло» от «пришло
пустым») — та же семья: ответ формально полон и отвечает не на тот вопрос.

## 65. Дифф `.secrets.baseline` — это сдвиг строк, а не новые секреты (и наоборот)

`.secrets.baseline` изменился в PR, который секретов не трогал (#332, каталог): восемь
строк диффа. Читать их по размеру нельзя — там `line_number` четырёх записей и
`generated_at`; `hashed_secret` и имена файлов те же. Хук `detect-secrets` переписывает
файл целиком при любом сдвиге строк в отслеживаемых файлах (#1560: «только синхронизация
номеров строк, которую хук делает сам, когда строки в `ci.yml` съезжают»). Обратная
сторона той же формы: **новая** запись `hashed_secret` в таком диффе прячется среди
десятка строк номеров и читается как тот же шум.

**Правило:** дифф baseline читать не строками, а множеством `hashed_secret` до и после
(`jq '.results | .. | .hashed_secret? // empty'` на обеих версиях, сравнить). Сдвиг
`line_number`/`generated_at` без новых хешей — не событие; новый хеш среди сдвигов —
событие, и объём диффа о нём не скажет.

Родственное: §13 (имя файла — данные, читать в машинной форме); §19 (полный по форме
ответ, отвечающий не на тот вопрос).

## 66. Инлайн в воркфлоу меняет, кто смотрит на форму

Парсер переписи тестов (`--collect-only -q` → число) жил инлайном в шаге `ci.yml` бота и
однажды отчитался `CENSUS UNREADABLE` на исправном выводе — сторож, который неверно
читает, хуже отсутствующего, а прочитать его форму некому: на инлайн-скрипт в YAML не
смотрит ни один тест. В каталоге он перенесён в `.github/scripts/census_count.py` и
поставлен под 18 тестов на реальных образцах вывода pytest обоих уровней тишины (#352).

**Правило:** всё, что в воркфлоу разбирает чужой вывод (pytest, junit, `docker`, `gh
api`), живёт файлом под тестом, а не строкой в `run:`. Инлайн допустим для команд, у
которых нет формы, которую можно прочитать неверно. Признак, что пора выносить: в
шаге есть регулярка или `awk`.

Родственное: §37 (сторож, читающий исходник как текст); §29 (зелёная строка рядом с
тестом не доказывает, что тест исполнялся).

## 67. `git` от root в чужом дереве не читает — `dubious ownership`

Шаг выкладки по проверенному SHA (#1625) звал `git rev-parse` и `rev-list` от root в
дереве, принадлежащем владельцу выкладки. Сторож «в дерево пишет владелец» покраснел на
чтениях, и первая реакция — «формально, чтения не пишут». Проверка показала: он прав по
существу — git от root в дереве другого владельца отвечает `fatal: detected dubious
ownership` и не отвечает ничего, кроме этого; «прочитать SHA от root» невозможно, а не
просто нежелательно.

**Правило:** правило «все обращения к дереву — от владельца» держится без исключения
для чтений не ради единообразия, а потому что исключение не работает. Перед тем как
просить у сторожа послабление «это же только чтение», исполнить чтение той же учёткой
на той же машине.

Родственное: §50–§51 (владелец, каталог); §52 (мера, исправная по форме).

## 68. Закрыто чтением — не закрыто: четвёртую поверхность нашло число

Три поверхности, печатавшие ориентир без происхождения, были закрыты чтением кода
(профиль, сводка, чипы — #1606 замер). Сторож поставлен иначе: один профиль
`unknown_legacy` с тремя числами `95 / 1850 / 2100`, и ни одно не должно встретиться в
тексте. Первый прогон показал `2100` — норма воды из `WaterTodayResponse`, четвёртая
поверхность, которой в замере не было (#1616). Подмена «гейт на норму воды снят»
ловится ровно одним тестом — тем, что нашёл дыру.

**Правило:** утверждение «все места закрыты» проверяется не списком мест, а
**числом-маркером**, которое не должно всплыть нигде: маркер найдёт поверхность, о
которой список не знал. Список мест — вход для чтения, число — сторож.

Родственное: §18 (правило без сторожа — совпадение); §54 (стеречь класс, а не
написание); §40 (метрика отвечает не на тот вопрос — здесь наоборот: число задаёт
вопрос шире, чем список).

## 69. Чужой сторож против своей ветки — до перебазы, слиянием в пробную ветку

#1592 (шаг выкладки) был зелёным на своей базе. В `dev` за это время вошёл #1596 —
новый сторож `test_every_container_process_carries_user`, написанный **из-за** #1592.
Перебазировать и смотреть, что покраснеет, — значит узнать это уже на перебазированной
ветке, с конфликтами и историей заодно. Дешевле: `git checkout -b tmp/probe && git merge
origin/<ветка сторожа>` и прогнать только его тесты — 36 passed за две минуты, ветка
удалена, своя не тронута.

**Правило:** перед перебазой на базу, куда вошёл новый сторож по твоему предмету,
прогнать его против своей ветки **в пробной ветке слиянием**, не перебазой. Красный
здесь — сведение, зелёный — право перебазироваться. Перебаза меняет, кто на тебя
смотрит; смотреть на себя их глазами надо до неё.

Родственное: §61 класс 4 (PR несёт старую копию сторожа) — зеркальный случай: там сторож
в PR старее `dev`, здесь `dev` новее ветки; §30 (у базы ветки тоже есть содержимое).

## 70. Свидетельство — для вердикта, не для свидетеля

`pre_check` записывает **все** срабатывания по всем корзинам в порядке словаря
(forensic). `evidence_ref` для safety-контекста брался бы с `matched_patterns[0]` — и
под вердиктом `BLOCK` первым мог стоять `CLARIFY`-шаблон: ссылка на прохожего, не на
того, кто вынес решение (#1619). Аудитор разрешил бы её в правило, которое вердикт не
определяло.

**Правило:** свидетельство привязывается к **выигравшей корзине** — той, что дала
вердикт по приоритету, — а не к первому элементу списка совпадений. Порядок forensic
списка — порядок словаря, не порядок силы. Сторож: `reference-from-a-bystander` —
подмена «взять `[0]`» красит два теста.

Родственное: §56 (ключ сортировки — не порядок); §35 (значение, проставленное пачкой,
отвечает не на тот вопрос).

## 71. Умолчание, которое ошибается громко, допустимо; молчащее — нет

`--user "$(id -u)"` под root давал `0:0` и **ничего не говорил** — мера по форме
исправна, по действию пуста (§52). В compose каталога поставлено
`user: "${APP_UID:-1000}:${APP_GID:-1000}"` (#354) — тоже умолчание, но с другим
свойством: неверный uid на другой машине **падает видимо** — `EACCES` на записи в
`staticfiles/`, — а не пишет от root молча. Умолчание принято ровно по этому признаку и
с названным условием (1000 = uid владельца дерева на пилоте).

**Правило:** у каждого умолчания спросить не «верно ли оно здесь», а «**как оно
ошибётся там, где неверно**». Умолчание, чья ошибка — видимое падение с именем, можно
оставить с комментарием об условии. Умолчание, чья ошибка — тихая подмена субъекта или
значения, нельзя оставить вовсе: его заменяет чтение у предмета.

Родственное: §52, §58 (fail-closed значение прячет происхождение), §12.

## 72. Два «пусто» в одном ответе — одно слово наружу, два состояния внутри

Бот считал «ориентира нет» только при `targets_source == "none"`; `unknown_legacy` —
«ориентир есть, происхождение не сохранялось» — печатался числами «Белки: 61 из 95 г»,
у двоих от подставленных 70 кг (#1606 B1). На пилоте все шесть профилей — `unknown_legacy`.
Починка (#1616): инвариант **на типе** — `ProfileResponse.__post_init__` читает ориентир
как отсутствующий при `source ∉ {ayla_calculated, user_entered}`; наружу оба состояния
дают один текст «ориентиров в профиле сейчас нет» намеренно; внутри они различимы
(`NOT_CONFIGURED` ≠ `none`).

**Правило:** где отсутствие бывает двух родов («не задано» и «задано без основания»),
наружу уходит одно слово, а различие живёт в состоянии — и инвариант ставится **на
типе**, а не в разборе ответа: разбор — не единственный конструктор (шесть тестовых
файлов собирали DTO руками и обошли бы правило в разборе).

Родственное: §34 («неприменимо» — не «неизвестно»); §58 (одно представление на факт);
§19 (два «пусто» неразличимы, если считать только истинные строки).
