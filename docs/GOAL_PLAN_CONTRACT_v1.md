# Goal Plan Contract v1

Статус: draft для ревью владельца

## Цель

Ayla должна уметь превращать пользовательское намерение вроде «хочу похудеть на 5 кг за 30 дней» в проверяемый и безопасный план действий.

Система не обещает достижение указанного результата. Число и срок сохраняются как пользовательский запрос, а не как гарантированный прогноз.

## Границы ответственности

- Backend является источником истины для целей, расчётов, плана, фактов и состояния безопасности.
- Orchestrator собирает контекст, выбирает следующий шаг и формирует объяснение.
- LLM не вычисляет калории, темп, медицинские ограничения и не меняет состояние без проверенного backend-решения.
- Дневник фиксирует факты. Запись в дневнике сама по себе не означает достижение цели.

## Модель запроса цели

`RequestedTarget`:

- `amount`: число, например `5`;
- `unit`: `kg`, `cm`, `count` или другой разрешённый тип;
- `period_days`: срок, например `30`;
- `source`: только `user_stated` или `user_confirmed`;
- `status`: `pending`, `accepted_for_planning`, `needs_clarification`, `blocked`.

Не допускается создавать эти значения из предположения модели.

## Решения проверки

Проверка возвращает одно из решений:

- `ACCEPT` — можно составлять план;
- `CLARIFY` — не хватает данных или согласия;
- `CAUTION` — запрос принят как пожелание, но срок/величина не подтверждены;
- `BLOCKED` — небезопасный или медицински чувствительный сценарий;
- `HANDOFF` — требуется специалист или внешний медицинский контур.

При `CAUTION` Ayla показывает безопасную альтернативу, не переписывая пользовательскую цель молча.

## План

План состоит из 1–3 действий из закрытого каталога:

- `log_food`;
- `log_water`;
- `book_service`.

Каждое действие имеет cadence и измеримый факт выполнения. План может быть:

- ручным и без активной цели;
- предложенным шаблоном, только при наличии активной цели;
- созданным после подтверждения пользователя.

Создание, изменение и закрытие плана должны иметь источник и ревизию.

## Контур работы

1. Пользователь формулирует цель.
2. Backend сохраняет исходный запрос.
3. Orchestrator проверяет readiness, consent и safety.
4. Backend рассчитывает допустимые nutrition targets только по подтверждённым входным данным.
5. Ayla предлагает действия.
6. Пользователь подтверждает или редактирует план.
7. Дневник и вода поставляют факты выполнения.
8. Плановая логика показывает факты и предлагает пересмотр только по явному правилу.

## Минимальные API-изменения

Нужно добавить:

- создание/чтение `RequestedTarget`;
- проверку цели с результатом `ACCEPT|CLARIFY|CAUTION|BLOCKED|HANDOFF`;
- ручное создание Plan Lite без `goal_id`;
- append-only историю ревизий плана;
- источник изменения: `user`, `template`, `engine`;
- replay-тесты для количественной цели, отсутствующих данных и safety-gates.

## Обязательные сценарии тестирования

- «Похудеть на 5 кг за месяц»;
- цель без веса, роста или возраста;
- несовершеннолетний пользователь;
- беременность/лактация;
- сигнал расстройства пищевого поведения;
- ручной план без цели;
- предложение шаблона при активной цели;
- изменение цели после создания плана;
- поздняя корректировка записи дневника.

## Не входит в v1

- гарантия достижения веса;
- автоматическое назначение лечения или диеты;
- выводы по весу без пользовательского измерения;
- скрытая корректировка цели;
- автоматическая отправка медицинских рекомендаций.
