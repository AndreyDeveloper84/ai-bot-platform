## Обязательные инварианты — от владельца, не подлежат пересмотру

1. **`UNKNOWN` → fail-closed.**
2. **`NOT_APPLICABLE` определяется типом capability, а не отсутствием данных.**
3. **Активная персонализация, `requires_health_check` или safety-sensitive candidate отменяют `NOT_APPLICABLE`.**
4. **Один sensitive candidate закрывает весь ответ.**
5. **`NORMAL` означает, что проверка выполнена и значимых сигналов нет.**
6. **Только `NORMAL` может дать `ELIG_SAFETY_CLEARED`.**
7. **`CAUTION` не означает автоматическое разрешение записи.**
8. **Safety-состояние не сбрасывается только потому, что следующая реплика не повторяет опасный сигнал.**
9. **Нужны `rule_id`, `evidence_ref`, `policy_version`, время активации и правила resolution/expiry.**
10. **Простое упоминание лекарства не равно `STOP`; `STOP` относится к запросу подобрать, назначить или рекомендовать препарат.**

### Приоритет состояний

```
STOP > CLARIFY > CAUTION > NORMAL
```

Заменяет прежний зашитый порядок `ALLOW < CLARIFY < BLOCK < HANDOFF`, где выигрывал старший.

### Три строки, данные владельцем ранее (§72)

| факт | семантика | поведение |
|---|---|---|
| safety применима, проверили, опасного сигнала нет | `NORMAL` | разрешено, `ELIG_SAFETY_CLEARED` допустим |
| safety применима, но данных или результата недостаточно | `UNKNOWN` | fail-closed |
| safety не применима к capability/решению | `NOT_APPLICABLE` | обычное выполнение **без** `ELIG_SAFETY_CLEARED` |

**Override поверх третьей строки, дословно:**

> `requires_health_check` / safety-sensitive кандидат / активная safety-relevant персонализация → `NOT_APPLICABLE` недопустим → требуется `SafetyResult`; при его отсутствии `UNKNOWN` → fail-closed.

**Почему `NOT_APPLICABLE` не даёт `ELIG_SAFETY_CLEARED`** — формулировка владельца, воспроизводить целиком: это тот же класс ошибки, что `rating = 0.0`. **«Не измеряли» нельзя превращать в значение результата измерения.** `NORMAL` означает «проверили и чисто», `NOT_APPLICABLE` — «проверять было нечего».

## Что уже построено — не переделывать

`apps/orchestrator/safety/`: `pre_check.py`, `post_check.py`, `outbound.py`, `voice_check.py`, `gate.py`.

Движок **детерминированный, на регулярных выражениях, без модели** — он не галлюцинирует. `SafetyResult` несёт provenance: `matched_patterns`, `reason`.

Замер по коду 08.09:

```python
class SafetyVerdict(str, Enum):
    ALLOW = "allow"; CLARIFY = "clarify"; BLOCK = "block"; HANDOFF = "handoff"

_VERDICT_PRIORITY = [ALLOW, CLARIFY, BLOCK, HANDOFF]   # выигрывает старший
```

Кризисный путь построен целиком: `CRISIS_HOTLINE = "8-800-2000-122"`, `CRISIS_REPLY_TEXT`, `BLOCK_REPLY_TEXT`. Скрининг здоровья — `apps/skills/health_screening/`, golden-фикстуры: температура, онемение, отдача в шею, боль в спине.

### Три расхождения с каноном

| | канон | сегодня |
|---|---|---|
| состояния | `NORMAL / CLARIFY / CAUTION / STOP` | `ALLOW / CLARIFY / BLOCK / HANDOFF` |
| `CAUTION` | обязателен | **не существует вовсе** |
| происхождение правила | `rule_id`, `policy_version` | отсутствуют |

**`CAUTION` — не переименование.** Единственное состояние «можно продолжать, но с оговоркой». Сегодня система умеет только пропустить или остановить.

## Что окно обязано сдать

1. **Канонический документ** матрицы: сигнал → состояние → поведение → что говорит Ayla → можно ли записаться.
2. **Таблица соответствия** старых `ALLOW / CLARIFY / BLOCK / HANDOFF` новым четырём состояниям. Там, где соответствия нет (`CAUTION`), — назвать это прямо, а не подобрать ближайшее.
3. **Список затронутых consumers** — кто сегодня читает вердикт и что у каждого сломается.
4. **Тестовые сторожа** на каждый инвариант.
5. **`rule_id`, `evidence_ref`, `policy_version`, время активации, resolution/expiry** — форма и происхождение. Половина provenance уже есть: `SafetyResult.matched_patterns`.

**Сначала контракт, затем код.** Кода не трогать, пока документ не сдан.

## Persistence — самое трудное, и оно новое

Инвариант 8: **состояние не сбрасывается только потому, что следующая реплика не повторяет сигнал.**

Сегодня проверка идёт **на каждом входящем**, памяти между ходами нет вовсе. То есть человек упомянул красный флаг, через три реплики просит записать — и система об этом уже не помнит.

Отсюда обязательное: **правила resolution и expiry**. Состояние должно уметь закончиться — но по правилу, а не по забывчивости. Владелец назвал требование, но не назвал сроки: **если понадобится число, это вопрос владельцу, а не ваше решение**.

## Запреты

* **Не расширять медицинскую политику своими решениями** — прямое указание владельца. Всё, чего нет в инвариантах, выносится ему.
* **Не ослаблять первый сигнал.** «Пропуск — провал, ложное срабатывание — цена UX» записано автором движка и подтверждено владельцем 03.07. Уменьшать полноту ради точности — не право исполнителя.
* **Не выводить недостающее из кода.** `CAUTION` в коде нет; догадка о намерении владельца — выдумка, на ней уже обжигались (§66: решение владельца вывели из детали реализации).
* **Не брать реестр планировочных правил** — отдельное окно, отдельная передача (`HANDOFF_PLANNING_RULES_REGISTRY.md`).
* **DRF-1528** (`HUMAN_LOCKED`) в работу не брать.
* `apps/orchestrator/safety/**` в реестре путей за окнами не числится — **объявить пакет главному окну до первого коммита**.

## Правила, стоившие нам трёх суток

* **Сторож по дереву, а не по тексту** (§74): текстовый ловит собственную документацию и **глушит детектор протухших исключений** — тот молчит ровно тогда, когда должен заговорить.
* **Лучше убрать путь, чем запретить конструкцию** (§72): владелец запретил `payload.get("safety") or NOT_APPLICABLE`, окно убрало поле из схемы. Отличить запрещённую от правильной на глаз нельзя.
* **Зелёный CI доказывает отсутствие обнаруженной регрессии, а не исправление.** Нужен targeted proof: краснеет до, зеленеет после.
* **`pytest` врёт кодом выхода** — верить только строке `N passed / M failed`.
* **Настоящий `ci` = 274201556, `replay` = 274201559**; двойники `279530142` / `279530140` носят те же имена. Различать **только** по `workflowDatabaseId`; `gh pr checks` показывает их как «fail» — это не поломка.
* **Не доверять именам функций и комментариям** — за трое суток двенадцать раз комментарий говорил одно, а код делал другое.
* **Замер конфигурации ≠ замер контура.**
* **Работать только в своём worktree.** Общий чекаут читать можно, писать нельзя.
* **Не мержить.** PR открыть, зелень дождаться, отчитаться главному окну: merge = выкладка на боевой пилот, решение владельца.
* **Убрать за собой** worktree, ветки, временные файлы — и перечислить снятое.

## Первый шаг

**Сверка, а не документ.** Бриф, действующие контракты и реализация — три источника; назвать, где они расходятся. Противоречия и недостающие продуктовые решения — владельцу **до** изменения поведения, а не после.
