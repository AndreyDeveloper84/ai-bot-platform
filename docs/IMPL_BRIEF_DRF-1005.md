## §1. Цель и решение владельца

Воронка записи проходит весь путь до выбора времени, а на тапе по слоту уходит в handoff: пользователь видит «Не получилось оформить запись — переключаю на менеджера». Автоматическая бронь на пилоте **невозможна в принципе**.

**Решение владельца (2026-08-12, зафиксировано): вариант 3 — тенант-скоуп переключатель health-check gate для пилота, с аудитом.** Канонический вариант (дотянуть разрешённый источник `resolved_requires_health_check` по паре мастер×услуга) остаётся плановой работой и **в этот объём НЕ входит**.

## §3. Что требуется сделать

Одна ветка, один PR в `dev`, осмысленные коммиты.

### 3.1 Переключатель (основное)

1. Ввести **настройку-allowlist тенантов**, для которых health-check gate выключен. Имя на твоё усмотрение, например `BOOKING_HEALTH_CHECK_GATE_DISABLED_TENANTS`, читается из env, по умолчанию **пусто** (то есть поведение по умолчанию не меняется — гейт закрыт).
2. Образец паттерна для парсинга и fail-safe поведения возьми с `EVENT_INGEST_ALLOWED_TENANTS` в `config/settings/base.py:1303-1315` — там список тенантов парсится из env, а при невалидной конфигурации процесс **отказывается стартовать**. Такая же строгость нужна и здесь: кривой список — ошибка загрузки, а не молча пустой allowlist.
3. В `_service_requires_health_check` (`skill.py:995-1017`) на ветке `_booking_via_ayla()`: если текущий тенант в allowlist — вернуть `False`, иначе сохранить нынешнее `True`. Идентификатор тенанта бери из активного `tenant_scope` тем же способом, что уже применён в DRF-997/1004.
4. **Аудит обязателен.** Каждое срабатывание «гейт выключен для тенанта» должно оставлять след: как минимум `logger.info` с тенантом и услугой, а лучше — запись через существующий `write_audit` (см. `apps/handoff/services.py`, там же образец вызова). Это требование владельца: решение отключить медицинскую проверку должно быть прослеживаемым, а не невидимым.
5. Докстринг `_service_requires_health_check` перепиши честно: что fail-closed остаётся дефолтом, что allowlist — временная мера Controlled Pilot под решением владельца, и что канонический путь — `resolved_requires_health_check` по паре мастер×услуга.

### 3.2 Наблюдаемость (обязательно, мелочь с большой отдачей)

6. Ветка health-check-handoff (`skill.py:1286-1293`) сейчас уходит в handoff **без единой лог-строки** — именно поэтому диагностика заняла у меня полчаса. Добавь `logger.info("booking.pick_slot.health_check_required master=%s service=%s", …)` перед возвратом. Аналогично проверь другие «немые» `_handoff(...)` в этом файле и добавь лог там, где его нет.

### 3.3 Текст пользователю (обязательно)

7. `_FALLBACK_HANDOFF_TEXT` («Не получилось оформить запись — переключаю на менеджера, он подскажет») для этой ветки **вводит в заблуждение**: это не сбой, а политика. Введи отдельный текст для health-check-ветки в духе «Для этой услуги нужна консультация — передаю менеджеру, он поможет с записью». Текст сбоя оставь сбоям. Не трогай `SCHEDULE_UNAVAILABLE_TEXT` (DRF-997) — он про другое.

### Критерии приёмки

- Тест: тенант **в** allowlist → `_service_requires_health_check` возвращает `False`, `pick_slot` доходит до карточки подтверждения, AdminTask **не создаётся**.
- Тест: тенант **не в** allowlist → поведение прежнее (`True`, handoff) — защита от регресса дефолта.
- Тест: пустая/невалидная настройка → дефолт закрыт (и невалидная конфигурация не даёт молча пустой allowlist).
- Тест: в health-check-ветке пользователю уходит новый текст, а не текст сбоя.
- Флаг-OFF путь (YClients) не затронут — существующие тесты зелёные.
