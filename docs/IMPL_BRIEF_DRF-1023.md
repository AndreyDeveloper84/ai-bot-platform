## §1. Цель

Сделать так, чтобы задачу оператора можно было закрыть через веб-интерфейс, а не из консоли сервера. Сегодня это невозможно: вход в админку не работает, и учётных записей не существует.

## §3. Объём и решение по доступу

**Рекомендуемый объём (если не видишь причин иначе — делай так):**

Пилот обслуживаем **мы**, а не сотрудники салона. Значит:

1. Чиним вход (CSRF + сопутствующие настройки безопасности).
2. Заводим учётную запись для **внутренней** команды, а не для салона.
3. Кросс-тенантный доступ **не трогаем** — но фиксируем документально, что админка кросс-тенантная и потому непригодна для выдачи наружу; тенантно-ограниченный доступ выносим в follow-up (связано с DRF-1022 — операторский эндпоинт).

**Почему не делать тенантную изоляцию прямо сейчас:** это правка десятка admin-классов, каждый из которых сознательно ходит кросс-тенантно, плюс модель ролей, которой в проекте нет. Для пилота на одном салоне это лишний риск. Если по ходу увидишь дешёвый и надёжный способ ограничить хотя бы `AdminTaskAdmin` тенантом пользователя — предложи в REPORT, но **в объём не бери без моего ответа**.

**Если считаешь, что рекомендуемый объём неверен — это эскалация**: опиши в REPORT и жди REPLY.

## §4. Что требуется сделать

1. **Настройки безопасности — отдельным осмысленным блоком.** Добавь в `config/settings/base.py` (или `staging.py`, реши сам и обоснуй) блок с директивами, читаемыми из env:
   - `CSRF_TRUSTED_ORIGINS` — список источников; для пилота `https://api-dev.gobeauty.site`. Пустой по умолчанию, парсинг строгий (кривое значение — отказ старта, по образцу `BOOKING_HEALTH_CHECK_GATE_DISABLED_TENANTS` из DRF-1005).
   - `SECURE_PROXY_SSL_HEADER` — чтобы Django знал, что снаружи HTTPS (сейчас он этого не знает, отсюда и часть проблем).
   - `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` — включить там, где контур за HTTPS; по умолчанию поведение не менять, управлять через env.
   - `SECURE_SSL_REDIRECT` — оценить: контур за прокси, включение может дать цикл редиректов. Реши и обоснуй; если не включаешь — напиши почему.
   - `ALLOWED_HOSTS = ['*']` — оцени, оставлять ли на контуре, доступном из интернета. Менять только если уверен, что не сломаешь вебхуки MAX и внутренние health-чеки; иначе — кандидат в Linear с обоснованием.
2. **Учётная запись.** Не хардкодь пароли и не клади их в репозиторий, отчёт или логи. Правильный путь — management-команда или documented-процедура, создающая суперпользователя из переменных окружения, чтобы владелец задал пароль сам при деплое. Если в проекте уже есть подходящий механизм — используй его, не изобретай.
3. **Предупреждение в интерфейсе.** В `AdminTaskAdmin` (и, если дёшево, в `ConversationAdmin`/`MessageAdmin`) добавь заметное предупреждение о кросс-тенантности — например через `Meta`-описание, `help_text` или баннер на странице списка. Смысл: следующий человек, выдающий доступ, должен увидеть, что раздаёт данные всех салонов, а не только своего.
4. **Документация процедуры.** Короткий раздел в подходящем месте репозитория: как создать учётку, какие переменные окружения нужны, что админка кросс-тенантная и кому её нельзя выдавать. Без этого следующая настройка контура повторит ту же историю.

### Критерии приёмки

- Тест на парсинг `CSRF_TRUSTED_ORIGINS`: валидное значение, пустое, кривое (отказ старта) — по образцу тестов настроек из DRF-1005/1007.
- Тест или явная проверка, что при выставленных настройках форма входа отдаёт 200, а не 403. Если это невозможно покрыть тестом — опиши процедуру ручной проверки для фазы C.
- Существующие тесты админки (`apps/handoff/tests/test_admin.py`, 8 тестов из DRF-980) — зелёные.
- Ничего из логики закрытия задач (DRF-980) не сломано.
