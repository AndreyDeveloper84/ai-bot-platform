## §1. DRF-1033 — одна бронь показывается дважды

**Симптом (живая приёмка владельца 13.08).** На вопрос «когда я записан» бот вывел одну бронь двумя одинаковыми секциями:

```
Ваши предстоящие записи:

Формула тела:
• УЗ-кавитация — 1 зона с Тихонова Ольга в 2026-08-14T10:00:00+00:00

Формула тела:
• УЗ-кавитация — 1 зона с Тихонова Ольга в 2026-08-14T10:00:00+00:00
```

**Первопричина (VERIFIED, замер в контейнере worker на пилоте).** В `_booking_lookup_scopes` (`apps/orchestrator/handoff.py`) стоит `.values_list("tenant_id", "bot_user_id").distinct()`. У модели `BookingRequest` задана сортировка по умолчанию (`apps/booking/models.py:421-424`, `ordering = ["-created_at"]`), и Django при DISTINCT добавляет поле сортировки в выборку:

```sql
SELECT DISTINCT tenant_id, bot_user_id, created_at FROM booking_bookingrequest ...
```

Две CONFIRMED-брони одного пользователя в одном тенанте с разным `created_at` дают две «разные» пары. Замер на пилоте: текущий запрос → **2**, он же с `.order_by()` → **1**.

**Фикс:** сбросить сортировку перед `.distinct()`. Одна строка.

**Побочный эффект, который уходит вместе с фиксом:** из-за лишней пары ответ уходил в мультисалонную ветку. При одном салоне должен работать однотенантный формат (byte-parity с тенантным путём — это заложено в `route_global_booking_lookup`, ветка `if len(scopes) == 1`).

**Тест (красный до фикса, обязателен):** две CONFIRMED-брони одного пользователя в одном тенанте → ровно **одна** секция, и ответ идёт по однотенантной ветке.

**Не переписывай** `_booking_lookup_scopes`, `_lookup_in_tenant`, `_compose_multi_tenant_text` и детектор `apps/skills/booking/lookup.py` — они продуманы и покрыты 14 тестами.

## §2. DRF-972 — «менеджер» не запускает эскалацию

**Симптом (та же приёмка, VERIFIED по `conversations_message` и логам).**

```
user      позови менеджера
assistant Я помогаю с записями к beauty-мастерам. Чем могу помочь?
user      оператор
assistant Передаю менеджеру — ответят в течение 30 минут.
```

По слову «менеджер» задача не создалась вообще — в логах worker'а нет `handoff.created` для этого сообщения.

**Первопричина (VERIFIED по коду).** `apps/skills/human_handoff/skill.py:34-42`:

```python
_HANDOFF_KEYWORDS: tuple[str, ...] = (
    "оператор",
    "связь с человеком",
    "поддержка живой",
    "живая поддержка",
    "human",
    "agent",
    "manager",
)
```

Русского «менеджер» нет. Латинское `manager` подстрокой в «менеджера» не попадает. То есть у русскоязычного пользователя рабочих формулировок ровно одна — «оператор» — плюс две неестественные («поддержка живой», «живая поддержка»).

**Почему это хуже, чем кажется.** Строкой ниже, `:44`:

```python
_HANDOFF_REPLY = "Передаю менеджеру — ответят в течение 30 минут."
```

Бот сам обучает пользователя слову, которое не работает. Человек, которому один раз ответили «передаю менеджеру», в следующий раз напишет «позови менеджера» и не получит ничего.

**Что сделать.** Дополнить список естественными русскими формулировками. Мой минимум: «менеджер», «администратор», «админ», «человек» — но **подумай сам** и обоснуй итоговый набор в REPORT. Требования к набору:

- Работает подстрочный поиск по нижнему регистру, поэтому «менеджер» покроет и «менеджера», и «менеджеру».
- **Проверь на ложные срабатывания.** Слово «человек» опасно: «я человек занятой», «нужен мастер, который понимает человека». Если считаешь, что риск выше пользы — не добавляй и объясни. Лучше не добавить сомнительное слово, чем ловить эскалации на ровном месте: каждая ложная эскалация глушит диалог и создаёт задачу оператору.
- Учти, что этот же список импортируется глобальным путём (`apps/orchestrator/handoff.py`, `matches_human_handoff_request` — DRF-1015), то есть изменение действует и там. Это правильно, но проверь, что импорт именно общий, а не копия.

**Тесты:** «позови менеджера», «нужен администратор» и прочие добавленные формулировки → эскалация срабатывает (**красные до фикса**); и негативные — фразы, которые не должны попадать в ветку. Существующие тесты `apps/skills/human_handoff/tests/test_skill.py` и `apps/channels/tests/test_global_human_handoff.py` должны остаться зелёными.
