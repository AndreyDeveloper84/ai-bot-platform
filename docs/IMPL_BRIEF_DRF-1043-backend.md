## §1. Что уже доказано — не перепроверяй с нуля

Расследование DRF-1035 закончено, отчёт — `docs/REPORT_DRF-1035.md`. Читать его целиком не обязательно; ниже выжимка того, что относится к тебе. Каждый факт проверен и мной, и окном-архитектором.

**Корневая причина.** В продакшене нет ни одного места, заполняющего `BotUser.ayla_user_id` на стороне бота. Механизм записи есть, но обработчики каналов зовут резолвер без этого аргумента. Единственный работающий аккаунт пилота — результат ручной правки в июле.

**Идентичность глобальна, не тенант-скоупная** (это проверялось отдельно по требованию владельца). Решающий аргумент: внешний идентификатор `bot:max:<id>` не содержит тенанта, а `username` глобально уникален — значит два разных субъекта для одного человека невозможны by construction. Дополнительно: `TenantUserRelationship` (`users/models.py:659-666`) прямо декларирует клиента как мультипровайдерного, «главного тенанта» у клиента нет.

**Резолвер идемпотентен на уровне БД.** `resolve_external_user` (`users/services.py:75-120`) — `get_or_create(username=external_user_id, …)`; в `pg_constraint` есть UNIQUE `users_user_username_key`. Гонка разрешается ретраем внутри `get_or_create`, дублей быть не может.

**Permission-класс уже делает всю работу.** `IsBotServiceWithVerifiedClient` (`users/permissions.py:173-207`): constant-time Bearer → `X-External-User-ID` → `resolve_external_user` → **подмена `request.user`**. Твоей вьюхе резолвить нечего: `request.user` уже канонический субъект.

**Прокси-клиент не порождает ПДн:** телефон, email, имя и фамилия не заполняются; создаётся пустая строка профиля.

## §2. Цель и контракт

Дать боту способ узнать канонический идентификатор Ayla **уже аутентифицированного и резолвнутого** внешнего субъекта. Не строить provisioning-сервис — только открыть существующий результат резолва доверенному вызывающему.

**Контракт, зафиксированный бот-стороной:**

```
GET /api/v1/internal/me/identity/

Auth:     IsBotServiceWithVerifiedClient (Bearer + X-External-User-ID)
Request:  тела нет
200:      {"ayla_user_id": "<uuid>", "is_proxy": <bool>}
```

**Обоснование формы** (проверено окном-архитектором по корневому urlconf `djangoProject/urls.py:28-39`): `api/v1/internal/me/` используется как **префикс пространства имён**, а не как ресурс — под ним смонтированы `me/bookings/` и `me/catalog/recommendations/`. Повесить ресурс на голый корень пространства значит смешать две роли. Форма `me/<resource>/` повторяет уже принятую `me/bookings/`.

**Ты обязан подтвердить эту форму по conventions репозитория** (§6 решения владельца: путь 1–7). Если существующая архитектура требует другого имени — **эскалируй в REPORT и жди ответа**, не меняй молча: бот-сторона уже вписала этот маршрут в свой контрактный тест, и расхождение сломает обе стороны.

**Почему GET /me, а не POST /resolve.** Если backend уже знает субъект из проверенного контекста аутентификации, вызывающий не должен иметь возможности назвать другого. Эндпоинт отвечает на вопрос «какой субъект Ayla соответствует **мне**», а не «дай субъект для произвольного идентификатора, который я назову». Это сокращает поверхность подстановки субъекта.

**Ответ минимальный.** Не возвращай телефон, email, профиль, данные тенанта, состояние согласий, персональный контекст, историю записей — ничего сверх двух полей. Перед добавлением любого поля отвечай себе: нужно ли это боту для DRF-1035. Если нет — не добавляй. Это identity-эндпоинт, а не профиль клиента.

## §5. Preflight — обязателен до кода

Короткий preflight в REPORT, четырьмя разделами. Только после него — реализация.

**A. Репозиторий и граница деплоя.** Репозиторий, ветка, база, текущий HEAD, механизм деплоя, целевая площадка, механизм отката.

**B. Проверенный путь кода.** Конкретные якоря: класс аутентификации; резолвер; место извлечения внешнего субъекта; модель прокси; где живёт маршрутизация URL; ближайший аналогичный внутренний эндпоинт, по образцу которого будешь делать.

**C. Контракт.** Метод, путь, аутентификация, запрос, ответ, ошибки — в финальном виде, который реально реализуешь.

**D. Объём.** Подтверди явно: миграций нет; booking не переписывается; DRF-1036 не чинится; перенос истории не делается.

## §6. Обязательные тесты

**Аутентификация:** без Bearer — отказ; неверный Bearer — отказ; без внешнего субъекта — отказ или явная контрактная ошибка; валидный вызывающий с валидным субъектом — успех.

**Разрешение идентичности:** существующий прокси — возвращается тот же идентификатор; первый валидный субъект — прокси создаётся; повторный GET — тот же идентификатор; `is_proxy` соответствует модели.

**Изоляция:** вызывающий A не может запросить B через параметры запроса; у эндпоинта нет произвольного селектора субъекта.

**Совместимость с контрактом записи** (интеграционным доказательством, не обязательно созданием реальной записи в тестах эндпоинта): резолвнутый субъект A → возвращён `ayla_user_id` A → `client_id` A в теле создания записи → существующий cross-check принимает. И негативно: `client_id` B → отвергается.

**Регресс:** поведение существующих внутренних API не изменилось; тесты резолвера зелёные; тесты booking зелёные.

## §8. Границы

Не входит: изменение booking-логики; удаление или ослабление cross-check `client_id`; новая подсистема идентичности; новая подсистема аутентификации; телефон; OTP; полноценная регистрация; слияние прокси с настоящим аккаунтом; перенос истории; Ayla-mediated communication; массовый рефакторинг резолвера; рефакторинг консьюмеров; изменения по consent; фикс DRF-1036 в этом же PR.

**DRF-1036 — отдельный блокер продакшена, не пилота.** Твой эндпоинт не создаёт первопричину, но удешевляет эксплуатацию: он сопоставляет перечислимый внешний идентификатор с UUID, а четыре существующие поверхности авторизуются только Bearer'ом по UUID. Чинить это здесь **нельзя** — другая поверхность, другой радиус поражения, другой набор тестов. Но и делать вид, что вопроса нет, тоже нельзя: зафиксируй в отчёте, что риск известен и вынесен.

Если обнаружишь реальный блокер, без которого эндпоинт нельзя реализовать безопасно, — остановись и эскалируй отдельно. Объём молча не расширять.
