## §2. DRF-980 — закрытие задачи должно возвращать бота

### Первопричина (VERIFIED)

| Что | Якорь | Факт |
|---|---|---|
| Кто глушит | `apps/skills/registry.py:105-107` | `if context.conversation.state == Conversation.State.HUMAN_HANDOFF:` → скилл не выполняется, `should_send=False` |
| Кто снимает | `apps/handoff/services.py:239-274` | `resolve_admin_task()` — единственное место, где `Conversation.state` возвращается в `IDLE`; делает это **вместе** со статусом задачи, в одной транзакции |
| Почему не срабатывает | `apps/handoff/admin.py:77-84` | `AdminTaskAdmin.save_model` штампует `resolved_at`, но **сервис не вызывает** и `Conversation.state` не трогает. Прод-вызовов `resolve_admin_task` нет ни одного |
| Подтверждено на живом пилоте | 2026-08-12 | Прямая правка статуса задачи через ORM оставила диалог в `human_handoff`; бот молчал, пока главное окно не вызвало `resolve_admin_task` штатно |
| Подводный камень | `services.py:256-258` | Сервис требует тенанта в скоупе (`current_tenant()`), а админка ходит кросс-тенантно (`AdminTask.all_tenants`, `admin.py:72-75`). Наивный вызов из `save_model` упадёт |

### Что сделать

1. **`AdminTaskAdmin.save_model` должен закрывать задачу штатным сервисом.** При переводе оператором в `RESOLVED` — вызывать `resolve_admin_task` внутри `tenant_scope(obj.tenant)` (тенант берётся из самой задачи, а не из контекста запроса — админка кросс-тенантная). Дублирование логики штампов недопустимо: сервис уже умеет и статус, и `resolved_at`, и возврат диалога в `IDLE`, и аудит.
2. **Идемпотентность.** Сервис — no-op на уже закрытой задаче (`services.py:253-254`). Учти это: если оператор сохраняет задачу, которая уже `RESOLVED`, диалог **не должен** остаться немым из-за раннего выхода. Реши явно: либо возвращать состояние диалога отдельной проверкой, либо расширить сервис. Решение обоснуй в REPORT — это ровно та ловушка, в которую я попал вручную.
3. **`CANCELLED` тоже должен возвращать бота.** Сейчас в `save_model` отмена оставляет `resolved_at` пустым — семантика «работа не выполнена». Но диалог всё равно обязан вернуться в `IDLE`: оператор закрыл вопрос, бот должен снова отвечать. Проверь и покрой тестом.
4. **Массовые действия.** Если в админке есть bulk-операции над статусом (или их легко добавить) — убедись, что они идут тем же путём, а не голым `queryset.update()`, который обходит `save_model`. Если bulk-пути нет — зафиксируй это в REPORT.
5. **Диагностика.** Лог при возврате диалога: кто, какую задачу, какой диалог.

**Вариант «операторский эндпоинт» (из описания задачи) в этот объём НЕ входит** — он про будущий операторский интерфейс. Сейчас нужен рабочий путь через админку.

### Критерии приёмки

- Тест: задача в `RESOLVED` через `AdminTaskAdmin.save_model` → `Conversation.state == IDLE`, бот отвечает (красный до фикса).
- Тест: то же для `CANCELLED`.
- Тест: повторное сохранение уже закрытой задачи не оставляет диалог немым.
- Тест: кросс-тенантность — задача чужого тенанта закрывается корректно, без утечки скоупа.

## §3. DRF-1007 — пилот без предоплаты

### Первопричина (VERIFIED)

| Что | Якорь | Факт |
|---|---|---|
| Backend умеет обе схемы | `appointments/application/services/create_booking_service.py:362-368` (репо backend) | `initial_status = CONFIRMED if dto.confirm_immediately else AWAITING_PAYMENT`; путь без предоплаты не создаёт Payment-строку (AMD-002 / D6) |
| Клиент бота умеет передать | `apps/integrations/ayla/booking_client.py:802-822` | `create_appointment(..., payment_required: bool = True)` → уходит в тело запроса |
| Адаптер умеет | `apps/skills/booking/provider.py:170-183` | `create_record(..., payment_required: bool = True)` |
| **Место дефекта** | `apps/skills/booking/tools.py:1087` | `payment_required=bool(payload.get("payment_required", True))` — в боте **никто не кладёт** это поле в payload, поэтому всегда уходит `True` |
| Для сравнения | `apps/miniapp_api/views.py:840` | MiniApp уже по умолчанию шлёт `payment_required=False` |
| Последствие | backend `notifications/tasks.py:87-95` | Напоминания рассылаются только по `CONFIRMED`; `awaiting_payment` клиенту не напоминают |
| Подтверждено на живом пилоте | 2026-08-12 | `Appointment 0d3f41d1-…` создан со `status=awaiting_payment`; в БД один Payment со `status=pending` и пустым `provider_payment_id` — до провайдера дело не доходит |

### Что сделать

1. **Признак предоплаты — настройкой, не хардкодом.** Решение владельца от 2026-08-12: Controlled Pilot идёт **без оплаты**. Но модель оплаты будет меняться, поэтому нужен переключатель, который снимается так же легко, как ставится. Сделай по образцу DRF-1005: тенант-скоуп allowlist в `config/settings/base.py` (например `BOOKING_NO_PREPAYMENT_TENANTS`), читается из env, **по умолчанию пусто → поведение не меняется** (`payment_required=True`, как сейчас). Строгий парсер и отказ стартовать при кривом значении — переиспользуй тот же механизм, что уже применён для `BOOKING_HEALTH_CHECK_GATE_DISABLED_TENANTS`.
2. Прокинуть значение в `tools.py:1087`: если текущий тенант в allowlist — `payment_required=False`. Явный `payment_required` в payload (если он там когда-нибудь появится) должен иметь приоритет над настройкой — это осознанный выбор пользователя/вызывающего, а не дефолт.
3. Проверь **все** места создания брони в боте, не только confirm: путь переноса записи (`tools.py:2155` — `create_record` без `payment_required`) тоже создаст `awaiting_payment`. Реши, как он должен вести себя, и обоснуй в REPORT.
4. Лог при срабатывании настройки — тенант и итоговое значение признака.

### Критерии приёмки

- Тест: тенант в allowlist → в тело запроса уходит `payment_required=False` (красный до фикса).
- Тест: тенант вне allowlist → `True`, поведение прежнее.
- Тест: пустая/невалидная настройка → дефолт `True`; невалидная не даёт молча пустой allowlist.
- Тест: явный `payment_required` в payload перекрывает настройку.
