- **Второй LLM-вызов intent_resolution** — чисто наш и **ненужный**: флаг `INTENT_RESOLUTION_FROM_TOOL_CHOICE_ENABLED` по умолчанию OFF, на пилоте не включён; детерминированный путь из tool_choice существует (`apps/orchestrator/intent_resolution.py:900-937`). Цена — 4–18 с на консьерж-ход (с ретраями Anthropic).
- **Ретраи Anthropic** (`APIConnectionError`, почти каждый консьерж-ход): +1 с сна + повторное подключение. Внешняя сеть/провайдер, но политика «2 попытки» наша.
- **7–9 синхронных `emit()` + 2 сохранения сообщения + 2 резолва identity за ход** — каждый отдельным коммитом (`apps/events/services.py:126`). На здоровом диске копейки; на этом диске (w_await 3.5 с) каждый коммит — лотерея: проба «INSERT+ROLLBACK» в PG бэкенда поймала **1106 мс** на одном коммите из пяти при медиане 0.3 мс. Многосекундные провалы «сохранение ответа 4–5 с» — это они. Код наш, цена — железо.
- «13 секунд приём → консьерж» из брифа подтверждается: даже в быстром ходе 11 до оркестратора сообщение дошло за 9.9 с (2.8 очередь + 6.8 typing + 0.4 прочее).

## 2. Что лежит в 5706 токенах запроса

**Способ.** В контейнере воркера через `manage.py shell` собраны те же компоненты, что кладёт `_compose_messages`, для боевого разговора `e8312259` (тот самый ход 5706/51). Скрипт `measure_prompt.py`, `measure_memory_blocks.py`.

| Компонент | chars | токенов (оценка, 2.4 chars/ток) | доля |

| Системный промпт (статика: персона, правила, boundary) | 3975 | ~1650 | 29 % |
| **Описания 10 инструментов** | 7731 | **~3200** | **56 %** |
| История, 10 сообщений | 1771 | ~740 | 13 % |
| Персональный контекст клиента | 202 | ~85 | 1.5 % |
| Блок памяти (declared prefs) | 0 | 0 | 0 % |
| **Итого** | **13 679** | **~5700** ✓ сходится с 5706 провайдера |

Каталога в запросе **нет** — он приезжает только результатами инструментов.

**tiktoken не установлен** (проверено в контейнере: `ModuleNotFoundError`; в `uv.lock` его нет). Бюджет истории 4000 «токенов» считается как `len//4` (ayla-ai-core `orchestrator.py:151-161`). Замеренный курс на этом разговоре — **2.4 chars/токен** (кириллица): эвристика занижает на ~40 %. Сейчас история короткая (1771 chars), переполнения нет; но при длинной переписке «4000 токенов» превратится в ~6600 реальных.

**Что можно не класть:**
- 4 нутриционных инструмента (health_screening, log_water, clarify_food_entry, start_nutrition_anketa — 1644 chars ≈ 680 ток., 12 %) не нужны в beauty-контексте; ещё ~2 KB — избыточные описания остальных шести. Инструменты — самая жирная и самая «отрезаемая» часть.
- Второй вызов (intent_resolution, вопрос 1) вообще не должен существовать — это ещё ~2 тыс. токенов на ход.

## 3. Сколько обращений на один показ расписания

**Способ.** Подсчёт GET в журнале воркера (4 показа) + замер бэкенда в процессе (`measure_backend.py`, 14 дат подряд через Django test Client с боевым bearer'ом).

- Бот просит **14 дат × 1 специалист = 14 GET**, строго последовательно (`apps/integrations/ayla/booking_client.py:924-965`, окно `AVAILABLE_DATES_WINDOW_DAYS=14`). Мультиспециалистного веера нет: слоты тянутся только для выбранного мастера.
- Каждый GET на бэкенде: **15 SQL-запросов**, 55–140 мс в процессе (тёплый), сумма SQL-времени 61 мс. По сети ~130 мс шаг.
- Итого один показ: **14 HTTP × 15 SQL = 210 запросов к базе, ~1.9 с** (до 10.7 с при 429-ретраях).
- Плюс каталог перед этим: 3 страницы × 6 запросов, ~0.4 с.
- 429 живы: 2 показа из 4 в журнале уперлись в квоту (`booking_client.429`, `schedule_unavailable`).

**Один запрос диапазона:** фетч специалиста и резолв услуги делаются один раз, записи за 14 дней забираются одним range-фильтром → **1 HTTP, ~10–15 SQL, ~0.1–0.2 с**. Экономия ~1.7 с на показ и 14/30 минутной квоты → 1/30 (429 исчезают как класс).

**Рядом та же болезнь у мини-приложения:** журнал `dev-web-1` показывает `/api/v1/tenants/me/day/?date=…` по одной дате, 20+ подряд по ~120 мс — клиентский календарь ходит так же.

## 4. Внутренние пути без своей квоты

**Способ.** Инвентаризация роутов в коде (origin/dev) + сверка с живым `REST_FRAMEWORK` из контейнера `dev-web-1` — совпало.

**Все ~30 путей под `/api/v1/internal/` — БЕЗ своей квоты.** `IsInternalBearer` оставляет `request.user` анонимным → все внутренние вызовы делят **одно per-IP ведро `anon: 30/min`** на весь бот-трафик.

| Путь | Квота | Зовёт ли бот пачками |
|---|---|---|
| `internal/specialists/<id>/slots/` | нет → anon 30/min | **да: 14 подряд за показ** (DRF-1446, не исправлено ни в коде, ни конфигом) |
| `internal/catalog/salon-services/`, `…/specialist-services/` | нет → anon | да: 3–6 страниц подряд |
| `internal/users/<id>/personal-context/` (+ask-eligibility, mark-asked, skip) | нет → anon | по 1–2 за ход |
| `internal/me/bookings/`, `internal/appointments/*` | нет → anon | потенциально (сценарии записи/отмены) |
| `internal/me/catalog/recommendations/`, `decision-context/`, `goals/select/`, `wellness-context/`, `identity/` | нет → anon | по ходу диалога |
| `internal/users/*` (bind-external, profile, cards, personal-data) | нет → anon | редко |
| `internal/services/*`, `internal/payments/<id>/`, `internal/billing/*` (кроме webhook) | нет → anon | редко |
| `internal/billing/webhook/` | **`webhook_payment` 100/min** | — |
| `/api/v1/payments/internal/<id>/retry/` (вне префикса) | `payment_internal` 60/min | — |
| `/api/v1/nutrition/internal/*` (вне префикса) | `food_scan_internal` 60/min | — |

Образец лечения рядом: `[ScopedRateThrottle]` + scope `*_internal: 60/min` (`payments/views.py:1046`, `nutrition/views.py:222`). Пока веер слотов (14) + страницы каталога (3–6) + personal-context за один ход съедают >20 из 30 минутных токенов ведра — любые два хода подряд гарантированно ловят 429.

## 5. Сколько запросов к базе на ход и на показ расписания

**Способ.** Бэкенд — прямой счёт `connection.queries` через `force_debug_cursor` в `manage.py shell` внутри `dev-web-1` (GET'ы, данные не менялись). Бот — счёт по журнальным событиям (каждый `emit` = 1 INSERT, каждое `message.stored` = INSERT + UPDATE) + карта кода; полный прогон обработчика не делали, т.к. он пишет в базу и зовёт LLM.

### Бэкенд: один вызов slots (холодный кэш, замерено, повторено на 14 датах)

**15 запросов**, повторы с кратностью:

| Запрос | × |
|---|---|
| `SpecialistProfile` (полный, с 4 prefetch'ами + 2 COUNT-аннотациями) | 3 (вьюсет, availability-сервис, values() для timezone) |
| `services_service` / `services_specialistservice` | 2 + 2 (резолвер + prefetch) |
| `appointments_specialistworkinghours` | 2 |
| `users_specialistportfolio` — **слотам не нужен вообще** | 1 |
| `salonservice`, `scheduleexception`, `appointment` (за день), `timeoff`, `tenantclosure` | по 1 |

На тёплом Redis-кэше (TTL 60 с) — всё равно **8 запросов**: фетч специалиста с фан-аутом и резолвер идут *до* проверки кэша. Склейка (один фетч без prefetch-фан-аута, резолвер после кэша): 15 → ~7 запросов, SQL-время 61 → ~15 мс; в связке с вопросом 3 — 210 → ~10 запросов на показ.

- catalog `salon-services`: 6 запросов/страница, 58 услуг на 3 страницах (page=20, `core/pagination.py:26`).
- `personal-context/`: 2 запроса, 13 мс.
- `ask-eligibility/`: замерено 1 запрос (short-circuit `first_interaction`); худший случай по коду — 9 (цикл из 8 кандидатов, каждый перечитывает контекст, `personalization_engine.py:116`).

### Бот: один ход (по журналу, n=10 ходов)

- `emit()` синхронный INSERT: **7–9 за ход**
- сообщения: 1–2 × (INSERT Message + UPDATE Conversation)
- identity: 2 резолва (SELECT + UPDATE last_seen), плюс sentinel-тенант перечитывается при каждом обращении (не кэшируется, `apps/identity/services/global_tenant.py:34`)
- идемпотентность: 1, история: 1 SELECT, ретрай-аудит LLM: 0–2 INSERT
- **Итого ~20–25 statements, из них 12–14 отдельных коммитов на ход.**

Сами запросы дешёвые (проба PG: SELECT 0.1–0.6 мс, коммит 0.2–0.7 мс), но каждый коммит — экспозиция на дисковые провалы (пойман единичный коммит 1106 мс). Склейка 7–9 emit'ов в одну транзакцию убрала бы ~10 таких экспозиций за ход — это и есть наблюдаемые провалы 3–7 с на «сохранить ответ» в неудачные минуты.

## Итог: наше vs железо, по величине выигрыша

**Железо/хостинг (не чинить кодом):** диск w_await 3.5 с с провалами под коммиты; внешняя сеть до botapi.max.ru (медиана ~2–4 с на POST, выбросы 22 с) и до api.anthropic.com (частые `APIConnectionError`). На «прогретых» 6.9 с из брифа железо отвечает за львиную долю разброса, но не за структуру.

**Наше, по убыванию выигрыша:**

1. **Второй LLM-вызов intent_resolution** — включить `INTENT_RESOLUTION_FROM_TOOL_CHOICE_ENABLED`: −4…−18 с на консьерж-ход, минус ~2 тыс. токенов. Одна переменная окружения (с пересозданием контейнера).
2. **Слоты диапазоном** (вопрос 3): −1.7 с и −195 SQL-запросов на показ, снимает 429 как класс. Свежая задача на эндпоинт диапазона.
3. **Квота на internal-чтение** (вопрос 4): scope `internal_read` ~120/min на ViewSet'ы slots/catalog — страховка до (2) и для остальных путей. Образец — `payments/views.py:1046`.
4. **Инструменты в промпте** (вопрос 2): −2…−3 KB на каждый LLM-проход (нутри-инструменты из beauty-контекста + сжатие описаний) → ~−1 с на вызове и меньше денег. Плюс поставить `tiktoken` (extra есть в библиотеке, не выбран) — иначе бюджет истории занижен на 40 %.
5. **Typing-POST'ы в фон/одним вызовом** и **пачка emit'ов в одной транзакции** — не ускорят на здоровом железе, но уберут многосекундные провалы на этом (вопросы 1, 5).
6. **Фетч специалиста 3× и prefetch-фан-аут в slots** (вопрос 5): 15 → ~7 запросов на вызов; само по себе мелочь (61 мс SQL), имеет смысл только вместе с (2).

**Не подтвердилось как узкое место:** N+1 в генерации слотов (чистый Python-цикл, пер-слотовых запросов нет), каталог (6 запросов/страница, ~35 мс), personal-context (2 запроса, 13 мс), ask-eligibility (1 запрос в боевом случае).
