# MEMORY_AUDIT — почему долговременная память бота почти пуста

Замер: 2026-08-30. Пилот: `taximeter@194.87.99.126`, проект `ayla-bot-staging`,
код на хосте — коммит `4005cc1`. Локальная копия репозитория на момент разбора —
`fb1aab5` (ветка `docs/ux-canon-reconciliation`); расхождение по ключевым
модулям проверялось через `inspect.getsource` внутри контейнера.

Всё, что делалось на пилоте, — только чтение: `count()`, `values_list`,
интроспекция кода, повторный прогон детерминированного экстрактора над уже
сохранёнными сообщениями. Ни одной записи, изменения или удаления.

---

## Вердикт одной строкой

**Путь записи работает и сработал по-настоящему — но условия для него почти не
наступали: у 7 из 8 пользователей глобального бота согласие отозвано или
отсутствует, а у единственного согласившегося экстрактор (5 ключей на
регулярках, не LLM) нашёл во всём его корпусе ровно один извлекаемый факт — тот
самый, который и лежит в базе.**

Это не «задумано так» и не «сломано». Это **третий вариант: механизм исправен,
но его входное условие — явное самоутверждение в узком наборе формулировок при
живом согласии — за 355 человеческих реплик выполнилось один раз.**

## 2. Пути записи

### 2.1 Единственный боевой писатель

```
apps/channels/max/handler.py:1426        record_explicit_green_facts(bot_user, event.text)
  внутри _handle_global_max_event_inner (handler.py:721) — ГЛОБАЛЬНЫЙ MAX-бот
  условие вызова: not was_memory_command
   |
apps/orchestrator/memory/personal_context.py:43   record_explicit_green_facts()
   |- гейт 1: apps/consent/memory.py:47          can_store_green_memory()
   |                                              -> has_global_consent(PERSONAL_DATA)
   |- гейт 2: apps/persona/memory_extract.py:418 extract_user_facts()
   |- гейт 3: apps/identity/services/ayla_link.py ensure_ayla_link()
   |- гейт 4: UPC не «забыт» (soft_deleted_at / forget_all_requested_at)
   |
apps/identity/services/memory_writer.py:123      write_entry() -> MemoryEntry.objects.create()
```

Порядок гейтов важен: **согласие проверяется первым**, до извлечения. Для семи
пользователей без живого согласия экстрактор не запускался вообще.

### 2.2 Второй писатель — заглушен намеренно

`apps/identity/services/memory_inferred.py:80` `record_inferred_green_facts()` —
путь для *выведенных* фактов. Его собственный докстринг (строки 3–9) фиксирует:

> «This writer has ZERO production callers (only tests exercise it) and is kept
> dormant … inference may become persistent memory ONLY through the proposal
> flow (MemoryProposal, Step 4+).»

Проверено грепом: вызовов вне тестов нет.

### 2.3 Где памяти нет вовсе

`apps/channels/max/salon_handler.py` и `apps/channels/telegram/` не содержат ни
записи, ни чтения `MemoryEntry`. Память живёт **только** на свободнотекстовом
ходе консьержа глобального MAX-бота.

### 2.4 Что физически умеет извлекать экстрактор

`apps/persona/memory_extract.py` — **детерминированные регулярки, не LLM**
(строка 4: «with plain patterns (NOT an LLM)»). Весь словарь:

| ключ | что ловит | обязательный якорь |
|---|---|---|
| `diet` | vegan / vegetarian / keto / halal / kosher + ретракции | «я …» вплотную к корню |
| `preferred_time_slots` | утро/день/вечер/«после шести» | «мне удобно», «я обычно могу», «предпочитаю» |
| `preferred_districts` | район как слово | «мне удобно в», «я предпочитаю» |
| `price_range` | «комфортно от…до…», «не готов платить больше…» | «комфортн» / «ориентиру» |
| `favorite_masters` | «мой мастер — Имя», «хожу только к Имя» | явная формула |

Имя человека, возраст, состав семьи, состояние кожи и волос — **не извлекаются
вообще**: таких ключей в контракте нет. Аллергии и непереносимости
**отбрасываются до извлечения** (`_ALLERGY_RE`, DRF-1290) — прямое исполнение
решения владельца от 25.08. Любой маркер сессии («сегодня», «сейчас», «завтра»,
«на этой неделе») **гасит извлечение на весь ход целиком**.

## 3. Пути чтения — читатель есть, и он сработал

### 3.1 Локальная зелёная память в системный промпт

```
apps/channels/max/handler.py:1187   render_current_personal_context(ayla_user_id)
   -> apps/persona/memory_surface.py:229
   -> apps/identity/services/memory_key_policy.py:143  read_current_view()
   -> apps/identity/services/memory_reader.py:97       read_green_entries()
```

Условие ровно одно: `ayla_user_id is not None`. Флага нет, согласия на этой
ветке не спрашивают (зелёная зона — договорное основание, ADR-0011 §11).

**Положительная стража (проверено на пилоте):** вызов
`render_current_personal_context()` для восьми пользователей глобального бота
вернул непустой блок (**202 символа**) ровно для того одного, у кого есть
запись, и пустую строку для остальных семи. Читатель не «не найден» — он вызван
и вернул содержимое.

### 3.2 Второй, параллельный блок — ai-core

`apps/channels/max/handler.py:1199` `build_concierge_memory_block(bot_user)`
(`apps/orchestrator/memory_block.py:110`) собирает блок из *декларированных*
предпочтений Ayla плюс локальных зелёных фактов. На пилоте он вернул **пустую
строку для всех восьмерых**, включая согласившегося. Разбор — §9.

### 3.3 Управление памятью

`apps/persona/memory_commands.py` («что ты обо мне знаешь», «забудь…») читает
через `read_green_entries`. В корпусе пилота **ноль** реплик, попадающих под
команды памяти, — эта ветка ни разу не запускалась.

### 3.4 Вопрос-о-памяти

`apps/orchestrator/memory_ask.py` (`maybe_weave_question` / `try_handle_answer`,
вызовы в `handler.py:1076, 1297`) пишет ответ **не в `MemoryEntry`**, а PATCH-ом
в декларированные предпочтения Ayla, и гейтится согласием `memory_green`
(живое — у одного пользователя). На счётчик `MemoryEntry` эта ветка не влияет
по устройству.

## 7. Положительная стража к отрицательному утверждению

Утверждение «извлечение почти никогда не срабатывает» подтверждено не
отсутствием находки, а **повторным прогоном того самого экстрактора того самого
коммита в том самом контейнере** над реальным корпусом:

| прогон | сообщений | реплик с ≥1 кандидатом | гистограмма ключей | явных дропов |
|---|---|---|---|---|
| все `role=user` | 357 | **1** | `{lifestyle/diet: 1}` | 0 |
| «допустимый» корпус (согласившийся пользователь, после выдачи согласия) | 91 | **1** | `{diet: 1}` | 0 |

не записал» **нет**: `drops = 0`, то есть ни одного случая, когда факт был
опознан и намеренно выброшен (аллергия, пищевое исключение), в корпусе не
встретилось.

## 8. `UserPersonalContext` — что это и как соотносится с `MemoryEntry`

Это **не** дубль и **не** «то же самое другими словами». Это родитель.

- `apps/identity/models.py:540` `UserPersonalContext` (UPC) — **одна строка на
  человека**, PK = канонический `ayla_user_id`. Держит `summary`, язык,
  предпочитаемое имя, `minor_lock` и оба флага «забудь всё».
- `apps/identity/models.py:627` `MemoryEntry` — **много строк на человека**,
  `FK personal_context -> UPC (CASCADE)`. Каждая строка — один зонированный факт.

Совпадение «1 и 1» — **не совпадение, а прямое следствие**: UPC создаётся
лениво, в момент первой записи, вызовом `get_or_create_personal_context()`
из `record_explicit_green_facts` (`personal_context.py:91`). Один факт — один
родитель. Метки времени подтверждают: UPC `13:42:38.447`, запись
`13:42:38.617`, тот же `user_id`, `upc.memory_entries.count() == 1`.
`summary` пуст (0 символов): боевого писателя `summary` в коде нет.

Отдельно, чтобы не путать: существует **третья** сущность с тем же именем —
`users.UserPersonalContext` на стороне Ayla (beautygo_backend). Это
*декларированные* предпочтения из мобильного приложения, они приходят по HTTP
через `get_declared_prefs()`. Коллизия имён зафиксирована в докстринге модели
(«NAME COLLISION NOTE (#1055) — NOT a duplicate»). На пилоте у согласившегося
пользователя эта, внешняя, сущность **тоже пуста**: Ayla отдаёт
`meta.filled_fields = 0`, все 12 полей контракта пустые (`diet_type = ""`,
списки `[]`).

## 9. Побочная находка — подтверждена на пилоте, кода не трогал

`apps/orchestrator/memory_block.py:242`:

```python
        elif key not in facts:
            facts[key] = value
```

Декларированная сторона кладёт в `facts` **все 12 ключей контракта, включая
пустые** (`memory_block.py:126-129` — фильтра на пустоту нет). Поэтому для
любого ключа из словаря контракта `key not in facts` всегда ложно, и локальный
зелёный факт **никогда не попадает в ai-core-блок**: пустое декларированное
значение затеняет живой локальный факт.

Проверено прямым прогоном на пилоте (`_merge_inferred` вызван вручную на живых
данных согласившегося пользователя):

```
host has 'elif key not in facts': True
facts BEFORE merge: n=12  'diet_type' in facts: True  repr(diet_type)= ''
facts AFTER  merge:                              repr(diet_type)= ''
keys added by merge: []
local green facts visible to merge: [('lifestyle', 'diet', 'explicit')]
```

Локальный факт **виден** мержу и всё равно не проходит. Сам сборщик исправен:
`build_memory_block({"diet_type": "vegan"})` в том же контейнере возвращает 82
символа, а `build_concierge_memory_block(bot_user)` — 0.

На исход этого замера это **не влияет**: факт всё равно доходит до промпта по
другой ветке — через `render_current_personal_context` (§3.1, 202 символа).
Речь о том, что вторая, параллельная поверхность памяти в промпте молчит, и
молчит она не из-за пустой памяти, а из-за порядка приоритета.

Правку не вносил — вопрос требует решения владельца/архитектора: «пустое
декларированное значение выигрывает у живого локального факта» может быть и
багом, и намеренным приоритетом Ayla как источника истины.

## 10. Чего этот метод не покрывает

1. **Логи недоступны.** Контейнеры пилота были пересозданы посторонним деплоем
   в 11:05 UTC 30.08 прямо во время замера; `docker compose logs` теперь
   начинается с этого момента (26 строк в `worker`, 75 в `web`). Поэтому
   счётчиков `orchestrator.memory.green_written`,
   `orchestrator.memory.extraction_drops`,
   `persona.memory_extract.allergy_clause_dropped` за историю пилота
   **предъявить нельзя**. Стража §7 построена на повторном прогоне по БД: по
   покрытию это сильнее логов, по доказательству «вызывалось в бою» — слабее.
   Прямое свидетельство боевого вызова одно: сама запись 23.08 (§6).
2. **Реплика ≠ то, что дошло до писателя.** Экстрактор прогонялся по всем
   сохранённым `Message.content`. Ходы, оборвавшиеся раньше строки
   `handler.py:1426` (ранний возврат по кнопке, ветка nutrition, исключение),
   в прогон попали, хотя в бою до писателя не доходили. Смещение — **в пользу**
   механизма («мог бы записать, но не дошёл»); на итог (1 кандидат) не влияет.
3. **Классификация тем — регулярки, а не смысл.** Ноль по классам «имя»,
   «здоровье», «бюджет» означает «ни одна из перечисленных формулировок не
   встретилась», а не «человек этого точно не сообщал иначе». Тексты я не читал
   — сознательно.
4. **Реальный человек или проверка разработчика.** По данным неразличимо (§6).
5. **Отозванные согласия DRF-1284 не разбирались.** Почему боевой welcome-флоу
   выдал живое согласие одному из восьми пользователей глобального бота —
   отдельный вопрос, за рамками этого замера. Это, а не память, — самый крупный
   числовой ограничитель: 266 из 357 реплик были недоступны писателю по
   согласию, а не по содержанию.
6. **Расхождение коммитов.** Локально `fb1aab5`, на пилоте `4005cc1`. Цитаты
   «файл:строка» даны по локальной копии; поведение, значения флагов и §9 сняты
   с пилота.

## Что из этого следует (без правок кода)

1. Пустая память — **не отказ механизма**. Запись и чтение проверены и работают.
2. Главный ограничитель — **не экстрактор, а согласие**: 266 из 357 реплик
   лежали вне контура согласия. Прежде чем расширять извлечение, стоит понять,
   почему боевой welcome выдал живой `personal_data` одному из восьми.
3. Второй ограничитель — **сознательно узкий экстрактор**: 5 ключей на
   регулярках, точность вместо полноты. Это записанное решение (докстринг
   `memory_extract.py`, ruling владельца 2026-08-23 «не фабриковать факты»), а
   не недоделка. Разговорное извлечение — post-pilot (M-C2, поток
   `MemoryProposal`).
4. **Третьего ограничителя — «люди рассказывали, а бот не услышал» — нет.**
   В корпусе нечего было запоминать.
5. Открытый вопрос владельцу — §9: пустое декларированное значение Ayla
   затеняет живой локальный факт во второй поверхности промпта.
