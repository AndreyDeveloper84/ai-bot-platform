## 1. Маркетплейсный первый экран действительно отсутствует

Агент правильно выяснил причину: wellness-чипы убрали **намеренно**, потому что пользователь находится на marketplace-path. Поэтому отсутствие «еда / вода / цель» — **не UI-баг сам по себе**.

Но после этого глобальный путь остался почти без собственного входного UX. **Это реальный gap.**

### Чего делать НЕ надо

Не создавать новый экран вида:

```
Цели | Города | Популярные услуги
```

как основную точку входа.

**Это противоречит уже более свежему CURRENT-контракту:**

- **DRF-1179** фиксирует **free text = primary**, а Quick Actions — только **необязательные ускорители**; отдельный mandatory Goal picker и фиксированная Goal taxonomy из Pilot **уже удалены**.
- **DRF-1272** строит journey как **free text → semantic resolution → clarification только при необходимости**, а не как обязательное меню.

### Как выглядит правильный marketplace welcome

```
Привет! Я Ayla.
Расскажи, чего тебе хочется или что хочешь изменить.

[ Написать Ayla...                         ]

Возможно, тебе проще начать отсюда:
[ Расслабиться ] [ Привести себя в порядок ]
[ Подготовиться к событию ] [ Не знаю, с чего начать ]

Уже знаешь, что нужно?
Найти услугу →
```

**Формулировки чипов здесь иллюстративные, не новая taxonomy.**

**Город** не спрашивать на первом экране без необходимости. Он появляется тогда, когда нужен для поиска исполнителя.

**«Популярные услуги»** — максимум secondary catalog shortcut. Иначе Ayla за первые пять секунд опять превращается в каталог.

### Владелец работы

**Новый эпик для marketplace first screen не заводить.** У этой работы уже есть правильный владелец — **DRF-1179 + DRF-1272**, а в **DRF-1319** отдельно закреплено, что `goal_select` не должен воскреснуть как обязательный Pilot-screen.

## 2. SPEC_CARE_CONTRACT — очень полезный документ, но это отдельный трек

Спецификация прочитана. Она действительно меняет картину существенно. **Важно помнить её собственный статус: рабочая спецификация; не канон, не PRD, не план работ.**

Она правильно разводит:

```
Desired Outcome → Personal/Care Plan → Observation → Progress → NBA
```

и очень хорошо выявляет, что часть понятий **уже существует в каноне**, а новая архитектура **не должна плодить параллельные сущности**.

### Шесть решений

| Вопрос | Решение владельца |
|---|---|
| **В-1** Consent для веса | Регистрировать **новый узкий consent scope** для persistent wellness observation. **Не переиспользовать `preference_memory`** и **не обходить запрет `health_related_signal`**. До amendment Registry + Privacy/Legal approval запись веса **BLOCKED**. |
| **В-2** Где хранить observation | В **Ayla backend**, в отдельном **wellness/obs bounded context**. Не в боте и не в `NutritionProfile.weight_kg`. **Nutrition остаётся потребителем.** |
| **В-3** Nutrition safety override vs Desired Outcome | Если Nutrition safety rules принудительно переводят расчёт в `maintain`, **weight-loss Personal Plan не открываем**. Новый слой **не должен обходить уже существующий safety invariant**. |
| **В-4** Goal | Развести **три понятия**: canonical **Transformation Goal** = semantic framing; **nutrition goal** = параметр расчёта; **service goal** = Execution Mapping. **Не заставлять пользователя выбирать Goal ради заполнения схемы.** |
| **В-5** Action ≠ outcome evidence | Провести как **отдельную нормативную норму в канон**, лучше **AYLA-DEC + amendment LDT §9**. Это должен быть **hard invariant**. |
| **В-6** Имя | На пользовательском и каноническом уровне оставить **Personal Plan**. **Care Plan** пока только рабочий alias спецификации. **`CareEpisode` категорически не использовать — имя уже занято другой сущностью.** |

Это хорошо согласуется с самой спецификацией: она прямо показывает, что вес сейчас хранится **неподходящим перезаписываемым полем**, что для расчёта может подставляться **искусственный 70 кг**, что observation должен быть **временным рядом**, а Progress обязан быть **производным** и не брать стартовую точку из `NutritionProfile`.

## 3. Самое важное правило из документа канонизировать первым

> **Факт выполнения действия не является доказательством достижения результата.**

То есть:

```
ходил на массаж
пил воду
заполнял питание
        ↓
   Plan Adherence
```

и **отдельно**:

```
96 кг → 94 кг
        ↓
  Outcome Progress
```

**Никакого:**

```
выполнил 80% плана
        ↓
значит достиг 80% результата
```

Это архитектурно и продуктово **очень сильная граница**. Спецификация показывает, что существующий канон вокруг неё уже есть, но **самой нормы в явном виде пока нет**.

## 4. Пробел внутри самой Care-спецификации

**Он не ломает документ, но его надо закрыть перед UX.**

**Plan Adherence нельзя считать просто по любому факту активности.** Например, спецификация приводит:

```
план питания заполнен  ✓
вода записывалась      ✓
```

Но это становится adherence **только если сам Personal Plan заранее содержал соответствующее обязательство/действие**.

Иначе получится: **человек один раз записал воду → система решила, что он «выполнил часть плана».**

Правильно:

```
Personal Plan
  action:  вести запись воды
  cadence: ...
        ↓
Nutrition сообщает факт записи
        ↓
Plan Adherence сопоставляет
  planned action ↔ actual fact
```

То есть **Nutrition отдаёт факт, но не решает, был ли план выполнен.**

Это хорошо соответствует общей границе документа: **поставщики поставляют факты, а домен Personal Plan вычисляет adherence.**

---

## 5. Что делать прямо сейчас

**Не смешивать marketplace welcome и Care Plan.** Это **два независимых трека**:

```
CLIENT PILOT UX
  free text
    → semantic resolution
    → recommendation
    → booking
    → diary / lifecycle
```

```
PERSONAL PLAN / PROGRESS
  Desired Outcome
    → Personal Plan
    → Observation
    → Progress
    → NBA
```

**Первый можно продолжать уже сейчас.**

**Второй пока упирается в В-1 consent**, и правильно, что спецификация считает его блокирующим. **Без разрешённого основания хранения веса бессмысленно проектировать весь вертикальный slice так, будто данные уже можно легально сохранять.**

### Ответ на вопрос агента «завести маркетплейсный первый экран?»

**Отдельный новый Goal/Menu screen — нет.**

**Довести существующий CURRENT C01 до полноценного marketplace first-contact — да.**
