# Решение владельца — граница домена сопровождения (24.08.2026)

**Записано главным окном дословно. Считать каноническим.**

Повод: обсуждение цели «сбросить вес», которая не укладывается в нынешнюю модель «цель = ярлык на услуге».

---

## Что происходит

Сейчас модель такая:

```
«Хочу расслабиться»
   -> Goal
   -> подходящие услуги
   -> выбор услуги
   -> запись
```

Это нормально для transactional-сценария.

Но **«Хочу снизить вес» не заканчивается одной записью.** Здесь появляется цикл:

```
намерение человека
   -> желаемый результат
   -> план
   -> действия
   -> наблюдения человека
   -> прогресс
   -> следующий лучший шаг
   -> корректировка плана
```

**Именно здесь Ayla начинает превращаться из AI-каталога с записью в систему сопровождения.**

---

## 1. Не делать «сбросить вес» новым типом Goal

И **не помещать эту механику внутрь Nutrition Questionnaire.**

Анкета питания должна отвечать за питание. Иначе через несколько месяцев получится:

```
Nutrition Questionnaire
├── калории
├── БЖУ
├── вода
├── массаж
├── тренировки
├── вес
├── напоминания
├── прогресс
├── рекомендации
└── косметология
```

То есть **nutrition-домен случайно станет владельцем всей системы заботы Ayla.**

### Правильное разделение

```
Goal                «Подтянуть фигуру»
   |
Desired Outcome     «Хочу снизить вес»
   |
Care Plan           «Работаем над этим следующие 8 недель»
   |
   ├── Nutrition      нормы · питание · вода
   ├── Services       подходящие процедуры
   ├── Activity       позже
   └── Observations   вес со слов человека · записи дневника · посещённые процедуры
   |
Progress
   |
NBA                 «Что Ayla предлагает сделать следующим»
```

**Для MVP совершенно не обязательно строить полноценный Care Plan engine.**

Это принципиально: **правильно определить границу сейчас, а реализовать очень тонкий вертикальный срез.**

---

## 2. Один пилотный Outcome — снижение веса

Не проектировать универсальный движок для всех возможных жизненных целей.

Берём **«Я хочу снизить вес»** и проверяем всю концепцию Ayla на одном сценарии.

Пример: человек говорит «Хочу похудеть к отпуску». Ayla уточняет необходимое и получает **явно сообщённую пользователем** цель:

```
Desired Outcome:
  type: weight_change
  direction: decrease

Target:
  target_weight: 90 kg

Time horizon:
  target_date: 2026-10-15
```

Если человек сейчас сообщил 96 кг — сохранить исходное наблюдение **согласно разрешённому consent/purpose**.

---

## 3. Чем измерять прогресс — два разных вида

**Нельзя придумывать прогресс из поведения пользователя.** Если человек сходил три раза на массаж, нельзя говорить «вы хорошо продвигаетесь в снижении веса». **Мы этого не знаем.**

Но можно сказать: «на этой неделе вы выполнили 3 из 4 запланированных действий». Это **совершенно другая семантика**.

### Outcome progress

Измеряется **только данными, которые действительно относятся к результату**:

```
Стартовый вес:  96 кг
Последний вес:  94 кг
Цель:           90 кг
```

Ayla математически может сказать: **«С момента начала вы сообщили снижение веса на 2 кг».**

**Без:** «хороший темп», «здоровое снижение», «организм хорошо реагирует», «массаж работает». Это медицинская и физиологическая интерпретация, которой нам сейчас касаться не нужно.

### Plan adherence

Отдельная вещь:

```
план питания заполнен      ✓
вода записывалась          ✓
2 процедуры посещены       ✓
контрольный вес отсутствует
```

Ayla может сказать: **«На этой неделе выполнены 3 запланированных действия из 4. Чтобы обновить прогресс по вашей цели, можно внести текущий вес.»**

Это и полезно, и гораздо безопаснее.

---

## 4. Вес — это observation, а не поле профиля

Недостаточно `User.weight = 96`, потом `User.weight = 94` — **первое значение исчезает.**

Нужна история:

```
WeightObservation
2026-08-24   96.0 kg   user_stated
2026-09-01   95.2 kg   user_stated
2026-09-08   94.4 kg   user_stated
```

Тогда Ayla получает **временной ряд**.

Паттерн впоследствии используется шире:

```
Observation
├── weight
├── water
├── mood
├── sleep
├── symptom
├── body measurement
└── ...
```

Хорошо ложится на уже задуманные wellness-поверхности.

---

## 5. Услуги не должны становиться доказательством результата

Каталог может сказать: `Service -> supports -> Goal / Outcome`. Массаж может быть релевантным действием внутри плана.

**Но связь «посетил массаж → значит похудел» запрещена.**

Правильно:

```
посетил массаж        ->  PlanAction completed
WeightObservation     ->  OutcomeProgress
```

**Это две независимые линии данных.**

---

## 6. Проактивность — не причина отказываться от плана

**Care Plan не должен иметь право самовольно писать пользователю.** Он может породить **повод** для взаимодействия:

```
Care Plan  ->  NBA candidate «Пора обновить вес»
                    |
             Consent Scope Registry
                    |
             Outbound authorization
                    |
             channel permission
                    |
             можно отправлять?
              /            \
            YES            NO
             |              |
           send          ничего
```

**План не владеет рассылками.** Это стыкуется с reverse outbound guard, который строится сейчас.

---

## 7. Четыре принятых решения

**Первое.** Не расширять Nutrition Questionnaire до владельца общего плана. Nutrition остаётся **одним из поставщиков** данных и действий для будущего Care Plan.

**Второе.** Прогресс разделить на **Outcome Progress** и **Plan Adherence**. Outcome Progress — только из наблюдаемых и сообщённых данных. **Выполнение действий не считается доказательством достижения результата.**

**Третье.** Проактивность отделить от Care Plan. Care Plan и NBA могут определить, что полезно сделать дальше, но **любое сообщение проходит существующий consent + outbound authorization pipeline**.

**Четвёртое.** **Не строить сейчас универсальный Care Plan framework.**

Сначала один вертикальный сценарий:

```
«Хочу снизить вес»
   -> Desired Outcome
   -> питание + вода + подходящие услуги
   -> пользовательские WeightObservations
   -> Outcome Progress + Plan Adherence
   -> NBA
   -> разрешённая коммуникация
```

Если этот сценарий заработает от начала до конца — получаем шаблон для «улучшить состояние кожи», «восстановиться», «подготовиться к событию», «наладить сон». **И только тогда имеет смысл обобщать модель.**

---

## Что делать сейчас

**Не отправлять агента писать код.**

Это редкий случай, когда стоит зафиксировать **очень маленький контракт**:

```
Desired Outcome -> Care Plan -> Observation -> Progress -> NBA
```

**Не огромный PRD — рабочую спецификацию на несколько страниц.** После неё можно быстро разбить первый вертикальный срез «снижение веса» на конкретные задачи и идти в код.
