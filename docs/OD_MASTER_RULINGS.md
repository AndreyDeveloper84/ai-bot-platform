# OWNER RULINGS — навигация мастера, текущий визит, завершение визита

**25.08.2026.** Записано дословно. Имеет приоритет над макетами `DRF-1181`/`DRF-1182` и над любым пересказом главного окна.

## OD-MASTER-IA — Master vs Solo navigation

### Salon master

Primary navigation:

```
Сегодня | Расписание | Ayla
```

**Profile / Settings доступны из header/menu и не являются отдельной primary tab в P0.**

### Solo practitioner

**Solo — отдельная operational persona.** Для неё сохраняется:

```
День | Записи | Клиенты | Услуги | Ещё
```

**Наличие двух вариантов navigation не считается нарушением design system.**

> Design system определяет внешний вид и поведение navigation component, а не единый набор разделов для разных ролей.

**Solo navigation не является текущим Controlled Pilot blocker**, пока solo tenant не участвует в Pilot.

## OD-MASTER-VISIT — Current visit presentation

**Passive derived UI разрешён:**

- «Идёт сейчас»
- время начала
- примерное время до конца

**Отдельное domain state `VISIT_IN_PROGRESS` не вводится.**

**Derived presentation не создаёт действия и не требует подтверждения от мастера.**

## OD-VISIT-COMPLETION — Authority

**Обычный мастер НЕ подтверждает факт состоявшегося визита.**

**Admin / Owner имеет право закрыть визит с салонной поверхности.**

> Если один человек имеет роли Master + Admin/Owner, **authority определяется активным role/surface context, а не физической личностью пользователя.**

**На Master surface кнопку `Состоялся` не добавлять.**

**На Salon/Admin surface действие оставить и выполнять как consequential write:**

```
intent
  -> explicit confirmation
  -> canonical completion command
  -> authoritative readback
```

**Downstream commission / review / lifecycle / RFM запускаются только от authoritative completed visit.**

## OD-MASTER-BOOKABLE — Когда мастер становится продаваемым

Дата решения: 2026-09-06. Владелец, лично.

Включение **автоматическое** — ручного подтверждения владельцем на каждого мастера нет.

Профиль считается готовым при выполнении **всех трёх** условий:

1. **заполнено имя;**
2. **назначена хотя бы одна активная услуга с ценой;**
3. **рабочее расписание явно подтверждено мастером или владельцем.**

**Наличие свободных окон на ближайшей неделе не требуется** — мастер с занятой неделей
остаётся продаваемым.

**Техническая заглушка 10:00–19:00 подтверждённым расписанием не считается.** Формулировка
владельца: иначе мастер автоматически появится для записи в часы, которые никто не утверждал.

### Следствия, зафиксированные главным окном

- Условие 3 сегодня выразить нечем: `WorkingHours` не различает утверждённое расписание и
  заглушку, положенную при заведении. Требуется **явный признак подтверждения** (кто и когда)
  и действие, которым он ставится.
- Существующие заглушки **не помечаются подтверждёнными задним числом**.
- Замер 06.09.2026: `WorkingHours` у **4 из 31** бронируемых мастеров, `SlotConfig` — 0 строк.
  Буквальное включение критерия сегодня снимает с продажи 27 мастеров из 31.
- **ИСПРАВЛЕНО 06.09. Заглушка живёт строками, и накрывает не тех, о ком я сначала написал.**
  Я предположил, что 10:00–19:00 — это поведение по умолчанию для тех, у кого строк нет.
  **Такого умолчания в коде нет.** Заглушку произвёл прежний посев в ветке приглашения,
  убранный DRF-1062, и её несут **ровно те четверо, у кого строки есть**
  (`apps/admin_api/views_invite.py:910-917`, дословно: «manufactured the 10:00-19:00 stub
  that all four pilot masters now carry»). Отображение обратное первоначальному.

- **Замер «`WorkingHours` у 4 из 31» измеряет локальное зеркало, а не то, по чему продают.**
  `apps/admin_api/views.py:293-296` и `views_invite.py:914-917` говорят это прямо: при
  `BOOKING_VIA_AYLA_REST` слоты отдаёт бэкенд Ayla, а `apps.scheduling` — зеркало бота.
  Значит вывод «27 из 31 перестанут продаваться при включении критерия» **из этого замера
  не следует**: он не про ту таблицу. Настоящее число берётся со стороны Ayla.

- **Отсюда открытый вопрос, которого не было в исходном решении: где живёт признак
  подтверждения.** Если расписание держит Ayla, то признак, повешенный на `WorkingHours`,
  встанет на таблицу, которая ничего не формирует, и критерий продаваемости будет спрашивать
  зеркало о том, что решает другой сервис. Такое проходит ревью незамеченным: код корректен,
  тесты зелёные, гейт гейтит — просто не то. См. `docs/OPEN_QUESTIONS_OWNER.md` §5.14.

- **`WorkingHours.created_by` признаком подтверждения не является** и заменителем не годится:
  он отвечает «кто создал строку», а не «кто утвердил расписание». Разметка существующих строк
  задним числом через него противоречит решению владельца. Отдельно: посев `WorkingHours`
  убран DRF-1062 — происхождение сегодняшних строк неоднородно, и разметка задним числом
  разметила бы неизвестно что.

- Поэтому **порядок работ обязателен**: признак подтверждения и действие → кампания
  подтверждения по подключённым мастерам → **только потом** гейт продаваемости, за флагом.
  Обратный порядок запрещён без отдельного решения владельца.
