## 1. Признак маппинга услуг (§40.4 п.1 / §6.1)

### Вопрос

Можно ли рекомендовать услуги, связанные с шаблоном, если доверие к этой связи не зафиксировано?

### Решение

Вводится обязательный статус связи:

| Статус | Значение | Участие в подборе |
|---|---|---|
| `VERIFIED` | Связь подтверждена человеком либо воспроизводимым детерминированным правилом с provenance | Да |
| `REVIEW_REQUIRED` | Связь существует, но её правильность не доказана | Нет |
| `UNMAPPED` | Валидной связи нет | Нет |

Правила:

1. Существующие 206 связей из 265 услуг нельзя автоматически объявлять `VERIFIED`.
2. Связь без доказуемого provenance мигрирует в `REVIEW_REQUIRED`.
3. Отсутствующая или повреждённая связь мигрирует в `UNMAPPED`.
4. Ноль `VERIFIED` не разрешает fallback на `REVIEW_REQUIRED`.
5. При отсутствии подтверждённых кандидатов API возвращает штатный результат `NO_VERIFIED_CANDIDATES`.
6. `REVIEW_REQUIRED` виден только во внутренней очереди проверки.
7. Подтверждение хранит автора/правило, время, версию и ссылку на основание.
8. Исправление достижимости `31 → 3` является отдельной задачей. Ослаблять `VERIFIED` ради покрытия запрещено.

Последовательность запуска полки:

`T7 → транзит → mapping_status → миграция → проверка связей → VERIFIED → исправление достижимости → рабочая полка`.

## 2. Четырнадцать клиентов салонного помощника

### Вопрос

Куда переносить 14 клиентов салонного бота, если в клиентском контуре их восемь?

### Решение

Все 14 сохраняются. Клиент принадлежит Ayla, а отношение и разговор — конкретному салону.

Целевая модель:

- `ClientProfile` / `Person` — единый профиль человека;
- `ExternalIdentity` — MAX, Telegram, телефон и другие подтверждённые идентичности;
- `SalonCustomer` — отношение человека с конкретным салоном;
- `Conversation` — разговор в конкретном канале и tenant-контексте;
- `Consent` — разрешённые цели использования данных.

Миграция:

1. Сопоставлять записи только по подтверждённому телефону, MAX ID или существующей identity-связи.
2. Совпавших связывать с одним `ClientProfile`, сохраняя `SalonCustomer`.
3. Несовпавшим создавать ограниченный `SHADOW`-профиль с `source = SALON_ASSISTANT`.
4. `SHADOW` не даёт права использовать глобальные цели, питание, health-контекст или межсалонную память.
5. Разговоры остаются в исходном салоне и не становятся глобальной памятью без отдельного основания.
6. Салон не видит цели, домашний/рабочий адрес, питание и историю других салонов.
7. Объединение по имени запрещено.

## 3. Матрица безопасности

### Канонические состояния

| Состояние | Смысл | Поведение |
|---|---|---|
| `NORMAL` | Проверка применима, выполнена, значимых сигналов нет | Обычный поток; допустим `ELIG_SAFETY_CLEARED` |
| `CAUTION` | Данных достаточно, но продолжение требует ограничения или оговорки | Только разрешённый правилами путь; запись не разрешается автоматически |
| `CLARIFY` | Для решения не хватает обязательной информации | Один конкретный safety-вопрос; до ответа рекомендация и запись закрыты |
| `STOP` | Обнаружен запрещающий сигнал | Обычный recommendation/booking flow прекращается |
| `UNKNOWN` | Проверка применима, но валидного результата нет | Fail-closed |
| `NOT_APPLICABLE` | Capability не выполняет safety-sensitive решение | Обычное выполнение без заявления о пройденной проверке |

Приоритет: `STOP > CLARIFY > CAUTION > NORMAL`.

Обязательные инварианты:

- `NOT_APPLICABLE` определяется capability, а не отсутствием поля.
- `requires_health_check`, health/symptom input, safety-sensitive кандидат или активная safety-relevant персонализация запрещают `NOT_APPLICABLE`.
- Один чувствительный кандидат без валидного `SafetyResult` закрывает весь персонализированный ответ.
- `NOT_APPLICABLE` не выдаёт `ELIG_SAFETY_CLEARED`.
- Конструкция `payload.get("safety") or NOT_APPLICABLE` запрещена и охраняется AST-тестом.
- Safety-контекст сохраняется между ходами и содержит `state`, `rule_id`, `evidence_ref`, `activated_at`, `policy_version`, `resolution/expiry`.
- Простое упоминание лекарства не является автоматическим `STOP`; запрос подобрать препарат, дозировку или схему — `STOP`.

## 4. Реестр планировочных правил

### Решение

Plan Engine не определяет, что важно. Он применяет версионируемые правила с указанными authority, evidence и поведением при `UNKNOWN`.

Каждая запись реестра должна иметь:

- `rule_id`, `title`, `scope`, `rule_type`;
- `condition`, `required_evidence`, `effect`, `priority`;
- `authority`, `source_ref`, `policy_version`, `effective_from`;
- `status`, `unknown_behavior`, `user_message_id`, `audit_event`;
- `supersedes`, `owner`.

Минимальные типы: `SAFETY`, `ELIGIBILITY`, `USER_CONSTRAINT`, `TIME`, `LOCATION`, `BUDGET`, `DEPENDENCY`, `CAPACITY`, `CONSENT`, `EVIDENCE`, `BUSINESS_POLICY`.

Значения применимого ограничения:

- `KNOWN_ALLOW`;
- `KNOWN_DENY`;
- `UNKNOWN`;
- `NOT_APPLICABLE` — только когда правило не относится к capability.

Приоритет правил:

1. Safety.
2. Consent и юридическая допустимость.
3. Eligibility.
4. Явные ограничения человека.
5. Время, место, бюджет и доступность.
6. Предпочтения и оптимизация.
7. Business policy.

LLM может извлекать кандидаты и формулировать текст, но не является authority, не назначает приоритет и не превращает предположение в факт.

Изменение фактов создаёт новую `PlanRevision`; старый план не переписывается задним числом. `DRAFT` снимается только с конкретного блокера, закрытого rule и owner ruling.

## 5. Три дефекта Goal / Habit / Profile Input

### 5.1 Норма воды из веса

Универсальная персональная норма вида `вес × N мл` не используется как утверждение Ayla.

- Пользователь может задать норму самостоятельно.
- Ayla может показать предварительный ориентир только внутри добровольного расчёта.
- Вес разрешено запросить именно для добровольного расчёта норм.
- Методика и использованные данные показываются человеку.
- Результат становится привычкой/шагом только после подтверждения пользователя.
- При health-факторах Ayla не рассчитывает индивидуальную норму.
- Домашние блоки замеров тела и действие «Добавить замер» из этого решения не возвращаются в пилот.

Справочно: [NHS — Water, drinks and hydration](https://www.nhs.uk/live-well/eat-well/food-guidelines-and-food-labels/water-drinks-nutrition/) и [EFSA — Dietary Reference Values for water](https://efsa.onlinelibrary.wiley.com/doi/10.2903/j.efsa.2010.1459).

### 5.2 «Цели сегодня»

Блок переименовывается в **«Шаги на сегодня»**.

- Goal — желаемый результат.
- Plan — путь к результату.
- Habit — повторяющееся действие внутри плана.
- PlanStep — конкретное действие.

Привычка или действие не создают отдельную `Goal`.

### 5.3 `area` и `feeling`

- `area` уточняет границы GoalCandidate, применимость услуг и safety/eligibility context.
- `feeling` выражает желаемое состояние, влияет на формулировку результата и предпочтение между уже допустимыми вариантами.
- `feeling` не является диагнозом и не может отменить safety, eligibility, бюджет или доступность.
- Если система не может показать `rule_id`, где поле повлияло на решение, нельзя заявлять, что поле было учтено.

## 6. OD-NUT-1 — пользователь без анкеты питания

Анкета не блокирует дневник.

Без анкеты доступны:

- добавление еды текстом, голосом или фотографией;
- просмотр, исправление и удаление собственных записей;
- отображение фактически внесённых значений;
- предложение настроить ориентиры.

До настройки скрыты:

- персональная норма калорий;
- «осталось на сегодня»;
- индивидуальные БЖУ и вода;
- оценки «мало», «много», «перебор»;
- прогноз изменения веса;
- персональный план питания.

Неизвестные нормы имеют `NOT_CONFIGURED`, а не ноль. Анкета запрашивается постепенно, только для конкретной функции. Пищевой дневник не передаётся салону или мастеру.

## 7. Q-CLIENT-03 — удаление аккаунта и личных данных

### Формулировка

Кнопка: **«Удалить аккаунт и личные данные»**.

Подтверждение сообщает:

- аккаунт будет отключён;
- профиль, цели, планы, дневники, адреса и персональный контекст будут удалены;
- срок завершения — не позднее 30 дней;
- состоявшиеся записи и оплаты могут сохраняться ограниченно или обезличенно при наличии обязательного основания;
- после начала удаления действие нельзя отменить.

После нажатия система немедленно показывает:

- что запрос принят;
- точную крайнюю дату;
- `request_id`;
- текущий статус.

Статусы: `DELETION_REQUESTED → DELETION_PROCESSING → DELETION_COMPLETED`.

Персонализация и новая обработка данных прекращаются сразу. Устойчивый `DeletionRequest` создаётся до показа успеха. Ошибка обязана явно говорить, что удаление не началось.

## 8. География и координаты на пилоте

Координаты нужны в пилоте.

В профиле клиента предусмотрены:

- домашний адрес и координаты;
- рабочий адрес и координаты;
- текущее местоположение — только по отдельному разрешению;
- выбранная точка отсчёта для конкретного решения.

Данные используются:

- для расчёта расстояния до точки оказания услуги;
- при выборе подходящего предложения;
- при формировании реалистичных целей, планов и шагов.

Система не угадывает, откуда человек поедет. При неоднозначности задаётся один вопрос. Отсутствие координат даёт `DISTANCE_UNKNOWN`, а не ноль или средний score.

До появления мобильного приложения предусматривается будущий запрос доступа к геоданным; адреса дома и работы могут быть введены пользователем заранее.

## 9. Двадцать семь старых адресов мастеров

Все старые адреса перестают быть авторитетными.

- Подтверждённый адрес салона переносится в `ServiceLocation`.
- Подтверждённое рабочее место соло-мастера становится его `ServiceLocation`.
- Совпавшие точки связываются без создания дублей.
- Неизвестное происхождение → `REVIEW_REQUIRED`.
- Тестовый, личный или недействительный адрес → `INACTIVE`.
- Автоматический массовый перенос запрещён.
- Расстояние считается до точки конкретного предложения, а не до профиля мастера.

Модель: `Master → works_at → ServiceLocation → address + coordinates`.

## 12. MAX-аккаунты и возможность освобождения

Замер:

- всего аккаунтов бота — 26;
- синтетических фикстур — 8;
- реальных MAX-идентификаторов — 6;
- с историей — `83146139`, `229831120`, `66368800`;
- без истории — `332809622`, `113751726`, `34952958`.

По одним числовым ID владелец не может определить людей. Поэтому:

1. Ничего не удалять по списку ID.
2. Сначала показать распознаваемую read-only карточку: маскированное имя/телефон, роль, tenant, даты входов и связанный контекст.
3. Если идентификацию безопасно показать нельзя — дать каждому человеку команду `/whoami` или эквивалент.
4. До подтверждения конкретного человека статус — `BLOCKED_BY_IDENTITY`.
5. Освобождение аккаунта возможно только двусторонней командой: бот + каталог.

## 13. Гейт O — наблюдения тела

Наблюдения тела включаются в пилот как добровольный модуль `wellness_observation`, но rollout остаётся закрытым до Privacy/Legal review.

Решения:

- отдельное версионируемое согласие на чувствительные wellness-наблюдения;
- данные видит пользователь, но не салон и не мастер;
- назначение ограничено личным планом пользователя;
- отзыв согласия немедленно прекращает использование данных;
- значения и производные данные удаляются в течение 30 дней при отсутствии иного законного основания;
- шесть зависимых задач можно разрабатывать, но выпускать нельзя до юридической проверки текста, основания и срока хранения.

## 14. Двадцать шесть задач BeautyGO до пивота

Массово закрывать задачи без просмотра нельзя. Каждая задача классифицируется:

- `CANCELLED_BY_PIVOT`;
- `ABSORBED`;
- `POST_PILOT`;
- `PILOT_RELEVANT`;
- `DUPLICATE`.

После классификации закрываются только отменённые, поглощённые и дубли. `POST_PILOT` переносится в соответствующее направление, `PILOT_RELEVANT` — в текущий release-контур.

## 16. Двусторонний сброс аккаунта

### 16.1 `AIRequestMetric`

Выбран вариант `SET_NULL`:

- метрика сохраняется;
- связь с пользователем снимается;
- прямые идентификаторы удаляются;
- текстовые payload очищаются или обезличиваются;
- агрегированные технические показатели сохраняются.

### 16.2 Тенант соло-мастера

- Тенант не удаляется.
- Разговоры и данные других клиентов не затрагиваются.
- Роль и карточка сбрасываемого мастера освобождаются.
- Второй салон автоматически не создаётся.
- Возврат к существующему салону возможен только через подтверждённую прежнюю identity или администратора.
- До подтверждения — `SETUP_PENDING`.

### 16.3 Состоявшиеся записи

Состоявшиеся записи остаются `PROTECT`. В текущей версии аккаунт с такими записями не сбрасывается. Будущая процедура обезличивания является отдельным privacy-процессом, а не обычным reset.

## 17. Операционные остатки

Следующие пункты не являются продуктовыми owner decisions и выполняются отдельно:

1. Путь к статике — требует ограниченного `sudo` для точного целевого пути; перед изменением необходимо проверить источник, назначение и права.
2. Восемь Dependabot PR — разбирать по одному или совместимыми группами, проверять changelog, breaking changes, тесты и lock-файлы; не сливать все восемь вслепую.

## 18. Общие инварианты, проявившиеся во всех решениях

1. **Не измеряли ≠ измерили ноль.**
2. **Нет данных ≠ `NOT_APPLICABLE`.**
3. **Название функции или поля не доказывает provenance.**
4. **LLM не является authority для ranking, eligibility, safety или правил плана.**
5. **Нет displayable evidence → нет пользовательского WHY.**
6. **Сначала нормативный контракт, затем runtime-код и тесты.**
7. **Любой guard должен иметь положительный тест на искусственно внесённое нарушение.**
8. **Персональные данные одного tenant нельзя раскрывать другому.**
9. **Необратимое удаление выполняется только после идентификации человека и явного подтверждения.**
10. **Старый контейнер закрывается только после переноса живых обязательств с traceability.**
