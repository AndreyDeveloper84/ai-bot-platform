## §2. Где граница

```
бот                                     каталог
apps/integrations/ayla/*_client.py  →   /api/v1/internal/*     44 маршрута, 3 вида авторизации:
  (12 клиентов)                                                  BEARER — сервисный токен
                                                                 BEARER_EXT — + X-External-User-ID,
                                                                   разрешаемый в ПРОВЕРЕННОГО клиента
                                                                 (users/permissions.py:
                                                                  IsBotServiceWithVerifiedClient)
```

Существенное для стенда: `BEARER_EXT` требует, чтобы в каталоге **уже был** пользователь,
связанный с `bot:<id>`. Связку создаёт каталог (`users/internal_identity_api.py`,
`users/identity_events.py`); бот её только читает (`identity_client.resolve_identity`). Значит любой
golden с `BEARER_EXT`-маршрутом начинается с **посева** на стороне каталога, а не с запроса бота.

## §3. Какой стенд детерминирован — три варианта, один годится

### A. Каталог как сервис в CI бота — РЕКОМЕНДУЮ

```
job cross-boundary:
  services: postgres:16, redis:7
  steps:
    checkout ai-bot-platform
    checkout beautygo_backend @ ПРИКОЛОЧЕННЫЙ SHA   (токен: тот же класс, что GH_DEPLOY_TOKEN)
    docker build каталога → run web :8000 (entrypoint: migrate → gunicorn)
    manage.py seed_golden --scenario p7        (каталог; см. §5)
    пульс: GET /healthz + печать SHA каталога в лог
    pytest tests/cross_boundary -m cross_boundary   (бот, AYLA_BASE_URL=http://localhost:8000)
```

Что даёт: настоящий HTTP, настоящая авторизация, настоящая база, **обе стороны на известных SHA**.
Это и есть `CROSS_BOUNDARY`, а не его имитация.

Цена: сборка образа каталога в каждом прогоне — по опыту его же CI, 3–6 минут (базовый образ
уже мирроруется в GHCR, значит без сети к Docker Hub). Плюс `migrate` на пустой базе. Итого
**+6–10 минут к job'у**, отдельным job'ом, параллельно шардам `apps/`.

Риск, и он главный: **расхождение версий двух репозиториев.** Golden зелёный на каталоге `X`
ничего не говорит про каталог `X+5`. Поэтому SHA каталога приколачивается в workflow **и печатается
в лог рядом с числом тестов** — предмет рядом с результатом; обновление SHA — отдельный PR с
перечнем изменившихся маршрутов. Это дисциплина, не автоматика; автоматика («всегда `dev`
каталога») дала бы зелень, зависящую от чужого слияния.

### B. Записанные ответы с версией контракта — НЕ годится как основной путь

Снять ответы каталога один раз, положить в фикстуры с `contract_version`, гонять бот против них.
Дёшево (3 SP), детерминированно, **но это уровень CONTRACT**, а он в матрице уже есть — 13
тестов. `CROSS_BOUNDARY` он не двигает: записанный ответ не краснеет, когда каталог меняет
ручку. Годится как страховка на случай, если A окажется дороже по времени CI, чем терпимо, — и
тогда его надо честно назвать CONTRACT, а не E2E.

### C. Ночной прогон против пилота — НЕ годится для golden

Уже есть (`test_ayla_integration.py` с `AYLA_BASE_URL`). Недетерминирован: данные пилота живые.
И пишет в пилот — а правило смоука, записанное в его же заголовке, гласит, что проверка не
должна менять проверяемое. Оставить как **дозор**, не как golden.

**Итог:** A. B — резерв, C — не трогать.

## §4. Сценарии — P7 первым, и вот почему это не трусость

### P7 — нет VERIFIED-кандидата → честный пустой ответ

Каталог отвечает `BLOCKED(CATALOG_NOT_RECOMMENDABLE)` — он же `NO_VERIFIED_CANDIDATES`
(`users/catalog_recommendations_api.py:68`, `recommendation/_authority.py:108`) — когда допущенных
кандидатов ноль. **Пустой каталог даёт это состояние по построению.** Значит посев минимален:

```
посев P7:  один tenant · один User, связанный с bot:golden-p7 · сервисный токен
маршруты:  GET  /internal/me/identity/                     BEARER_EXT   (бот читает связку)
           POST /internal/me/catalog/recommendations/      BEARER_EXT   (каталог → BLOCKED)
проверка:  ответ бота человеку — честное «пока нечего предложить», без имён, без чисел,
           без «загляните позже» из ниоткуда; и в ответе каталога reason_code именно
           CATALOG_NOT_RECOMMENDABLE, а не пустой список без причины
```

Почему первым: он **проходит на пилоте сегодня** (`verified = 0`, матрица P7 — «лучший узел
контура»), у него самый короткий посев, и он проверяет самое дорогое свойство границы — что
**отсутствие доезжает отсутствием с именем**, а не превращается по дороге в пустую полку или в
выдуманного мастера. Ровно тот класс дефекта, который весь сентябрь ловили на ориентирах питания.

Оценка: **3 SP** после стенда (A) — один сценарий, две ручки, посев в одну команду.

### P1 — прямая услуга → бронь

```
посев P1:  tenant · мастер ACTIVE · услуга с ценой и длительностью · расписание с ≥1 слотом ·
           связанный клиент
маршруты:  GET  /internal/catalog/specialist-services/     BEARER
           GET  /internal/specialists/{id}/slots/          BEARER
           POST бронь с X-Idempotency-Key                   BEARER_EXT
           GET  /internal/me/bookings/{id}/                BEARER_EXT
проверка:  бронь существует в каталоге с той же ценой/длительностью, что бот показал
           человеку; повтор с тем же ключом идемпотентности не создаёт вторую
```

Здесь golden упрётся в известное из матрицы: «цена/длительность подменяются молча» (P1 PARTIAL).
Golden не чинит это — он **делает это видимым**: проверка «бот показал X, каталог записал X»
покраснеет ровно там. Это надо назвать заранее, чтобы красный P1 прочли как находку, а не как
поломку стенда.

Оценка: **5 SP** после стенда — четыре ручки, посев с расписанием, идемпотентность как
отдельная проверка.

### Итого

```
стенд A (job, сборка каталога, посев-команда, пульс, сторож пустого прогона)   5 SP
P7                                                                             3 SP
P1                                                                             5 SP
                                                                              13 SP
```

Калибровка якорей — из замера дневника: 3 SP — один замкнутый предмет с проверкой, 5 SP —
несколько точек приложения со своей последовательностью.

## §5. Сторож «стенд не поднялся ≠ зелёный»

Пустой прогон читается как зелень — это записано и уже ловилось (`failures=0` при `tests=0`).
Здесь три способа не подняться, и у каждого своя ловушка:

```
каталог не собрался        шаг сборки красный — очевидно
каталог собрался, но не    healthcheck зелёный (контейнер жив), а migrate упал: код впереди схемы;
  мигрировал                 ловится ТОЛЬКО запросом к ручке с данными, не к /healthz
каталог поднялся, но       AYLA_BASE_URL не выставлен → test_ayla_integration.py молча пропускает
  бот его не увидел          ВЕСЬ модуль — и job зелёный с нулём тестов
```

Поэтому:

1. `tests/cross_boundary/` — **новый каталог, без `skipif`**. Нет стенда — тест **падает**,
   а не пропускается. Пропуск — это разрешение читать зелень как успех.
2. Первый тест каталога — **пульс с предметом**: `GET /healthz` плюс ручка, которая ходит в
   базу (`/internal/me/identity/` для посеянного клиента), плюс печать SHA каталога из
   `/version` или из env в лог теста. Не ответил — красный с именем причины.
3. Junit-выгрузка с `tests=` раньше `failures=` — уже есть (#1544); job обязан отказывать при
   `tests == 0` так же, как шарды.

## §6. Что этот план НЕ решает — названо

* **`NetworkTripwire` остаётся.** Replay-фикстуры и дальше не ходят в сеть — это правильно для
  их предмета. Cross-boundary — отдельный уровень, не переделка replay.
* **P2–P6, P8–P10** не оцениваются: P2 упирается в `verified = 0` на самом пилоте (нечего
  проверять, пока некого допускать), P4–P6 — в неисполненные решения. Оценивать их golden
  сегодня значило бы оценивать тест для кода, которого нет.
* **Каталожная половина посева** (`seed_golden`) — полоса каталога; здесь названа, не написана.
* **Совместимость версий двух репозиториев** решается дисциплиной приколоченного SHA, а не
  автоматикой. Это честный предел: автоматика дала бы зелень из чужого слияния.

## §7. Чего не мерил

1. Время сборки образа каталога в GitHub Actions — взято из его собственного CI по памяти
   разбора, не замерено на раннере бота. Первый прогон стенда даст число.
2. Живой пилот — ни одного вызова.
3. Прогон тестов — ни один вывод на него не опирается.

## §8. Шаг 2 — что строится первым

Стенд A с одним тестом-пульсом и golden P7. Доказательство — три раскладки: (а) стенд поднят,
каталог пуст → зелёный с `reason_code = CATALOG_NOT_RECOMMENDABLE` в логе; (б) стенд поднят,
посеян один VERIFIED-мастер → P7 **краснеет** (положительная стража: тест различает пустой каталог
от непустого, а не зелен всегда); (в) стенд не поднят → красный с причиной, **не пропуск**.
