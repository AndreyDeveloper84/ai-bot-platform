## 1. Что такое Plan Lite — дословно, а не пересказ

§133 (директива владельца, 10.09):

> Полный Plan Engine к пилоту не обязателен. Но **продукт обязан уже показывать связный путь**:
> ```
> Goal → следующий полезный шаг → nutrition / service context → Recommendation → Booking / execution
> ```
> Урезание допустимо **в глубине механизма** (Plan Lite вместо Plan Engine), но **не в наличии способности**.

Рамка, которая с этим сталкивается — §112 (10.09): «К реализации Plan не переходить, пока не закрыты Goal Domain Contract и
DecisionReadiness»; «`Goal → PlanEligibility → optional Plan`».

**Столкновение надо разрешить первым, иначе любая работа будет либо нарушением §112, либо нарушением §133.** Чтение, при котором
оба решения держатся: *Plan Lite — это не Plan.* Это связный путь, собранный из **уже существующих** звеньев без новой сущности
плана, без `PersonalPlan`/`DesiredOutcome`-писателей и без DecisionReadiness в контуре; «следующий полезный шаг» вычисляется
детерминированно из `goal_key` (ключ → категории → каталог/подбор), а не планировщиком. Тогда §112 не нарушен (Plan не
реализуется), §133 исполнен (способность показана). Это чтение — исполнителя; **вопрос 1 владельцу** (§4).

Слов `Plan Lite`, `PlanEligibility`, `PlanEngine` в коде обоих репозиториев — 0. Предмета под этим именем нет; есть звенья под
другими именами.

## 2. Состояние пяти звеньев — по §138

| звено | категория §138 | одной строкой (детали и строки кода — в инвентаре) |
|---|---|---|
| 1 Goal | **ИСПОЛНЕНО** | `ClientGoal`, анкета, экран «Моя цель» в Mini App без шкал (§35 п.13); 33 цели, 3 активных (`relax`×2, `recharge`), все ключевые, текста нет. Бот цель не показывает — только deep-link |
| 2 Следующий шаг | **ПОДЛЕЖИТ** | вычислителя «шага из цели», доходящего до человека, **нет**: `next` в decision-context — константа `browse_catalog`; триггеры коуча ждут ключи `sleep_*/energy_*`, живой словарь — `relax, recharge, body_shape, self_care, event, new_look, skin_care` → пересечение пустое; OBSERVE — ЗАПЕРТО и без отправки; чипы после анкеты — шаг из анкеты, не из цели |
| 3 Context | ИСПОЛНЕНО механизм / **экспозиция цели 0** | цель в промпт консьержа только при `goal_text` (0 из 3 живых); `GOAL_RESOLUTION_ENABLED=True` режет полку 3 и `/home/`, которые никто не рендерит и не вызывает |
| 4 Recommendation | ИСПОЛНЕНО механизм / **непустой быть не может ни у кого** | `recommendation_eligible = VERIFIED`, verified = 0 (замер 09.09), подтверждение — ручное через админку, применено 0 раз; бот-каталог по реплике — CatalogResult, не Recommendation (§110), сохранённую цель не читает |
| 5 Booking | **ИСПОЛНЕНО** (бронь) / **ПОДЛЕЖИТ** (связь с целью) | бронь работает (18 Appointment); связи «эта запись — шаг к этой цели» в данных **нет вовсе** (grep по `appointments/`, `apps/booking/` → 0); «Найти время» — реестр §4 без ответа |

**Связность:** ни одна поверхность не показывает два соседних звена, связанных данными. Дашборд Mini App: «Цель: relax» →
«Подобрать услугу под твою цель» → каталог, **который цель не читает** (`getCatalogBrowse()` без аргументов). Единственная цепочка
из трёх звеньев подряд — бот: реплика → каталог → бронь — обходит Goal и Recommendation по построению.

**Вывод для §133:** способность «показывать связный путь» сегодня **отсутствует**, при том что четыре звена из пяти построены.
Не хватает двух вещей: вычислителя шага из цели (звено 2) и **данных, связывающих звенья** (цель → выдача, бронь → цель). Обещание
уже висит на экране («под твою цель», «предложу следующий шаг» в welcome-тексте бота) без вычислителя за ним — по §133 это хуже,
чем отсутствие обещания.

## 4. Решения владельца — без них не начинать

1. **Plan Lite — это Plan (§112 запрещает до Goal Domain Contract) или связный путь из существующих звеньев (§133 требует)?**
   (а) связный путь без новой сущности — работа выше, 10–16 SP, стартует сейчас; (б) Plan Lite = урезанный Plan Engine — ждёт
   DRF-1660 + DecisionReadiness, к пилоту не успевает, §133 в части «связный путь» не исполняется; (в) §133 сужается до «звенья есть
   порознь» — дешевле всего и это уже так, но обещания на экране надо снять (PL-4).
2. **Каталог под цель как звено «Recommendation» на пилоте при `verified = 0`?** §110 запрещает называть каталог рекомендацией,
   §125 разрешает честный каталог. (а) да, с честным заголовком, Recommendation появится при `verified > 0` без правок пути;
   (б) нет — путь на пилоте обрывается на звене 4 до ручного разбора §93.
3. **Связь бронь ↔ цель в данных** (PL-3): (а) писать `goal_id` в `attribution_metadata` бота сейчас, 3 SP, каталог не трогать;
   (б) ждать Goal Domain Contract и вводить FK в `Appointment` — вместе с DRF-1660; (в) не связывать — тогда «execution» в §133
   недоказуемо навсегда, замер пути невозможен.
4. **Коуч питания — часть «следующего шага» на пилоте?** (а) да — PL-6, 2 SP, словарь ключей утверждает владелец; (б) нет —
   коуч остаётся отдельной способностью, триггеры на живых целях не срабатывают, и это названо.
5. **Кто и когда делает ручной разбор §93** для пилотного салона — без этого звено 4 пусто при любом коде.
