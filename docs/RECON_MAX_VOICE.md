# Разведка: умеет ли MAX голос

**Дата:** 2026-08-25 · **Задача:** выяснить, есть ли куда приземлить OpenAI Realtime · **Ничего не строилось, кода нет.**

---

## 1. Ответ одной строкой

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Бот может **получить** аудио от человека? | **ДА** — как вложение `type: "audio"`, приходит **ссылка + готовая текстовая расшифровка**. |
| 2 | Бот может **отправить** аудио человеку? | **ДА** — через `POST /uploads?type=audio` → токен → вложение в сообщение. |
| 3 | Есть потоковое: звонок / стрим / вебсокет? | **НЕТ** — в Bot API нет ни одного такого метода. Только HTTPS-вебхук и long-polling. |

**Вывод для решения: Realtime-модель к MAX неприменима.** MAX — это обмен файлами, а не сессия. Перебивание, реакция на паузы, дуплекс — физически некуда посадить.

**Но голос есть, и он дешевле, чем ожидалось:** MAX отдаёт боту расшифровку голосового **сам**, бесплатно, в теле вебхука. То есть ASR нам, скорее всего, вообще не нужно покупать.

---

## 2. Доказательства

### Источник 1 — наш код: голос не поддержан (но это не значит, что его нет)

Наш MAX-канал знает **только** `image`. Ни `audio`, ни любого другого типа вложения он не разбирает.

- `ai-bot-platform/apps/channels/max/parser.py:151` — парсер кладёт `attachments` в `CanonicalEvent` **как есть**, не глядя на `type`.
- `ai-bot-platform/apps/channels/max/photo.py:116` — единственное место, где тип вообще читается:
  ```python
  if att.get("type") != "image":
  ```
- `ai-bot-platform/apps/channels/max/handler.py:1706` — вниз по стеку уезжает только булев факт: `has_attachments=bool(event.attachments)`.
- Grep по `apps/channels/max/**` и по `legacy_maxbot/` на `audio|voice|голос|транскрип|ogg|mp3` — **ноль попаданий** по существу (только «brand voice»).

**Что это доказывает:** только то, что мы никогда этим не пользовались. Отсутствие в нашем коде — не доказательство отсутствия в API. Поэтому дальше — источники 2 и 3.

### Источник 2 — официальная спецификация MAX Bot API

Официальная OpenAPI-схема, **Max Bot API v0.0.33** (схема снимается скриптом прямо с `dev.max.ru/docs`; зеркало: `github.com/max-messenger-bot/max-bot-api-schemas`, файл `schema.yaml`).

**Q1 — приём аудио. Тип есть в дискриминаторе вложений:**

```yaml
Attachment:
  discriminator:
    propertyName: type
    mapping:
      image: '#/components/schemas/PhotoAttachment'
      video: '#/components/schemas/VideoAttachment'
      audio: '#/components/schemas/AudioAttachment'     # <- вот он
      file:  '#/components/schemas/FileAttachment'
      sticker / contact / inline_keyboard / share / location
```

**Главная находка — MAX сам отдаёт расшифровку:**

```yaml
AudioAttachment:
  allOf:
    - $ref: '#/components/schemas/Attachment'
    - properties:
        payload:
          allOf:
            - $ref: '#/components/schemas/MediaAttachmentPayload'
        transcription:
          description: Аудио транскрипция      # <- ГОТОВЫЙ ТЕКСТ В ВЕБХУКЕ
          type: string
          nullable: true
      required:
        - payload
```

`payload` = `AttachmentPayload` (обязательное поле `url` — прямая ссылка на файл) плюс `token` (для переиспользования вложения).

Это не случайность: в апреле 2026 MAX выкатил встроенную расшифровку голосовых (кнопка «Т» рядом с дорожкой, бесплатно, всем, без подписки). Поле `transcription` в Bot API — она же.

**Q2 — отправка аудио.** `POST /uploads`, `UploadType` enum:

```yaml
UploadType:
  enum: [image, video, audio, file]
```

Ограничения из описания метода, дословно:

> `audio` — аудиофайлы. Доступные форматы: **MP3, WAV, M4A и другие**. Максимальный размер одного аудио: **до 256 МБ или длительностью не более 60 мин** — должны выполняться оба критерия.

Схема отправки: `POST /uploads?type=audio` → `url` (хост `vu.okcdn.ru`) → заливаем файл → получаем `token` → `POST /messages` с `{"type":"audio","payload":{"token":"..."}}`.

Два ограничения, которые бьют по продукту:

- `AudioAttachmentRequest`: *«Должен быть **единственным вложением** в сообщении»* → **аудио нельзя отправить вместе с инлайн-клавиатурой.** Кнопки придётся слать отдельным сообщением.
- Между загрузкой и отправкой нужна пауза, иначе `attachment.not.ready` («Если отправить сообщение с вложением сразу после загрузки, может возникнуть ошибка»). Ретраи с растущим интервалом.

Есть и индикатор состояния — `SenderAction` enum содержит `sending_audio` («Бот отправляет аудиофайл»). Аудио в протоколе — полноправный гражданин, не костыль.

**Q3 — потоковое. Полный список путей в схеме:**

```
/me  /me/commands  /chats  /chats/{chatId}  /chats/{chatId}/actions
/chats/{chatId}/pin  /chats/{chatId}/members/*  /subscriptions
/uploads  /messages  /messages/{messageId}  /videos/{videoToken}
/answers  /updates
```

Grep по всей схеме на `websocket|streaming|real.?time|voice|/calls` — **ноль попаданий.**

Транспорт ровно два, оба «запрос-ответ»:

- **Webhook** — `POST /subscriptions`, MAX шлёт HTTPS POST на наш endpoint, порт только 443, ответ 200 в течение 30 сек.
- **Long polling** — `GET /updates`, таймаут максимум 90 сек. В самой доке: *«этот способ не подходит для production-окружения»*.

Постоянной двусторонней сессии не существует ни в каком виде.

### Источник 3 — живой API и живое поле

- **Хост отвечает.** `POST https://platform-api2.max.ru/uploads?type=audio` без токена → `401 {"code":"verify.token","message":"No access token"}`. Эндпоинт живой. Токен пилота не трогал, в боевые беседы не писал — ничего не отправлялось.
- **Независимое подтверждение приёма аудио ботами:** в MAX работают сторонние боты-транскрибаторы («Войси», «Голос в текст»), которым пересылают голосовое сообщение и получают текст. Значит, голосовые до ботов **фактически доходят** — не только по схеме.
- **Официальная библиотека** `github.com/max-messenger/max-botapi-python` независимо описывает то же поле:
  ```python
  class Audio(Attachment):
      type: AttachmentType = AttachmentType.AUDIO
      transcription: Optional[str] = None
  ```
- **Официальный TS-клиент** `max-messenger/max-bot-api-client-ts` содержит `AudioAttachment` и `ctx.api.uploadAudio(...)` — отправка подтверждена вторым источником.

Противоречий между источниками **не найдено**. Все три сходятся: файлы — да, поток — нет.

## 3. Что осталось непроверенным

1. **Голосовое (кнопка «микрофон») vs аудиофайл — один и тот же `type: "audio"`?**
   В схеме отдельного типа `voice` **нет** — оно физически не может прийти ничем, кроме `audio` или `file`. Плюс наличие поля `transcription` именно на `AudioAttachment` практически не оставляет вариантов: расшифровывают в MAX именно голосовые. **Но своими глазами боевой вебхук с голосовым мы не видели** — у нас в логах таких событий нет, наш парсер их и не различает.
   *Проверяется за 10 минут:* один раз записать голосовое боту на пилоте и посмотреть сырой payload в `CanonicalEvent.raw`. Это единственная дыра в доказательствах, и она закрывается дёшево.
2. **Всегда ли `transcription` непустая.** Поле `nullable: true`. Неизвестно: приходит ли она сразу в первом вебхуке или с задержкой; есть ли лимит по длине; что с шумом и фоновой музыкой; расшифровывает ли MAX загруженный mp3-файл или только записанное голосовое. Качество расшифровки для салонной лексики (названия услуг, имена мастеров) не проверялось вообще.
3. **Длительность входящего аудио.** У `VideoAttachmentDetails` поле `duration` есть, у `AudioAttachment` — **нет**. Понять «это 3 секунды или 4 минуты» до скачивания файла нельзя.
4. **Мобильный клиент сжимает аудио** при отправке (десктоп позволяет слать оригинал). На качество расшифровки влияет, насколько — не измеряли.

## 4. Если голос есть — в каком виде

**В виде файлов. Строго асинхронно. Поток невозможен.**

Что это значит для решения:

**Realtime-модель (OpenAI Realtime) — не применима.** Она продаёт постоянную сессию: перебивание на полуслове, реакция на паузу, дуплексный звук. Транспорта под это в MAX нет ни одного. Покупать Realtime под MAX — платить за возможность, которую канал не пропустит.

**Применимая архитектура — и она сильно проще:**

```
голосовое -> вебхук: attachments[0].transcription (готовый текст!)
                          |
              существующий консьерж (текстовый, уже работает)
                          |
              ответ текстом   <- рекомендуемый путь
              (опционально: TTS -> /uploads?type=audio -> аудио-ответ)
```

Три следствия для сметы:

1. **ASR, скорее всего, покупать не нужно.** MAX отдаёт расшифровку сам и бесплатно. Классическая связка «скачать файл → Whisper → текст» нужна только как запасной вариант на случай пустой `transcription`. Это меняет порядок цены разговора о голосе.
2. **Работа сводится к «разобрать ещё один тип вложения»** в `parser.py` / `handler.py` — рядом с тем, что уже сделано для фото. Голос становится просто ещё одним способом ввода текста в существующего консьержа, а не новым продуктом.
3. **Голосовой ОТВЕТ — отдельное и куда более дорогое решение,** и его стоит обсуждать отдельно: нужен TTS, загрузка файла на каждый ответ, пауза против `attachment.not.ready`, и главное — **аудио нельзя отправить вместе с кнопками**, а весь наш UX построен на инлайн-клавиатурах. Отвечать голосом = ломать текущий сценарий записи.

**Рекомендация:** прежде чем считать любую цену — сделать шаг из п. 3.1 (записать одно голосовое боту на пилоте и посмотреть сырой payload). Это подтвердит или опровергнет бесплатный ASR, и только после этого смета вообще имеет смысл.
