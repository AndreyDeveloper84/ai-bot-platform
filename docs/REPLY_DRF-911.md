## №6 (2026-08-13): приёмка вскрыла дефект выдачи — DRF-1033. Чини, диагноз готов

Отбой предыдущей секции: работа окна не закончена. Живая приёмка владельца прошла на задеплоенном `4373bb5`, записи показались — **но одна бронь выведена дважды**, двумя одинаковыми секциями «Формула тела».

Дословно из `conversations_message` (VERIFIED):

```

• УЗ-кавитация — 1 зона с Тихонова Ольга в 2026-08-14T10:00:00+00:00

Формула тела:
• УЗ-кавитация — 1 зона с Тихонова Ольга в 2026-08-14T10:00:00+00:00
```

**Первопричину я нашёл и подтвердил замером на пилоте — не трать на неё время.** В `_booking_lookup_scopes` стоит `.values_list("tenant_id", "bot_user_id").distinct()`, а у `BookingRequest` задана сортировка по умолчанию (`apps/booking/models.py:421-424`, `ordering = ["-created_at"]`). Django при DISTINCT добавляет поле сортировки в выборку, и дедупликация ломается. Реальный SQL с пилота:

```sql
SELECT DISTINCT tenant_id, bot_user_id, created_at FROM booking_bookingrequest ...
```

У владельца две CONFIRMED-брони в одном тенанте с разным `created_at` → две пары вместо одной. Замер в контейнере worker: текущий запрос отдаёт **2**, он же с `.order_by()` — **1**.

**Фикс — одна строка:** сбросить сортировку перед `.distinct()`.

**Тест обязателен, красный до фикса:** две CONFIRMED-брони одного пользователя в одном тенанте → ровно **одна** секция, и ответ идёт по однотенантной ветке (тот самый byte-parity с тенантным путём, который ты закладывал). Обрати внимание: сейчас из-за лишней пары ответ ушёл в мультисалонный формат — с фиксом владелец увидит обычный однострочный вид, и это правильно.

**Что приёмка подтвердила как рабочее:** прошедшая бронь от 12 августа в выдачу не попала — фильтр будущего работает.

Задача в Linear — **DRF-1033**. Порядок: ветка от свежего `origin/dev`, фикс + тест, PR, зелёный CI, **перечитать этот файл перед merge**, merge обычный. Деплой потом, вместе с фиксом DRF-972, — отдельным GO.
