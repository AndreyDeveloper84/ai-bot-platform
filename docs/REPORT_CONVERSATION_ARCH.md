## Вопрос 1. Где проходит граница «цель → услуга» и кто ей владеет

**Рекомендация: каталог** — соответствие «цель → услуги/категории» как курируемые данные; движок получает уже разрешённое (`category_id`/набор категорий); доменный агрегат `Goal` не строить, пока канон его не определил.

### Что измерено под это

- **Движок ранжирует мастеров, а не услуги.** Единица скоринга — `SpecialistProfile`; `service_match` — подскор с весом 0.15, работающий от `category_id`/`price_max` (`recommendation_engine.py:371-415`). Цель же — утверждение про услуги («антицеллюлитный массаж помогает при цели X»). VERIFIED.
- **Каталог уже содержит паттерн «данные, заполняемые владельцем»:** `ServiceTemplate` (канонический сид с `requires_health_check`, `contraindications`, `is_popular`), `RegionalPricing` (курируемые вилки цен) — `services/models.py:78-213`. Таблица маппинга цель→категории/шаблоны ложится в существующий паттерн без новых архитектурных понятий. VERIFIED.
- **Канон объявляет Transformation Goal «центральной доменной сущностью»** (`01 Product/Ayla Product Principles.md`, §4.2), но: Core Domain Model её **не содержит** (`05 Architecture/Ayla Core Domain Model Specification.md` — слово Goal отсутствует, 0 совпадений; `03 AI System/Ayla Intent Model Specification.md:124-127` прямо констатирует: «определение находится вне Domain Model»); владелец хранения `explicit_goal` — **открытый вопрос** (`06 Safety and Governance/Consent Scope Registry.md:133`); маппинга цель→услуга в каноне нет нигде; `Recommendation Contract` не принимает цель во входы. VERIFIED.

### Цена каждого варианта

**Домен** (`Goal` как сущность с персистентностью, услуги правилом):
- Платим: определяем кодом то, что канон сознательно отложил (агрегат, консент-владелец, жизненный цикл) — фактически пишем канон задним числом; миграции, модель доступа, синк бот↔Mini App; знание «какие услуги под цель» всё равно надо где-то хранить — сущность его не порождает.
- Обратимость: **дорогая** — после появления потребителей агрегата откат тянет миграции и контракты.

**Движок** (`goal` как поле `RecommendationQuery`, вес в скоринге):
- Платим: знание о соответствии целей услугам переезжает в код скоринга — владельцем становится алгоритм, а не продуктовый эксперт; каждая правка контента = деплой; ломается прецедент экономической нейтральности (сегодня веса свободны от контентных факторов и это защищено assert'ом); поле не решает главное — откуда берётся соответствие.
- Обратимость: поле убрать легко, но контент, вросший в скоринг, извлекается больно. Средняя.

**Каталог** (маппинг как данные владельца):
- Платим: кураторская работа — кто-то должен заполнить и поддерживать соответствие (на тенанта: категории tenant-scoped, `services/models.py:25-37`); холодный старт на пустом маппинге; риск устаревания данных; нужен осознанный ответ на «под эту цель ничего не привязано».
- Обратимость: **дешевле всех** — дроп таблицы/сида, движок и домен нетронуты.

### Существенная оговорка (INFERRED)

Какой бы вариант ни выбрали, **слой разрешения «цель → категории» нужен всегда** — движок на вход принимает категории, а не цели. Вопрос только в том, где живёт знание и кто его редактирует. При варианте «каталог» движок вообще не меняется для однокатегорийных целей (`category_id` уже есть); для мультикатегорийных — точечное расширение до набора категорий. Учитывая факт §0.2 (category_id сегодня не передаётся ниоткуда), расширение интерфейса дешёвое — обратной совместимости почти не с чем ломать.

## Вопрос 3. Минимальный контракт `Goal`

Три требования из брифа: (а) `RecommendationQuery` смог принять цель; (б) цель переживает перезапуск и смену канала; (в) по ней строится воронка.

### Минимальный набор полей

| Поле | Тип | Зачем (какое требование закрывает) |
|---|---|---|
| `client_id` | UUID, FK | владелец цели; без него нет персистентности (б) и атрибуции (в) |
| `goal_key` | slug, NULL | ключ из списка — если §3 решится в закрытый список; детерминированный маппинг (а, в) |
| `goal_text` | str, NULL | исходная формулировка пользователя — если §3 решится в свободный текст; храним как сказано, даже когда распознано в ключ |
| `selected_at` | timestamp | точка отсчёта воронки (в) |
| `source_channel` | enum {bot, miniapp} | смена канала (б) + разрез воронки по каналу входа (в) |
| `is_active` | bool | одна активная цель на клиента; замена цели = новый ряд, старый закрывается (б, в) |

**Инвариант:** хотя бы одно из `goal_key`/`goal_text` не NULL. Оба могут быть заполнены (текст распознан в ключ).

### Как это стыкуется с движком (при варианте «каталог» из вопроса 1)

`RecommendationQuery` **не обязан** принимать `Goal` как объект. Вызывающая сторона разрешает активную цель клиента через маппинг каталога в `category_id` (или набор — точечное расширение) и передаёт движку как сегодня. Движок о целях не знает. INFERRED — проектное суждение на измеренных интерфейсах.

### Воронка — это события, а не поля контракта

Три обязательные эмиссии, каждая с `goal_key` (или признаком free-text): `goal_selected`, `recommendation_shown`, `booking_created`. Атрибуция записи к цели — через `goal_key`, пронесённый в момент рекомендации, а не через JOIN после факта. Замечание из канона: evidence point `goal established/updated` уже задекларирован (`Ayla MVP User Journey Specification.md:1602-1607`), но имена событий там «NOT_DEFINED до Measurement Framework» — наш контракт их фактически определяет, это надо будет вернуть в канон. VERIFIED (существование точки) / INFERRED (вывод про контракт).

### Сознательно НЕ входит в первый контракт

Приоритет цели, дедлайн, целевые метрики (вес, объёмы), множественные активные цели, история смен (закрытые ряды и есть история), прогресс по цели, consent-грамульность сверх существующего S2. Всё это не участвует в трёх требованиях брифа.

## §3. Развилка для владельца — НЕ РЕШЕНО, выносится

**Цель выбирается из закрытого списка или формулируется свободным текстом?**

### Сторона А. Закрытый список (чипы)

- **Получаем:** считаемую воронку (каждая когорта — ключ), детерминированный маппинг цель→услуги данными каталога, дёшево строится, дёшево проверяется на пилоте с одним салоном.
- **Платим:** обещание «расскажи, что хочешь изменить» урезается до меню; риск «моей цели нет в списке» (пункт «другое» возвращает свободный текст через чёрный ход, но уже без бюджета на его обработку); таксономию кто-то должен придумать и владеть ею; **противоречие канону**: `BOT-001:162` нормативно фиксирует «state their goal in free text», а `Product Principles §4.2` — «Ayla помогает сформулировать, но никогда не навязывает». Закрытый список = изменение канона или осознанное отклонение от него, зафиксированное решением.

### Сторона Б. Свободный текст

- **Получаем:** соответствие канону и продуктовому тезису («goal-first», начни с человеческого намерения); нет потолка «моей цели нет»; данные о том, как люди реально формулируют цели — топливо для будущей таксономии.
- **Платим:** на пилоте с одним салоном — бесконечный хвост формулировок и ноль сравнимых когорт, результат пилота по цели посчитать нельзя; требуется извлечение намерения → классификация в категории через LLM, то есть маппинг становится алгоритмическим и недетерминированным (владелец знания — алгоритм, см. цену варианта «движок» в вопросе 1); классификатор надо валидировать, а валидировать не на чем — корпуса формулировок нет.

### Сигналы, зафиксированные в артефактах

- Кнопка в коде названа `open_goal_select` — изначально предполагался **выбор** (`skill.py:643`). VERIFIED.
- Канон нормативен за **свободный текст** (`BOT-001:162`). VERIFIED.
- Онбординг-документ откладывает Goal selector **post-pilot** (`customer-onboarding-flow.md:103`). VERIFIED.

Три артефакта тянут в три стороны — это и есть подтверждение, что решение не принималось. Гибрид «чипы + пункт „своё"» существует как третий вариант (основная масса считается, хвост — нет), но выбор — за владельцем. **От его ответа зависит, можно ли вообще посчитать результат пилота по цели.**

- Deprecation: `CheckConstraint.check` → `condition` (Django 6.0 warning) — в новом коде оставлено `check=` для консистентности с существующими моделями (`appointments/models.py` имеет тот же warning); переименование — отдельной уборкой по всему репо.
