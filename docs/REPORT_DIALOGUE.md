### Ответ на вопрос 2 §15: перенос навыков в инструменты канону не противоречит

Проверял сам, не по брифу. Основания:

1. **«Does not own»** прямо относит prompt assembly, tool schemas, provider abstraction к ayla-ai-core (Roadmap §3.3, §6.3). Инструмент — легальный слой, не собственность Intent Model и не посягательство на неё.
2. **Прецедент команд памяти** (Does not own, последний пункт): разговорные формулировки распознаются как management speech act «исключительно для маршрутизации orchestration к владеющей capability» — не новый intent type, не расширение реестра, не смена контракта. Навык-инструмент — ровно этот паттерн.
3. **«Outputs»**: resolver не вызывает tools и не создаёт side effects. Перенос сохраняет границу: resolution порождает контракт, исполнение инструмента — orchestration/capability layer после resolution и (для side-effect) подтверждения.
4. Реестр типов заморожен (11 + `UNKNOWN`); инструмент типом не становится.

**Три натяжки, которые не противоречие, но требования к дизайну переноса:**

- `PROVIDE_CONTEXT` safety-sensitive, а persistence `context_fact` whitelist-ограничен (Roadmap §3.4, CAP-001). Профиль питания (35 полей) пишется инструментом через Ayla API — это capability execution, канонически чисто, но **нельзя** пытаться провести эти данные через persistence-правила resolver'а (ему писать запрещено, CSR §5.1).
- Инвариант «`evidence` не пуст для `resolved`» с дословным `fragment` — обязателен и при tool-маршрутизации. Это и есть разрыв DRF-1273; перенос его не создаёт и не закрывает.
- 5-шаговая FSM анкеты — orchestration на стороне capability, а не resolver clarification: предел «2 подхода к уточнению» на неё не распространяется, но и смешивать эти два механизма нельзя (иначе слоты FSM будут выглядеть как нарушение clarification-бюджета).

### Ответ на вопрос 3 §15: раскладка и самое рискованное место

1. **Шаг 0.** Свой worktree от свежего `origin/dev` (`ai-bot-platform-drf1273`), ветка `feat/drf1273-output-contract`, PR против `dev`. Основное дерево сейчас на `feat/live-shadow-stage1` — не трогаю.

План: resolver-проход модели (structured output, 16 полей, обязательный verbatim `fragment`) + **детерминированный валидатор инвариантов** (`blocked_safety ⇔ safety_flags ≠ []`, UNKNOWN-правила, enum'ы `clarification_reason/effect`, `status_reason`). Проверка — живой ход на пилоте + негативный `out_of_scope`.
3. **DRF-1268.** Шесть навыков питания → tool schemas на глобальной тропе. **Самое рискованное место** — эмиссия контракта моделью с verbatim evidence. Инвариант «`evidence` не пуст для `resolved`, `fragment` — дословная цитата» означает: если модель сфабрикует fragment, контракт формально есть, а прослеживаемости нет — та самая непрозрачность через модель вместо регулярок. Лечение детерминированное: каждый `fragment` обязан быть подстрокой нормализованного текста пользователя, иначе результат отбраковывается в `unresolved/low_confidence`.
