### Решение по §3 — в чью очередь падает задача

**Правило адресации:**
1. Ищем активные per-tenant диалоги пользователя по `(channel, channel_user_id)` (tenant ≠ sentinel, `is_active`). Если есть — задача создаётся на **тенантном диалоге самого свежего** (по `last_message_at`, tie-break `created_at`) в `tenant_scope(T)`. Салон — та сторона, которая реально может помочь; заодно `create_admin_task` штатно глушит тенантный диалог (включая booking-callback'и — registry guard).
2. Если тенантного контекста нет — задача на **глобальном диалоге** в `tenant_scope(sentinel)`: платформенная очередь. Транскрипт глобального диалога — релевантный контекст для платформенного оператора. Вариант «честный отказ — уточните салон» отвергнут: пользователь зовёт человека именно потому, что бот не помог; отказ без эскалации воспроизводит исходную проблему.
3. Несколько тенантных контекстов → **последний активный**, без вопроса пользователю. Обоснование: детерминировано и не добавляет UX-раунд-трип на аварийном пути (пользователь, зовущий человека, уже фрустрирован; вопрос «какой салон?» ухудшил бы именно этот сценарий). Это эвристика, а не продуктовая политика — если владелец захочет «спросить салон», это отдельная задача (кандидат в Linear ниже).

**Глушение глобального диалога (главный риск брифа):**
- Guard в начале reply-логики глобального обработчика, ДО safety/concierge: молчим, если (а) `global_conversation.state == HUMAN_HANDOFF` (случай платформенной задачи — флипает сам `create_admin_task`, отпускает DRF-980), ИЛИ (б) существует открытая (OPEN/IN_PROGRESS) handoff-AdminTask по этому `(channel, channel_user_id)` в любом тенанте (случай тенантной задачи — отпускается автоматически при закрытии задачи, без какого-либо bookkeeping связей между диалогами).
- Во время мьюта пользовательский ход записывается (parity с тенантным путём), ответ не отправляется. Повторное «оператор» во время активной эскалации НЕ создаёт дубликат задачи (guard раньше триггера).
- Пользователь не получает ответов ни по одному диалогу: тенантный глушит registry guard, глобальный — новый guard.

**Триггер:** детерминированная ветка до LLM (по образцу `cb:book:*`, handler.py:642), `elif matches_human_handoff_request(event.text)` после safety и до onboarding/concierge. Список НЕ дублирую — импорт `_HANDOFF_KEYWORDS` из `apps/skills/human_handoff/skill.py`.

**Ложные срабатывания (§4.4):** «я сам менеджер» / «работаю агентом» текущий словарь вообще не матчит (кириллических «менеджер»/«агент» в нём нет — это DRF-972). Реальная ловушка одна: «мне не нужен оператор». Голой подстроки недостаточно → минимальный детерминированный фильтр: вхождение ключевого слова отклоняется, если в окне ~15 символов перед ним стоит отдельное «не»/«без»; матч есть, если хотя бы одно вхождение не отрицано. Классификатор не строю (гиперинженерия).

**Ответ пользователю:** переиспользую `_HANDOFF_REPLY` («Передаю менеджеру — ответят в течение 30 минут»). 30 минут ничем не подкреплено (ни SLA, ни нотификаций оператору) → кандидат в Linear, текст не выдумываю.

**Эскалация не требуется**: решение укладывается в ориентиры §3 брифа (адресовать салону при контексте, глобальный тенант существует, «последний активный» назван допустимым правилом).

### Кандидаты в Linear (создаёт главное окно)
1. **Текст `_HANDOFF_REPLY` обещает 30 минут, которые система не гарантирует.** Нет ни SLA-механики, ни уведомления операторов. Предложение: либо поменять текст на нейтральный («Передаю менеджеру — ответим здесь, как только оператор освободится»), либо завести SLA-нотификацию. Продуктовое решение.
2. **DRF-972 после этого фикса становится осмысленной**: расширить словарь русскими формами («менеджер», «администратор», «человек») — теперь триггер реально достижим на глобальном пути.
3. **Правило «последний активный тенант» при множественных контекстах** — эвристика; если хотим «спросить пользователя, какой салон», это отдельная продуктовая задача.
4. **Платформенной очереди (sentinel) нужен просмотрщик**: задачи без тенантного контекста падают на тенанта `global_bot`; проверить, что у платформенной команды есть к ним доступ в админке (UNKNOWN — не проверял, за границами брифа «не строить операторский интерфейс»).
