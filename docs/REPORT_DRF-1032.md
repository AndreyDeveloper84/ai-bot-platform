## Резюме для главного окна (60 секунд)

1. **Бэкенд-эндпоинты существуют и пригодны, но ни один из них не отвечает на вопрос «какие визиты состоялись».** `section=history` — это «терминальные ИЛИ прошедшие», то есть отменённые и неявки в одной куче с состоявшимися. Политику OD-H2 придётся реализовывать на боте фильтром по `derived_status`. Бэкенд менять для этого не нужно.
2. **Клиент бота к `me/bookings` уже написан — и он нерабочий.** `get_user_appointments` разбирает форму `{upcoming, history}`, которой бэкенд не отдаёт, и не шлёт `section`. Против реального бэкенда метод вернёт **пустой список**, не ошибку. Тесты зелёные, потому что мокают ту же выдуманную форму. Это ровно случай «функция есть, живой возможности нет» из §6 брифа.
3. **Развилка §4 решается не аргументом, а устройством кода: разделить будущие и прошлые записи технически нельзя.** Вход один — детектор `is_personal_booking_lookup`, и «мои визиты» он сегодня вообще не ловит (слова «визит» в нём нет). Расширив детектор, мы получаем одну команду и один ответ. Значит либо весь ответ из бэкенда, либо весь из зеркала; «будущие из зеркала, история из бэкенда» — не архитектурный выбор, а невозможность. **Моё предложение — переводить целиком, в этой задаче.** Перевод при этом *сокращает* код DRF-911, а не наращивает: кросс-тенантную агрегацию бэкенд делает сам.
4. **«Записаться ещё» реализуется одной кнопкой без новой машины состояний.** История отдаёт ровно те идентификаторы, которые ожидает существующий вход `cb:book:pick_master:<specialist>:<service>`; тенант резолвится по мастеру. Новый код — только сборка кнопки и обработка отказов.
5. **Оба внешних гейта подтверждаю независимо:** до DRF-1048 список состоявшихся визитов пуст by construction, до DRF-1049 кнопка повтора получает `"None"` вместо услуги. Оба — вне моего объёма, оба обязаны быть закрыты до включения фичи на пилоте.
6. Уязвимости класса DRF-1036 в этих трёх эндпоинтах **не нашёл**: субъект берётся только из заголовка, тело не читается, чужой id даёт 404. Останавливаться и эскалировать не потребовалось.

**Уточнение 1 (VERIFIED) — `section=history` ≠ «состоявшиеся визиты».**
`records_api.py:331-337`: `Q(status__in=TERMINAL_STATUSES) | Q(start_datetime__lt=now)`. Терминальные — `completed`, `cancelled`, `no_show` (`appointments/models.py:33`). Плюс любая прошедшая запись **в любом статусе**, включая протухшие `pending` / `awaiting_payment` / `confirmed`. Статуса `failed` в модели нет вообще — «технические сбои» из OD-H2 в данных не выражены.
⇒ политику «только состоявшиеся» обеспечивает не бэкенд, а фильтр бота по `derived_status`.

**Уточнение 2 (VERIFIED) — «последние пять» нельзя получить через `limit=5`.**
Пагинация курсорная по `start_datetime` (`records_api.py:216-255`), `limit` по умолчанию 20, максимум 100 (`:66-67`), курсор — ISO-строка, не opaque-токен. Поскольку в выдаче перемешаны отменённые и неявки, `limit=5` вернёт пять *любых* прошлых записей, среди которых состоявшихся может не быть. Правильно: тянуть страницу с запасом и отбирать пять на стороне бота; курсор — внутренний механизм добора, а не пользовательская пагинация (OD-H3 запрещает пользовательскую).
Побочно: тай-брейк по `id` есть в `ORDER BY`, но отсутствует в фильтре курсора (`:231-246`) — на границе страницы записи с одинаковым `start_datetime` могут быть потеряны. Для нашего сценария (одна страница) неактуально; отмечено как ограничение бэкенда.

**Уточнение 3 (VERIFIED) — `repeat-intent` не проверяет актуальность вообще.**
`records_api.py:413-431`: единственная выборка — бронь клиента по id; ответ собран из полей исторической строки; `suggested_slots` — хардкод `[]`. Не проверяются ни активность услуги, ни активность мастера, ни связь между ними, ни цена, ни статус салона. Спроектированного в Tau `can_prefill_booking` (`docs/screens/customer-records-flow.md:618`) на бэкенде **не существует**.
⇒ ответ на §22 документа владельца: сегодня eligibility физически может жить только на боте. Это не архитектурный выбор, а фактическое состояние.

**Уточнение 4 (VERIFIED, независимо подтверждено REPLY №1) — `repeat-intent` сломан для наших броней.**
XOR-констрейнт `appointment_exactly_one_service_source` (`appointments/models.py:198-207`) разрешает ровно одно из `service` / `salon_service`. `_build_item` XOR учитывает (`records_api.py:166`), `repeat-intent` — нет (`:426`), поэтому для салонной брони возвращает литеральную строку `"None"` с HTTP 200. По данным пилота у единственной брони `service_id IS NULL` ⇒ сломано для 100% броней бота. Заведено главным окном как **DRF-1049**; в моём объёме не чинится.

Дополнительно (VERIFIED, влияет на разбор ответа): сериализаторы в рантайме не применяются — вьюхи возвращают словари, поэтому `price` / `last_price` приезжают **числом** (DRF-энкодер конвертирует `Decimal` → float), хотя схема объявляет строку. Разбор на боте должен принимать оба варианта.

### A.2. Резолв субъекта — гипотеза брифа §2 подтверждена; у неё есть обратная сторона

**C.7. Набор статусов «состоявшегося визита» — одна константа.**

**C.8. Наблюдаемость.**
События из §39 документа владельца через существующий `emit` (`apps/events/services.py:54-131`). ## E. Влияние на машину состояний

Новой машины нет. Повтор входит в существующую **в точке «мастер и услуга уже выбраны»**:

```
визит в списке
   └─ «Записаться ещё»
        └─ repeat-intent (историческая пара)
             └─ проверка актуальности по бэкенду
                  ├─ валидна → cb:book:pick_master:<specialist>:<service>
                  │             → route_booking_callback → выбор даты → слот → подтверждение
                  └─ невалидна → разумная альтернатива (мастер / услуга / пара), техтекста нет
```

Существующие гарантии сохраняются: тенант резолвится по мастеру (`handoff.py:332-341`); бессервисный `pick_master` невозможен — скилл сам отдаёт «контекст устарел» при отсутствии услуги (`skill.py:414-419`); инвариант NEED-FIRST (дата и слот запрещены до определённой услуги) не нарушается, потому что услуга известна до входа.

## G. Риски

### G.1. Блокеры пилота (закрываются вне этой задачи)

- **G-1. Нет состоявшихся визитов и не появится (DRF-1048).** До решения владельца список пуст by construction. Реализация от этого не отменяется, но включать фичу пилоту бессмысленно: пользователь увидит «визитов пока нет» после реального визита. Требование к реализации: набор статусов вынесен в одну константу (C.7), чтобы любой из четырёх вариантов применялся правкой одной строки.
- **G-2. `repeat-intent` отдаёт `"None"` (DRF-1049).** Кнопка «Записаться ещё» не заработает для 100 % пилотных броней. Требование к реализации: бот обязан валидировать ответ и не строить кнопку на мусоре — иначе пользователь получит тупик вместо отказа.
- **G-3. Порядок деплоя.** История не зависит от `ayla_user_id` (A.2.1), но **продолжение записи зависит** — `provider.py` берёт `client_id` именно оттуда. Значит «Мои визиты» технически может ехать до identity-моста, а «Записаться ещё» — нет. Порядок владельца (DRF-1043 → DRF-1035 → E2E → DRF-1032) остаётся; факт снимает риск, а не меняет очередь.

### G.2. Блокеры продакшена

- **G-4. Связывание прокси с аккаунтом стирает видимую историю** (`users/services.py:202-208`). Пилота не касается (связывание выключено), но обещание «Ayla помнит ваши визиты» до DRF-1037 включать в продакшене нельзя.

### G.3. Известные ограничения (принимаются)

- **G-5. Тихая пустота.** Неверный внешний идентификатор даёт пустую историю, а не ошибку. Смягчение — телеметрия (C.8), устранить полностью нельзя: это свойство ленивого резолва на бэкенде.
- **G-6. Отказ бэкенда = отсутствие истории.** Прямое следствие OD-H1 и §30. Зеркало как fallback не используется.
- **G-7. Курсор без тай-брейка по `id`** — на одной странице неактуально.
- **G-8. Историческое имя услуги** приходит из снапшота брони (`records_api.py:161-169`) — если услугу переименовали, в истории останется старое имя. Это правильно (история описывает прошлое), но при повторе рядом может оказаться новое имя. Учесть в текстах.

### G.4. Follow-up

- **G-9. DRF-1034 сужается, но не закрывается.** Призрак перестанет быть виден в выдаче, но напоминания строятся по зеркалу и продолжат отправляться. Операционная часть остаётся за DRF-1034. Здесь не чиню.
- **G-10. DRF-1033 частично устаревает.** Его фикс (`handoff.py:639`, `.order_by()` перед `DISTINCT`) живёт в `_booking_lookup_scopes`, который при переводе на бэкенд уходит. Код и его регресс-тест станут неактуальны. **Молча не удаляю** — выношу решением в §H-1; если развилка решается в пользу переноса, удаление должно быть явным и отмеченным в задаче DRF-1033, а не побочным эффектом.
- **G-11. Тап `cb:menu:my_bookings` на глобальном пути не обрабатывается** (A.5). Отдельный мелкий дефект, в объём не входит; кандидат в задачу.
- **G-12. Единый эндпоинт проверки актуальности** (`can_prefill_booking` из спеки Tau) — кандидат в бэкенд-follow-up. Сегодня бот склеивает 1–2 вызова; если склейка начнёт разрастаться в бизнес-правила, это сигнал остановиться и вернуть правило на бэкенд (§22).

## H. Новые продуктовые решения (только то, что действительно требует владельца)

**H-1. Развилка §4 — будущие записи. Моё предложение: переводить в этой задаче, целиком.**

Аргумент не в архитектурной красоте, а в устройстве кода: **вход один**. «Мои записи» и «Мои визиты» ловит один детектор (`is_personal_booking_lookup`), и его расширение на слово «визит» (без которого задача не решается — A.5) физически сливает обе формулировки в одну команду с одним ответом. Разделить источники можно было бы только по формулировке пользователя, то есть показывать разную правду в зависимости от того, какое слово он выбрал, — это ровно та внутренняя несогласованность, которую владелец запретил.

Цена перевода меньше, чем кажется: кросс-тенантную агрегацию бэкенд делает сам (`records_api.py:312-323`), поэтому `_booking_lookup_scopes` + `_lookup_in_tenant` + `_compose_multi_tenant_text` (≈130 строк, добавленных DRF-911) **удаляются**, а не переписываются. Появляется одно новое свойство — сетевой вызов на пути, который сегодня гарантированно не падает; отсюда требование честной ошибки и телеметрии.

Что нужно от главного окна: решение по объёму и указание, как поступить с кодом и регресс-тестом DRF-1033 (G-10).

**H-2. Терминология. Моё предложение: «Мои визиты» — в чате, «Записи» — в Mini App, менять Mini App не нужно.**

Проверил conventions: в чат-текстах бота канонизировано «Мои записи» (`menu/matching.py:437`, `menu/replies.py:35`, `welcome/skill.py:502`); «История» в Python-коде отсутствует вовсе, она есть только в Mini App; «Мои визиты» встречается только в legacy-кнопках за выключенным флагом. Спека Tau (`docs/screens/customer-records-flow.md`) описывает **другую поверхность** — MAX webview Mini App, вкладку «Записи», и включает в «Историю» отменённые и неявки, что расходится с OD-H2. Конфликта между решениями нет: поверхности разные, решение владельца новее.

Предложение: в чате раздел состоявшихся называть «Мои визиты» (точнее отражает политику), будущие оставить «записями», Mini App не трогать. Если владелец предпочтёт единый термин на обеих поверхностях — это правка спеки Tau и Mini App, то есть отдельная задача, а не эта.

**H-3. Что показывать, пока DRF-1048 не решён.** Вопрос не мой (политику не переопределяю), но реализация обязана знать ответ, чтобы не выдавать пользователю после реального визита «визитов пока нет». Прошу зафиксировать вместе с решением по DRF-1048: до его закрытия фича на пилоте **не включается**, либо включается с формулировкой пустого состояния, согласованной владельцем.

## §3.4. Ревью — две находки исправлены, обе по делу

Два независимых прохода Code Reviewer, дружественный и состязательный. Оба независимо пришли к одному и тому же главному дефекту, и он был настоящим.

**Находка 1 (обе стороны) — тихая пустота выжила в самом парсере.** Первый коммит объявил войну молчаливому пустому результату и оставил его живым на соседней ветке собственного условия: любое тело без ключа `items` — старая выдуманная форма, `{"data": null}`, переименование поля на бэкенде — проваливалось в `_as_rows` и возвращало `[]` без единой строчки лога. Состязательный проход показал пять таких входов эмпирически. Это ровно тот инцидент, ради предотвращения которого заведён тикет: клиенту говорят «у вас нет визитов», пока Ayla отвечает данными, и нигде ничего не краснеет.

Исправлено: принимаются только `{items: [...]}` и голый список, всё остальное логируется и поднимает `BookingUnavailableError` — как `_ok` уже поступает с нечитаемым JSON и по той же причине, дословно записанной в его докстринге. Мусорные записи внутри распознанной страницы по-прежнему пропускаются: битая строка — не отказ сервиса. То же правило применено к `get_booking_detail`, который на не-словарном теле строил карточку без услуги, мастера и даты.

**Находка 2 (обе стороны) — тест на 404 проверял базовый класс.** `BookingUnavailableError` тоже наследует `BookingAPIError`, поэтому тест остался бы зелёным, если бы 404 когда-нибудь уехал в 5xx-ветку `_fail_status`. А та ветка пишет отказ в breaker, который **общий на весь booking-трафик процесса**: пользователь, несколько раз тапнувший устаревшую запись, открыл бы его для всех. Сужено до `BookingBadRequestError` + `status_code == 404`.

**Прочее по ревью, исправленное там же:** `derived_status` стал `str | None` — симметрично уже обоснованному `price` (различие «поля нет» / «поле пустое» существенно: при version skew фильтр отбросил бы все строки и показал пустую историю против непустого бэкенда); `RepeatIntentUnusableError` несёт `field` и `value`, потому что известный `"None"` из DRF-1049 и произвольный мусор — разные тикеты; `suggested_slots` оставляет только строки вместо стрингификации чего угодно; идентификаторы повтора нормализуются; `_parse_price` ловит `OverflowError` и отбрасывает `inf`/`nan`, чтобы в чат не ушло «inf ₽»; `raw` помечен `repr=False` (карточка визита несёт заметки и платежи — один будущий `logger.info` вывалил бы всё); новые символы экспортированы из пакета.

**Фактическая поправка к моей формулировке.** Оба ревью независимо показали: при `BOOKING_VIA_AYLA_REST` включённом у `AylaYClientsAdapter.get_user_records` **нет ни одного достижимого вызывающего** — оба места ветвятся раньше (`tools.py:1698-1703`, `tools.py:2710-2712`). Я называл его «единственным продовым вызывающим». Корректность фикса это не меняет, но объясняет, почему дефект разбора жил так долго. Докстринг исправлен, тест совместимости переписан так, чтобы гонять цепочку **через адаптер**, а не только через клиент — иначе он остался бы зелёным, если бы кто-то позже передал `section="history"` из `provider.py`.

**Атаки, которые не прошли** (проверено состязательным проходом эмпирически, не рассуждением): `uuid.UUID` не бросает ничего кроме `ValueError` на достижимых входах; исключение повтора не открывает breaker; path-injection через `booking_id` невозможен — билдер percent-кодирует сегменты; позиционное конструирование DTO не сломано; фейки протокола целы; тесты не вакуумны — снятие `section` или полей DTO красит ровно то, что должно; границы объёма не нарушены.

**Оставлено follow-up'ом** (зафиксировано в коде и здесь, не чинится в этом PR): `_translate_errors` в `provider.py:341-359` схлопнет `RepeatIntentUnusableError` в общий `YClientsAPIError` — значит слой отображения должен ловить его **до** адаптера, либо адаптеру нужна своя ветка трансляции; правка `provider.py` выходит за границы условия 1. Отдельно: постраничный добор нужно писать с потолком по образцу `_get_all_rows`, а курсор бэкенда фильтрует только по `start_datetime`, не включая тай-брейк по `id`, — на границе страниц две записи с одинаковым временем в разных салонах могут разойтись (чинится на стороне Ayla, здесь — не строить на этом гарантию «ровно N визитов»).

# ЧАСТЬ 4. Контракт проверки актуальности повтора — доразведка (2026-08-13)

Сделано в ожидании E2E DRF-1035, кода не написано. Цель — ответить на три вопроса до начала реализации: сколькими вызовами различаются сценарии отказа, не разрастается ли это в бизнес-правило (§22 документа владельца), и какая цена считается «текущей».

## §4.1. Авторитет — один вызов, и он же различает две из трёх причин

Единственный эндпоинт, который валидирует **комбинацию** «мастер + услуга», — слоты:
`GET /api/v1/internal/specialists/{id}/slots/?service_id=<uuid>&date=<YYYY-MM-DD>` (`users/internal_catalog_api.py:44-68`, auth `IsInternalBearer`, тот же токен, что у остальных чтений).

Внутри он гоняет **тот же резолвер, что и создание записи** — `resolve_bookable_service` (`services/service_resolver.py:59-135`); в докстринге прямо сказано: «Used identically by the internal slots path and CreateBookingService — do NOT add a second resolution path elsewhere». Это и есть ответ на §22: **правило остаётся на бэкенде**, слоты — его же голос.

Ответы (VERIFIED по коду):

| Что вернулось | Что это значит |
|---|---|
| `200`, `slots` непустой | повтор возможен |
| `200`, `slots: []` | пара валидна, но день нерабочий или занят — **это не отказ**, а «предложи другую дату» |
| `404`, тело `{"error": {"code": "NOT_FOUND", "message": "Service not found"}}` | услуга снята **ИЛИ** связь мастер↔услуга снята **ИЛИ** услуга чужого тенанта — объединено намеренно, «no existence leak» (`service_resolver.py:33-45`) |
| `404`, тело `{"detail": …}` без `error.code` | **мастер вне каталога**: `status != ACTIVE` ИЛИ `is_available=False` ИЛИ `user.is_active=False` (`users/specialists_api.py:430-437`) |
| `400 MISSING_PARAM` / `INVALID_PARAM` | ошибка вызова, не состояние каталога |

**Две формы 404 различимы на стороне бота уже сегодня, без нового кода.** `_fail_status` (`booking_client.py:725-743`) кладёт `error.code` в `BookingBadRequestError.code`: у «услуги» это `"NOT_FOUND"`, у «мастера» — `"unknown"`, потому что тело не несёт `error.code`.

Почему формы разные — проверено до конца, потому что на первый взгляд кажется, что кастомный обработчик схлопнет обе. Он не схлопывает: `APIView.handle_exception` передаёт обработчику **исходное** исключение, а преобразование `Http404 → NotFound` живёт внутри дефолтной функции DRF. Поэтому `Http404` от queryset мастера не попадает в ветку `isinstance(exc, NotFound)` кастомного обработчика (`djangoProject/exception_handler.py:102-107`), уходит в fallback `drf_default_handler` (`:119`) и рендерится дефолтным `{"detail": …}`. Услуга же возвращается вьюхой вручную как `{"error": {...}}` (`users/specialists_api.py:250-254`).

**Риск, который из этого следует (важный).** Различение держится на побочном эффекте, а не на объявленном контракте. Одна безобидная правка обработчика на стороне Ayla — добавить `isinstance(exc, Http404)` в ветку `NOT_FOUND` — молча схлопнет два случая, и бот начнёт говорить «услуга больше не доступна» человеку, у которого на самом деле уволился мастер. Ни один тест этого не поймает. Поэтому: закрепить обе формы контрактным тестом на стороне бота **и** предложить бэкенду машиночитаемую причину (см. §4.4).

## §4.2. Третье различение — «услуга снята» vs «связь распалась»

Слоты их не разделяют. Один дополнительный вызов, любой из двух:

- `GET /api/v1/internal/catalog/salon-services/{id}/` → `is_active=false` ⇒ услуга снята; `true` ⇒ значит распалась связь.
- `GET /api/v1/internal/catalog/specialist-services/?specialist=<id>&salon_service=<id>&is_active=true` → пусто ⇒ связь снята; строка есть ⇒ снята услуга. **И этот вариант заодно отдаёт цену** (`services/internal_api.py:58-75`, фильтры `tenant, specialist, salon_service, is_active`).

Второй предпочтительнее: одинаковая цена вызова, но полезной нагрузки больше.

**Итого вызовов:** счастливый путь — **1** (слоты), плюс 1, если показываем цену до подтверждения. Отказ — **2**. Это не «склейка бизнес-правил на боте»: решение принимает бэкенд, второй вызов нужен исключительно чтобы объяснить человеку, что случилось.

**Инвариант реализации, который надо соблюсти буквально:** сначала слоты, потом объяснение. Если бот начнёт решать по `specialist-services` (там ведь тоже есть `is_active`), он продублирует правило и разойдётся с бэкендом — например, на мастере, у которого связь активна, но профиль деактивирован.

## §4.3. Цена — нашёл живое расхождение, шире DRF-1032

Проверял, откуда брать «текущую цену» по OD-H4, и обнаружил, что бот и бэкенд считают её **из разных полей**.

- **Бэкенд создаёт бронь** по `resolved.price` (`create_booking_service.py:94, 269-280`), а для салонной услуги резолвер берёт `link.price` — цену **ребра** `SpecialistService` (`service_resolver.py:126-133`). Поле обязательное, `MinValueValidator(1)` (`services/models.py:434-437`).
- **Бот показывает** `CatalogService.price_from` (`tools.py:2905`), которое зеркало заполняет из `SalonService.base_price` (`apps/catalog/services/http_client.py:440`). Поле **nullable** (`services/models.py:354-358`).

То есть в квоте пользователю называется базовая цена салона, а бронь создаётся по цене конкретного мастера. Если они разошлись — человеку называют не ту сумму; если `base_price` пуст, бот говорит «точную цену озвучит администратор», хотя цена у ребра есть.

Это **не дефект DRF-1032**: расхождение существует в текущем booking-флоу независимо от истории. Но для «Записаться ещё» оно критично — OD-H4 требует показывать текущую цену и делать изменение видимым, а показывать мы будем не то поле. Практический вывод для реализации: цену повтора брать из `specialist-services.price`, а не из зеркала.

**Кандидат в отдельную задачу** (не чиню здесь): «цена в квоте берётся из `base_price` зеркала вместо цены ребра, по которой реально создаётся бронь».

## §4.4. Предложение по §22 — минимальный backend follow-up

Расшифровка причины сейчас стоит боту одного лишнего вызова и держится на форме тела ответа. Обе проблемы снимаются одним аддитивным изменением на стороне Ayla: добавить в 404-ответ слотов машиночитаемую причину, например `{"error": {"code": "NOT_FOUND", "reason": "master_unavailable" | "service_inactive" | "link_inactive"}}`.

Аргумент, почему это не нарушает «no existence leak»: правило скрытия защищает **анонимного** вызывающего от разведки чужого каталога. Здесь поверхность внутренняя, вызывающий — сервисный токен бота, и он и так знает обе сущности: он пришёл с ними из истории того же самого клиента. Раскрытие причины именно на internal-поверхности не даёт злоумышленнику ничего нового.

Это ровно тот «минимальный backend follow-up», о котором говорит §22 документа владельца. **В объём DRF-1032 не тащу** — пилот проходится существующими вызовами; фиксирую как кандидата и жду решения.

## §4.5. Что из этого уже умеет бот

Проверено по коду: **нового транспорта почти не нужно.**

- Слоты — `get_available_times(specialist_id, date, service_id)` (есть), даты — `get_available_dates` (есть).
- Различение причин — доступно через `BookingBadRequestError.code` (есть, после PR #1175 код едет в исключении).
- Цена ребра и факт связи — `catalog/specialist-services/` уже вызывается внутри `get_services(specialist_id=…)` (`booking_client.py:777-786`), но там результат используется только как фильтр списка и **цена ребра отбрасывается** (`_service_from_wire` читает `base_price`). Для повтора нужен узкий метод, возвращающий саму строку ребра, а не отфильтрованный каталог: `get_services` тянет весь каталог тенанта и требует активного tenant-scope (`_require_tenant_id`), что на глобальном пути придётся открывать отдельно.

**Вывод:** к транспорту добавляется один точечный метод (строка ребра по паре мастер+услуга). Всё остальное — существующие вызовы.

## §4.6. Запрос среза к главному окну (по приглашению REPLY №1)

Нужны два факта с пилота, чтобы понять, расхождение цен теоретическое или живое:

1. По тенанту «Формула тела»: сколько строк `SpecialistService`, у которых `price` отличается от `salon_service.base_price`; и сколько таких, где `base_price IS NULL`, а `price` заполнена.
2. Профили мастеров пилота: значения `status`, `is_available`, `user.is_active` — чтобы понять, встречается ли сценарий «мастер вне каталога» на пилоте вообще, или ветка UX для него пока умозрительная.

**Порядок проверки актуальности внутри `prepare_repeat`** (из части 4, инвариант обязателен): сначала слоты — они авторитет, потому что гоняют тот же резолвер, что и создание записи; только при отказе — уточняющий вызов, чтобы отличить `service_unavailable` от `link_unavailable`. Решение принимает бэкенд; второй вызов нужен исключительно для формулировки ответа человеку.

## §6.5. Адаптеры — тонкие

**Глобальный путь, `apps/orchestrator/handoff.py`.** `route_global_booking_lookup` перестаёт быть местом бизнес-логики и становится адаптером: вызвать способность → отдать результат форматтеру → вернуть `DiscoveryReply(text, action_data)` с клавиатурой. ## §6.6. Tool security (§14.G, §5 документа)

Аргументы будущего инструмента — **только** `scope` (`upcoming`|`history`) и `limit`. Ни `ayla_user_id`, ни `tenant_id`, ни `appointment_id` чужого субъекта: субъект берётся trusted runtime'ом из `bot_user` → `bot:{channel}:{channel_user_id}`, а бэкенд резолвит его из заголовка и фильтрует `client=request.user`. LLM сообщает намерение, идентичность определяет runtime — ровно инвариант §5.

## §7.2. Решения, принятые по ходу

**1. Ответ покрывает и предстоящие записи, и визиты.** H-1 требует единого источника, а детектор после DRF-1055 ловит и «мои записи», и «мои визиты» — одна команда. Значит один ответ: сверху предстоящие, ниже последние визиты. Две секции из одного источника не могут противоречить друг другу.

**2. Отказ половины ответа — это отказ.** Если предстоящие прочитались, а история упала, показать только первую половину нельзя: список будет выглядеть полным, не будучи им. Отвечаю честной временной ошибкой.

**3. Пустой список слотов — не отказ.** Проверка актуальности спрашивает слоты на сегодня; пустой ответ означает «сегодня занято», а не «повторить нельзя». Иначе бот уводил бы человека от мастера, свободного завтра.

**4. Никаких падежей в текстах.** Первый прогон дал «у Инна» — имя приходит в именительном, а русский требует родительного. Склонять чужие имена по эвристике нельзя, поэтому мастер отделён разделителем: «Массаж спины · Инна · 12 августа». То же в тексте повтора. Это нашли тесты, а не ревью.

**5. Цена повтора — из ребра `SpecialistService.price`**, а не из `base_price` зеркала: именно ребро бэкенд ставит в новую запись. На пилоте поля совпадают (232/232), но это разные поля, и расхождение станет живым при первой же индивидуальной цене.

**6. `closed_by` заведён, но пуст.** OD-V1 требует различать, кто закрыл визит; на бэкенде такого поля пока нет (проверил по `5c9abea`). Поле в DTO есть, код нигде не предполагает, что все `completed` равны. Когда бэкенд начнёт отдавать источник — заполнится без переделки.

# ЧАСТЬ 8. Ревью реализации и правки (2026-08-15)

Два прохода Code Reviewer, дружественный и состязательный. Оба независимо нашли **одну и ту же пару блокеров** — и оба указали на общую причину, которая важнее самих дефектов.

## §8.1. Причина, которую назвали оба

Мои тесты перестали разговаривать через шов. Тест способности утверждал, что в `service_name`/`master_name` нет кириллицы — и проходил ровно потому, что поля всегда пустые; тест адаптера собирал `RepeatResult` руками с заполненными именами — и проверял форму, которой способность никогда не возвращает. Ни один тест не гонял обе половины вместе, поэтому дефект был «зелёным» с обеих сторон.

Добавил недостающий класс тестов: один фейковый HTTP-клиент → настоящая способность → настоящий адаптер. Он и ловит всё, что описано ниже.

## §8.2. Блокеры — исправлены

**Б1. Повтор никогда не называл услугу и мастера.** `prepare_repeat` не заполняла имена, поэтому в проде текст всегда был «Повторим: **ту же услугу**», а отказ — «**Мастер** сейчас не принимает». Для функции, смысл которой в узнавании прошлого визита, это была половина смысла. Имена берутся из карточки визита — из снапшота брони, то есть ровно из того, что человек помнит.

**Б2. Время показывалось в UTC.** Тот самый DRF-1071, о котором предупредил ответ №7: бэкенд отдаёт `start_datetime` из БД в UTC, а форматтер печатал часы как есть — визит на 14:00 по Москве читался как 11:00. Чиню в своём коде, потому что мой адаптер заменил старый вывод и дефект иначе просто переехал бы на новую поверхность. Время переводится в зону салона (дефолт — пилотный, как в `client_notify.tenant_timezone`), формат стал «19 августа, среда, 14:00».
В тестах не было ни одного случая с формой `...Z` — единственной, которая реально приходит с провода. Добавил её и зимнюю дату.

## §8.3. Предпилотные — исправлены все три

**Сбой сети выдавался за факт о салоне.** `_specialist_service_edge` ловил любую ошибку и возвращал `None`, а вызывающий читал `None` как «связь распалась» — то есть двухсекундный таймаут или открытый брейкер сообщали человеку «мастер больше не делает эту услугу». Худший случай — авария бэкенда: брейкер открыт, и каждый тап повтора врёт про мастера. Теперь уточняющий запрос отличает «спросили и получили пусто» от «не смогли спросить», второе — честная временная ошибка.

**Недоступность мастера утверждалась по косвенному признаку.** Различение двух форм 404 держится на том, что `Http404` минует конверт бэкенда, но `"unknown"` возвращается и для HTML-страницы nginx, и для переименованного маршрута. Теперь отсутствие мастера **подтверждается** прямым запросом к `specialists/{id}/`, где 404 — определённый ответ. Не подтвердилось — говорим об аварии, а не о мастере.

**Потолок пагинации читался как «визитов нет».** При длинной серии отмен обход упирался в предел, `collected` был пуст, и человек получал «у вас пока нет завершённых визитов» — уверенную неправду. Теперь непрочитанная история при исчерпанном потолке — `backend_unavailable`.

**Плюс найденное состязательным проходом:** отсутствующий `derived_status` фильтровался как «не состоялся» и давал ту же ложную пустоту; теперь это ошибка контракта. Регистр статуса нормализуется.

## §8.4. Мелочи, взятые в тот же PR

Хардкод префикса кнопки заменён константой; `emit` переведён на канонические `distinct_id` + `properties` вместо устаревшего `payload`; тап повтора больше не помечается как `booking_lookup` — это начало записи, и воронка не должна их смешивать; `limit<=0` не отдаёт один визит.
