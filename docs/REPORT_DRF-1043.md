### C. Контракт — в финальном виде, который реализую

```
GET /api/v1/internal/me/identity/

Auth:        Authorization: Bearer <AYLA_INTERNAL_API_TOKEN>
             X-External-User-ID: <source>:<seg>[:<seg>...]   (например bot:max:12345)
             X-App-Type НЕ требуется (префикс /api/v1/internal/ освобождён)
Request:     тела нет; query-параметров нет; селектора субъекта нет ни в каком виде
200:         {"data": {"ayla_user_id": "<uuid>", "is_proxy": <bool>}}
403:         нет Bearer / неверный Bearer / нет X-External-User-ID /
             X-External-User-ID не проходит формат  → {"detail": "Bot service auth required"}
405:         любой метод кроме GET (и HEAD/OPTIONS, которые даёт DRF)
```

**Форма пути — подтверждаю, менять не прошу (VERIFIED).** Проверено по conventions репозитория: `api/v1/internal/me/` используется исключительно как префикс пространства имён, ресурсы висят на `me/<resource>/`. Форма `me/identity/` повторяет уже принятую `me/bookings/`. Конфликта резолвинга нет: `identity` — статический сегмент, соседний include `me/bookings/` смонтирован по своему префиксу. **Эскалация по §2 брифа не требуется.**

**🟡 Уточнение C-1 по обёртке ответа — расхождение снято, эскалация НЕ требуется (VERIFIED).** Бриф фиксирует тело как `{"ayla_user_id": …, "is_proxy": …}` без обёртки, а конвенция репозитория (`users/response.py:9-14`, `success_response`) даёт `{"data": {...}}`. Я проверил, как это читает бот-сторона, по её собственному коду — `ai-bot-platform-drf1035/apps/integrations/ayla/identity_client.py:158-184`, функция `_parse`: она **сознательно принимает обе формы** — сначала пробует `payload["data"]`, если это dict, иначе читает верхний уровень; в докстроке прямо сказано, что это защита ровно от этой неопределённости. Плюс `is_proxy` у неё необязателен (дефолт `True`).

Поэтому беру конвенцию репозитория — `success_response` → `{"data": {...}}`. Это совместимо с уже написанным клиентом бота и не создаёт исключения из общего формата ответов проекта. Уведомляю, а не спрашиваю; если главное окно решит иначе — скажи, снять обёртку это одна строка.

**Сверка с контрактным тестом бота (VERIFIED).** В `ai-bot-platform-drf1035/apps/integrations/ayla/tests/test_contract_route_table.py:128` уже стоит `Route("GET", "/api/v1/internal/me/identity/", Auth.BEARER_EXT)` — метод, путь и класс аутентификации совпадают с тем, что реализую, символ в символ. Клиент бота ждёт 200, трактует 401 и 403 одинаково (auth-ошибка, breaker не взводится), ≥500 — как недоступность, таймаут 4.0 с.

Чтение репозитория бота — только чтение фактов о контракте, без координации с тем окном; отклонений от зафиксированного контракта не вношу.

```
GET /api/v1/internal/me/identity/

200 OK
  {"data": {"ayla_user_id": "<uuid>", "is_proxy": true|false}}

403 Forbidden
  {"detail": "Bot service auth required"}

           AYLA_INTERNAL_API_TOKEN не сконфигурирован (fail-closed)

  Любой метод кроме GET (плюс HEAD/OPTIONS от DRF)
```

`is_proxy=false` означает, что внешняя идентичность привязана к настоящему аккаунту через `bind_external_identity`, и резолвер прошёл по указателю `linked_user` (Phase C). `is_proxy=true` — изолированный прокси.

### Какие свойства безопасности сохранены

1. **Нет подстановки субъекта.** Тела запроса нет, query-параметры не читаются, метод один. Единственный источник субъекта — заголовок, уже проверенный слоем аутентификации. Тест `TestIsolation` пытается назвать чужого субъекта пятью разными написаниями query-параметра — все пять резолвятся в вызывающего.
2. **Fail-closed при отсутствии конфигурации.** Пустой `AYLA_INTERNAL_API_TOKEN` отвергает всех (наследуется от permission-класса, покрыто тестом).
3. **Никакого timing-оракула не добавлено.** Классификатор отказов **не сравнивает** Bearer с ожидаемым — иначе появилось бы небезопасное по времени сравнение рядом с `compare_digest`. Все неверные токены попадают в общую категорию `auth_rejected`.
4. **Отказ не провижионит аккаунт.** Классификатор не вызывает `resolve_external_user`; отдельный тест проверяет, что после 403 строки пользователя не появилось.
5. **Минимальность ответа зафиксирована на проводе.** Закрытый DTO + тест на точный набор ключей и на отсутствие десяти конкретных полей (телефон, email, имя, тенант, профиль, согласия, персональный контекст…).
6. **Cross-check `client_id` не ослаблен.** `appointments/` не тронут; двусторонний регресс-тест на месте.
7. **ПДн не логируются.** Пишутся `user_id`, `is_proxy`, внешний идентификатор — по существующей политике проекта (`nutrition/views.py:296` логирует тот же внешний идентификатор). Свежесозданный прокси персональных данных не содержит — отдельный тест.

| **Обратная совместимость** | Текущая версия бота этот маршрут не знает и не заметит деплой: маршрут аддитивен, соседние поверхности не изменены (регресс-тест на `me/bookings/` и на отсутствие теневого перекрытия маршрутов) |
