## 2026-08-09 — Сессия 1

## ⛔ ГЛАВНЫЙ ВЫВОД: ЭСКАЛАЦИЯ ПО §10. Декартово произведение — это КАНОНИЧЕСКАЯ ИСТИНА AYLA, а не мусор в bot-platform.

Локальный миррор `MasterService` тенанта formula-tela **совпадает с тем, что отдаёт backend, ровно и полностью**: 232 ребра = 232 ребра, множества пар `(мастер, услуга)` идентичны, расхождений ноль в обе стороны. Ayla по своему `specialist-services` endpoint утверждает, что **каждый из 4 мастеров выполняет каждую из 58 услуг**, все рёбра `is_active=True`, снапшот `complete=True`.

Следствие, ломающее план брифа: **чистка локальных строк + реконсиляция воссоздадут ровно те же 232 ребра.** Пункты §5.4.3–5.4.4 (после синка «у каждого мастера набор услуг совпадает с backend» и «„классический массаж“ → не все 4 мастера») внутренне противоречивы — первый критерий уже выполнен СЕЙЧАС, а второй недостижим, пока Ayla говорит «все умеют всё».

Задача в её текущей формулировке (§1: «убрать декартово произведение… устранить источник мусора») **не может быть решена в репозитории ai-bot-platform.** По ADR-0009 каталог и связь «мастер↔услуга» принадлежат Ayla; bot их только зеркалит и не имеет права владеть. Чинить нужно данные (или логику их создания) на стороне Ayla.

Это ровно триггер §10 брифа: «расхождение backend-истины со здравым смыслом» + «источник мусора не seed».

| Проход | Итог | Что закрыто |

Обе находки-блокера были настоящими, обе проверил на коде сам, прежде чем чинить.

**P1 дружественного — TOCTOU дампа.** Удаление переоценивало предикат вместо удаления зафиксированного набора. MM4-матрица создаёт NULL-строки живьём из админки, значит ячейка, которую оператор отметил между дампом и удалением, сносилась **без записи в бэкап** — прямое нарушение контракта, заявленного в докстринге самой команды. Теперь удаление идёт по захваченным `id` (гард `isnull` сохранён, чтобы строку, которую успел проштамповать конкурентный синк, не снести по устаревшим данным).

**P0 состязательного — два файла PR давали взаимоисключающие причины инцидента.** Докстринг команды подразумевал, что декартово произведение породила «бессмертность», а диагностика говорит обратное: сетку публикует Ayla, а неаудируемый импорт её отзеркалил с NULL-провенансом. Разница операционная и опасная: при **неисправленном upstream** чистка + синк вернут ту же сетку уже **sync-owned**, где эта команда её не достанет никогда. Докстринг теперь фиксирует проверенную цепочку и обязательный порядок (сначала фикс данных Ayla), success-сообщение больше не обещает «rebuild the real edges».

Прочее по состязательному:
- **предупреждение по `created_by` не могло сработать никогда** — ни один писатель `MasterService` его не заполняет (проверил `views_services_mapping.py`, `views_invite.py`), то есть молчание предупреждения читалось бы как «ручных правок нет». Заменено на безусловную оговорку с указанием на `AuditLog MASTER_SERVICES_CHANGED` — дискриминатор, который реально существует;
- добавлен **`--check-upstream`**: спрашивает у Ayla, какие кандидаты она бы пересоздала, и делит отчёт на «вернётся» / «потеряется навсегда». Обычный отчёт отвечает «что исчезнет», но не «что вернётся», а настоящая потеря — только второе. Fail-soft: недоступная Ayla говорит об этом, а не выглядит как «ничего не вернётся»;
- центральное утверждение «штамп передаёт строки синку» было **не покрыто тестом** — теперь прогоняется через настоящий `upsert_master_services`;
- счётчик sync-owned обещал больше, чем даёт READ COMMITTED (и равный по числу обмен его обходит) → заменён на утверждение о том, что фильтр реально гарантирует; удаление чанкуется; дамп открывается create-exclusive; seed дополнительно отказывается работать вне `DEBUG`, так как его slug совпадает со slug живого пилота;
- guard импорт-границ (MKT1) поймал чтение `CatalogService.all_tenants` в новом коде — переведено на `tenant_scope`.

**Собственная поправка:** в regression-модуле я написал, что существующие негативные тесты держат по одному мастеру. Это неверно — `test_broad_query_matches_every_massage` держит троих и требует подмножество. Докстринг переписан честно, дублирующий тест удалён.

### 3.1. `cleanup_orphan_master_services` — новая management-команда

Удаляет по одному тенанту рёбра с `ayla_specialist_service_id IS NULL`, чтобы синк мог пересоздать их уже как свои.

* dry-run по умолчанию; `--apply` обязателен для удаления;
* `--apply` **требует** `--dump PATH`, дамп пишется и закрывается **до** удаления (json со всеми полями для обратной вставки);
* sync-owned строки отфильтрованы, их число проверяется после удаления — расхождение = rollback транзакции + ошибка;
* выбор тенанта `--tenant-slug` XOR `--tenant-id`;
* отчёт называет поимённо мастеров, которые останутся с НУЛЁМ рёбер до следующего синка (это и есть цифра для GO-гейта).

### 3.2. `seed_dev_formula_tela` — закрыт реальный (хоть и не сработавший здесь) дефект

* каждое создаваемое ребро штампуется детерминированным `uuid5`-провенансом → строки становятся sync-owned, и синк может их реконсилировать (раньше seed плодил ровно тот класс бессмертных строк, что мы наблюдаем на пилоте); повторный прогон идемпотентен, старые NULL-строки от прошлых прогонов «усыновляются»;
* команда **отказывается** засеивать fixture-данные в тенант, у которого уже есть Ayla-grounded услуги (`--force` перекрывает).

## 4. Что чистка ДАЁТ и чего НЕ даёт (для GO-гейта §5.3)

Честная картина, потому что бриф ожидал от неё другого:

**НЕ даёт:** чистка + синк воссоздадут те же 232 ребра (уже sync-owned). Discovery-фильтрация по услуге останется такой же инертной, гард неоднозначности DRF-962 продолжит срабатывать. **Повторная live-приёмка DRF-962 после одной лишь чистки не пройдёт.**

**Даёт:** снимает бессмертность. Сейчас 232 операторские строки не удалит уже ничто, кроме ручного вмешательства — и когда Ayla починит свои данные, **пилот этого не увидит**. После чистки миррор становится sync-owned, и любая правка на стороне Ayla доедет автоматически ближайшим 15-минутным beat'ом.

Поэтому чистка — **необходимая предпосылка** для того, чтобы Ayla-side фикс вообще подействовал, но не самостоятельное решение.

**План применения на пилоте (когда будет GO):**
- удаляется: 232 строки (все NULL-провенанс), останется: 0 sync-owned;
- после `--apply` у **всех 4 мастеров временно 0 услуг** → запись не работает до первого синка (окно ≤ 15 мин, либо синк запускается вручную сразу);
- дамп-бэкап: путь на хосте задаётся `--dump`, содержимое дублируется в этот отчёт;
- откат: обратная вставка из json + повторный синк.

Учитывая, что выигрыш реализуется только вместе с Ayla-side фиксом, **рекомендую не трогать пилотный runtime сейчас**, а выполнить чистку сразу после того, как Ayla поправит specialist-services — одним окном, с проверкой результата.

Нужно решение:
1. **Данные правит Ayla-сторона** (ожидаемый путь) → нужна задача в Ayla-репо/команде: привести `SpecialistService` к реальным компетенциям мастеров + проверить, не создаёт ли backend решётку автоматически. DRF-967 в bot-platform тогда сводится к «почистить бессмертный миррор и дать синку овладеть им» + ждать Ayla.

Либо это **действительно так** (все мастера универсальны) → тогда DRF-967 закрывается как «не дефект», а претензии переезжают в UX discovery: при честной универсальности фильтрация по услуге не может сузить список мастеров, и ветка «спроси услугу» — единственно корректное поведение.
