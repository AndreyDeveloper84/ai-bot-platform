## Опровержение 1 — «кода, читающего `goals`, нет» — неверно

**Читатель есть:** `ai-bot-platform/apps/kb/projectors.py:90`

```python
if row.goals:
    parts.append("Подходит: " + ", ".join(row.goals))
```

Это **тело статьи знания** — текст, который модель цитирует человеку. Поиск шёл по `apps/catalog/`, потребитель живёт в `apps/kb/`.

**Почему это меняет решение, а не просто уточняет факт:** `", ".join(...)` требует список строк, и строки попадают в текст для человека. Отдай мы боту список ключей — в выдаче появилось бы буквально «Подходит: relax, self_care», **утёкший внутренний жаргон**.

Поэтому в зеркало едет `{"key", "label"}`, проектор печатает `label`, а `key` остаётся для будущего структурного фильтра.

Без этой находки поле уехало бы в неверной форме и это заметили бы уже на живом ходу.

## Опровержение 2 — разметка трёх листьев ставит ЛОЖНУЮ цель, нарушая п. 4

Задание (от главного окна, по анализу) предлагало разметить `Комплексы для тела` → `body_shape + relax`, `для лица` → `skin_care`, `красоты` → `new_look + event`.

**Так делать не надо.**

**Две строки из трёх не меняют ничего.** В `Комплексы для лица` и `Комплексы красоты` — **ноль услуг** по всему контуру.

**Третья ставит ложную цель.** В `Комплексы для тела` ровно три услуги пилота:

| Услуга | Что это | Что дала бы пара `body_shape + relax` |
|---|---|---|
| «Гладкая кожа»: антицеллюлит + VelaShape | коррекция фигуры | `body_shape` верно, **`relax` — нет** |
| «Лёгкие ноги»: лимфодренаж + вибромассаж | восстановление | спорно оба |
| **Спина без боли — комплекс массажа** | массаж спины | `relax` верно, **`body_shape` — нет** |

**Человек, сказавший «хочу подтянуть фигуру», получил бы массаж спины.** Ровно то, что п. 4 запрещает дословно.

Перенос цели с корня на лист не отменяет проблему — он опускает её на уровень ниже: владелец писал про «semantic purpose **конкретного пакета**», а лист с 17 шаблонами от «плоский живот» до «восстановление после родов» — не конкретный пакет.

**91/94 — правильная остановка.** Оставшиеся 3 имеют честный `[]`.

**Единственный способ закрыть эти три без ложной цели** (данные, ноль схемы, ноль кода) — не размечать лист, а **переложить услуги в семантически верные листы**, где цель уже наследуется:

```
«Гладкая кожа»   → лист под «Аппаратный массаж и коррекция фигуры»  ⇒ body_shape
«Лёгкие ноги»    → лист под «Массаж тела»                            ⇒ relax + recharge + body_shape
Спина без боли   → лист под «Массаж тела»                            ⇒ relax + recharge
```

Три `UPDATE`. Издержка честная: салон теряет собственную группировку «пакеты» в дереве — это его витрина. **Решение владельца.**

## Опровержение 3 — «резолвер поднимается вверх» описывает половину работы

П. 1 решения владельца сформулирован **от услуги** («вверх к родителю»), Шаг 0 анализа — **от цели** («вниз на потомков»).

Это **два направления одного отношения**, нужны оба:

- только «вверх» — цели поедут в бота, но выбор цели в приложении ничего не отфильтрует;
- только «вниз» — фильтр заработает, а у бота останется `[]`.

Реализованы оба. **Ни одна формулировка сама по себе задачу не закрывала.**

## Сценарий живого прогона (делает главное окно)

Предусловие: обе ветки в `dev`, Ayla выложена, синхронизация прошла хотя бы раз.

**2. Цели в зеркале.** `select (goals='[]'::jsonb) empty, count(*) from catalog_catalogservice group by 1;` Было `[] | 94` → стало `false | 91`, `true | 3`.

**3. Текст для модели.** `select body from kb_article where body like '%Подходит:%' limit 3;` Ожидание `Подходит: Привести себя в порядок` — **подпись, не ключ**. `Подходит: relax` = дефект.

**4. Живой ход.** «хочу привести себя в порядок» → услуги, у которых цель действительно проставлена.

## Открытое

**О-1 (главное).** Структурного фильтра «выбранная цель → услуги с этой целью» на боте **нет**. Проверка «а не выдача по совпадению слов» пройдена **наполовину**: цель у услуги теперь есть и видна, но отбор идёт по тексту.

Внутри DRF-1308 не строилось — это уже работа над отбором, граничит с эпиком DRF-1174. **Отдельная задача ~2 SP:** инструмент бота, фильтрующий каталог по вхождению ключа в `goals`. Ключ в зеркале уже лежит — форма поля выбрана с расчётом на него.

**О-2. Метрика покрытия на форму решения не повлияла** — Шаг 0 от неё не зависел.

По существу: покрытие как метрика **опасно ровно тем, что толкает закрывать последние проценты ложными целями** — что и произошло бы при разметке `Комплексы для тела`. Если метрика останется, нужен парный показатель «доля целей, поставленных вручную владельцем», иначе она вознаграждает подделку.

**О-3.** Три услуги без цели ждут решения владельца по переносу в верные листы. Ничего не блокирует.

**О-4.** `base_price = 0.00` у 7 строк контура проходит мимо `MinValueValidator(1)`. К DRF-1308 отношения не имеет, но это живой дефект данных.

## Воспроизведение замера

```sql
with cat_goals as (
  select gc.category_id cid, array_agg(go.key order by go.sort_order, go.key) g
    from services_goaloptioncategory gc
    join services_goaloption go on go.id=gc.goal_option_id
   where go.is_active group by gc.category_id),
cat_resolved as (
  select c.id cid, coalesce(cg.g, pg.g) g
    from services_servicecategory c
    left join cat_goals cg on cg.cid=c.id
    left join cat_goals pg on pg.cid=c.parent_id)
select case when own.g is not null then 'own'
            when tpl.g is not null then 'template' else 'none' end src, count(*)
  from services_salonservice ss
  left join cat_resolved own on own.cid=ss.category_id
  left join services_servicetemplate st on st.id=ss.template_id
  left join cat_resolved tpl on tpl.cid=st.category_id
 group by 1;
-- own 88 | template 3 | none 3
```
