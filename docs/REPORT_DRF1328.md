# Опровержения постановки

**Два из пяти изменили то, что надо было строить.**

## 1.1. Ветка забирает ход **не там**, где сказано в задаче

Задача: «ход забрала детерминированная ветка `looks_like_booking_request`
(`apps/skills/menu/matching.py:208-221`)».

Условие действительно оттуда, но **забирает ход не оно**. Забирает
`apps/channels/max/handler.py:848` — единственное место, где предикат стоит
перед консьержем. У самого предиката **ещё два потребителя**, к этой задаче
отношения не имеющих:

```
apps/skills/menu/skill.py:130               — MenuSkill на АРЕНДАТОРСКОМ пути,
                                              последний перехват перед эхо
apps/channels/max/global_onboarding.py:229  — обход приветствия (DRF-1205):
                                              «намерение обходит церемонию»
```

**Почему это меняет работу.** Перевернув умолчание внутри `looks_like_booking_request`,
я бы одновременно:

* сузил последний перехват MenuSkill — фразы, которые сегодня доходят до
  записи у салона, начали бы падать в эхо;
* вернул приветствие поверх первого осмысленного сообщения — ровно тот дефект,
  который закрыт DRF-1205.

Оба — за границами задачи и оба тихие.

**Сделано вместо:** переворот сделан **в гейте**, новым модулем
`apps/orchestrator/fast_path.py`. `looks_like_booking_request` **не тронут ни
одной строкой** — оба его других потребителя ведут себя байт-в-байт как вчера.

## 1.2. Куча отказов растёт **не в одном месте, а в двух** — «дописать ещё один» пришлось бы в третьем

Задача рисует кучу как список условий в одной функции. На деле DRF-1312 живёт
**не в `matching.py`**, а внутри самой ветки:

```
apps/skills/menu/matching.py:208   looks_like_booking_request  — «услуга упомянута?»
apps/orchestrator/concierge.py     generate_direct_show_masters_reply
                                     |- has_discovery_criteria        (пусто -> вопрос)
                                     |- split_requested_services >= 2 (составной -> None)  <- DRF-1312
                                     +- not cards                     (ноль -> None)       <- DRF-1283
```

То есть отказы уже распределены по **двум модулям на разных уровнях**, и решение
«кому принадлежит ход» невозможно было прочитать в одном месте. Отказ про салоны
логично лёг бы в третье — а автор следующего инструмента должен был бы найти все
три.

**Сделано вместо:** решение сведено в **одну функцию**
(`fast_path.claims_direct_show_masters`), и она вызывается **из обоих мест** —
из гейта обработчика и из самой ветки. Ветка проверяет ещё раз намеренно:
гейт может обойти любой будущий вызывающий, а ответ на вопрос «чей ход» не
должен зависеть от того, в какую дверь ход вошёл.

Отступление при составном запросе (DRF-1312) **не откачено и не исчезло** — оно
стало **пунктом нового разбора** (`reason == "composite_request"`), потому что
одного правила «нераспознанное слово -> консьерж» для него не хватает: в
«массаж и маникюр» нераспознанных слов нет, оба — услуги.

## 1.3. Порядок навыков переворот **не** делает невозможным — проверено

Задача просила сказать прямо, если порядок мешает. Не мешает. Ветка 2.7 живёт
внутри `else`-блока, после проверок команд памяти и ожидающего ответа и **до**
структурных пищевых ходов и консьержа (`handler.py`, ветки 0 -> 0.5 -> 0.7 -> 1
-> 2 -> 2.5 -> 2.7 -> 3). Переворот меняет **условие входа** и ничего больше: ни
одна ветка не поменялась местами, ни одна не добавлена и не удалена.

## 1.4. Требуемый тест **нельзя было написать** над тем кодом, что был

Условие приёмки: «тест, который падает, когда появился новый инструмент
консьержа, а ветка про него не знает». Список инструментов был **литералом
внутри функции**:

```python
    concierge = AIConcierge(
        ...
        tool_definitions=[SHOW_MASTERS_TOOL_SPEC, SHOW_SALONS_TOOL_SPEC, ...],
```

Тест не может прочитать реестр, у которого нет имени, а разбор исходника
регулярным выражением по литералу — это и есть та таблица, которая расходится.

**Сделано:** реестр вынесен в модульную константу
`apps.orchestrator.concierge.CONCIERGE_TOOL_SPECS` (поведение не изменилось,
порядок сохранён — у пищевых спеков он несущий).

**И одного импорта константы мало.** Импорт доказывает, что лежит в константе,
а не чем вооружён консьерж: правка, дописывающая инструмент прямо в вызов —
ровно та форма, из которой константу и вынули — оставила бы тест зелёным.
Поэтому `TestRosterIsTheRealOne` **дополнительно читает `concierge.py`** и
пришпиливает, что `tool_definitions` получает именно константу. Тот же приём,
что в `test_miniapp_routes.py` (DRF-1326): таблица читается из источника, а не
переписывается в тест.

## 1.5. Переворот делает дешёвый путь **на один запрос дороже** — и это правильная цена

Честно: «покажи массажистов в пензе» теперь стоит **один дополнительный
`SELECT DISTINCT tenant__city`** — разбор обязан знать, что «пензе» это место,
которое мы обслуживаем, а не неопознанное слово.

Почему это не подорожание пути, а его цена:

* запрос делается **только** для хода, который уже назвал услугу **и** оставил
  необъяснённое слово. Ход без услуги («какие у вас салоны») уходит на нулевом
  чтении, ход из одних известных слов («хочу массаж») — тоже;
* решение принимается дважды — в гейте и в самой ветке (см. 1.2, защита от
  обхода), поэтому ход, называющий город, платит **два** таких DISTINCT.
  Оба — по одной маленькой таблице, оба уже греют тот же план запроса, что
  и третий, который делает `discover_masters`;
* тот же самый DISTINCT `discover_masters` делает следующей строкой, для того
  же хода;
* альтернатива — не узнавать города, то есть отдавать «покажи массажистов в
  пензе» модели. **Это и был бы подорожавший дешёвый путь**: вызов LLM вместо
  одного DISTINCT.

Вызова модели в условии по-прежнему **ноль**.

## Умолчание

```
было:   услуга упомянута?  ->  забираю ход
стало:  разобрал ход целиком и в нём нет ничего,
        кроме запроса мастеров по услуге  ->  забираю
        во всём остальном                 ->  консьерж
```

`apps/orchestrator/fast_path.py`, `decide()` — два правила и один пункт:

1. **назван сервис** — те же корни слов, что уже используются
   (`apps.skills.menu.matching`, seed-список не тронут);
2. **и больше ничего** — каждое оставшееся слово обязано быть либо самой
   услугой, либо связкой запроса мастеров (`_REQUEST_WORDS` / `_REQUEST_STEMS`
   / `_SERVICE_QUALIFIER_STEMS`), либо городом, где у нас есть кто-то бронируемый;
3. пункт DRF-1312: перечисление двух услуг в одном ходе — консьержу.

**Правило 2 и есть переворот.** Незнакомое слово — это не шум, это **отказ**.
«салоны», «стоит», «болит», «калорий» — все незнакомы, и каждое отдаёт ход, при
том что модуль **не знает ни одного из инструментов**, которым эти ходы нужны.
Инструмент, построенный через месяц, достижим в день выкладки: его словаря в
этом файле нет.

**В какую сторону это ошибается.** Запрос мастера, написанный неизвестными
словами («массаж 60 минут»), уходит консьержу: **один вызов LLM и правильный
ответ**. Обратная ошибка — забрать ход, который запросом мастеров не был, —
стоит уверенного неправильного ответа. Словарь поэтому можно свободно
**расширять** и нужно осторожно **сужать**.

## Отдельно: почему словарь связки не переиспользован

`apps.marketplace.discovery._FILLER_TOKENS` содержит **«салон», «услуга»,
«мастер»** как мусорные слова. Там это **правильно** — список существует, чтобы
*расширять* поиск по каталогу, и выброшенное слово может только добавить
находок. Здесь выброшенное слово значит «оно не мешает мне забрать ход», и
«салон» с «услугой» — ровно те слова, которые обязаны мешать.

**Переиспользовать этот список значило бы воспроизвести DRF-1328 с чёрного
хода**, из модуля, который понятия не имеет, что ветка его читает. Поэтому
словарь у `fast_path` свой, а `TestVocabularyDoesNotOverlapTheTools` следит,
чтобы тема чужого инструмента никогда не стала связкой.

## Отдельно: ходы, названные целью (DRF-1308 / DRF-1317)

Владелец в задаче предсказал следующий отказ в куче — «отступи, если названа
цель». **Дописывать его не пришлось**: цель формулируется словами, которых в
словаре ветки нет, и она отдаёт такой ход сама.

```
Хочу снять напряжение            -> no_service_named
Хочу расслабиться                -> no_service_named
Расслабиться и снять стресс      -> no_service_named
Снять отёки                      -> no_service_named
Восстановиться после тренировки  -> no_service_named
Хочу снять напряжение массажем   -> unaccounted: снять, напряжение
Массаж для снятия стресса        -> unaccounted: снятия, стресса
Антицеллюлитная программа        -> unaccounted: программа
```

Единственное исключение — `«Расслабляющий массаж»`, которое забирается веткой.
Это **название услуги**, а не цель: карточки мастеров — правильный ответ на него.

**Это и есть проверка формы.** Отказ, который в старом умолчании пришлось бы
дописать третьим, в новом уже работает — потому что умолчание «не моё», а не
«моё».

Контур: `api-dev.gobeauty.site`, глобальный бот MAX, тот же аккаунт, с которого

## Ход 1 — то, что сломалось

**Отправить:** `Найди мне САЛОНЫ массажа`

**Должно прийти:** список **салонов** — название, город, адрес, «что там

**Не должно** прийти «Вот мастера, которые могут подойти».

Ключевое — строка `handed_to_concierge` с `residue=салоны`. Она означает, что
ветка отдала ход **не потому, что кто-то дописал ей отказ про салоны**, а

**Отправить:** `где делают лимфодренаж`

**Должно прийти:** карточки **мастеров** — как вчера, «Вот мастера, которые
могут подойти».

**В логе искать:**

```
orchestrator.concierge.direct_show_masters count=N trace=...
```

Строки `handed_to_concierge` быть **не должно**. Вызова модели — тоже.

## Ход 3 — дешёвый путь не подорожал

**Отправить:** `покажи массажистов в пензе`

**Должно прийти:** карточки мастеров, **мгновенно**.

**В логе искать:**

```
orchestrator.concierge.direct_show_masters count=N trace=...
```

и **ни одной** строки провайдера LLM с этим `trace`. Проверить по таблице:

```sql
SELECT skill_selected, llm_model, llm_provider, latency_ms
FROM observability_airequestmetric
WHERE trace_id = '<trace>';
```

Должна быть **одна** строка, `skill_selected=concierge_direct`, `llm_model` и
`llm_provider` пустые — то есть модель не звалась.

**Отправить:** `давай будет несколько: массаж классика, и маникюр`
**Должно прийти:** карточки массажистов **плюс** названная вслух отсутствующая
услуга (DRF-1312, не откачено). В логе — `handed_to_concierge reason=composite_request`.

# Что изменилось в поведении сверх задачи

Честно перечислено, потому что это заметно на контуре:

1. **Ход, где названа услуга и есть незнакомое слово, теперь идёт к модели.**
   Примеры: «сколько стоит массаж» (был бы список мастеров вместо цены),
   «болит спина, хочу массаж» (симптом обязан попасть в скрининг раньше —
   DRF-358 T04), «можно ли массаж при беременности». Все три раньше отвечались
   карточками. Это и есть смысл правки.

2. **Ход из одних только фраз про свободное время больше не забирается веткой.**
   «есть окошко на завтра» раньше проходило гейт, шло в `discover_masters` с
   этой фразой как запросом, находило ноль и **всё равно** уходило консьержу
   (DRF-1283). Теперь уходит сразу, без чтения каталога. Наблюдаемый исход тот
   же, одним запросом меньше.

3. **Стоимость.** Доля ходов, отвечаемых без модели, снизится. Насколько —
   считается из `observability_airequestmetric` по доле
   `skill_selected=concierge_direct` до и после. Направление ошибки выбрано
   осознанно (см. 1.5 и «в какую сторону это ошибается»).
