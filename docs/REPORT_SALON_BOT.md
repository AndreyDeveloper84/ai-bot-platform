## §4. Гейт «prompt regression» не может поймать регрессию промпта

`replay.yml` называет себя гейтом качества AI: «Blocks merges that break the fixture set», «The fixture diff IS the design review for AI changes». На диске 12 наборов golden, 30 adversarial, 20 voice.

Что он **фактически** запускает:

```
uv run pytest apps/replay/                       # тесты самого движка replay
uv run pytest apps/replay/tests/test_fixtures.py # фикстуры парсятся + baseline-clean
```

Ни одна фикстура не прогоняется через реальный путь ответа. В самом же workflow это написано: «When Sprint 6 lands apps.orchestrator.pipeline.turn, this workflow upgrades to invoke `python -m apps.replay run`». **`pipeline.turn` существует** (`orchestrator/pipeline.py:411`) — апгрейд не сделан.

Три вещи из разведки, которые определяют конструкцию:

**1. `AIConcierge` однопроходный.** Он парсит `tool_call`, диспатчит и возвращает `action_type` — второго прохода с результатом инструмента обратно в модель нет. Решение: возврат данных в модель **без tool-протокола** — вторым обычным сообщением. Работает у обоих провайдеров и не требует правки чужих адаптеров.

**3. `Conversation` читают 18 мест, все клиентские** (`master_api/conversations`, `handoff`, `eventbus/consumers/payment`, `bookings/followups`, …). Разговор сотрудника в той же таблице — это 18 мест, где пропущенный фильтр становится тихим дефектом. Отдельные таблицы, поэтому, не вкусовщина.

```

"tenancy_tenantstaff_tenant_id_bot_user_id_role_141d9321_uniq"
```

Это не дефект — тотальный индекс по определению не примет два таких ряда. Но следствие практическое:

> **Путь назад существует ровно до первого повторного найма.** Как только кто-то воспользуется отзывом и вернёт человеку ту же роль, `0012` становится необратимой.

### A.7. Техническое решение: реестр ботов, а не второй экземпляр

Бриф §3 просит обосновать выбор, потому что от него зависит цена третьего бота.

**Решение: параметризация через маленький реестр ботов, а не копия механизма.** Одна структура — источник истины:

```
bot_slug → { webhook_secret, api_token, tenant_slug, stream, kind }
```

Три записи сегодня: клиентский (global), салонный, и место под будущий. Тогда:
- гейт проверяет вхождение в множество секретов реестра и **возвращает, чей это секрет**;
- поток берётся из записи реестра — `enqueue(channel=entry.stream, ...)`;
- исходящий токен берётся из записи;
- `verify_init_data` перебирает ключи-кандидаты из реестра.

**Обоснование.** Второй экземпляр (скопировать `is_global_bot_token` в `is_salon_bot_token`, `if/else` в три ветки, ещё один одиночный `SALON_BOT_TOKEN` рядом с `MAX_BOT_TOKEN`) даёт тот же результат на два бота дешевле на пару часов — и умножает четыре допущения из §A.2 на три вместо того, чтобы снять их один раз. Цена третьего бота в этом варианте — снова девять точек правки. С реестром цена третьего бота — **одна строка окружения и ноль строк кода**, а четыре разрозненных места сходятся в одно, которое можно покрыть тестом.

Против реестра работает то, что он трогает разделяемый код (гейт, outbound, initData-проверку), где сидят три других окна. Это реальный риск, и он управляется размером: реестр — это ~40 строк и одна функция `resolve_bot(secret)`; поведение при одном боте остаётся байт-в-байт прежним (дефолтная запись из `MAX_WEBHOOK_SECRET`/`MAX_BOT_TOKEN`), так что клиентский путь не меняется вообще.

**Отвергнутая альтернатива — отдельный URL вебхука** (`/api/v1/ingress/max/salon/`): технически это самый дешёвый вариант, идентичность бота несёт сам маршрут. Отвергнут, потому что владелец и бриф явно зафиксировали общий адрес, а выигрыш — только в этих же ~40 строках; при этом отдельный URL не решает ни (2), ни (3), ни (4) из §A.2, то есть экономит меньше, чем кажется.

## §C. Онбординг — как человек становится сотрудником

### C.1. Форма кода

Человек набирает код **в чате салонного бота**. Отсюда требования: короткий, без регистрозависимости, без похожих символов, произносимый по телефону.

- алфавит без `0/O`, `1/I/L` — 8 символов вида `AYLA-7K3M` (префикс постоянный, 4 значащих символа из 28-символьного алфавита ≈ 614 тыс. комбинаций);
- регистр не важен, дефис не важен — нормализую перед сверкой;
- в базе хранится **хэш**, не сам код (SHA-256; код показывается один раз при выдаче);
- срок жизни — 7 суток, как у мастерских приглашений (единообразие);
- **одноразовый** — гасится при успешном приёме.

614 тыс. комбинаций мало для криптографии, поэтому короткий код обязан идти в комплекте с ограничением попыток (см. C.5). Это сознательный размен: длинный код владелец не наберёт, а неверный ввод должен стоить дорого.

### C.1-бис. Ввод кода — не единственный способ, и второй лучше

Проверил сам: `apps/channels/max/parser.py:262-263` — событие `bot_started` несёт диплинк-payload и сворачивается в синтетический текст `/start <payload>`:
```python
deeplink_payload = payload.get("payload") or ""
synthetic_text = f"/start {deeplink_payload}".strip() if deeplink_payload else "/start"
```
Значит владельцу можно **не набирать ничего**: ссылка `max://bot/<салонный_бот>?start=inv_AYLA7K3M` открывает бота и сразу приносит код. (Ограничение «payload — плоский слаг без `=` и `&`» относится к кнопкам `open_app`, к `?start=` — нет; но алфавит кода из §C.1 и так плоский.)

**Делаю оба входа, один и тот же код:**
- **ссылка** — основной путь, ноль ввода, ноль опечаток;
- **набранный код** — резервный: ссылку неудобно передать голосом, она протухает в пересылках, а критерий готовности сформулирован именно как «вводит код приглашения». Резервный путь обязан работать, а не существовать на бумаге.

**Состояние диалога хранить не нужно.** Логика без FSM: если у человека нет роли — любое сообщение, похожее по форме на код, проверяется как код; не похожее — получает подсказку «пришлите код приглашения или ссылку». Ни одного поля состояния, ни одного шанса застрять в незавершённом шаге.

### C.2. Кто выдаёт — и как решается проблема первого администратора

Курица и яйцо: экран `/admin/team/invite` требует `@require_admin_role`, а администраторов ноль.

- **Первый администратор — management-командой.** `issue_staff_invite --tenant formula-tela --role owner` печатает код в консоль. Запускается на пилотном хосте по GO, код передаётся владельцу через тебя. Мутация ровно одна — строка приглашения.
- **Дальше — из админки.** Когда владелец стал `owner`, `/admin/team/invite` расширяется полем роли (снимается заглушка `views_invite.py:249-256`) и выдаёт коды сам: администратору, ресепшену, мастеру.

Почему командой, а не строкой в Django-админке: DRF-1025 прямо запрещает выдавать учётки Django-админки сотрудникам салона, а тенантных ограничений там нет.

### C.3. Что происходит при верном коде

Одна транзакция, семантику беру из `create_solo_provider` (`solo_onboarding.py:256`) — он делает ровно это и уже написан:

1. `BotUser` под тенантом из реестра бота (`formula-tela`) — `get_or_create` по `(tenant, channel="max", channel_user_id)`;
2. по роли приглашения:
   - `owner`/`admin`/`receptionist` → `TenantStaff(tenant, bot_user, role)`, `deactivated_at = NULL`;
   - `master` → приглашение выдаётся **привязанным к конкретному `CatalogMaster`**, и приём ставит `linked_bot_user`, `invite_status = ACCEPTED`, `mode = INVITE`, **и `is_active = True`** — тот самый дефект A.4/1, который я на своём пути не воспроизвожу;
3. гашу приглашение: `used_at`, `used_by`;
4. аудит + событие (по образцу `MASTER_INVITED` / `MASTER_INVITE_DISPATCHED`);
5. в ответ — приветствие с ролью и меню (§D), включая кнопку в Mini App.

Кэша роли нет (§A.5) — админка откроется со следующего запроса.

### C.4. Повторный вход

- **Тот же человек, тот же код** — код уже погашен → «этот код уже использован». Но если у человека **уже есть эта роль**, отвечаю успехом и показываю меню: для владельца это неотличимо от нормы, а `unique_together (tenant, bot_user, role)` всё равно не даст дубля. Идемпотентность важнее буквальности.
- **Просто написал боту, уже будучи сотрудником** — код не спрашиваю вообще, сразу меню по роли.
- **Вторая роль поверх первой** — роли аддитивны (`resolve_role` объединяет capabilities), новый код добавляет строку, старая живёт.
- **Один активный owner на тенант** — частичный уникальный индекс. Второй код на `owner` упрётся в базу; ловлю `IntegrityError` и отвечаю «у салона уже есть владелец», а не 500.

### C.5. Что при неверном коде

- ответ один и тот же на «не существует», «истёк», «погашен» — чтобы перебор не отличал случаи; в логи пишу настоящую причину;
- **ограничение попыток: 5 в час на `channel_user_id`**, дальше отказ с паузой. Без него 4 значащих символа перебираются машиной; с ним — нет;
- превышение лимита пишу в аудит: это сигнал, а не рутина;
- код не логируется целиком нигде.

### C.6. Новая модель — и почему её не избежать

`TenantStaff` полей приглашения не имеет, `CatalogMaster.invite_token` — мастер-специфичен и уже занят. Нужна маленькая `StaffInvite` в `apps/tenancy`:

`tenant`, `role`, `code_hash`, `catalog_master` (null, только для `master`), `expires_at`, `used_at`, `used_by` (FK BotUser, null), `created_by`, `created_at`, + индекс по `code_hash`.

**Проверка на границу ADR-0009:** это не новый транзакционный домен и не дубль канонического состояния Ayla. `TenantStaff` — собственная модель доступа бота к собственной Mini App (ADR-0008), Ayla про неё не знает и знать не должна. Правило 4 не нарушается. Роли в бэкенде (TUR) — отдельная система, ей владеет окно расписания (§B.4).

## §D. Меню

### D.0. Сначала плохая новость: «мастер видит свой день» сегодня не заработает даже с открытой дверью

Это самая важная находка секции, и она ставит под сомнение половину критерия готовности (§7 брифа).

`GET /api/v1/master/dashboard` (`apps/master_api/views.py:687-705` → `services/dashboard.py:785`) и `GET /api/v1/master/schedule` строят день **из локальной таблицы `BookingRequest`** — например `dashboard.py:373-383`:
```python
    booking = (
        BookingRequest.all_tenants.filter(
            tenant_id=master.tenant_id,
            master_id=master.id,
            status=BookingRequest.Status.CONFIRMED,
            ...
```
Ни одного обращения к Ayla в файле нет (VERIFIED субагентом по коду).

А живые брони пилота лежат **в другой таблице**. Замерил сам, сейчас:

| Таблица | Строк | Заполнен мастер |
|---|---|---|
| `booking.BookingRequest` — то, что читает дашборд | **4** | **0 из 4** (`master_id = None` у всех) |
| `booking.RemoteBookingProxy` — то, что пишут события Ayla | **21** | **21 из 21** (`specialist_id` заполнен везде) |

`BOOKING_VIA_AYLA_REST = True` (VERIFIED). Единственная живая бронь из аудита (`4d67c3cd`, 12.08, `confirmed`) — **в `RemoteBookingProxy`**, с мастером.

**Значит дефекта два, и они складываются:**
1. дашборд читает не ту таблицу — брони Ayla до него не доходят вообще;
2. даже те 4 строки, что есть в его таблице, **без мастера** — фильтр `master_id=master.id` не вернёт ни одной.

Поэтому мастер увидит идеально пустой день: HTTP 200, `active_visit: null`, `next_visit: null`, `today_summary {0, 0, null}` — без ошибки, без единого признака, что данные просто ищутся не там. **Худший вид поломки: выглядит как «сегодня записей нет».**

Субагент пометил это как INFERRED и просил проверить за пять минут — проверил, подтвердилось живыми данными. Класс: **VERIFIED**.

**Важная поправка к самому себе: раздвоение броней — не открытие, а твоё же решение.** Нашёл в проектной памяти: **A2-POST от 2026-06-01** — flip записи `BookingRequest → RemoteBookingProxy` сознательно отложен post-pilot, двойной источник истины принят как осознанный долг (yclients-брони → `BookingRequest`, AI/Mini App-брони → Ayla с зеркалом в `RemoteBookingProxy`). Мигрировать это сейчас никто и не должен.

**Новое — только следствие, которого в том решении нет.** Там перечислены риски для аналитики («может понадобиться запрашивать оба источника»), и это учтено. Про **мастерский дашборд** не сказано ничего, а он читает **ровно одну** половину — ту, где на пилоте ноль строк с мастером. То есть отложенный долг тихо забрал функцию, которая в критерий готовности входит.

Отсюда и предложение ниже: не трогать сам flip (это post-pilot, Sprint 7+), а **точечно перевести чтение мастерского дня на `RemoteBookingProxy`** — это не приближает и не откладывает A2-POST, а просто заставляет день читать обе половины. Окно расписания в своём PR 4 разводит **слоты** — к броням это отношения не имеет.

**Что предлагаю.** Взять в свой объём перевод мастерского дня на `RemoteBookingProxy` — иначе мой же критерий готовности недостижим, и «открыть дверь» окажется открыванием двери в пустую комнату. Объём небольшой: источник данных в `dashboard.py` и `schedule.py`, плюс сопоставление `CatalogMaster` ↔ `specialist_id`. **Но формально это не входит ни в §4 брифа, ни в чужой объём — эскалирую (Э-5), не делаю молча.**

### D.1. Принцип

Кнопки, не угадывание формулировок (бриф §4.2, урок DRF-1070). Соглашение уже есть и его надо соблюсти, а не выдумывать своё: `cb:{domain}:{action}[:{ref}]`, единственный разборщик — `parse_callback()` (`apps/orchestrator/ui/keyboards.py:149`), **минимум три сегмента** — `cb:staff:day` легально, `cb:staff` молча теряется. Для кнопок `open_app` payload обязан быть плоским слагом без `=`, `&`, `?`, двоеточия разрешены (`outbound.py:352-359`, тест `test_outbound.py:300`).

Домен беру `staff`. Салонный бот **не разговорный**: LLM-консьерж и диспетчер скиллов на этом пути не подключаются вовсе — только меню, коды приглашений и кнопки.

### D.2. Меню администратора

### D.4. Чего в меню сознательно нет — и почему

- **Ручная запись, перенос, отмена силами салона.** Проверено аудитом и подтверждается кодом: в Ayla **нет ни одного эндпоинта, где актором был бы сотрудник салона** (публичный `create` пускает только клиента, внутренний требует резолва в клиента, walk-in — только мастера из приложения). Это не «докрутить permissions», а новая семантика актора на стороне Ayla. **Не мой репозиторий и не моя половина.**
- **Завершить визит / не пришёл.** Та же причина: обе ручки жёстко проверяют `is_specialist` и владение строкой. Кнопка в боте без эндпоинта в Ayla — обман.
- **Правка графика мастера администратором.** Это ровно то, что сейчас пишет окно расписания (`/api/v1/tenants/me/masters/{id}/schedule/`). Когда их PR доедет, бот сможет дёргать эндпоинт. **Сейчас — нет, чтобы не строить поверх ненаписанного.**
- **Экран «Ayla Pro».** Не существует, планов вокруг него не строю (бриф §1.3).

### D.5. Одна оговорка про `open_app`, которую надо закрыть до реализации

Диплинки Mini App сегодня знают **только три клиентских слага** — `open_catalog`, `open_visits`, `open_profile` (`apps/miniapp/src/lib/max-sdk.ts:105-114`); `parseStartRoute()` возвращает `null` на всё остальное. Слага ни для одного `/admin/*` или `/master/*` **нет**. Без него кнопка «Команда» откроет Mini App на маршруте по умолчанию, а не на нужном экране — работать будет, но грубо. Лечится одной записью в `_ROUTE_MAP` и одной кнопкой. Закладываю в объём.

### Механизм

Группы создаются лениво в `enqueue`, при первом вебхуке. Поток зарегистрирован, но трафика не видел → группы нет → одним своим присутствием он останавливает вычитку рабочих потоков.

Проверено на боевом Redis: смешанное чтение `ingress:max_global` (живой, 246 записей) + несуществующий поток → `NOGROUP` и больше ничего.

Транспорт тот же, что и везде, где работает, отправка — **от салонного бота**: это переписка сотрудников, и приходить от клиентского аватара она не должна.

## Асимметрия адресатов — сознательная

- **мастер → админ:** `manager_chat_id`, затем настроенный запасной канал. Тот же каскад, что у уведомления о брони, чтобы салон настраивал **один** адрес, а не по одному на функцию;
- **админ → мастер:** лично мастеру через `linked_bot_user.chat_id`, **без запасного канала**. Разослать сообщение, адресованное одному мастеру, в общий чат салона — значит показать приватный разговор всем, кто этот чат читает. Здесь правильный отказ — молчание плюс предупреждение в лог. На пилоте все четыре мастера не связаны, так что эта ветка живая с первого дня.

## Содержимое

Тема и короткая выдержка, никогда не весь текст: уведомление говорит «зайди и прочитай», а не подменяет собой тред. Для темы, которую модель пометила чувствительной (жалобы, разговор об уходе), **выдержка не приводится вовсе** — копировать такое в общий чат значит обессмыслить сам флаг. Тест берёт `OTHER_MASTER_COMPLAINT`, то есть проверяет настоящий авто-флаг модели, а не выставленный руками булев.

Подключено `on_commit` в обеих точках — `send_message` и первое сообщение `create_thread`, — так что откатившееся сообщение о себе не объявляет. Админский путь «позвать мастера» создаёт тред без сообщения и корректно молчит.

# Секция 16 — Ответ на вопрос из Ответа 12: штатного способа нет, и «одна строка» невозможна в принципе (2026-08-21)

Отвечаю сначала на прямой вопрос, потом на то, что нашёл, пока его проверял. Второе важнее.

## Короткий ответ: штатного способа нет. Руками не создаю

Проверил все четыре канала, каждый — чтением кода Ayla, не предположением.

| Канал | Есть? | Чем проверено |
|---|---|---|
| Management-команда | **нет** | `users/management/commands/` — только `cleanup_deleted_users`; `tenants/…` — только `backfill_tenants`. Ни одна команда в проекте не упоминает `TenantUserRelationship` |
| Django admin | **нет** | `TenantUserRelationship` не зарегистрирован ни в одном `admin.py`. Строку через админку не создать вообще |
| REST-эндпоинт grant | **нет** | есть только **revoke** (`tenants/relationships_admin_api.py`), и он под `IsTenantAdmin` — курица и яйцо: чтобы назначить админа, нужен админ |
| Мост «`user.role` + `user.tenant` → `save()`» | **есть, но не работает** | `users/signals.py:66` |

Мост — единственный кандидат, и он отказывает **дважды**, независимо:

1. `get_or_create(user=…, tenant_id=…, is_active=True, defaults={'role': …})`. У актора бота **уже есть активная строка** с ролью `customer` (твой же замер). `get_or_create` её найдёт и вернёт — `defaults` к найденной строке не применяются. Роль останется `customer`. Молча.
2. `User.tenant` вообще нет в `fieldsets` админки (`users/admin.py:80-84` — там только `role`, `phone`, `is_verified`, `deleted_at`). Выставить привязку штатно негде.
3. А если сначала деактивировать `customer`-строку и потом сохранить пользователя — включится F2-защита `has_revoked` (`users/signals.py:52-65`) и мост **сознательно** пропустит: «re-grant requires explicit admin action».

Так что нет. Согласен с тобой и не создаю строку руками.

## Что важнее: «одна строка» — не одна строка, и она ломает владельцу бронирование

Пока искал способ, упёрся в схему.

**`tur_unique_active`** (`users/models.py:741-747`) — partial unique на `(user, tenant)` при `is_active=True`. **Максимум одна активная роль на пару.** Роли в Ayla взаимоисключающие — в отличие от бота, где по ADR-0008 они аддитивны.

Значит `INSERT` admin-строки при живой customer-строке — не «одна строка», а `IntegrityError`. Апгрейд роли неизбежно двухшаговый: погасить активную `customer`, создать `admin`.

И вот здесь цена, которую надо назвать вслух.

`appointments/application/services/create_booking_service.py:206-219`:

```python
existing = list(
    TenantUserRelationship.objects.select_for_update().filter(
        user_id=dto.client_id, tenant_id=specialist.tenant_id,
    )
)
has_revoked = any(not row.is_active for row in existing)
if has_revoked:
    raise NotFound("Specialist not found.")
```

Фильтр — **без роли**. Любая неактивная строка для пары `(человек, салон)` запрещает бронирование навсегда, по любому каналу. Смысл правильный: забаненный клиент не должен перезайти через другой вход.

Но погашенная `customer`-строка от апгрейда роли выглядит **точно так же**, как бан. Следствие:

> **Владелец, ставший администратором «Формулы тела», больше не сможет записаться в свой салон. Ни через бота, ни через приложение. Отказ — `NotFound`, то есть «мастера не существует».**

И вернуть это штатно нельзя: F2 в сигнале смотрит на то же самое и откажется ре-грантить.

Владелец 14 августа тестировал продукт именно записью на себя. После выдачи ему роли админа этот путь у него закроется, а сообщение будет выглядеть как поломка каталога, а не как следствие роли.

Это не аргумент против DRF-1228 — это то, что надо решить **до** первой выданной роли, потому что операция необратима штатными средствами.

## Развязки — выбор не мой, но вот они

**Вариант 1 — различать «отозван» и «роль изменена».** При апгрейде закрывать строку с `revoke_reason='role_change'` и исключить такие строки из двух проверок `has_revoked` (`create_booking_service.py:213`, `signals.py:52`). Минимальная правка, честная семантика: смена роли не есть прекращение доступа. Цена — лёгкое искажение 152-ФЗ-истории: строка закрыта, хотя доступ не прекращался; в аудите это будет видно по `revoke_reason`.

**Вариант 2 — разрешить несколько активных ролей**: включить `role` в partial unique. Правильнее по модели и ближе к ADR-0008, но трогает каждое чтение TUR, включая `get_jwt_tenant_claim`. Дороже, и это не пилотный объём.

Рекомендую **вариант 1 на пилот, вариант 2 после**. Но это правка в чужом домене и с необратимым следствием для людей — прошу решение владельца, а не моё.

## Как выдавать роль, когда развязка выбрана

Курица-и-яйцо снимается не админским JWT, а служебным входом: `IsInternalBearer` (`users/permissions.py:210`) — бот уже так ходит, и docstring прямо предписывает шаблон «per-tenant эндпоинт требует явный `tenant_id` в теле, чтобы утёкший bearer не гулял по тенантам». То есть grant — это `internal`-ручка, а не admin-ручка, и приглашение работает без предсуществующего админа.

Для **DRF-1227** серверная половина в Ayla уже есть и переиспользуема: `revoke_tenant_user_relationship` (`users/services.py:196`) — транзакция, `select_for_update`, всегда `OutboxEvent tenant.relationship.revoked`, каскад по уходу мастера. Нужен только служебный вход к ней, потому что бот не носит JWT администратора.

**Атрибуция сохраняется** — проверил, это была моя главная тревога. Бот шлёт `X-External-User-ID: bot:{channel}:{channel_user_id}` (`apps/integrations/ayla/user_proxy.py:46`), то есть `bot:max:831…` — это **конкретный человек**, а не единый актор бота. Действие приглашённого администратора оставит его идентификатор. Прокси-пользователь создаётся лениво с `is_proxy=True, role='client'` (`users/services.py:99`).

# Секция 17 — DRF-1227, бот-половина: отзыв доступа. И дефект схемы, который она вскрыла (2026-08-21)

Взял то, что ни от чего не зависит и нужно при любой развязке в Ayla. Ayla-половину не трогал — жду GO.

## Что было

Ты написал: `deactivated_at` упоминается тринадцать раз и не выставляется никем. Подтверждаю и уточняю: **в живом коде он только читается** — каждый фильтр `deactivated_at__isnull=True`. Пишут его исключительно тесты. То же самое с `CatalogMaster.linked_bot_user`: погашение кода его ставит, не снимает никто.

То есть салон мог нанимать и не мог уволить. Каждый выданный код оставался живым до конца существования тенанта.

## Что построил

`apps/identity/services/staff_revoke.py` + `POST /api/v1/admin/staff/revoke/`.

**Отзыв — про человека, а не про роль.** Снимается всё сразу: каждая активная строка `TenantStaff` и линк мастера. «Снять админа, оставить ресепшен» — это *изменение* роли, другое намерение; отдавать его боковой дверью опасной операции неправильно.

**Мастер остаётся бронируемым.** `invite_status` и `is_active` не трогаю: `bookable()` фильтрует ровно по ним, и отзыв доступа, который заодно снимает мастера с продажи, обнаружат клиенты, а не оператор. Отзыв логина и уход мастера — разные решения, у второго уже есть дом (архив, MM5).

**Владелец — отказ.** Активный владелец один, и owner-код может выдать только владелец. Деактивировать эту строку значит оставить салон, в который никто никогда не войдёт. Передача владения — настоящая операция (снять старого + создать нового атомарно), и она заслуживает своего пути; пока его нет, дверь без обратного хода закрыта.

**Себя отозвать нельзя.** Админ, снявший себя, обратно не вернётся без владельца.

**Повтор — не ошибка.** Второй вызов отвечает 200 и `changed: false`: человек, не уверенный, что первый раз сработал, нажмёт ещё раз, и ошибка научила бы его, что не сработало.

Идентификация двумя способами, ровно одним за вызов: `master_id` (то, что у экрана команды уже есть на руках) или `bot_user_id`. Одного было бы мало — админская поверхность знает мастеров только по каталожному id.

## Дефект, который нашли тесты

Тест «после отзыва можно нанять заново» упал с `IntegrityError`.

`TenantStaff.Meta.unique_together = (tenant, bot_user, role)` — **тотальный** unique, без учёта `deactivated_at`. И он противоречит полю, рядом с которым стоит: докстринг `deactivated_at` обещает, что мягкая деактивация сохраняет назначение для аудита, — но под тотальным индексом эта история вмещает ровно одну запись. Повторная выдача той же роли тому же человеку падала, и падала бы **пятисоткой на экране владельца**, потому что не-owner `IntegrityError` пробрасывался наружу.

Итог был бы такой: отозвал доступ у администратора, через месяц зовёшь обратно — и получаешь ошибку сервера без объяснений.

Миграция `0012`: тотальный unique → partial по активным строкам, той же формы, что уже существующий `unique_active_owner_per_tenant`. Схема была наполовину в этом стиле; теперь согласована. На живых данных безопасна в обе стороны: снятие уникального индекса не конфликтует никогда, а добавление partial не может конфликтовать, потому что двух активных строк с одной ролью снятый индекс не допускал.

Заодно поправил обработку гонки в `_grant_staff_role`: не-owner `IntegrityError` теперь означает «параллельное погашение уже выдало ту же роль» и отвечает `already_had_role`, а не 500. Вставка обёрнута в savepoint — иначе исключение отравляет внешнюю транзакцию.

## Отличие от Ayla, которое стоит держать в голове

В боте отзыв **не бан**: деактивированная строка не мешает выдать роль заново. В Ayla — ровно наоборот, любая неактивная строка `TenantUserRelationship` навсегда запрещает и бронирование, и ре-грант (F2-защита, §16). Две системы, где «отозван» значит разное, — то самое место, где рассинхронизация прав перестаёт быть теоретической. Когда придёт GO на Ayla-половину, это надо будет свести явно, а не понадеяться на симметрию.

## По твоему вопросу из Ответа 13 — `base.py:1290-1305`

Да, тот же класс, что DRF-1233. Абзац утверждает «a MAX webhook is first gated on the single shared `MAX_WEBHOOK_SECRET`» и «the current single-secret gate is unchanged by #1019» — оба неверны с блока 1.1.

**Но поправка там уже есть — двадцатью строками ниже**, на `base.py:1326-1329`, я её написал тогда же:

> «NOTE for readers of the GLOBAL_BOT_TOKENS comment above: the "single shared secret" gate it describes is what DRF-1061 replaces. Once a deployment declares MAX_BOTS, the gate matches against every registered secret and the matching entry — not the GLOBAL_BOT_TOKENS membership test — decides the stream.»

Так что ловушка ровно в том, что читатель верхнего абзаца не обязан дочитать до поправки. Чинить надо сам абзац, а не добавлять третье уточнение. Однострочная правка, и она в DRF-1233 — не трогаю, чтобы не пересечься с тем, кто её взял; скажи, если удобнее, чтобы сделал я.

По существу утверждение тоже устарело: `bot.stream` берётся из записи реестра (`views.py:131`), а `GLOBAL_BOT_TOKENS` участвует только при синтезе legacy-записи, когда `MAX_BOTS` не объявлен.
