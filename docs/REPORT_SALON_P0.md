# ИТОГОВЫЙ ВЕРДИКТ

# DRF-1249 READY TO DESIGN WITH EXPLICIT BLOCKED STATES

Дизайнер может рисовать **восемь** сценариев как работающие, **один** — с явным ограничением, **шесть** — только как заблокированные состояния с известной причиной.

**Условие вердикта** — обе поставки мержатся и принимаются два решения владельца:

**№2 (администратор в правильной форме) — обязательно.** Без него ни один из восьми SUPPORTED-сценариев на пилоте не выполнится: всё отдаёт 403. Это операция ops, не код.

**№1 (право бота ставить отгул) — определяет**, три сценария SUPPORTED или BLOCKED. Без решения рисовать как BLOCKED.

Базовую архитектуру переделывать не придётся: второго booking-движка нет, новой permission-модели нет, AI-специфичной логики нет, Controlled Pilot не расширен.

# Восемь опровержений

## О-1. Пробела В-2 не существует — полномочие уже проверялось

Аудит утверждал, что салонные `create` / `reschedule` / `cancel` опираются только на классовый список.

По коду неточно. `IsTenantAdmin` проверяет активную admin-связь именно в `request.tenant` (`users/permissions.py:339-344`), а `_SalonBookingBase._get_booking` достаёт строку с фильтром `tenant=request.tenant` (`tenants/appointments_api.py:230-241`). Композиция этих двух — **ровно те две проверки**, которые делает ветка `SALON` в `resolve_booking_operator`.

Новая проверка сегодня **не может не пройти**. Полномочие есть и оно правильное.

**Отсутствовал тест.** Ни один тест не утверждал этих свойств — можно было ослабить permission-список или убрать `tenant=`, и набор остался бы зелёным.

Сделано: `resolve_booking_operator` подключён к `reschedule` и `cancel` **как явная формулировка правила**, не как затыкание дыры. К `create` не подключено ничего: `may_operate_on_bookings` слабее уже стоящего `IsTenantAdmin`, вызов был бы тавтологией. Вместо кода — 23 теста на отказ.

**Деталь, которую легко сломать:** разрешённая capacity намеренно **не переиспользуется** как `initiator_role` в DTO. Это значение выбирает политику возврата при отмене, а мастер с админским грантом на своей записи резолвится как `specialist` — прогон через DTO молча переоценил бы отмену, сделанную за стойкой.

## О-2. Отдельный read-only токен ничего не даёт

Аудит рекомендовал `AYLA_READONLY_API_TOKEN`. Посылка верна, вывод нет: предъявитель — **один и тот же сервис**. Бот уже держит `AYLA_INTERNAL_API_TOKEN` и уже имеет салонную write-поверхность под ним. Второй секрет добавляет ops-артефакт и **ноль защиты**.

Аналогия с `IsIdentityProvisioningBearer` не работает: тот секрет **никогда не деплоится в бот**, в этом весь смысл.

Реально ограничивает доступ — проверка админского гранта у **человека** из `X-External-User-ID`. Утёкший токен плюс чужой слаг не читает ничего.

## О-3. Четыре смешанных класса не надо разделять

Пометодная гранулярность в DRF достигается permission-классом, читающим `request.method` — так устроен штатный `IsAuthenticatedOrReadOnly`.

`ServiceCredentialIsReadOnly` отказывает всему кроме `GET`/`HEAD`/`OPTIONS`, **только если** запрос аутентифицирован сервисным Bearer, и воздерживается для человека с JWT. Он только вычитает. Правило владельца выполняется **по построению**, а не по памяти разработчика, и не плодит четыре дублирующих view.

## О-4 (снято). Флаг автозакрытия выставлен 23.08 в 13:38 UTC

Выставлен **главным окном** по отдельному указанию владельца, уже после написания брифа и до замера исполнителя. **Бриф был верен, когда писался**; расхождение — дрейф контура, а не ошибка постановки.

Существеннее другое: **одного флага мало.** Обязательна вторая настройка `BOOKING_AUTO_COMPLETE_NOT_BEFORE` — без неё задача отказывается работать и пишет ERROR, потому что без нижней границы она завершила бы (**и выставила счёт, и запросила отзывы по**) каждую прошедшую запись в истории. Граница выставлена на момент включения.

Поэтому «завершённых визитов ноль» на замере — **не загадка, а корректная работа защиты**: две прошедшие записи остались незакрытыми намеренно, чтобы не выставить счёт задним числом.

Пара настроек закомментирована в `djangoProject/settings/base.py:896`.

Вывод для DRF-1249 не меняется: **завершение визита на пилоте практикой не подтверждено ни разу.**

## О-5. Одинаковых копий overlap-запроса две, а не три

`users/schedule_api.py:428` и `users/internal_schedule_api.py:143` — посимвольно одинаковый `.count()`. Третья, `schedule_admin_api.py:280`, — **другая семантика**: обработка `UnresolvedBookingsError`, возвращает список неразрешённых id плюс полный impact, а не число.

Вынести все три значило бы слить два разных контракта. Владелец сказал «только безопасно идентичную часть» — вынесены две.

## О-6. Ayla сегодня не может действовать администратором ни в одном салоне

```
ayla-marketplace admins: 1   rels: 11
formula-tela     admins: 0   rels: 7
mkt-*            admins: 0
proxy users: 16 | bound proxies: 1
```

Единственный админский грант принадлежит учётке с `role="admin"`, `is_proxy=False`. `bind_external_identity` (`users/services.py:185-189`) **отказывается** привязывать внешнюю идентичность к такой учётке: цель обязана быть настоящим активным **клиентским** аккаунтом.

**Обе поставки код-полны, но операционно закрыты.** Пока в тенанте не появится администратор *в форме клиентского аккаунта, повышенного связью*, Ayla получает 403 на всё.

## О-7. Ayla читает график, но писать не может — расхождение со списком владельца

Список SUPPORTED включает «partial-unavailability proposal». Часть 2.1 требует, чтобы запись не открылась. Требования несовместимы без отдельного решения.

Выбрана буква части 2.1: сервисный credential read-only. Следствие — `POST .../time-off/` для Ayla **закрыт**. Осознанный выбор: та ручка **отменяет записи клиентов** по resolutions, и отдать боту такое право — владельческое решение, а не побочный эффект открытия чтения.

## О-8. Салон видит внешний идентификатор клиента

`_client_name` (`tenant_day_service.py:122-138`) при пустых именах возвращает `user.username`, отсекая только значения на `+`. Для клиента из бота это `bot:<канал>:<внешний id>`. Журнал дня показывает салону `bot:telegram:123456789` как «имя клиента».

Телефон не раскрывается, но стабильный внешний идентификатор мессенджера виден. Пре-существующее.

# Что изменилось в контракте

## Чтение (PR #240)

**Было:** сервисный credential доставал пять ручек — четыре write и поиск клиента. Журнал дня и график аутентифицируются JWT, который отвечает **401 на непрозрачный Bearer до любого permission**. Единственное дерево, куда токен проходил (`/api/v1/internal/`), исключено из tenant-middleware: `GET /internal/specialists/` отдаёт **всех активных мастеров платформы**.

**Стало.** Доступны на `GET`: `/tenants/me/day/`, `masters/{id}/schedule/`, `schedule/impact/`, `time-off/`, `schedule-exceptions/`, `/tenants/me/closures/`.

Арендатор берётся из `X-Tenant` через middleware, querysets скоуплены, произвольный `tenant_id` из тела не принимает никто. Чужой слаг недостаточен: `IsTenantAdmin` доказывает, что **человек** из `X-External-User-ID` держит активный грант именно в этом салоне.

Контракт заголовков: `Authorization: Bearer <AYLA_INTERNAL_API_TOKEN>`, `X-External-User-ID`, `X-Tenant`, **`X-App-Type: pro`**.

`IsProApp` оставлен на всех шести view. Исключить префикс из `AppTypeMiddleware` было нельзя — исключение выставляет `request.app_type = None` и делает `IsProApp` невыполнимым **для всех вызывающих навсегда**. **Ни один permission не ослаблен.**

## Запись графика (PR #241)

**Было:** `PUT schedule-exceptions/` с `is_working_day=false` отвечал **200** поверх живой записи; `POST closures/` отвечал **201**. Ни одного теста.

**Стало:** обе операции отвечают стабильным `HAS_ACTIVE_APPOINTMENTS` **409**. Ничего не отменяется, ничего не переносится, resolution-пути нет.

Три вещи сделаны правильно:

**Окно считается по мастеру, а не по салону** — у `Tenant` нет таймзоны, одна локальная дата даёт разное UTC-окно каждому мастеру. Закрытие проверяет **всех** мастеров тенанта.

**Границы дня строятся из двух дат** (DST-безопасно), как в `TenantClosureBusyIntervalProvider` — чтобы read и write не разошлись в том, какие мгновения покрывает «закрытый вторник».

**Отказ ничего не пишет.** `PUT` — upsert; отказ оставляет прежнюю строку побайтово нетронутой.

Сохранено различие двух 409: `CLOSURE_EXISTS` и `HAS_ACTIVE_APPOINTMENTS`.

# Пробелы

## Решения владельца

**№1. Дать ли боту право ставить мастеру отгул**, если этот отгул отменяет уже записанных клиентов. Сегодня закрыто. Цена открытия — одна строка плюс тесты на соблюдение `impact_token`-контракта (иначе бот подтвердит решения по набору записей, которого не видел).

**№2. Завести пилотного администратора в правильной форме.** Клиентский аккаунт → повысить связью → один раз связать бот-идентичность. Без этого весь салонный контур отвечает 403.

## Backend-пробелы

**№3. Operational events — `NOT SUPPORTED`.** Read-API событий нет ни одного во всём URL-дереве. Отвечать «с 8 утра произошло 3 изменения» **нечем**.

**№4. Weekly recurring shrink guard.** Оформлен как gap **и закреплён тестом** `TestWhatIsDeliberatelyNotGuarded` — закрытие потребует осознанно поменять assertion.

Нужно: старая effective frame против новой → развёртка по `BOOKING_MAX_AHEAD_DAYS = 60` → отбор записей, потерявших покрытие **именно из-за изменения** → transaction/race protection, которой у `ScheduleView.put/patch` нет.

Наивно нельзя: запись **законно** существует вне рабочих часов — `check_schedule_frame` зовётся только для `actor_role == "user"`.

**№5. Сокращение часов на конкретную дату** — та же задача сравнения рамок. Тоже закреплено тестом.

**№6. Authoritative free-time search — отсутствует.** `specialist_id` скаляр и в DTO, и в протоколе провайдера. Ayla **не вправе** утверждать «это время гарантированно свободно».

**№7. Privacy-safe discriminator клиента — отсутствует.** Полный телефон не отдаётся **нигде** (проверены все пять поверхностей). Хелпера маскирования в дереве нет ни одного. Различить двух «Анн» нечем.

Готовый вариант ценой одной строки: `TenantUserRelationship.granted_at` — «клиент этого салона с такого-то числа». Строка уже загружена через `select_related`, скоуплена по тенанту, PII не является. **Требует одного слова владельца, не работы.**

**№8. Атрибуция салонной отмены сломана.** `cancel_reschedule_service.py:251, 477, 492` — три тернарника без ветки `salon`, событие уходит как `actor: "user"`. Правильные таблицы лежат рядом и не вызываются. Не чинилось: часть 4 запрещает событийный слой.

**№9. Изменения графика не порождают событий вовсе.** Именно это делает «Требует внимания» непостроимым даже при появлении event-API.

**№10. TOCTOU на всех дешёвых 409.** Проверка вне транзакции и без блокировки — и в новых guard'ах, и в старых. Для P0 приемлемо: ловит человеческую ошибку, не гонку. Гарантией называть нельзя.

**№11. Салон видит `bot:<канал>:<id>` вместо имени.** См. О-8.
