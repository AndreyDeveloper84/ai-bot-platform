# Секция 2 — 2026-08-24, экран выдачи кодов сотрудникам

## Что это за экран

Форма в админской поверхности Mini App, где владелец салона выдаёт человеку
**одноразовый код доступа**. Человек отправляет код салонному боту и получает роль.

Сегодня единственный способ завести сотрудника — management-команда на пилотном
хосте, то есть **через SSH**. Докстринг самого эндпоинта говорит это прямо:

> «That does not scale and it puts the platform team on the critical path of
> every hiring decision. The owner should be able to add an administrator
> without asking anyone.»

## Что уже готово — обе половины, кроме экрана

**Выдача:** `POST /api/v1/admin/staff/invite/`
(`config/urls.py:102` → `apps/admin_api/urls.py:92` → `apps/admin_api/views_staff_invite.py:78`)

```
body:  role       owner | admin | receptionist | master   (обязательно)
       master_id  обязателен при role=master — СУЩЕСТВУЮЩАЯ строка каталога
       note       произвольная метка для себя
→ 201  {code, role, expires_at, invite_id}
```

**Погашение:** человек шлёт код в диалог салонному боту —
`apps/channels/max/salon_handler.py:199` (распознавание) → `:510`
(`redeem_staff_invite`). С ограничением частоты и хешированием.

**Две роли делают разное, и это определяет форму экрана:**

| role | что происходит | код |
|---|---|---|
| `admin` / `receptionist` / `owner` | создаётся строка `TenantStaff` — **выдаётся доступ** | `_grant_staff_role`, `staff_invites.py:358` |
| `master` | **связывается существующая** карточка каталога с MAX-аккаунтом, новая не создаётся | `_link_master`, `staff_invites.py:419` |

`owner` может выдать только владелец (`views_staff_invite.py:113`) — иначе админ
мог бы забрать салон, и единственной защитой остался бы частичный уникальный индекс.

## Чего нет

Фронта. `git grep 'staff/invite' -- apps/miniapp` — **пусто**.

Экран `/admin/team/invite` существует и **делает другую работу**:
`AdminInviteMasterScreen.tsx:299` зовёт `inviteMaster` (`admin-api.ts:815`), который
бьёт в `masters/invite/` и **создаёт нового мастера в каталоге**. Существующему
человеку доступ он не даёт — ровно то расхождение, ради которого эндпоинты и развели.

Значит это не «доработать экран», а **второй экран рядом**, и на него нужны входы
из `AdminTeamScreen.tsx:310` и `AdminServicesMatrixScreen.tsx:521`, которые сегодня
оба ведут в форму создания мастера.

## Острая деталь, которую нельзя проглядеть в вёрстке

Код возвращается открытым текстом **ровно один раз** — хранится только хеш,
восстановить нельзя (`views_staff_invite.py:38-42`). Экран обязан это показать и
**не может предполагать, что перечитает код позже**. Это отдельное состояние
экрана, а не тост.

## Про твой мотив — механизм подтверждаю, счёт нет

Ты пишешь: «не связаны трое мастеров из четырёх — они открывают «Мой день» и видят

**Механизм подтверждаю**: `role=master` связывает существующую строку, это

**Счёт «трое из четырёх» — не подтверждаю и не опровергаю.** Это данные пилотной

## 4. DRF-1226 — вызывающий назван, причина установлена, правки нет

Граница задачи соблюдена: **замер, не правка**.

### Кто зовёт

**Mini App, и он единственный, кто вообще зовёт эту ручку.**

```
apps/miniapp/src/App.tsx:1204          useEffect(() => { void loadMe(); }, [loadMe])   ← безусловно при старте
apps/miniapp/src/App.tsx:1185          loadMe → getMe()
apps/miniapp/src/lib/admin-api.ts:122  request("/api/v1/me", { method: "GET" })
```

Ручку отдаёт **бот**, не бэкенд: `config/urls.py:85` → `apps/identity/urls.py:19` → `apps.identity.views.me_view`. В коде бота других вызывающих нет.

### Почему 400, а не 401

```
apps/miniapp/src/lib/admin-api.ts:51   if (initData) headers.set("Authorization", `MaxInitData ${initData}`);
```

**При пустом `initData` заголовок не ставится вовсе.** Сервер отвечает `apps/miniapp_api/auth.py:176` — `InitDataMalformed("missing Authorization header")` → **400**, а Django `log_response` пишет это как обычный `Bad Request: /api/v1/me`.

Это ровно то, что в задаче: 400, не `TENANT_REQUIRED`, ноль совпадений с ним в логах.

### Воспроизведено снаружи, только чтение, ничего не мутировано

```
GET https://api-dev.gobeauty.site/api/v1/me
  без заголовка                → 400 {"error":"malformed","detail":"missing Authorization header"}
  Authorization: Bearer x      → 400 {"error":"malformed","detail":"expected 'MaxInitData <raw>' prefix"}
  MaxInitData <мусор>          → 401 {"error":"bad_signature",...}

miniapp-dev.gobeauty.site и proapp.gobeauty.site — тот же ответ, оба проксируют туда же.
```

Значит **каждый из девяти отказов — запрос вообще без валидного префикса `MaxInitData`**, то есть старт приложения с пустым `initData`.

### Когда `initData` пуст

Мост `https://st.max.ru/js/max-web-app.js` живой (200, 21 КБ), стоит блокирующим `<script>` в `<head>` **до** бандла, и читает `WebAppData` **синхронно** из `location.hash` с запасным чтением из `sessionStorage`.

**Гонки нет** — я её проверял отдельно, потому что она была самой правдоподобной гипотезой. Приложение, открытое изнутри MAX, имеет `initData` уже на первом рендере.

Пусто оно значит одно: документ открыт **без `#WebAppData`** — то есть в обычном браузере, а не в контейнере MAX. Автоповтора нет (`App.tsx:1113` — только кнопка «Попробовать снова»), так что один отказ = один старт или один тап по кнопке.

### Ответ на вопрос владельца «эти 400 ловит Mini App?»

**Да — но с уточнением, которое меняет вывод.**

Ловит их Mini App, и других вызывающих нет. Но Mini App, открытый **правильно, из MAX**, получает 200. Восемь двухсоток — это он. Девять четырёхсоток — это открытия **мимо контейнера**.

Чего я **не могу** доказать отсюда: были ли эти девять живыми людьми или пробами монитора. Различает это одна строка на хосте:

```bash
zgrep -h '/api/v1/me' /var/log/nginx/access.log* \
  | awk '$9==400' | grep -oE '"[^"]*"$' | sort | uniq -c | sort -rn
```

User-Agent отделит браузер человека от `curl`/монитора. **Это последний шаг задачи, и он твой** — ssh мне здесь недоступен.

### Что видит человек, когда это случается

Не падение: `App.tsx:1255` роняет старт в `CustomerFallbackWithBanner` — клиентская поверхность с плашкой «Не получилось загрузить ваш профиль».

Но условие `if (initData)` повторено **в четырёх местах трёх клиентов** (`api.ts:21`, `admin-api.ts:51`, `master-api.ts:30`, `master-api.ts:291`), поэтому в этом состоянии **весь** Mini App шлёт запросы без заголовка. Человек получает оболочку, в которой отказывает всё, что он тронет.

### Что я предлагаю сделать (после твоего GO, не раньше)

Две правки, обе маленькие, обе в моей территории:

1. **Сервер: нет заголовка → 401, а не 400.** «У меня нет учётных данных» — это 401 по определению. Сегодня это 400, и из-за этого `loadMe` (`App.tsx:1191` ловит только 404) уходит не в «Доступ не настроен», а в клиентский фолбэк. Правка меняет и код, и экран, который видит человек.
2. **Клиент: не слать запрос без `initData` вовсе.** Четыре `if (initData)` заменить на явный отказ на старте — тогда в логах пилота вместо девяти 400 будет ноль, а человек получит честный экран.

**Не делаю ни того, ни другого до ответа**, потому что вторая правка обнулит сигнал, по которому ты меряешь, и делать это надо после того, как посмотрел User-Agent, а не до.

## 5. DRF-1323 — заблокирована, и один блокер территориальный

### Опровержение шага 1

Задача говорит: «Не трогать `MAX_BOT_WEB_APP`… Работать с `MAX_MINIAPP_URL`».

**Так чип работать не будет.** Лестница `apps/skills/welcome/skill.py:716-745, 865-890`:

* `MAX_BOT_WEB_APP` задан → `open_app`, Mini App открывается **внутри клиента MAX** и получает `initData`;
* `MAX_BOT_WEB_APP` пуст, `MAX_MINIAPP_URL` задан → **`link`**, то есть `apps/channels/max/outbound.py:362` — обычная ссылка во **внешний браузер**.

Внешний браузер не получает `#WebAppData`. Значит чип, построенный через `MAX_MINIAPP_URL`, приведёт человека ровно в состояние из пункта 4: `/api/v1/me` → 400 → плашка «Не получилось загрузить ваш профиль».

**Заполнение `MAX_MINIAPP_URL` не откроет карточку мастера — оно увеличит число 400.** Настройка, которая нужна на самом деле, — это `MAX_BOT_WEB_APP`, и задача её запрещает трогать по верной причине (значение неизвестно, выдумывать нельзя). **Значит блокер задачи — не «заполнить настройку», а «узнать идентификатор приложения клиентского бота у MAX».** Это вопрос владельцу, а не работа.

### Вторая находка: приветствие не знает про реестр ботов

`skill.py:697-698` и `865-866` читают **глобальные** `settings.MAX_BOT_WEB_APP` / `settings.MAX_MINIAPP_URL`, тогда как реестр держит их **на каждого бота** (`bot_registry.py:221` — префикс `MAX_BOT_{SLUG}_`, поля `web_app`, `miniapp_url`).

Поэтому салонный бот Mini App открывает (через `staff_menu.py`, который ходит в реестр), а клиентское приветствие — нет, и починить это правкой одного env нельзя: глобальная переменная уедет обоим ботам сразу.

Сделать приветствие реестро-осведомлённым — это **моя** территория («построение ссылок Mini App»), объём небольшой, ~2 SP. **Но файл делят с окном первого экрана** (они правят тексты и чипы). Бриф велел координироваться через тебя. **Скажи, брать ли** — я не полезу молча.
