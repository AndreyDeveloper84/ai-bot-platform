# §142 `salon_block` — замер до кода

**Дата замера:** 11.09.2026.
**Базы:** `ai-bot-platform` — `a6d24a72`; каталог (`djangoproject`) — `origin/dev` `ba0954aa`.
**Задача:** DRF-1240 / §142.

Замер сделан чтением кода двух репозиториев, а не рассуждением о них. Ниже
названы файлы и строки, чтобы каждое утверждение можно было перепроверить.

---

## Вопрос

Решение владельца (§142) требует, чтобы салон закрывал время мастера
**отдельным действием**, а не заявкой, якобы поданной мастером, и чтобы
**перенос или отмена решались отдельно для КАЖДОЙ записи**.

Прежде чем это писать, надо знать: **что происходит сегодня с уже стоящими
записями, когда отгул мастера одобряют?**

## Ответ: ничего. Отгул отказывают.

```
bot-platform  apps/admin_api/services/availability.py:183
              → booking_client.create_specialist_time_off(...)
              → POST api/v1/internal/specialists/{id}/time-off/

каталог       users/internal_schedule_api.py:161-171
              active_count = count_active_bookings_in_window(...)
              if active_count > 0:  → 409 HAS_ACTIVE_APPOINTMENTS
```

Записи **не переносятся и не отменяются**. Одобрение не проходит вовсе:
`ScheduleBlockConflictError` → `AvailabilityDecisionError("has_active_appointments", 409)`
(`availability.py:191-198`).

Это не дефект. Отказ верен сам по себе: никто не должен мочь бросить
записанного клиента мимоходом. Массовое действие, которое §142 запрещает,
сегодня попросту невозможно — потому что возможно **никакое**.

### Чего администратор при этом НЕ узнаёт

Внутренний маршрут отвечает **числом**, а не списком:

> `f"Cannot block time: {active_count} active appointment(s) overlap this period."`

Кого именно затронет закрытие — из этого ответа не следует. Требование §142
«показать затронутые записи» сегодня не выполняется на этом пути.

## Дверь ровно одна, и это проверено счётом

`create_specialist_time_off` во всём `apps/` зовётся **из одного места** —
`availability.py:183`, одобрение заявки, поданной мастером. Отрицательный
эталон `TestTheOnlyDoorIsTheMastersOwnRequest`
(`apps/admin_api/tests/test_availability_ayla_block_1062.py:362`) пинит это
и в докстринге говорит прямо:

> **Этот тест обязан покраснеть в день, когда появится вторая дверь.**

Салонная инициатива, проведённая через эту дверь, записала бы в журнал
**ложного автора** — мастера, который ничего не подавал. Это и есть то, что
§142 запрещает дословно.

## Половина §142 уже существует — в каталоге, не у нас

Каталог реализовал DRF-1062 §C на **административной** поверхности:

| маршрут | что делает |
|---|---|
| `GET tenants/me/masters/{id}/schedule/impact/` | какие живые записи вытеснит предполагаемое отсутствие; отдаёт `impact_token`, отпечаток набора |
| `POST tenants/me/masters/{id}/time-off/` с `resolutions` | отсутствие и решение по КАЖДОЙ вытесненной записи применяются вместе, одной транзакцией |

`users/schedule_admin_api.py:293` и `:331`. Отказы названы словами:
`IMPACT_CHANGED` (пока администратор решал, набор изменился — 409 со свежим
предпросмотром), `UnresolvedBookingsError` (решение принято не по всем),
`UNSUPPORTED_RESOLUTION`.

`apply_absence_with_resolutions` принимает `actor` и, судя по докстрингу,
«offer a reschedule» намеренно заменён на cancel-then-offer, а бот
подхватывает предложение из `booking.cancelled` с
`reason_code=master_unavailable` (`users/services.py:1269-1291`).

То есть предпросмотр, поштучное решение, атомарность и автор — **есть**.
Нет их у нас.

## Почему мы туда не дотягиваемся сегодня — и это сделано НАРОЧНО

Внутренний маршрут, которым ходит бот, поштучные решения не принимает, и
докстринг объясняет почему:

> The flow that settles those bookings (preview → decide per booking →
> apply) is deliberately **NOT** exposed here: cancelling somebody's
> appointment is a decision with money and a message attached, and it
> belongs on a surface where a **named human** is the actor, not a shared
> service token.

Административные же маршруты защищены `IsAylaReadOnly` (DRF-1297 B-1):
сервисный Bearer Ayla получает **только чтение**, всё, кроме
`GET/HEAD/OPTIONS`, отказывается (`users/schedule_admin_api.py:51-59`).

**Следствие, важное для планирования:**

* `GET .../schedule/impact/` — сервисным токеном **достижим**. Предпросмотр
  мы можем показать уже сегодня.
* `POST .../time-off/` с `resolutions` — сервисным токеном **недостижим по
  построению**. Нужен названный человек, а не общий токен.

Это не препятствие, которое надо обойти. Это ровно то, чего требует §142
(«сохранить автора»), только выраженное правами, а не проверкой. У нас уже
стоит тот же принцип на одобрении: §143, отказ `actor_required` 409 при
отсутствии названного автора (`availability.py:176-182`).

## Что из §142 чем закрывается

| требование §142 | сегодня | где писать |
|---|---|---|
| отдельное действие, не заявка мастера | **нет** — одна дверь | bot-platform |
| указать причину | есть в `reason` | — |
| сохранить автора и время | **время да, автор нет** на строке `SpecialistTimeOff` (`appointments/models.py:335-347`: `created_at` есть, автора нет); атрибуция уходит только в аудит Ayla через `external_user_id` (§117) | каталог |
| уведомить мастера | есть на одобрении (`_enqueue_master_dm_post_commit`) | bot-platform |
| показать затронутые записи | **нет** на нашем пути (число, не список); в каталоге есть `impact` | bot-platform |
| решить перенос/отмену КАЖДОЙ записи | **нет** у нас; в каталоге есть `resolutions` | bot-platform |
| записать в аудит | частично (лог + `external_user_id`) | оба |

## Названные пределы этого замера

* Читался **код**, а не боевая база. Сколько раз отказ 409 случался на пилоте
  и сколько записей обычно попадает в окно — **не измерено**.
* Рабочая копия каталога в общем чекауте стоит на ветке
  `feat/memory-foundation-internal-api` (`8711af52`), и по ней маршрутов
  `internal/.../time-off/` **не видно вовсе**. Все утверждения выше сняты с
  `origin/dev` содержимым (`git show origin/dev:<файл>`), а не с рабочей
  копии. Первый проход по рабочей копии дал ложный вывод «маршрута нет» —
  устаревшая база невидима, если её не спросить.
* `apply_absence_with_resolutions` прочитан по докстрингу и сигнатуре;
  построчного разбора его транзакции здесь нет.
