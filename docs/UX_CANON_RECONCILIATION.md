# 2. RECONCILIATION RULES — как я применял старшинство

```
1. явное решение владельца
2. явное CURRENT / canonical обозначение
3. принятый контракт реализации   <- здесь важен sign-off, см. §1
4. происхождение в рантайме        <- сюда попадает orchestrator GO 19.07
5. и только потом дата документа
```

**Code defect ставлю только при `CURRENT contract ≠ runtime`.** «Августовский макет ≠ рантайм»
дефектом не считается. Каждый вывод несёт метку `VERIFIED` / `INFERRED` / `NO SOURCE` по слоям.

### 3.1.3 «Ayla подобрала» без обоснования — главное расхождение клиента

```
MAY:     customer-booking-flow.md §2.1 правило 2, дословно:
         «REASONING TEXT REQUIRED для каждого "Ayla подобрала" item»
         помечено NON-NEGOTIABLE. §2.3 даёт разрешённые и запрещённые формулировки. VERIFIED
AUGUST:  DRF-1270 «C04 — Recommendation + WHY: следующий лучший шаг Ayla»          VERIFIED
CODE:    CustomerCatalogScreen.tsx:131 рисует «✨ Ayla подобрала»
         lib/customer-booking.ts:7-16 — reasoning_text удалён, источника нет      VERIFIED
OWNER:   25.08 — «Нет displayable WHY -> нет блока "Ayla подобрала"»                VERIFIED
RUNTIME PROVENANCE: orchestrator GO 2026-07-19 санкционировал удаление заглушки   VERIFIED
```

**Что произошло.** Заглушку удалили правильно — фронт не имеет права выдумывать обоснование,
это была бы «фейковая дата в проде». Но удалили **половину**: поле обоснования исчезло,
**а сама секция осталась**. Сегодня клиент видит подборку от Ayla и не может узнать, почему
именно эти три услуги.

**Почему это не косметика.** Майская спека строит на этом всю этику продукта (§1, LOCKED 26.05):

> «Ayla ВСЕГДА на стороне пользователя» — НЕ салона, НЕ мастера, НЕ платного продвижения.
> Если customer once думает «мне показывают тех, кто заплатил» → trust gone forever.

Необъяснённая подборка — ровно тот вход в это подозрение, против которого правило писалось.

**Владелец уже дважды выносил принцип, который сюда ложится дословно** (`OPEN_DECISIONS.md` §20):

> Блок, который всегда пуст или всегда показывает нули, **хуже отсутствующего**: он обещает то, чего нет.
> Прецедент того же дня: поле аллергий с подписью «Передадим мастеру для вашей безопасности»,
> которое не читалось ни одним мастерским экраном (DRF-1371).

**Статус: `IMPLEMENTATION_MISMATCH`.** Май и август согласны (оба требуют объяснения),
рантайм не соответствует. Определение постановки §2 выполняется буквально.

### Решение владельца 25.08 — принято, вариант выбран

Из трёх вариантов ниже владелец выбрал **второй, в усиленной форме**:

> **Нет displayable WHY -> нет блока «Ayla подобрала».**
>
> Если backend отдаёт допустимые reasons: `Recommendation = WHAT + WHY + WHAT NEXT`,
> где WHY — 2–3 коротких displayable reason, **только из реальных разрешённых user facts /
> explicit context**: без internal reason codes, без confidence numbers, без chain-of-thought,
> без fake copy.
>
> Если WHY нет — брендированную рекомендацию Ayla не показывать. Можно показать обычный
> каталог / execution surface, но **нельзя подписывать его как персональную подборку Ayla**.
>
> Фронтенду запрещено генерировать WHY самостоятельно или использовать generic-заглушки
> («подходит тебе», «выбрано по твоей цели», «Ayla рекомендует»), если source этого не доказывает.

**Статус остаётся `IMPLEMENTATION_MISMATCH`** — пока рантайм показывает секцию без WHY,
он не соответствует уже и решению владельца, а не только двум слоям канона.

**Минимальное приведение в соответствие:** скрыть секцию `«✨ Ayla подобрала»`, пока
`POST /recommendations` возвращает только `{service_id, score}`. Каталог и мастера остаются —
теряется только брендированная подпись, права на которую сейчас нет.

### Исходный разбор вариантов (провенанс)

| вариант | цена |
|---|---|
| backend отдаёт reasoning вместе со score | `POST /recommendations` возвращает `{service_id, score}`; добавить поле причины. Майская спека §2.3 даёт готовый список разрешённых формулировок — придумывать не нужно |
| секцию скрыть до появления обоснования | клиент теряет подборку; scorer остаётся, но не показывается. Соответствует принципу §20 буквально |
| узаконить подборку без обоснования | требует нового owner ruling, отменяющего NON-NEGOTIABLE правило майской спеки. Возможно — но это должно быть сказано вслух, а не получиться само |

**Сегодня выбран третий вариант — но никем и молча.** Это и есть то, что reconciliation должен
был найти.

**нет** — в `CustomerProfileScreen` такого поля не было никогда. Решение исполнено полностью.
`VERIFIED`, ложную тревогу снимаю до того, как её кто-нибудь поднимет.

## 3.7 Системный паттерн: текущая ветка не самодостаточна

Не capability, а свойство всей клиентской поверхности — и оно объясняет §3.2 лучше,
чем случайная опечатка в одной строке.

**Ветка `/customer/*` трижды уходит в легаси-ветку посреди пути:**

| откуда | куда | что это значит |
|---|---|---|
| `CustomerCatalogScreen` → карточка услуги | `/catalog/:serviceId` (`ServiceDetailScreen`) | аналога в `/customer/*` нет вовсе |
| `CustomerBookingDetailScreen` → «Перенести» | `/my-visits/:id/reschedule` (`RescheduleScreen`) | канонический экран зовёт легаси |
| `CustomerBookingSuccessScreen` → «Открыть запись» | `/my-visits/:id` | §3.2, доказанный дефект |

**Статус: `CURRENT_RUNTIME_ONLY`.** Ни майский слой, ни августовский не описывают
сосуществование двух веток — оно возникло при поэтапной миграции и живёт без контракта.

**Это меняет формулировку §3.2.** Кнопка на экране успеха — не единичная ошибка, а
**третий случай одного и того же незавершённого перехода**. Чинить только её — значит
оставить два других и получить тот же баг снова.

**Действие:** отдельная задача «завершить миграцию клиентской ветки» — три перехода,
из них один дефект (1 SP) и два решения «достроить или узаконить» (2 SP). Не в этом заходе.

Из пяти её сценариев в салонной админке построен **один**:

| сценарий MAY-a | рантайм |
|---|---|

в самом коде — `MasterServicesScreen.tsx:9-11`:

> in bot-platform).

ADR — принятый архитектурный контракт (уровень 3 старшинства), и рантайм ему **соответствует**.
Каноническая спека описывает провайдерскую поверхность целиком, включая ту её часть, что
реализуется в Ayla. Расхождения между контрактом и рантаймом нет — есть **граница периметра**.

**Статус: `KEEP_FROM_MAY`, реализация F1/F2/F4/F5 вне периметра bot-platform по ADR-0009.**

### Что исполнено, хотя строилось не по этой спеке

| норма MAY-a | рантайм | статус |
|---|---|---|
| Q-PSP-2 LOCKED — мастер команды не меняет цену/длительность/буфер | `MasterServicesScreen` read-only | `KEEP_FROM_MAY` ✅ |
| Q-PSP-2 — мастер может «предложить изменение, отправить запрос администратору» | через внутренний чат «Со студией» (на снимке пилота — тема «Добавление услунг») | ✅ по сути, не по форме — отдельной кнопки запроса нет |
| **Критерий 7** — услуга без длительности недоступна для записи | `apps/miniapp_api/views.py:558` — `if not service.duration_min: service_unbookable` | `KEEP_FROM_MAY` ✅ |
| — | плюс отказ, если услуга не связана с движком (`ayla_service_id`), с честным «лучше ясный отказ, чем пустой пикер» | сильнее, чем требует спека |
| §14 B6 «карточка внимания» о услугах без мастера | «Услуги без мастеров (2)» **поимённо** | подробнее спеки; частично закрывает `DRF-1164` |

**Совпадение не случайно:** handoff 18.05 и каноническая спека 29.05 описывают один продукт,
поэтому построенное по первому во многом удовлетворяет второй.

### Единственный реальный пробел — операционная видимость

§14 канонической спеки предлагает **четыре** карточки внимания:

```
N услуг без мастера      <- построена
N услуг скрыты           <- нет
N услуг без длительности <- нет
N услуг без цены         <- нет
```

Клиент при этом защищён — API отсекает услугу без длительности (критерий 7 выше).
**Не защищён администратор:** он не узнает, что услуга нерабочая, пока на неё не наткнётся
клиент. Это не дефект (данные корректны, запись невозможна), а **пробел в наблюдаемости**,
и он дешевле любого из непостроенных сценариев: счётчики берутся из того же каталога,
что уже отдаётся экрану.

**Действие:** кандидат в задачу, ~1 SP. Не блокер.

### Навигация — сноска вместо баннера

`provider-services-prices-flow.md` §6 повторяет салонный набор
`Главная · Календарь · Клиенты · Команда · Профиль` и помещает «Услуги» внутрь `Профиль / Ещё`.
Решение владельца 25.08 сделало «Услуги» top-level вкладкой.

**Полный OVERRIDE здесь не поставлен намеренно.** Норма сформулирована рекомендательно
(«возможна такая», «могут находиться»), и спека **сама** предусматривает исход, который выбрал
рантайм: «Если салон активно управляет каталогом, в будущем `Услуги` можно вынести в отдельную
top-level вкладку». Ставить баннер на рекомендацию, которая допускает то, что произошло, —
преувеличение. Поставлена короткая сноска с перекрёстной ссылкой на баннер в
`provider-calendar-schedule-flow.md` §3, где тот же набор дан императивно.

### Не проверено — честно

`snapshot_price` / `snapshot_duration_minutes` / `snapshot_service_name` (Q-PSP-3, Q-PSP-4 LOCKED):
в bot-platform совпадений **ноль**. Но записи создаются в Ayla (`tenants/me/appointments/`),
и снапшоты по определению живут там же. **`NO SOURCE` в этом периметре, за периметр не ходил.**
Если кто-то будет проверять корректность цены в уже созданных записях — проверять надо в Ayla.

| допустимо — проекция существующего факта | недопустимо — выдуманная сущность |
|---|---|
| клиент написал, есть непрочитанное | «Обращение №…» с собственным идентификатором |
| время последнего сообщения | «тип: звонок» без интеграции телефонии |
| связанная запись | «создал сотрудник» как атрибут несуществующего объекта |
| «требует ответа» как производное состояние | «ответственный» как назначаемое поле нового объекта |
| мастер, назначенный на запись | «статус обращения» как отдельный жизненный цикл |

Разница проходит по одному вопросу: **есть ли за строкой существующая строка в базе.**
У диалога есть. У «обращения (звонок)» из августовского макета — нет.

**Статус: `KEEP_FROM_MAY` для проекции диалога, `UNRESOLVED` для «обращения»** — августовский
макет просит сущность, которой нет, владелец запретил её выдумывать, а откуда брать факт
телефонного звонка без интеграции — не решено ни одним слоем.

## 4.10 Ayla · Изменения — вердикт «backend-blocked» подтверждён, но по другой причине

Я пытался опровергнуть этот вердикт и **не смог** — и то, что выяснилось по дороге, важнее,
чем сам вердикт, потому что мешает опровергнуть его следующему.

```
MAY:     provider-messages-flow.md §11 «Lifecycle event card» — событие Booking Engine
         («Запись перенесена через Ayla: было 16:00 → стало 18:00») в списке входящих  VERIFIED
AUGUST:  DRF-1236 — блок «Ayla · Изменения», счётчик «N новых»                          VERIFIED
OWNER:   23.08 — backend-blocked; LLM не имеет права реконструировать изменения         VERIFIED
```

**Что нашлось в коде и почему это НЕ снимает блокировку.**

События жизненного цикла записи **публикуются**:

```
apps/booking/services/transitions.py:80-85   booking.cancel_requested / cancelled /
                                             cancel_undone / reschedule_requested /
                                             reschedule_abandoned / rescheduled
apps/booking/services/create.py:340          booking.created
```

Выглядит как готовый источник. **Но `emit` здесь — из `apps.events.services`, а это телеметрия**,
и её собственный контракт запрещает на неё опираться (`apps/events/services.py:8-14`, дословно):

> **Never raises.** Events are telemetry — if the DB is down, the request must continue.
> Log the swallow for Sentry.

Событие, которое разрешено молча потерять, **не может быть источником операционного факта**.
Показать «14:18 Новая запись» из телеметрии — значит утверждать полноту, которой у неё нет:
пропуск не отличим от «ничего не происходило».

Надёжный механизм в проекте есть — `apps.eventbus.DomainEvent`, настоящий outbox с диспетчером.
В него пишется **ровно одно событие записи**: `booking.completed` из системного сканера
автозакрытия (`apps/bookings/tasks.py:473`). Ни создания, ни отмены, ни переноса.

**Статус: остаётся backend-blocked.** Формулировка утверждена владельцем 25.08 —
писать так и не иначе:

> **booking lifecycle events существуют, но часть публикуется как best-effort telemetry
> и может быть потеряна; authoritative complete operational source для create / cancel /
> reschedule отсутствует.**

И разводить два механизма явно:

```
apps.events                 -> best-effort telemetry  -> НЕ source of truth
apps.eventbus.DomainEvent   -> reliable outbox        -> покрывает недостаточный lifecycle set
```

**Не строить operational history на lossy telemetry.**

**Для разблокировки нужны три вещи вместе:** authoritative lifecycle source + reliable outbox +
projection/read API (или эквивалентно полный источник). Ни одной из трёх сегодня нет целиком.

Формулировка «событий нет» **запрещена**: следующий найдёт `booking.created` и построит витрину
на данных, которые разрешено молча терять.
