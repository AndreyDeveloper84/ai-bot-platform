# ПРОТОКОЛ ОБМЕНА МЕЖДУ ОКНАМИ (v1, 2026-08-09)

Применяется ко всем окнам проекта Ayla: главное окно (координатор/Chief Architect) и окна-исполнители (Opus-оркестраторы по брифам). Каждый бриф ссылается на этот файл — читать при старте окна.

## 1. Файловая шина (вместо пасты в чат)

Все файлы — в `C:\Users\user\PycharmProjects\Ayla\docs\`:

| Файл | Пишет | Читает | Назначение |
|---|---|---|---|
| `IMPL_BRIEF_<задача>.md` / `DEPLOY_BRIEF_<задача>.md` | главное окно | исполнитель | постановка: цель, контекст, границы, гейты |
| `REPORT_<задача>.md` | ТОЛЬКО исполнитель | главное окно | отчёты секциями с датой/временем; эскалации — секцией «Эскалация»; кандидаты в Linear-задачи — отдельной секцией |
| `REPLY_<задача>.md` | ТОЛЬКО главное окно | исполнитель | решения, ответы на эскалации, GO-сигналы, дополнения к брифу. Новые ответы — СВЕРХУ файла, старые уходят в «(архив)» |

Паста между окнами через чат владельца — только аварийный канал (файл потерялся/конфликт).

## 2. Двусторонний мониторинг (обязателен)

Обе стороны ставят persistent-монитор на «чужие» файлы (сравнение по md5-содержимому, не mtime). Исполнитель при старте окна ставит монитор на свой REPLY-файл:

```
f="C:/Users/user/PycharmProjects/Ayla/docs/REPLY_<ЗАДАЧА>.md"
last=""; [ -f "$f" ] && last=$(md5sum "$f" | cut -d' ' -f1)
while true; do
  h=""; [ -f "$f" ] && h=$(md5sum "$f" | cut -d' ' -f1)
  if [ -n "$h" ] && [ "$h" != "$last" ]; then echo "ОБНОВЛЁН REPLY — перечитай верхнюю секцию: $f"; last=$h; fi
  sleep 30
done
```

Реакция на событие: перечитать верхнюю (новую) секцию REPLY и действовать по ней. Главное окно аналогично мониторит `REPORT_*.md`.

**Важное ограничение, вскрытое 2026-08-13 (окно DRF-1029, VERIFIED):** такой монитор в окне-исполнителе изменения ловит, но его `echo` **не приходит в диалог сам** — цикл бесконечный, доставка получается «по опросу», то есть окно узнаёт об ответе только когда само посмотрит. Из-за этого в один день дважды произошла гонка: окно мержило PR ровно в ту минуту, когда главное окно писало требование, и требование уезжало в follow-up.

Отсюда два правила, оба обязательны:

1. **Перед каждым необратимым шагом — merge, деплой, мутация на пилоте — перечитай REPLY заново.** Монитор мог отстать. Это десять секунд.
2. **Главное окно не считает ответ доставленным по факту записи.** Проверяй результат по состоянию мира (ветка, `origin/dev`, контейнеры), а не по рапорту окна и не по тому, что файл записан.

Рабочий обход, если окно умеет cron: дополнить монитор периодической проверкой md5 с записью в файл-маркер — тогда изменение поднимается активно, а не по опросу.

Правило для обоих: **вопрос задал — работу не бросай.** После записи эскалации в REPORT продолжай ту часть объёма, которая не заблокирована; жди только там, где без ответа нельзя.

## 3. Что НЕ автоматизируется (остаётся на владельце)

1. **Запуск нового окна** — владелец вставляет путь к брифу в новое окно.
2. **GO-гейты на мутации runtime** (деплой, правка данных на пилоте) — явное «GO» владельца; окно останавливается и ждёт.
3. **Пермишены** (ssh, сеть и т.п.) — подтверждает владелец в окне-исполнителе.
4. **Live-приёмка в MAX** — только владелец со своего аккаунта.

## 4. Linear

- Задачи создаёт ТОЛЬКО главное окно. Исполнитель фиксирует кандидатов в REPORT.
- Комментарии/статусы — главное окно по REPORT'ам (помечай «→ в Linear»). Исполнителю доступ к Linear не нужен.
- Кириллица в GraphQL-мутациях — только ASCII-escaped JSON (`\uXXXX`), после записи верифицировать чтением (иначе «?»).

## 5. Инварианты (всегда)

- **NO FALSE SUCCESS:** merge ≠ Done; Done только после runtime-приёмки на пилоте.
- Границы брифа жёсткие; отклонение = эскалация в REPORT, не тихое решение.
- Evidence-классификация в отчётах: VERIFIED / INFERRED / CLAIMED / UNKNOWN.
- Секреты (ключи, токены) в файлы шины и отчёты не попадают никогда.

### 5.1. Локальное окружение перед регрессом (читать до первого прогона)

**Подними dev-Redis, иначе получишь ложный кластер падений.** Без него `apps/orchestrator/tests/test_pipeline.py` даёт ~16 падений с `redis.exceptions.ConnectionError: Error 10061 connecting to localhost:6379` в `_update_short_term` — к любому дифу это отношения не имеет. Штатный способ: `docker compose up -d redis` (контейнер `ai-bot-platform-redis-1`, порт 6379). С поднятым Redis — 40/40 зелёные (VERIFIED окном DRF-1029, 2026-08-13).

**Три окна подряд потеряли на этом время**, каждое заново доказывая предсуществование кластера методом «откатить свой диф → прогнать базу → сверить списки». Метод остаётся правильным, но применять его к этому кластеру больше не нужно. Задача на устранение — DRF-1031.

Остаточные падения, которые Redis НЕ чинит и которые дифом не вызваны:
- `apps/orchestrator/tests/test_faq_latency.py::test_p95_under_4000ms_over_50_runs` — перформанс-гейт `@pytest.mark.slow`, в CI не входит.
- `tests/smoke/test_ayla_import.py::test_package_sha_pinned` — локальный venv ставит `ayla-ai-core` из локального пути, git-SHA-гейт к такой установке неприменим; CI ставит через `uv sync --frozen` из git.
- `manage.py makemigrations --check` → `InconsistentMigrationHistory` — состояние локальной dev-БД, к моделям отношения не имеет.

CI гоняет smoke + contract + eventbus + линты, а не полный apps-suite — сверяйся с ним, а не с локальной машиной.

### 5.1.1. Точная команда деплоя пилотного бота (三 файла, не два)

**Стек бота на пилоте поднимается ТРЕМЯ compose-файлами:**

```
docker compose -f docker-compose.yml -f docker-compose.staging.yml -f docker-compose.staging.local.yml -p ayla-bot-staging up -d
```

**Шапка `docker-compose.staging.yml` называет только два первых — она неполна.** Третий, `docker-compose.staging.local.yml`, специфичен для хоста и делает две критичные вещи: переопределяет порт `web` с `8001` на `127.0.0.1:8014` (тот самый канонический health-адрес) и обнуляет `CHROMA_HTTP_HOST` / `CHROMA_AUTH_TOKEN`, которых в пилотном профиле нет.

**Что происходит, если довериться шапке (инцидент 2026-08-13, окно DRF-1033/972):** `web` пытается занять порт 8001, который на хосте уже держит посторонний Django-процесс, и остаётся в состоянии `Created`. **Веб-эндпоинт пилота лежит ~5 минут** — то есть входящие вебхуки MAX в это время не принимаются. В тот раз обошлось: входящего трафика в интервале не было (последний вебхук за час до). Остальные сервисы при этом поднимаются, но без оверрайда chromadb.

Проверка после `up -d`: `docker ps` должен показывать у `web` проброс `127.0.0.1:8014->8000/tcp`. Если видишь `8001` — команда была неполной.

### 5.2. Одно окно — один рабочий каталог (обязательно при параллельном запуске)

**Два активных окна не должны работать в одном git-чекауте.** Ветка в чекауте одна на всех: пока окно A делает `checkout -b`, окно B переключает каталог под собой, и коммит A оказывается на ветке B.

Инцидент 2026-08-13 (окна DRF-911 и DRF-1029 в `C:\Users\user\PycharmProjects\ai-bot-platform`): коммит `51ef519` окна DRF-911 оказался на ветке `feat/drf1029-notify-zero-queries`. Восстановлено cherry-pick'ом, потерь нет — но повезло: worktree был чист, и обе ветки уже были запушены. При грязном worktree это стоило бы работы.

**Правило:** при запуске второго и последующих параллельных окон каждое получает **свой каталог** — `git worktree add ../ai-bot-platform-<задача> <ветка>` либо отдельный клон (в `PycharmProjects` такие каталоги уже заведены исторически: `ai-bot-platform-drf962`, `-drf967` и т. д.). Каталог указывается в шапке брифа явно.

**Ответственность главного окна, не исполнителя:** окно не может знать, что рядом работает другое. Разводит каталоги тот, кто пишет брифы.

## 6. Параметры запуска окна: сложность / контекст / модель

Перед запуском каждого нового окна главное окно сообщает владельцу (в чате, и дублирует шапкой в брифе):

1. **Сложность задачи:** низкая (точечный фикс, один репо, готовый рецепт) / средняя (один репо + ревью, или диагностика по известной методике) / высокая (мультирепо, деплой-цикл, runtime-мутации, неизвестная территория).
2. **Ожидаемый размер контекста к концу сессии:** маленький (<60k — короткая сессия, немного файлов) / средний (60–120k) / большой (>120k — вероятны /compact или разбиение на фазы; если предсказуемо >150k — задачу лучше резать на два брифа заранее).
3. **Рекомендуемая модель окна:**
   - **Haiku 4.5** — механические задачи по готовому рецепту без решений (прогон скриптов, рутинные апдейты по шаблону);
   - **Sonnet 5** — низкая/средняя сложность: точечные фиксы, диагностика по методике, документация;
   - **Opus 5** — высокая сложность: оркестрация сабагентов, независимое ревью, деплой-циклы, работа на пилотном хосте, всё с GO-гейтами;
   - главное окно (координатор) остаётся на своей модели.

Ошибиться моделью вниз дороже, чем вверх: при сомнении между двумя — брать старшую. Если по ходу окно упирается (модель не тянет), эскалация в REPORT → главное окно советует перезапуск с той же точки (бриф + REPORT дают полный контекст для рестарта).

## 7. Эпик-режим (планирование пакета окон)

Для эпика главное окно готовит `EPIC_PLAN_<эпик>.md`: список окон (бриф-файлы), зависимости между ними (кто чей REPORT ждёт), GO-гейты и точки участия владельца. Владелец один раз запускает окна пакетом (каждому — путь к его брифу), дальше координация идёт по шине §1–§2 почти без него: окна сами видят решения главного окна, главное окно само видит их отчёты. Владелец нужен только в точках §3.
