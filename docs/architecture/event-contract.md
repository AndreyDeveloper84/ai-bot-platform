# Event Contract — Ayla djangoproject → ai-bot-platform

> **Status:** v1 — draft 2026-05-21
> **Owner:** Phase 0 Stream Beta (W4)
> **Authority:** ADR-0009 §Mandatory event contract — this doc is the verbatim implementation of the envelope + taxonomy + rules referenced there.
> **Scope:** Cross-service domain events published by **Ayla djangoproject** and consumed by **ai-bot-platform** over HTTP. Internal in-process events on either repo are out of scope (see §10 «Relationship to other event docs»).
> **Audience:** Outbox publisher implementers (Ayla side, #429/#430/#431), ingest endpoint implementer (bot-platform side, #432), consumer implementers (#442–#446), contract test author (#447).
> **PREREQUISITE for:** #429, #430, #431, #432, #433, #442, #443, #444, #445, #446, #447. No implementation may start until this doc lands.

---

## 1. Purpose

Per ADR-0009 (Variant A — split-domain architecture), Ayla djangoproject owns the canonical state of booking, payment, master schedule, services, reviews, and user profile. ai-bot-platform needs a faithful, near-real-time view of that state to:

- update conversational memory (`apps/identity/UserPersonalContext`)
- maintain reminder + escalation FSM (`RemoteBookingProxy` + `BookingReminder`)
- invalidate the catalog mirror (`apps/catalog`)
- update RFM / sentiment (`apps/clients/ClientProfile`)
- emit analytics (`apps/events/` snake_case bus)

Without this contract, AI gives wrong answers about user state. This doc locks the wire format, naming, ordering guarantees, and failure handling so that ten different consumer authors produce a coherent system.

**The contract is one-way: Ayla → bot-platform.** bot-platform never publishes domain events back; if bot-platform needs to mutate Ayla state (e.g. cancel a booking on a user's instruction), it uses the Ayla REST API and Ayla emits the resulting event back. This keeps Ayla as the sole writer of its own state.

## 2. Envelope schema

Every event published to ai-bot-platform's ingest endpoint MUST conform to the envelope below. The envelope is fixed across all 12 events; per-event payload sits in `data` and is versioned separately (see §4).

| Field             | Type            | Required | Description                                                                                          |
|-------------------|-----------------|----------|------------------------------------------------------------------------------------------------------|
| `event_id`        | string (ULID)   | yes      | Unique per event. Used as the dedupe key by every consumer. Bare ULID, no prefix.                    |
| `event_name`      | string          | yes      | Dot-notation lowercase (`booking.created`). Must match one of the 12 names in §3.                    |
| `event_version`   | integer         | yes      | Starts at `1` for MVP. Bumped on breaking change to the `data` payload. See §4.                      |
| `occurred_at`     | string (ISO8601) | yes     | UTC timestamp when the state change happened in Ayla. Includes timezone suffix (`Z` or `+00:00`).    |
| `tenant_id`       | string (UUID) \| null | yes | The tenant the state change belongs to. `null` only for user-scoped events with no tenant binding.  |
| `user_id`         | string (UUID)   | yes      | Canonical Ayla `User.id`. Always present — even `tenant_id=null` events have a user.                 |
| `actor`           | enum string     | yes      | One of: `system`, `user`, `admin`. Identifies WHO triggered the state change.                        |
| `correlation_id`  | string (UUID)   | yes      | Trace identifier for related events in one logical flow. Generated by Ayla at flow start.            |
| `causation_id`    | string (UUID) \| null | yes | `event_id` of the event that caused this one, or `null` for root events. Used for causal lineage.   |
| `data`            | object          | yes      | Per-event payload. Schema defined per event in §3. Subject to PII rules in §7.                       |

### 2.1 Full envelope example

```json
{
  "event_id": "01J9HXKM8Z2T4V6R8Q1P3D5F7E",
  "event_name": "booking.created",
  "event_version": 1,
  "occurred_at": "2026-05-21T14:32:11.482Z",
  "tenant_id": "9c3a7e1b-4d52-4f8e-b3a1-7c2d8e1f0a5c",
  "user_id": "f1a2b3c4-d5e6-4789-9abc-def012345678",
  "actor": "user",
  "correlation_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "causation_id": null,
  "data": {
    "appointment_id": "b8d3e4f5-1c2d-4e6f-8a9b-c3d4e5f6a7b8",
    "specialist_id": "7c2d8e1f-0a5c-9c3a-7e1b-4d52f8eb3a17",
    "service_id": "3d5f7e1c-8a2d-4e6f-b9c0-1d2e3f4a5b6c",
    "start_at": "2026-05-22T15:00:00+03:00",
    "end_at": "2026-05-22T16:00:00+03:00",
    "status": "confirmed",
    "price_total": "1800.00",
    "source": "mobile_app"
  }
}
```

### 2.2 Field-by-field semantics

**`event_id`:** Ayla generates one ULID per event at publish time. ULID gives lexicographic time ordering and 80-bit randomness — adequate for global uniqueness across publishers. The same `event_id` MUST be reused if the outbox retries delivery; consumers dedupe by it.

**`event_name`:** Validated against the closed set in §3. Unknown names → DLQ (see §8.5). No wildcard subscriptions; consumer registration is per exact `(event_name, event_version)` pair.

**`event_version`:** Integer, not SemVer. Cross-service handler routing benefits from integer comparison and a simple deprecation calendar. SemVer would imply patch versions that consumers shouldn't care about. See §4 for the versioning rule.

**`occurred_at`:** When the state changed in Ayla, NOT when the event was published. If publish lags (outbox dispatcher 30s behind), `occurred_at` still reflects the original transaction time. Consumers should treat `occurred_at` as canonical for ordering within a `correlation_id`.

**`tenant_id`:** Required field, value nullable. `null` only for the `user.profile.updated` event when the change is to user-global fields (name, avatar) not tied to any tenant. All booking/payment/service/master events MUST have a non-null `tenant_id`.

**`user_id`:** Always present. For events triggered by an `admin` actor, `user_id` is the AFFECTED user, not the admin. (Example: admin cancels a customer's booking — `user_id` is the customer; the admin's identity is captured elsewhere if needed.)

**`actor`:** Categorical signal of who initiated the change. Three values only:
- `system` — automated process in Ayla (cron, expiration timer, integration callback)
- `user` — the `user_id` themselves acted (most bookings, cancellations)
- `admin` — a tenant admin/master acted on behalf of the user

The `actor` field does NOT identify which specific admin. If consumers need that, it goes in `data` (see `booking.cancelled.cancelled_by`, etc).

**`correlation_id`:** New UUID at flow start, propagated through all events in the same logical flow. Examples:
- User taps "Book now" → `booking.created` + `payment.authorized` + `payment.captured` all share one `correlation_id`
- Cron expires a hold → `booking.cancelled` + `payment.failed` share one `correlation_id`

**`causation_id`:** The `event_id` of the immediate parent event in the causal chain. Root events of a flow have `causation_id: null`. Example: `payment.captured` has `causation_id` = the `event_id` of the `payment.authorized` that preceded it.

### 2.3 Why these specific fields

`correlation_id` + `causation_id` together give consumers a directed causal graph per flow. This unblocks observability (trace a flow end-to-end) and consumer logic (e.g. the `payment.*` consumer needs to update the `Conversation` referenced by the original `booking.created` — it walks `causation_id` back to find it).

`actor` is a deliberately coarse three-value enum. Finer-grained attribution (which specific admin, which automation rule) lives in `data` only when a specific consumer needs it. Keeping the envelope coarse prevents the envelope from sprawling into a kitchen sink.

## 3. Event taxonomy (MVP — 12 events, all `event_version: 1`)

For each event below: trigger condition, `data` schema, JSON example with realistic UUIDs (not placeholders), and consumer behavior contract (what bot-platform MUST do on receipt).

> **Consumer contracts specify observable behavior, not implementation.** Each contract states the side-effect (DB write, cache invalidation, event emission) the consumer MUST produce. The consumer ticket (#442–#446) chooses the exact method (helper function, manager method, ORM call). If a contract step references an existing bot-platform module (`apps/scheduling`, `apps/catalog`, etc.), the consumer ticket integrates with that module's current public API; if the API doesn't exist yet, the consumer ticket adds it as part of its scope.

### 3.1 `booking.created`

**Trigger:** A new appointment is created in Ayla — by user via mobile, by admin via console, or by automation (e.g. recurring subscription). Emitted after the appointment row is committed.

**`data` schema:**

| Field            | Type              | Description                                              |
|------------------|-------------------|----------------------------------------------------------|
| `appointment_id` | string (UUID)     | Canonical Ayla `Appointment.id`.                         |
| `specialist_id`  | string (UUID)     | The master assigned to the appointment.                  |
| `service_id`     | string (UUID)     | The service being booked.                                |
| `start_at`       | string (ISO8601)  | Appointment start in salon's local timezone (with offset).|
| `end_at`         | string (ISO8601)  | Appointment end in salon's local timezone.               |
| `status`         | enum string       | One of: `confirmed`, `pending_payment`, `tentative`.     |
| `price_total`    | string (decimal)  | Total price as decimal string. Currency from tenant config. |
| `source`         | enum string       | One of: `mobile_app`, `admin_console`, `automation`, `yclients_sync`. |

**Example:**

```json
{
  "event_id": "01J9HXKM8Z2T4V6R8Q1P3D5F7E",
  "event_name": "booking.created",
  "event_version": 1,
  "occurred_at": "2026-05-21T14:32:11.482Z",
  "tenant_id": "9c3a7e1b-4d52-4f8e-b3a1-7c2d8e1f0a5c",
  "user_id": "f1a2b3c4-d5e6-4789-9abc-def012345678",
  "actor": "user",
  "correlation_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "causation_id": null,
  "data": {
    "appointment_id": "b8d3e4f5-1c2d-4e6f-8a9b-c3d4e5f6a7b8",
    "specialist_id": "7c2d8e1f-0a5c-9c3a-7e1b-4d52f8eb3a17",
    "service_id": "3d5f7e1c-8a2d-4e6f-b9c0-1d2e3f4a5b6c",
    "start_at": "2026-05-22T15:00:00+03:00",
    "end_at": "2026-05-22T16:00:00+03:00",
    "status": "confirmed",
    "price_total": "1800.00",
    "source": "mobile_app"
  }
}
```

**Consumer contract (`booking.*` consumer, #442):**
1. Upsert `RemoteBookingProxy` keyed by `data.appointment_id`. If exists, update fields; if not, create.
2. Schedule `BookingReminder` rows per tenant's reminder policy (typically 24h before `start_at`, 2h before `start_at`). The reminder policy is owned by `apps/scheduling` (mirrored from Ayla via a separate read API; the consumer ticket #442 adds the policy fetcher if not yet present). Scheduling MUST be idempotent on `(appointment_id, offset_minutes)`.
3. Emit internal `booking.created` event on bot-platform's `apps/events/` snake_case bus for analytics fan-out.
4. Ensure a `Conversation` row exists for `(user_id, tenant_id)` (create if missing) and set its `last_booking_at` to `data.start_at` for AI context grounding.

### 3.2 `booking.cancelled`

**Trigger:** Appointment cancelled — by user, by admin/master, or by automation (e.g. payment hold expired). Emitted after `Appointment.status` transitions to `cancelled`.

**`data` schema:**

| Field            | Type              | Description                                              |
|------------------|-------------------|----------------------------------------------------------|
| `appointment_id` | string (UUID)     | Canonical `Appointment.id`.                              |
| `cancelled_by`   | enum string       | One of: `user`, `admin`, `master`, `system`.             |
| `reason`         | string \| null    | Free-text reason if provided (max 500 chars). PII rules in §7 apply: no full names, no contact info. |
| `cancelled_at`   | string (ISO8601)  | When cancellation was committed.                         |

**Example:**

```json
{
  "event_id": "01J9HY4N2K7T5V8R3Q1P9D5F2C",
  "event_name": "booking.cancelled",
  "event_version": 1,
  "occurred_at": "2026-05-21T16:08:45.119Z",
  "tenant_id": "9c3a7e1b-4d52-4f8e-b3a1-7c2d8e1f0a5c",
  "user_id": "f1a2b3c4-d5e6-4789-9abc-def012345678",
  "actor": "user",
  "correlation_id": "c4d5e6f7-a8b9-0123-cdef-456789012345",
  "causation_id": null,
  "data": {
    "appointment_id": "b8d3e4f5-1c2d-4e6f-8a9b-c3d4e5f6a7b8",
    "cancelled_by": "user",
    "reason": "не успеваю",
    "cancelled_at": "2026-05-21T16:08:45.119Z"
  }
}
```

**Consumer contract (`booking.*` consumer, #442):**
1. Update `RemoteBookingProxy.status` to `cancelled`.
2. Cancel any pending `BookingReminder` rows for this `appointment_id`. Idempotent: cancelling already-cancelled reminders MUST NOT error.
3. If `cancelled_by` ∈ {`admin`, `master`, `system`} (i.e. NOT the user themselves), enqueue a customer notification through the existing notification stream (Epic #296 once shipped; until then, internal log entry only).

### 3.3 `booking.rescheduled`

**Trigger:** Appointment moved to a new time slot. Emitted instead of cancel+create when the same `appointment_id` persists. (If the system cancels old and creates new with different IDs, emit `booking.cancelled` + `booking.created` instead — both pathways are valid; tenant's booking engine chooses.)

**`data` schema:**

| Field             | Type              | Description                                              |
|-------------------|-------------------|----------------------------------------------------------|
| `appointment_id`  | string (UUID)     | Canonical `Appointment.id` (unchanged).                  |
| `old_start_at`    | string (ISO8601)  | Original start time before reschedule.                   |
| `new_start_at`    | string (ISO8601)  | New start time after reschedule.                         |
| `rescheduled_by`  | enum string       | One of: `user`, `admin`, `master`, `system`.             |

**Example:**

```json
{
  "event_id": "01J9HZ8P4M9T6V0R5Q3P1D7F4E",
  "event_name": "booking.rescheduled",
  "event_version": 1,
  "occurred_at": "2026-05-21T18:14:02.741Z",
  "tenant_id": "9c3a7e1b-4d52-4f8e-b3a1-7c2d8e1f0a5c",
  "user_id": "f1a2b3c4-d5e6-4789-9abc-def012345678",
  "actor": "admin",
  "correlation_id": "e6f7a8b9-c0d1-2345-ef67-890123456789",
  "causation_id": null,
  "data": {
    "appointment_id": "b8d3e4f5-1c2d-4e6f-8a9b-c3d4e5f6a7b8",
    "old_start_at": "2026-05-22T15:00:00+03:00",
    "new_start_at": "2026-05-23T11:00:00+03:00",
    "rescheduled_by": "admin"
  }
}
```

**Consumer contract (`booking.*` consumer, #442):**
1. Update `RemoteBookingProxy.start_at` to `data.new_start_at`. Update `end_at` by preserving the original duration (`new_end_at = new_start_at + (old_end_at - old_start_at)`).
2. Cancel reminders pegged to `old_start_at` and reschedule them relative to `new_start_at`. Idempotent.
3. Update the conversation context — AI now references the new time on next user query.

## 4. Versioning rules

### 4.1 What constitutes a breaking change

Breaking changes require a new `event_version`:

- Removing a field from `data`.
- Renaming a field in `data`.
- Changing a field's type (e.g. integer → string, even if semantically equivalent).
- Changing a field's semantics (e.g. `price_total` switches from "before tax" to "after tax").
- Adding a NEW required field (existing consumers' validation would reject events lacking it).

Non-breaking (no version bump needed):

- Adding a new OPTIONAL field that consumers ignore by default.
- Adding a new value to an open enum (e.g. new `source` value for `booking.created`). Consumers MUST default to a safe behavior on unknown enum values.
- Tightening validation that consumers already enforced.

### 4.2 Handler registration

Consumers register handlers per `(event_name, event_version)` tuple. The ingest endpoint (#432) routes each event to the registered handler for its exact version. Two versions of the same event MAY have separate handlers running in parallel during a deprecation window.

### 4.3 Deprecation procedure

When publishing a new `event_version`:

1. Publisher (Ayla) starts emitting BOTH the old and the new version in parallel for the deprecation window (default 30 days, extensible by tech-lead memo).
2. Consumers register a handler for the new version. They MAY keep the old-version handler running concurrently or replace it after verifying the new handler.
3. After ≥30 days, publisher stops emitting the old version. Old-version handlers receive no more events.
4. Old-version handlers MAY be deleted after a further 7-day quarantine.

**Minimum deprecation window: 30 days.** Tech lead may extend per case, never shorten without explicit cross-team coordination announced in writing.

### 4.4 No silent breaks

A breaking change without a version bump is a contract violation, treated as P0. If a publisher accidentally ships one, consumers will dedupe-by-event_id but their handlers will mis-process the new shape. The on-call rotation is responsible for catching this via the contract test (#447).

## 5. Idempotency requirements

Every consumer MUST be idempotent with respect to `event_id`. The contract is:

> Given the same `event_id` delivered N times (N ≥ 1), the observable side-effects MUST be exactly equivalent to the side-effects of delivering it exactly once.

### 5.1 Concrete implementation pattern

Consumers maintain a dedupe table indexed by `event_id` with the timestamp of first processing. On receipt:

1. Attempt INSERT into dedupe table with `(event_id, processed_at=now())`.
2. If INSERT succeeds: process the event normally.
3. If INSERT fails with unique-constraint violation: skip processing (already handled).

### 5.2 What "observable side-effect" means

- DB writes: row counts must be identical (no duplicate inserts; updates land on the same final state).
- External API calls: the consumer MUST NOT make a duplicate outbound call. If the consumer hands off to an external API (e.g. firing a customer DM), it tracks an outbound dedupe key derived from `event_id`.
- Internal bus emissions: snake_case `apps/events/` analytics fan-out MUST NOT duplicate per inbound dedupe.

### 5.3 Dedupe table retention

Dedupe rows kept for at least 30 days (matches the deprecation window). After 30 days, an event_id retry that hits an empty dedupe table will re-process. This is acceptable because the outbox retry budget is 5 attempts with max ~1h backoff total — events older than 30 days are dead-letter, never retried live.

### 5.4 Contract test discipline

`#447` (Idempotency contract test) verifies this property per consumer by replaying the same canned event 3 times and asserting exactly one effect. Every consumer ticket (#442–#446) MUST include this test before merge.

## 6. Delivery contract

### 6.1 Transport

- **Source:** Ayla djangoproject Postgres outbox table. Outbox row inserted in the same DB transaction as the domain state change (transactional outbox pattern). Separate dispatcher reads the outbox and ships events.
- **Wire:** HTTPS POST to `https://api.ai-bot-platform.internal/api/v1/internal/events/ingest` (production hostname; dev/staging differ).
- **Content-Type:** `application/json; charset=utf-8`.
- **Body:** single event envelope per request. No batching in MVP (simplifies dedupe + handler routing; batching is a Phase 2 optimization).

### 6.2 Signature verification (HMAC-SHA256)

- **Shared secret:** stored in Vault, distributed to both repos via deploy config. Rotated quarterly.
- **Signature header:** `X-Ayla-Event-Signature: sha256=<hex>` where `<hex>` is `hmac_sha256(secret, raw_request_body)`.
- **Verification:** ingest endpoint (#432) computes the HMAC over the raw request body and rejects with 401 if mismatch.
- **Timestamp header:** `X-Ayla-Event-Timestamp: <unix_ms>` — server rejects with 401 if `|now - timestamp| > 300s` to prevent replay of intercepted requests.

### 6.3 Retry policy

- **Max attempts:** 5 (counting the initial attempt + 4 retries).
- **Backoff:** exponential — 1s, 5s, 30s, 120s, 600s between attempts.
- **Retry triggers:** HTTP 5xx response, network error, timeout (>10s). DO NOT retry on HTTP 4xx (those indicate a permanent error — bad signature, malformed body, unknown event_name; retrying won't help).
- **Same event_id reused on every retry** — consumer dedupe makes retries safe.

### 6.4 Dead-letter

- After 5 failed attempts, the outbox row is marked `dead=true` and an alert fires (PagerDuty rotation `ayla-events`).
- Dead-lettered events are NOT automatically retried. On-call investigates, manually re-publishes if root cause is fixed.
- Dead-letter retention: 90 days (matches red-zone retention for symmetry).

### 6.5 Lag SLA

- **Target:** P95 of `(event.processed_at - event.occurred_at)` < 5 minutes.
- **Alert:** P95 over a rolling 15-min window > 5 min → alert. Sustained > 15 min → page.
- **Why 5 min:** AI conversational memory must reflect recent state changes within one conversational turn. 5 min is the practical upper bound where users perceive "AI knows my latest action".

### 6.6 Ordering guarantees

- **Within a `correlation_id`:** consumer receives events in publish order (outbox dispatches FIFO per correlation key).
- **Across correlation IDs:** NO ordering guarantee. Consumers MUST NOT rely on cross-flow ordering.
- **Consequence:** if a consumer needs to react to a cross-flow ordering (e.g. "this `payment.captured` must come after a specific unrelated `booking.created`"), it queries Ayla REST for current state instead of relying on event order.

## 7. PII rules

The envelope and `data` payloads MUST NOT carry free-text PII. The rule:

> If a field could contain a person's name, contact info, address, medical detail, or other personally identifying free-text — it is referenced by ID and fetched on demand via Ayla REST, not inlined in the event.

### 7.1 What goes in events

- **IDs are fine.** `user_id`, `appointment_id`, `master_id`, `service_id`, `payment_id`, `external_id` (provider reference).
- **Coarse categoricals are fine.** Status enums, source enums, `actor`, `change_type`, `cancelled_by`, `reason` enums.
- **Numeric / temporal data is fine.** Prices, durations, timestamps.
- **Booleans are fine.** `has_text`, `is_anonymous`.

### 7.2 What stays out

- Names, emails, phone numbers, addresses.
- Review text bodies (only the `has_text` boolean).
- Cancellation/refund reasons containing free-text (only enum reasons; `booking.cancelled.reason` field has a soft 500-char cap AND is forbidden from containing names/phones — Ayla strips on publish if detected).
- Medical details (symptoms, contraindications). These belong only to bot-platform's `UserPersonalContext` and never appear in events.
- Payment card numbers, CVVs, full PAN — only provider's `external_id` is shipped, never card details.

### 7.3 Why this matters

- The HMAC-signed transport protects against MITM, but the events traverse internal network + sit in outbox tables + sit in dedupe tables + appear in logs. Each surface is a PII risk. Keeping events to IDs limits the blast radius.
- 152-ФЗ compliance: minimum-necessary-data principle. Events satisfy "what happened, when, to whom by ID"; consumers fetch the PII they actually need when they need it.
- Future analytics replay: events may be replayed against historical analytics jobs. Replay must not re-leak PII that's been purged from user-facing surfaces (e.g. forget-all per Epic #220).

### 7.4 On-demand PII fetch

When a consumer needs PII (e.g. to render a notification with the user's first name):

1. Call Ayla REST: `GET /api/v1/users/{user_id}` with the consumer's service-account JWT.
2. Receive ONLY the fields the consumer is authorized for (Ayla scopes by service-account role).
3. Use immediately; do not persist beyond the operation. If persistence is required (e.g. bot-platform's `ClientProfile.display_name`), it lives behind the same authorization boundary.

## 8. Failure modes

### 8.1 Consumer raises an exception

The ingest endpoint's handler-routing layer:

1. Catches the exception.
2. Returns HTTP 500 to Ayla's dispatcher.
3. Logs the exception with `event_id`, `event_name`, `event_version`, handler identifier.
4. Increments a Prometheus counter `events_consumer_failed_total{event_name, handler}`.
5. Ayla's dispatcher retries per §6.3 (exponential backoff, max 5 attempts).
6. After max attempts, outbox row goes dead per §6.4.

The consumer's own dedupe table is NOT written on exception — that way the retry actually re-attempts processing.

### 8.2 Ingest endpoint is down (HTTP 5xx, timeout, connection refused)

Ayla's dispatcher keeps the outbox row pending and retries per §6.3. Outbox rows accumulate during the outage. On recovery, dispatcher drains the queue; lag SLA alert (§6.5) will fire if drain takes >5 min.

If the outage exceeds the dispatcher's retry budget for individual events, those events go dead and require manual re-publish.

### 8.3 Signature verification fails (HMAC mismatch OR stale timestamp)

Ingest endpoint:

1. Returns HTTP 401.
2. Increments `events_signature_failed_total{reason}` where `reason` is `hmac_mismatch` or `timestamp_stale`.
3. Logs the request headers (NOT the body — body might contain partial valid data).
4. Threshold alert: >10 signature failures in 5 min → page (suggests secret rotation drift OR active attack).

Ayla's dispatcher does NOT retry 401s (per §6.3 — 4xx are not retryable). Operator investigates the secret distribution.

### 8.4 Unknown `event_version` for a known `event_name`

This means the publisher has emitted a version the consumer hasn't yet registered a handler for. Possible scenarios:

- Publisher deployed a new version, consumer rollout still pending.
- Publisher accidentally emitted a future version.

Ingest endpoint:

1. Returns HTTP 422 (Unprocessable Entity).
2. Routes the event to the dead-letter table immediately (no retry — retrying won't make the consumer materialize a handler).
3. Alert: any DLQ entry from unknown-version → page.

Operator either (a) ships the missing consumer handler quickly and replays the DLQ, or (b) rolls back the publisher.

### 8.5 Unknown `event_name` entirely

Indicates a contract drift — Ayla shipped a new event taxonomy entry without updating this doc.

Ingest endpoint: returns HTTP 422, dead-letter, page. Same response shape as §8.4.

Operator updates this doc + adds consumer handler before replaying.

### 8.6 Malformed event body (invalid JSON, missing required envelope field)

Returns HTTP 400 + logs the malformed body. NOT retryable. Counted in `events_malformed_total`. Almost always indicates a publisher bug — Ayla side investigates.

### 8.7 Duplicate `event_id` delivery

Expected and handled by consumer dedupe (§5). Consumer's dedupe-table check skips processing; the ingest endpoint still returns HTTP 200 so Ayla's dispatcher marks the outbox row processed. This must NOT produce an alert; duplicates are the normal cost of at-least-once delivery.

### 8.8 Consumer hung (no response within timeout)

Ingest endpoint's per-handler timeout is 8 seconds (giving Ayla's 10-second outer timeout 2 seconds of headroom). On timeout, the handler invocation is interrupted, treated as failure (§8.1), and Ayla retries.

Long-running consumer work (e.g. catalog cache rebuild) MUST be moved off the synchronous handler path — handler enqueues a job and returns 202.

## 10. Relationship to other event docs

There are two distinct event systems in this stack. Do not confuse them.

| | This doc (`event-contract.md`) | `docs/design/policies/event-taxonomy.md` |
|---|---|---|
| Scope | Cross-service: Ayla → bot-platform over HTTP | In-process: within bot-platform `apps/eventbus/` Postgres outbox |
| Authority | ADR-0009 §Mandatory event contract | bot-platform two-bus architecture |
| Envelope | This doc §2 (integer `event_version`, enum `actor`, bare UUIDs) | event-taxonomy.md §2 (SemVer `event_version`, structured `actor` object, prefixed IDs) |
| Taxonomy size | 12 events (MVP) | ~80+ events across many modules |
| Consumer location | bot-platform consumers (per §3 of this doc) | bot-platform internal handlers, analytics, retention |

**Why two:**

- The cross-service contract (this doc) crosses a trust boundary, needs HMAC signing, has a deprecation calendar, and must be conservative in scope.
- The in-process taxonomy is a richer catalog for analytics and module composition inside bot-platform — it can iterate faster and carries more domain-specific shape.

**Bridge:** consumers defined in this doc MAY emit derived events on bot-platform's internal bus (e.g. `booking.*` consumer emits an internal `booking.created` snake_case event for the analytics fan-out). The two systems remain independent in their envelope shapes and ownership.
