## 3. Снято с продажи — 2 услуги, 0 рёбер (решение владельца, REPLY №4 п.3)

Единственное сознательное исключение из инварианта. `SalonService` не трогаем — гасим только рёбра, услуги остаются в каталоге без исполнителя и потому недоступны для записи.

| Услуга | Категория (интейк) | Почему снята |
|---|---|---|
| Комплекс "Гладкая кожа": антицеллюлитный массаж (45 мин) + VelaShape (60 минут) | Массажные комплексы | **смешанная**: ручная часть (Д/Т) + аппаратная (О); ни один мастер не покрывает обе |
| Комплекс "Лёгкие ноги": лимфодренажный массаж + вибромассаж (60 минут) | Массажные комплексы | **смешанная**: ручная часть (Д/И/Т) + аппаратный вибромассаж (О) |

**Наблюдение (не блокер, в объём GO не входит):** флага «снято с продажи» у `SalonService` в модели нет, есть только `is_active`. Услуги без рёбер остаются видимыми в каталоге, просто небронируемыми. Если нужно убрать их из выдачи полностью — это отдельное решение (`is_active=False` на `SalonService`), в текущий GO не входит.

## 4. Структурные оговорки (не блокируют матрицу, но нужны в план)

1. **«Массаж в 4 руки» и «Парный массаж»** требуют двух мастеров на один слот. Модель `SpecialistService` — это ребро «один мастер ↔ одна услуга», а `Appointment` держит одного специалиста. Назначение всем троим делает услугу бронируемой, но бронь займёт только одного мастера, второй останется свободен в календаре → риск двойной записи. Кандидат в отдельную задачу (не в объёме DRF-974).
2. **Смешанные комплексы** (2 шт., §3) — тот же корень: одна услуга требует двух разных исполнителей последовательно.
3. Обе оговорки — про модель данных, а не про эту чистку; чинить их сейчас не предлагаю.
