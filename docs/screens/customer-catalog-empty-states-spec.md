# CustomerCatalog — контекстные состояния отсутствия рекомендаций (P1)

> **Статус:** решения по пилоту LOCKED, 2026-07-02 (founder).
> **Экран:** `CustomerCatalogScreen` (`/customer/catalog`).
> **Переименование тикета:** не «состояние ‘ничего не найдено’», а **«контекстные состояния отсутствия рекомендаций»**.

---

## 0. UX-принципы

**0.1 Сквозной (не только каталог):**
> **Экран отсутствия рекомендаций — это не ошибка системы, а следующий шаг диалога.**
> Любой empty state отвечает не на «Почему пусто?», а на **«Что Ayla предлагает сделать дальше?»**. Применять шире каталога — поиск, запись, любые тупики. Кандидат в `docs/design/policies/` (design-стрим).

**0.2 Голос — точность формулировки:**
> Избегать «**не нашла**», если причина **объективна и известна системе** — тогда говорить фактом: «нет свободных мест», «нет подключённых салонов».
> «Я не нашла…» оставить для случаев, когда Ayla реально делала **подбор** и не смогла предложить подходящее.
> Никогда не выносить внутреннюю логику наружу («Trust Filter исключил…», «ничего безопасного…»).

## 1. Пилот — 3 контекстных состояния (+ default)

| `empty_reason` | Когда | Сообщение | Primary CTA |
|---|---|---|---|
| *(есть рекомендации)* | хотя бы одна секция непуста | — (пустые секции **скрываем**, no empty) | — |
| `search_no_match` | free-text запрос дал 0 | «Не нашла ничего по такому запросу» | «Посмотреть все услуги» |
| `region_empty` | город без подключённых салонов (реальность GLOBAL marketplace-пилота) | «Пока здесь нет подключённых салонов» | «Сообщить, когда появятся» |
| `booking_unavailable` | подходящие услуги есть, но **недоступны для записи** сейчас (нет слотов / провайдер не принимает) — **CONFIRMED трактовка** | **каталог (time-agnostic — CONFIRMED):** «Подходящие услуги есть, но сейчас нет свободных мест для записи. Могу подобрать другое время или похожие варианты.» | «Подобрать ещё раз» · «Смотреть все услуги» |
| *default* (reason отсутствует/неизвестен) | fallback | текст `booking_unavailable` | те же |

> **Точный текст для экрана слотов** (`CustomerSlotsScreen`, где есть выбранное время) — LOCKED дословно founder'ом: «На выбранное время сейчас нет свободных мест. Могу подобрать другое время или похожие варианты.» В каталоге он не применяется (там нет «выбранного времени»).

Правила `ui-ux-pro-max`: `empty-states` (helpful message + action), `no-results` (подсказка что делать, не «0 результатов»).

## 2. `empty_reason` — контракт API (добавляем в пилот)

**Решение:** backend каталога возвращает `empty_reason` уже сейчас — **ради расширяемого контракта, не ради UX**. Клиент маппит `reason → состояние`, не накапливая условную логику.

```
empty_reason ∈ { search_no_match, region_empty, booking_unavailable }
```

- Переименовано founder'ом: `no_available_results` → **`booking_unavailable`** (точнее отражает причину: «услуги есть, но не забронировать»).
- **Домен:** catalog-mirror + ranking/trust — **bot-platform** (ADR-0009), **in-domain**, не cross-repo.
- **Почему сейчас:** сегодня причин 3, через год — 10 (Quality Guardian / Premium / AI Ranking). Причина живёт на сервере → API растёт без ломки фронта. Клиент не обрастает условной логикой.

---

## 3. Guardian — строгий (пилот)

- Строгий Guardian: **никаких «Показать всё равно»**, никаких объяснений про качество.
- Сейчас Guardian фильтрует **не «плохие», а недоступные** варианты (отключён / не принимает / бронь невозможна) — trust = простая eligibility, не quality scoring ([[project_booking_flow_implementation_cut]]).
- **Осознанный выбор** (показать скрытое с честным предупреждением) — **post-pilot**, когда появится Quality Score.

## 5. Post-pilot target (полная модель)

Когда появятся фильтры / Quality Score / explainable AI:
- Новый класс: «Я не нашла вариантов, которые **могу уверенно рекомендовать**» (суждение о качестве).
- Осознанный-выбор Guardian: скрываем по умолчанию, показываем по явной просьбе с предупреждением.
- Структурные фильтры → CTA «ослабить фильтр» / «расширить радиус».
- Расширение `empty_reason` (quality_filtered, premium_only…) — без ломки фронта.
