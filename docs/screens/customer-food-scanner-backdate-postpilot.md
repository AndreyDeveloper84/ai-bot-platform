# Food Scanner — выбор даты (бэкдейт): DEFERRED post-pilot

> **Статус:** DEFERRED post-pilot. Пилот работает в режиме **«только сегодня»**.
> **Решение:** founder, 2026-07-02.
> **Область:** `FoodScannerCaptureScreen` (`/customer/food-scanner/capture`) + cross-repo контракт логирования еды.
> **Родитель-спек:** `docs/screens/customer-food-scanner-flow.md` §2, §13 (там date-picker описан как in-scope — см. «Расхождение со спеком» ниже).

---

## 1. Проблема (пользовательская)

Пользователь хочет «записать съеденное», дата для него вторична. Но иногда запись относится **не к сегодняшнему дню**: вечером забыл записать ужин; утром вспомнил вчерашний перекус; хочет заполнить прошлый день задним числом. Сейчас **вся еда попадает в «сегодня»**.

## 2. Решение и обоснование

**На пилот бэкдейт НЕ делаем. Логирование остаётся «только сегодня».** Полноценный выбор даты (day-strip) уходит в post-pilot.

Причины:
- **SCALED Wellness MVP** + support-mode — scope discipline (см. [[project_wellness_mvp_scaled_pilot]], [[project_pilot_scope_discipline]]).
- **Даты нет ни на одном слое контракта** — это не UI-задача, а cross-repo изменение:

| Слой | Состояние на 2026-07-02 | Дата в контракте? |
|---|---|---|
| Mini App `apps/miniapp/src/lib/food-scanner.ts` → `logMeal` | **stub** («served from stub — W4 follow-up»), пишет в память, `todayKey()` | ❌ в `LogMealRequest` поля даты нет |
| bot-platform `apps/integrations/ayla/nutrition_client.py` → `log_meal` | боевой REST-клиент | ❌ body = `{meal_type, portion_multiplier, scan_id?, dish_name?}` |
| Ayla `POST /api/v1/nutrition/internal/food-log/` | канонический стор, **репо Ayla** (домен Ayla по ADR-0009) | штампует «сейчас» на сервере |

- Food-log — **канонический домен Ayla** (ADR-0009). Окно бэкдейта — новое **продуктовое + backend** решение, требует ACK founder/tech-lead и работы в репо Ayla.

## 3. Порядок реализации post-pilot (contract-first, НЕ UI-first)

1. **Продукт:** решить окно бэкдейта — `вчера` / `3 дня` / `7 дней` / `14 дней`. Пока **не задано** (в родитель-спеке «7 дней» — гипотеза дизайна, не backend-факт). Это решает founder/продукт, не дизайн.
2. **Ayla:** `food-log` принимает опциональный `for_date` (или `consumed_at`) + серверная валидация окна.
3. **bot-platform:** `nutrition_client.log_meal` пробрасывает `for_date` в body.
4. **Mini App:** `food-scanner.ts` — добавить дату в `LogMealRequest`, снять stub (W4), пробросить.
5. **UI:** day-strip по разделу §4 ниже.

Строить п.5 раньше п.1–4 = полировать ленту поверх stub, который дату игнорирует.

## 4. Зафиксированный UI-дизайн (готов к реализации post-pilot)

Позиция подтверждена 2026-07-02. Обоснование — правила `ui-ux-pro-max` (домен `ux`).

### 4.1 Размещение (progressive disclosure)
- Верх экрана — **фото еды** (камера/галерея). Это главное действие; дата не должна его перебивать. → `primary-action` (один primary CTA), `progressive-disclosure`.
- Дата по умолчанию **свёрнута**: чип **«Сегодня»** + ссылка **«Изменить»**. Тап по «Изменить» → раскрывается горизонтальная лента дней (day-strip).
- **Никакого календаря** — оверкилл; строго day-strip.
- Не показываем ленту 100% пользователей ради 5% сценариев бэкдейта.

### 4.2 Day-strip
- Первые два элемента — слова: **«Сегодня»**, **«Вчера»**; далее формат **«Пн, 30 июн»**. → `date-formatting` (relative/locale, не `30/06`).
- Плитка дня ≥ **44×44px** → `touch-target-size` (High). Anti: `w-6 h-6`.
- Зазор между днями ≥ **8px** (`gap-2`) → `touch-spacing`.
- Выбранный день отличается визуально **не только цветом** (вес/подчёркивание/рамка) → `state-clarity`.
- Диапазон ограничен окном бэкдейта (см. §3.1); дни за границей не рендерим.
- Образец паттерна выбора дня в коде: `CustomerSlotsScreen` / `MasterScheduleScreen` / `RescheduleScreen`. Токены — `docs/design/system/design-tokens.md`. Каркас — `ScreenLayout` + `StickyCta`.

### 4.3 Подтверждение ДО распознавания
- При выбранном прошлом дне — **явный заметный текст** рядом с CTA: **«В дневник за 28 июня»** (или «Будет добавлено за 28 июня»).
- **CTA не перекрашиваем** — только текст. Другой цвет кнопки заставляет людей «искать ошибку».

### 4.4 Подтверждение ПОСЛЕ распознавания (недостающее состояние)
- Success-экран показывает не только «Салат добавлен», но и **«Записано за 28 июня»** → `success-feedback`. Пользователь мог забыть, что переключил день.

### 4.5 Требования к данным/edge cases (когда будет контракт)
- Дата фиксируется **в момент выбора** и едет с запросом; используется даже при повторной отправке / через offline-очередь (идемпотентность).
- День считается по **локальному времени пользователя** (таймзона путешественника).
- **Нет авто-переключения в полночь**: 23:59 выбрал «Сегодня» → 00:00 нажал «Распознать» → пишем в дату, показанную в UI на момент выбора, а не в новый день.
