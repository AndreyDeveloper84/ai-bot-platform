# MasterConversationDetail — «живое» обновление переписки (P1)

> **Статус:** решения по пилоту LOCKED, 2026-07-03 (founder).
> **Экран:** `MasterConversationDetailScreen` (M6, `/master/conversations/:id`).
> **Задача одной фразой:** переписка не должна казаться «замороженной».

---

## 0. Рефрейм и почему НЕ WebSocket в пилоте

У MAX **нет push за пределы чата** ([[reference_max_platform_capabilities]] / max-platform). Значит даже идеальный WebSocket даёт выгоду **только пока Mini App открыт** — он не открывает новую возможность, а лишь снижает задержку с ~15с до ~0. Это **улучшение качества, а не функциональность** → инфраструктурные усилия в пилоте невыгодны.

Что реально хочет мастер: **«не пропустить новое сообщение клиента».** Для этого достаточно обновления при открытии / возврате / раз в 15с.

Живой участник треда — **клиент** (AI-драфты в пилоте застабаны, backend возвращает null).

---

## 1. Пилот = Variant B (frontend-only, in-domain)

Всё на клиенте, переиспользуя существующий `load()` (`MasterConversationDetailScreen`). Без backend-изменений.

| # | Поведение | Деталь |
|---|---|---|
| B1 | **Refresh on focus/visibility** | возврат в Mini App/вкладку → `load()` |
| B2 | **Интервальный поллинг 15с** | пока экран **виден**; при скрытии — **полностью остановлен** (0 запросов) |
| B3 | **Пилюля «Новые сообщения ↓»** | появляется, если пришли новые, а мастер **не внизу**; тап → переход вниз |
| B4 | **Автоскролл только если внизу** | у последних сообщений — тихо дописываем; читает историю — **ничего не двигаем** |
| B5 | **Refresh перед отправкой — только при рассинхроне** | НЕ перед каждым сообщением (задержка). Триггеры: есть ожидающие новые / признак рассинхрона / сервер вернул конфликт (`:770` уже есть) |
| B6 | **Индикатор актуальности** | подпись над перепиской «Обновлено только что / N минут назад». При тихом сбое просто **стареет** — единственный ненавязчивый сигнал устаревания |

**Почему 15с:** 5с — лишняя нагрузка/незаметно; 30с — для чата уже «медленно». 15с — компромисс.

**B5 — почему важно:** мастер пишет «Хорошо, жду завтра», а за 2с до этого клиент прислал «Отменяю запись». Без refresh получится абсурдный диалог. Но refresh — только по признаку рассинхрона, не блайндом на каждом сообщении.

## 2. Acceptance criteria

1. Открытие экрана и возврат в Mini App/вкладку → переписка перезагружается.
2. Пока экран виден — авто-обновление каждые 15с; когда скрыт — поллинг **полностью остановлен** (0 запросов).
3. Новые сообщения при позиции «не внизу» → пилюля «Новые сообщения ↓»; при позиции «внизу» → тихо дописываются с плавной анимацией (без рывка вверх).
4. Отправка от себя делает refresh **только** при признаке рассинхрона (ожидающие новые / конфликт), НЕ перед каждым сообщением.
5. **Тихий поллинг:** неудачная попытка (сеть / таймаут / 5xx) **НЕ показывает ошибку**; следующая попытка — автоматически; текущая переписка остаётся читаемой. Никаких повторяющихся тостов «Не удалось обновить чат».
6. Подпись «Обновлено …» присутствует; при тихом сбое **стареет** (единственный сигнал устаревания). Индикаторов «Соединение…/Подключение…/Онлайн» **нет**.

---

## 3. Голос / UX — что НЕ добавлять
- Индикаторы «Соединение…» / «Подключение…» / «Онлайн» — пока нет WebSocket, только усложняют UX и создают ложное ожидание live.

Правила `ui-ux-pro-max`: паттерн «пилюля новых + автоскролл только снизу» (Telegram/WhatsApp/Slack); `progressive-loading` (поллинг в фоне, не блокируя); `state-transition` (плавное появление); `input-latency` (поллинг вне основного взаимодействия); `no-blocking-animation`.
