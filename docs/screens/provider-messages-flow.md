## 0. Обзор

### Что это за модуль

`Provider Messages Flow` — это provider-side экран и логика, где мастер, администратор или владелец видит обращения клиента, связанные с записью, и отвечает через Ayla.

Это не обычный прямой чат.

Главная идея:

> Клиент общается с Ayla, а Ayla помогает передать смысл мастеру/салону и вернуть клиенту спокойный, понятный ответ.

---

## 1. Почему это важно

После записи у клиента часто возникают вопросы:

- “Я опоздаю на 10 минут.”
- “Не могу найти вход.”
- “Что взять с собой?”
- “Можно ли прийти раньше?”
- “Можно поменять время?”
- “Можно уточнить, кто мастер?”
- “Мне не подходит этот день.”
- “Есть противопоказания?”
- “Болит спина, можно ли массаж?”

Если у провайдера нет понятного места для таких сообщений, появятся проблемы:

- клиент пишет, но мастер не видит;
- администратор не понимает, кто должен ответить;
- мастер отвечает напрямую и ломает Ayla-first опыт;
- важное сообщение теряется;
- перенос/отмена не запускаются корректно;
- клиент теряет доверие.

Этот модуль нужен, чтобы клиентская запись была обслужена не только технически, но и человечески.

---

## 2. Продуктовый принцип

### Ayla-mediated, not direct chat

Ayla остаётся посредником между клиентом и провайдером.

Плохо:

```text
Клиент ↔ мастер напрямую
```

Правильно:

```text
Клиент → Ayla → провайдер
Провайдер → Ayla → клиент
```

Почему так лучше:

- Ayla сохраняет единый спокойный тон;
- клиент не чувствует хаоса;
- сообщения можно фильтровать по безопасности;
- можно скрывать личные контакты;
- можно логировать события;
- можно управлять статусами;
- можно передавать вопросы администратору;
- можно избегать медицинских/обещающих формулировок.

---

## 3. Важное разделение: сообщение vs действие Booking Engine

Не каждый текст клиента должен становиться сообщением мастеру.

Некоторые запросы — это не “чат”, а доменное действие.

Главное правило:

```text
message = коммуникация
booking workflow = изменение записи через backend
provider notification = результат действия
```

Пример:

```text
Клиент: “Можно перенести на вечер?”
```

Это не обязательно сообщение мастеру.

Если Ayla может выполнить перенос через Booking Engine, правильный путь:

```text
Клиент просит перенос
→ Ayla определяет reschedule intent
→ Ayla проверяет правила переноса
→ Ayla получает доступные слоты
→ клиент выбирает новое время
→ backend атомарно переносит запись
→ клиент получает подтверждение
→ провайдер получает уведомление “Запись перенесена через Ayla”
```

Мастер/администратор не должен быть ручным bottleneck для обычного eligible reschedule.

---

## 4. Что этот модуль НЕ является

Это не:

- общий мессенджер;
- прямой чат клиента с мастером;
- WhatsApp внутри приложения;
- канал для маркетинговой рассылки;
- медицинская консультация;
- публичная поддержка;
- внутренний чат сотрудников;
- место, где вручную согласовывают каждый обычный перенос.

Это именно:

> операционные сообщения вокруг конкретной записи или клиентского действия, с разделением коммуникации и доменных действий Booking Engine.

---

## 5. Основные сценарии клиента

### C1. Клиент опаздывает

Клиент пишет Ayla:

```text
Я задержусь на 10 минут.
```

Provider-side видит:

```text
Клиент написал по записи:
“Я задержусь на 10 минут.”
```

Действия:

```text
[Ответить через Ayla]
[Отметить как решено]
[Передать администратору]
```

---

### C2. Клиент не может найти вход

Клиент пишет:

```text
Не могу найти вход.
```

Provider-side видит сообщение и может быстро ответить шаблоном:

```text
Я подскажу клиенту, как пройти.
```

Customer-facing ответ от Ayla:

```text
Анна, вход со стороны парковки. Я передала уточнение, вас ждут.
```

---

### C3. Клиент хочет уточнить подготовку

Клиент пишет:

```text
Что взять с собой?
```

Provider-side может выбрать быстрый ответ:

```text
Напомнить подготовку
```

Ayla возвращает клиенту утверждённый текст.

---

### C4. Клиент хочет перенести запись

Клиент пишет:

```text
Можно перенести на вечер?
```

Provider-side не должен автоматически получать это как обычный message thread.

Правильно:

```text
Ayla распознаёт intent переноса
→ если перенос eligible, запускает Booking Engine workflow
→ если перенос невозможен или требует человека, создаёт provider/admin message/task
```

---

### C5. Клиент сообщает чувствительную информацию

Пример:

```text
У меня сильная боль, немеет нога, можно ли массаж?
```

Provider-side должен видеть это аккуратно, но Ayla не должна обещать лечение.

Возможная маркировка:

```text
Требует осторожного ответа
```

Действия:

```text
[Ответить через Ayla]
[Рекомендовать консультацию специалиста]
[Передать администратору]
```

Запрещено:

```text
Да, массаж точно поможет.
```

## 6. Персоны и права

### 6.1. Одиночный мастер

Ольга видит все сообщения по своим записям.

Она может:

- открыть сообщение;
- ответить через Ayla;
- использовать быстрый ответ;
- отметить как решено;
- перенести запись, если нужно;
- отменить/изменить запись по правилам booking detail;
- увидеть историю сообщений по записи.

Ольга не нуждается в передаче администратору, потому что она сама администратор.

Но кнопка может быть заменена на:

```text
[Оставить заметку]
```

---

### 6.2. Мастер в команде

Мастер в команде видит сообщения только по своим записям, если салон разрешает.

Он может:

- прочитать сообщение;
- ответить через Ayla, если разрешено;
- выбрать быстрый ответ;
- отметить как решено, если вопрос простой;
- передать администратору.

Он не может по умолчанию:

- писать клиенту напрямую;
- видеть телефон клиента;
- менять условия записи без прав;
- обещать скидки/возвраты;
- отменять запись напрямую;
- давать медицинские рекомендации.

---

### 6.3. Администратор салона

Администратор видит:

- все сообщения по салону;
- непрочитанные;
- требующие ответа;
- переданные мастерами;
- сообщения по отменам/переносам;
- конфликтные сообщения;
- эскалации, когда Ayla не смогла выполнить booking workflow сама.

Администратор может:

- отвечать через Ayla;
- назначать ответственного;
- передавать мастеру;
- переносить запись;
- отменять запись;
- закрывать обращение;
- добавлять внутреннюю заметку.

---

### 6.4. Владелец салона

Владелец видит всё, что видит администратор.

Дополнительно может:

- смотреть качество коммуникации;
- видеть проблемные обращения;
- видеть частотность вопросов;
- контролировать стиль ответов.

Но подробная аналитика сообщений — post-MVP.

---

## 7. Навигация

### Solo-provider

Сообщения не обязательно делать отдельной вкладкой.

Рекомендуемо:

```text
Главная → Сообщения сегодня
Записи → Карточка записи → Сообщения по записи
Профиль / Ещё → Все сообщения
```

Для solo-мастера лучше не перегружать bottom nav.

---

### Салон / команда

Для салона сообщения могут быть:

```text
Главная → Новые запросы
Календарь → Запись → Сообщения
Профиль / Ещё → Сообщения
```

Если сообщений много, post-MVP можно сделать отдельную вкладку:

```text
Сообщения
```

Но для P0/P1 достаточно встроить их в `Главная` и `Карточка записи`.

Карточка входящего сообщения должна показывать:

```text
Клиент
Время

Краткий текст
Статус
Ответственный
```

Пример:

```text

```


## 12. B3 — Карточка сообщения

### Основные поля

```text
Текст сообщения клиента
Время получения
Связанная запись
Клиент
Статус
Кому назначено
```

### Пример

```text
Анна С. написала:

“Я задержусь на 10 минут.”

Запись:
Завтра, 16:00 · Массаж спины · Ольга
```

### Важное правило

Сообщение клиента показывается как цитата клиента.

Ayla не должна медицински интерпретировать сообщение в provider UI без специальной safety-логики.

## 13. B4 — Контекст записи

Чтобы провайдер быстро понял ситуацию, рядом с сообщением показываем краткий booking context:

```text
Завтра, 16:00
Массаж спины · 60 мин
Мастер: Ольга
Статус: Подтверждена
```

Действия:

```text
[Открыть запись]
[Открыть клиента]
```

Если сообщение связано с переносом и требует человека:

```text
[Открыть перенос]
```

Если перенос уже выполнен Ayla:

```text
[Открыть запись]
[Открыть в календаре]
```

## 14. B5 — Ответ через Ayla

### Назначение

Провайдер пишет или выбирает ответ, но клиент получает его в спокойном Ayla-tone.

UI label:

```text
Ответить через Ayla
```

Не использовать:

```text
Написать клиенту
Чат с клиентом
Ответить напрямую
```

---

### Как это должно работать

1. Провайдер вводит смысл ответа.
2. Ayla приводит текст к безопасному и спокойному формату.
3. Провайдер видит preview.
4. Провайдер подтверждает отправку.
5. Клиент получает сообщение от Ayla.

---

### Пример

Провайдер пишет:

```text
Ок, жду.
```

Ayla preview:

```text
Анна, вас ждут. Если задержка будет больше 10 минут, я помогу подобрать другое время.
```

Провайдер нажимает:

```text
[Отправить через Ayla]
```

---

## 15. B6 — Быстрые ответы

Быстрые ответы нужны, чтобы мастер/админ не писал одно и то же вручную.

### MVP-набор

```text
Клиент опаздывает
Как найти вход
Что взять с собой
Подготовка к услуге
Предложить перенос
Передать администратору
Отметить как решено
```

### Пример быстрых ответов

#### Клиент опаздывает

```text
Спасибо, передала. Вас ждут.
```

#### Как найти вход

```text
Вход со стороны парковки. Если не найдёте, напишите мне — подскажу.
```

#### Подготовка к услуге

```text
Лучше прийти за 5–10 минут до начала и взять удобную одежду, если она нужна для процедуры.
```

### Правило

Быстрые ответы должны быть:

- короткими;
- спокойными;
- без давления;
- без медицинских обещаний;
- без грубых формулировок.

## 17. Статусы сообщений и событий

### Основные статусы

| Статус | Метка в UI | Значение |
|---|---|---|
| `new` | Новое | сообщение ещё не обработано |
| `needs_reply` | Требует ответа | нужен ответ клиенту |
| `in_progress` | В работе | кто-то уже занимается |
| `assigned_to_admin` | Передано администратору | мастер передал вопрос |
| `resolved` | Решено | вопрос закрыт |
| `system_handled` | Ayla ответила | ответ был автоматический или системный |
| `blocked` | Требует проверки | сообщение нельзя обработать автоматически |
| `booking_workflow_completed` | Выполнено через Ayla | Ayla выполнила доменное действие через backend |
| `provider_notification` | Уведомление | провайдеру нужно знать о событии, но не обязательно отвечать |

## 18. Сценарий F1 — Клиент опаздывает

### Поток

```text
Клиент пишет Ayla: “Я задержусь на 10 минут”
→ Ayla связывает сообщение с записью
→ Provider получает уведомление
→ Provider открывает сообщение
→ Выбирает быстрый ответ или пишет ответ
→ Ayla отправляет клиенту спокойный ответ
→ Сообщение становится resolved
```

### UX copy provider-side

```text
Клиент сообщил, что задержится.
```

### Customer-facing copy

```text
Анна, спасибо, я передала. Вас ждут.
```

## 19. Сценарий F2 — Клиент не может найти вход

### Поток

```text
Клиент пишет: “Не могу найти вход”
→ Provider получает сообщение
→ Provider выбирает быстрый ответ “Как найти вход”
→ Ayla отправляет инструкцию
```

### Нужно в будущем

Для салонов полезно хранить:

```text
entrance_instruction
parking_instruction
floor / кабинет
landmark
```

Но для MVP можно использовать ручной ответ.

## 20. Сценарий F3 — Клиент задаёт вопрос по подготовке

### Поток

```text
Клиент спрашивает, что взять с собой
→ Provider выбирает быстрый ответ
→ Ayla использует service preparation note
→ Клиент получает ответ
```

### Важно

Если у услуги нет preparation note, не придумывать медицинские советы.

Лучше:

```text
Я уточню у салона и вернусь с ответом.
```

## 21. Сценарий F4 — Клиент хочет перенести запись

### Важное правило

Запрос на перенос — это не всегда сообщение.

Если Ayla может выполнить перенос через Booking Engine, это становится booking workflow.

---

### F4A — Auto-reschedule через Booking Engine

```text
Клиент пишет: “Можно перенести на вечер?”
→ Ayla определяет reschedule intent
→ Ayla находит активную запись клиента
→ Ayla проверяет reschedule policy
→ Ayla запрашивает доступные слоты
→ Ayla показывает клиенту варианты
→ клиент выбирает новое время
→ backend атомарно переносит запись
→ клиент получает подтверждение
→ provider получает notification “Запись перенесена через Ayla”
```

Provider-side notification:

```text
Запись перенесена через Ayla

Анна С.
Массаж спины · 60 мин

Было:
Сегодня, 16:00

Стало:
Сегодня, 18:00

[Открыть запись]
[Открыть в календаре]
```

---

### F4B — Escalation to admin/provider

Если Ayla не может перенести сама:

```text
нет доступных слотов
поздний перенос
спорная оплата
услуга/мастер меняется нестандартно
запись почти началась
нужна approval policy салона
есть safety/medical context
```

Тогда создаётся provider/admin message/task:

```text
Клиент хочет перенести запись, но Ayla не смогла выполнить перенос автоматически.
```

Actions:

```text
[Открыть перенос]
[Предложить время]
[Передать администратору]
```

---

### Запрещено

Провайдер не должен просто написать:

```text
Да, приходите в 18:00.
```

без проверки слота на backend.

Ayla не должна обещать перенос текстом без backend transaction.

## 27. Locked decisions

### Q-PMSG-1 — Нужна ли отдельная вкладка “Сообщения” в MVP?

**Решение:** LOCKED.

Нет.

В MVP нет отдельной top-level вкладки “Сообщения”.

Сообщения живут внутри:

```text
Главная / Dashboard
Карточка записи
Календарь → индикатор на записи
```

Post-MVP можно добавить полноценный inbox, если объём сообщений вырастет.

---

### Q-PMSG-2 — Может ли team-master отвечать клиенту через Ayla?

**Решение:** LOCKED.

Да, но только в ограниченных случаях.

Team-master может отвечать через Ayla только:

- по своим записям;
- на low-risk operational messages;
- если политика салона разрешает.

Low-risk:

```text
клиент опаздывает
как найти вход
простая подготовка
“да, вас ждут”
```

Передавать администратору:

```text
возврат
оплата
жалоба
медицинский вопрос
перенос/отмена, требующие проверки
скидка
конфликт
запрос прямого контакта
```

---

### Q-PMSG-3 — Должен ли ответ всегда переписываться Ayla перед отправкой?

**Решение:** LOCKED.

Свободный текст провайдера проходит через Ayla rewrite/preview.

Утверждённые быстрые ответы могут не переписываться, но всё равно отправляются как Ayla-mediated messages.

Провайдер подтверждает финальный текст перед отправкой.

---

### Q-PMSG-4 — Может ли Ayla отвечать или действовать автоматически без провайдера?

**Решение:** LOCKED UPDATED.

Ayla может автоматически отвечать только в безопасных шаблонных случаях.

Ayla также может автоматически выполнить перенос записи, но только через официальный Booking Engine workflow.

Allowed auto-replies:

```text
message received acknowledgement
entrance instruction
approved preparation note
late arrival received acknowledgement
```

Allowed auto-action:

```text
eligible reschedule через Booking Engine
```

Для auto-reschedule обязательно:

- запись принадлежит клиенту;
- запись активна;
- policy разрешает перенос;
- есть доступные слоты;
- клиент выбрал слот;
- backend атомарно выполнил перенос;
- billing chain проверен;
- provider получил notification.

Запрещено:

- обещать новое время без backend slot check;
- менять запись без подтверждения клиента;
- пропускать cancellation/reschedule policy;
- пропускать billing checks;
- автоответы по медицинским, финансовым, конфликтным и refund-сценариям.

---

### Q-PMSG-5 — Нужно ли хранить всю историю сообщений?

**Решение:** LOCKED.

В MVP история хранится по booking context.

Provider может видеть:

- сообщения по конкретной записи;
- историю сообщений клиента по ролям и доступам.

Не делаем бесконечный WhatsApp-like global chat в MVP.

Post-MVP можно добавить полный inbox/history.

---

### Q-PMSG-6 — Должен ли клиент видеть имя мастера в ответе?

**Решение:** LOCKED.

Клиент видит отправителем Ayla.

Ayla может упоминать мастера/салон внутри текста, если это полезно:

```text
Ольга вас ждёт.
В салоне знают, что вы задерживаетесь.
```

Не использовать формат прямого отправителя:

```text
Ольга: ...
```

## 33. Acceptance criteria

1. Провайдер видит список входящих сообщений.
2. Провайдер видит сообщения по конкретной записи.
3. Сообщение связано с booking context.
4. Нажатие на сообщение открывает карточку сообщения.
5. Из сообщения можно открыть запись.
6. Из сообщения можно открыть клиента, если роль позволяет.
7. Одиночный мастер видит все свои сообщения.
8. Team-master видит только сообщения по своим записям, если политика салона разрешает.
9. Администратор видит все сообщения салона.
10. Ответ клиенту отправляется только через Ayla-mediated flow.
11. UI не использует wording “чат с клиентом”.
12. Быстрые ответы доступны для частых сценариев.
13. Сообщение можно отметить как решённое.
14. Сообщение можно передать администратору.
15. Если сообщение связано с переносом и перенос eligible, Ayla запускает Booking Engine workflow.
16. Provider approval не требуется для обычного eligible reschedule.
17. После auto-reschedule provider получает notification “Запись перенесена через Ayla”.
18. Provider notification открывает Booking Detail или Calendar.
19. Если перенос не eligible, создаётся provider/admin message/task.
20. Если ответ содержит unsafe claims, отправка блокируется или требует review.
21. Offline state отключает отправку ответа.
22. Permission denied state покрыт.
23. События отправляются для открытия, ответа, передачи, решения, safety block и provider notification.
24. Role-based visibility enforced server-side.
