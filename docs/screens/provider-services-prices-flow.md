## 0. Обзор

### Что это за модуль

`Управление услугами и ценами` — это provider-side экран, где одиночный мастер или администратор салона управляет каталогом услуг.

Этот модуль отвечает на вопрос:

> “Какие услуги мы продаём, сколько они стоят, сколько длятся, кто их выполняет и видит ли их клиент?”

Ayla не сможет корректно записывать клиентов без данных об услугах.

Каждая запись зависит от связки:

```text
услуга
+ мастер
+ длительность
+ буфер после услуги
+ свободное окно
+ цена
```

Мы уже описали:

1. карточку записи;
2. календарь и расписание.

Теперь описываем слой каталога: услуги, цены, длительности, буферы и доступность для записи.

---

## 1. Почему это важно

Без модуля услуг и цен:

- клиентский каталог будет пустым или неправильным;
- Ayla не сможет посчитать длительность свободного слота;
- буфер между записями может быть проигнорирован;
- мастер может быть записан на услугу, которую он не выполняет;
- изменение цены может незаметно сломать переносы и billing logic;
- изменение длительности может создать пересечения в календаре;
- администратор не сможет скрыть временно недоступную услугу;
- одиночный мастер не сможет самостоятельно вести прайс;
- описания услуг могут стать небезопасными, например с медицинскими обещаниями.

Это P0-модуль, потому что без него запись клиента не может быть надёжной.

## 2. API reality notes

### 2.1. Текущая модель услуги из Spec v2.0

В текущей API Specification v2.0 модель `Service` содержит:

```text
id
specialist_id
category_id
name
description
price
price_max
duration_minutes
is_active
created_at
```

Создание услуги в Pro self-service описано через:

```text
POST /specialists/me/services
```

Обязательные поля:

```text
category_id
name
price
duration_minutes
```

Обновление услуги:

```text
PATCH /specialists/me/services/{id}
```

Удаление услуги:

```text
DELETE /specialists/me/services/{id}
```

При удалении есть ошибка:

```text
409 HAS_APPOINTMENTS
```

если есть активные записи на услугу.

---

### 2.2. Changelog-дополнение по Booking Engine

В `API Changelog — BeautyGO Backend` зафиксировано, что Booking Engine добавил snapshot-поля в `Appointment`:

```text
snapshot_service_name
snapshot_price
snapshot_commission_percent
snapshot_specialist_income
snapshot_platform_fee
snapshot_timezone
```

Также в `Service` добавлено поле:

```text
buffer_after_minutes
```

Это значит:

- цена в уже созданной записи должна жить отдельно от текущей цены услуги;
- название услуги в уже созданной записи должно сохраняться;
- финансовые расчёты должны опираться на snapshot-поля;
- свободные окна должны учитывать не только `duration_minutes`, но и `buffer_after_minutes`.

---

### 2.3. Spec drift policy

По результатам API-аудита и Implementation Status важное правило:

```text
Если Spec v2.0 расходится с текущим backend/OpenAPI/changelog,
то перед реализацией нужно проверить актуальную OpenAPI schema.
```

Для реализации использовать:

1. текущую backend OpenAPI schema;
2. документированные deviations;
3. затем обновлять Spec.

Не писать frontend/backend “по старой спеки”, если backend уже сознательно ушёл вперёд.

## 3. Обещание продукта

Провайдер должен уметь:

- видеть список всех услуг;
- создать услугу;
- изменить цену;
- изменить цену “от–до”;
- изменить длительность;
- изменить буфер после услуги;
- назначить мастеров;
- скрыть услугу из клиентского каталога;
- безопасно перенести услугу в архив;
- восстановить услугу из архива;
- понимать, как изменения повлияют на будущие записи;
- не ломать уже созданные записи.

Интерфейс должен быть достаточно простым для одиночного мастера и достаточно структурным для администратора салона.

## 4. Персоны

### 4.1. Ольга — одиночный мастер

Ольга сама управляет своим прайсом:

- создаёт услуги;
- меняет цену;
- меняет длительность;
- меняет буфер после услуги;
- пишет описание;
- решает, видна ли услуга клиентам;
- архивирует устаревшие услуги;
- восстанавливает услуги при необходимости.

Для Ольги экран должен ощущаться так:

> “Я сама управляю своими услугами и прайсом без администратора.”

---

### 4.2. Администратор салона

Администратор управляет каталогом салона:

- редактирует услуги;
- назначает услуги мастерам;
- скрывает и архивирует услуги;
- следит за корректностью длительности;
- следит за ценами;
- не допускает ошибок в записи.

Администратор — основной ежедневный оператор каталога.

---

### 4.3. Владелец салона

Владелец имеет полный контроль:

- ценовая политика;
- видимость услуг;
- назначение мастеров;
- архивирование и восстановление;
- контроль истории изменений.

---

### 4.4. Мастер в команде

Мастер в команде обычно не редактирует услуги салона.

Он может видеть:

- какие услуги назначены ему;
- длительность;
- публичное описание;
- внутренние подготовительные заметки, если они нужны для работы.

Мастер может предложить изменение, но по умолчанию не меняет каталог напрямую.

## 5. Пользовательские задачи

### Задача одиночного мастера

> “Когда я меняю прайс или добавляю услугу, я хочу быстро обновить это в Ayla, чтобы клиенты сразу записывались правильно.”

### Задача администратора

> “Когда в салоне меняется услуга, цена или мастер, я хочу обновить каталог без риска сломать уже созданные записи.”

### Задача владельца

> “Когда я управляю каталогом, я хочу понимать, какие услуги активны, кто их выполняет и как изменения повлияют на записи.”

### Задача мастера в команде

> “Когда я смотрю свои услуги, я хочу понимать, на какие процедуры меня могут записать и что увидит клиент.”

## 6. Навигация

### Одиночный мастер

Для одиночного мастера `Услуги` могут быть отдельной вкладкой нижнего меню:

```text
Главная
Записи
Клиенты
Услуги
Профиль
```

Почему: для solo-мастера услуги — это часть ежедневного управления бизнесом.

---

### Салон / команда

Для салона возможна такая нижняя навигация:

```text
Главная
Календарь
Клиенты
Команда
Профиль
```

В этом случае услуги могут находиться здесь:

```text
Профиль / Ещё → Услуги и цены
```

или как быстрый переход с главной:

```text
Главная → Услуги и цены
```

Если салон активно управляет каталогом, в будущем `Услуги` можно вынести в отдельную top-level вкладку.

При заведении нового solo-мастера или салона услуги должны быть добавлены до публикации записи для клиентов.

## 9. B1 — Заголовок и состояние каталога

### Назначение

Показывает общее состояние каталога.

Примеры:

```text
Услуги и цены
12 активных услуг
```

Возможные статусы:

```text
Каталог готов
Есть услуги без мастера
Есть скрытые услуги
Есть услуги без длительности
Есть услуги без цены
Есть услуги без буфера
```

---

### Правила готовности каталога

Услуга доступна для клиентской записи только если у неё есть:

- название;
- категория;
- длительность;
- цена или понятная ценовая метка;
- хотя бы один назначенный мастер;
- активный статус;
- видимость для клиента.

## 11. B3 — Категории услуг

Примеры категорий:

```text
Массаж
Аппаратные процедуры
Косметология
Эпиляция
Маникюр
Другое
```

### Правила

- категория влияет на группировку в каталоге;
- категория может влиять на рекомендации Ayla;
- категория не должна обещать медицинский результат;
- категория обязательна по текущей API-спецификации при создании услуги;
- если категория не выбрана, услуга остаётся черновиком.

## 12. B4 — Список услуг

### Поля карточки услуги

Каждая карточка показывает:

```text

Длительность
Буфер после услуги
Видимость
```

Пример нормальной карточки:



```text

```

Нажатие открывает:

```text

```

## 13. B5 — Видимость и назначенные мастера

### Метки видимости

| Состояние | Метка в интерфейсе | Комментарий |
|---|---|---|
| `visible` | Видна клиентам | Можно показывать в клиентском каталоге |
| `hidden` | Скрыта | Не видна клиентам, но доступна провайдеру |
| `draft` | Черновик | Не готова к записи |
| `archived` | В архиве | Не используется для новых записей |

### Текущий backend gap

В Spec v2.0 у услуги есть `is_active`, но нет отдельного `visibility`.

Для продукта нужно различать:

```text
is_active = техническая активность
visibility = публичная видимость в клиентском каталоге
```

MVP может временно использовать `is_active=false` как скрытость/неактивность, но стратегически лучше добавить enum `visibility`.

---

### Метки назначенных мастеров

```text
Ольга
2 мастера
Нет мастера
```

### Предупреждение

Если у услуги нет назначенного мастера:

```text
Клиенты не смогут записаться на эту услугу, пока не назначен мастер.
```

## 16. Сценарий F1 — Создание услуги

### Назначение

Создать новую услугу в каталоге.

### Поток

```text
Нажать “Добавить услугу”
→ Заполнить название
→ Выбрать категорию
→ Указать длительность
→ Указать цену или диапазон цен
→ Указать буфер после услуги
→ Назначить мастеров
→ Выбрать видимость
→ Сохранить
```

### Обязательные поля

- название;
- категория;
- длительность;
- цена или ценовая метка;
- назначенный мастер;
- видимость.

### Необязательные поля

- описание;
- подготовительная заметка;
- внутренняя заметка;
- фото;
- утверждённый текст ограничений / противопоказаний от салона;
- буфер после услуги, если используется дефолт.

### MVP-поля

```text
Название
Категория
Длительность
Цена
Цена до / price_max
Буфер после услуги
Мастера
Видимость
Описание
```

## 17. Сценарий F2 — Редактирование услуги

### Назначение

Изменить существующую услугу.

Можно редактировать:

- название;
- описание;
- категорию;
- длительность;
- цену;
- price_max;
- буфер после услуги;
- назначенных мастеров;
- видимость.

---

### Правило безопасного редактирования

Изменения применяются к будущим записям.

Уже созданные записи сохраняют snapshot.

Snapshot-поля:

```text
snapshot_service_name
snapshot_price
snapshot_commission_percent
snapshot_specialist_income
snapshot_platform_fee
snapshot_timezone
```

Дополнительное требование:

```text
snapshot_duration_minutes
```

Если отдельного поля `snapshot_duration_minutes` пока нет, source of truth для длительности существующей записи:

```text
start_datetime + end_datetime
```

---

### Предупреждение при изменении цены

```text
Изменить цену?

Новая цена будет применяться к будущим записям.
Уже созданные записи сохранят цену на момент записи.
```

---

### Предупреждение при изменении длительности

```text
Изменить длительность?

Это повлияет на будущие свободные окна.
Уже созданные записи не изменятся автоматически.
```

---

### Предупреждение при изменении буфера

```text
Изменить буфер после услуги?

Это повлияет на будущие свободные окна.
Уже созданные записи не изменятся автоматически.
```

## 18. Сценарий F3 — Назначение мастеров

### Назначение

Определить, какие мастера могут выполнять услугу.

### Одиночный мастер

Обычно назначается автоматически:

```text
Ольга
```

### Салон

Администратор выбирает мастеров:

```text
☑ Ольга
☑ Анна
☐ Мария
```

### Правила

- клиент может записаться на услугу только к назначенному мастеру;
- расчёт свободных окон использует выбранного мастера, длительность услуги и буфер;
- удаление мастера из услуги не отменяет уже созданные записи;
- будущие записи с удалённым мастером остаются активными, но требуют внимания, если нужно проверить корректность.

### Предупреждение

```text
У Анны есть 2 будущие записи на эту услугу.
Если убрать мастера, эти записи останутся активными, но новые клиенты не смогут выбрать Анну для этой услуги.
```

## 19. Сценарий F4 — Скрыть / показать услугу

### Назначение

Временно убрать услугу из клиентского каталога без удаления.

Сценарии:

- услуга временно недоступна;
- оборудование на обслуживании;
- сезонная услуга;
- цена ещё не готова;
- мастер временно не оказывает эту услугу;
- услуга доступна только по договорённости.

### Поведение скрытой услуги

Скрытая услуга:

- не показывается клиентам в каталоге;
- не предлагается Ayla;
- остаётся видимой в админском/provider-каталоге;
- может быть доступна для ручной записи admin/owner/solo-master;
- не ломает уже созданные записи.

### Текст подтверждения

```text
Скрыть услугу?

Клиенты не увидят её в каталоге и не смогут записаться самостоятельно.
Уже созданные записи останутся активными.
```

## 20. Сценарий F5 — Перенос услуги в архив

### Назначение

Безопасно вывести услугу из активного каталога.

Архив — это сильнее, чем “скрыть”.

Архивная услуга:

- скрыта из клиентского каталога;
- недоступна для новых записей;
- остаётся в истории;
- используется в прошлых записях;
- может быть восстановлена администратором, владельцем или solo-мастером, если это разрешено.

### Предупреждение при архивировании

```text
Перенести услугу в архив?

Новые записи на неё будут недоступны.
История старых записей сохранится.
```

Если есть будущие записи:

```text
На эту услугу есть будущие записи.

Перед архивированием нужно решить, что с ними делать.
```

Действия:

```text
Открыть записи
Сначала скрыть услугу
Назад
```

## 21. Locked decisions

### Q-PSP-1 — Может ли одиночный мастер редактировать свои услуги напрямую?

**Решение:** LOCKED.

Да.

Одиночный мастер может напрямую создавать и редактировать свои услуги.

Причина:

Одиночный мастер является владельцем, администратором и мастером в одном лице. Без прямого управления услугами он не сможет самостоятельно вести бизнес.

Требования безопасности:

- изменение цены требует подтверждения;
- изменение длительности требует подтверждения;
- изменение буфера требует подтверждения;
- архивирование требует подтверждения;
- уже созданные записи сохраняют snapshot.

---

### Q-PSP-2 — Может ли мастер в команде менять цену и длительность услуги?

**Решение:** LOCKED.

Нет по умолчанию.

Мастер в команде не может напрямую менять цену, длительность и буфер услуги.

Мастер в команде может:

- видеть назначенные ему услуги;
- видеть длительность и описание;
- предложить изменение;
- отправить запрос администратору.

Каталогом управляет администратор или владелец.

Причина:

Цена, длительность и буфер влияют на выручку, расписание, доступность слотов и ожидания клиента. Это зона операционного контроля салона.

---

### Q-PSP-3 — Должно ли изменение цены влиять на уже созданные записи?

**Решение:** LOCKED.

Нет.

Изменение цены применяется только к будущим записям.

Уже созданные записи сохраняют:

- `snapshot_price`;
- `snapshot_service_name`;
- `snapshot_specialist_income`;
- `snapshot_platform_fee`;
- другие billing snapshot-поля, если они используются.

UX-предупреждение:

```text
Новая цена будет применяться только к будущим записям.
Уже созданные записи сохранят цену на момент записи.
```

---

### Q-PSP-4 — Должно ли изменение длительности влиять на уже созданные записи?

**Решение:** LOCKED.

Нет.

Изменение длительности применяется только к будущему расчёту свободных окон.

Уже созданные записи сохраняют свой исходный интервал:

- `start_datetime`;
- `end_datetime`;
- желательно `snapshot_duration_minutes`.

Если `snapshot_duration_minutes` пока не реализован, создать follow-up:

```text
Add explicit snapshot_duration_minutes to Appointment
or document end_datetime - start_datetime as duration source of truth.
```

UX-предупреждение:

```text
Новая длительность будет применяться только к будущим записям.
Уже созданные записи не изменятся автоматически.
```

---

### Q-PSP-5 — Должны ли скрытые услуги быть доступны для ручной записи?

**Решение:** LOCKED.

Да, но только для ролей с правами управления каталогом.

Скрытая услуга:

- не видна клиентам;
- не предлагается Ayla;
- не доступна для самостоятельной клиентской записи;
- доступна для ручной записи admin/owner/solo-master, если роль позволяет.

Причина:

В реальном бизнесе бывают услуги “по договорённости”, временные услуги и услуги только для постоянных клиентов.

Backend/spec gap:

В текущей модели есть `is_active`, но нет отдельного `visibility`.

Рекомендуемый follow-up:

```text
Add service.visibility enum:
- draft
- visible
- hidden
- archived
```

---

### Q-PSP-6 — Должны ли архивные услуги быть восстановимыми?

**Решение:** LOCKED.

Да.

Архив — это soft-archive, не физическое удаление.

Правила:

- архивная услуга недоступна для новых записей;
- архивная услуга остаётся в истории старых записей;
- архивную услугу можно восстановить, если роль позволяет;
- hard delete разрешён только для черновика без записей, отзывов и платежей.

Причина:

Услуга может быть связана с историей записей, отзывами, оплатами и аналитикой. Физическое удаление ломает историю.

---

### Q-PSP-7 — Можно ли использовать AI для написания описания услуги?

**Решение:** LOCKED.

Да, но только как черновик.

AI может помочь написать описание услуги, но публикация требует подтверждения человеком.

Запрещено публиковать без проверки:

- медицинские обещания;
- гарантии результата;
- диагнозы;
- формулировки “лечит”, “избавляет”, “устраняет болезнь”;
- стыдящие формулировки про тело;
- агрессивные маркетинговые обещания.

UX-правило:

```text
AI подготовила черновик. Проверьте текст перед публикацией.
```

## 23. Edge cases

### 23.1. Цена изменилась после создания записи

Уже созданная запись сохраняет старый snapshot цены.

Карточка записи provider-side должна показывать snapshot, если запись уже создана.

Если происходит перенос, billing chain сравнивает старый и новый snapshot по правилам billing.

---

### 23.2. Длительность изменилась после создания записи

Уже созданная запись сохраняет старую длительность через:

- `start_datetime`;
- `end_datetime`;
- желательно `snapshot_duration_minutes`.

Будущая доступность рассчитывается по новой длительности.

Если администратор хочет поменять длительность уже созданной записи, это должен быть отдельный явный edit/reschedule flow.

---

### 23.3. Буфер после услуги изменился после создания записи

Уже созданная запись не меняется.

Будущие свободные окна рассчитываются с новым буфером.

Если буфер конфликтует с уже созданными будущими записями, показать attention item.

---

### 23.4. Услуга скрыта, но есть будущие записи

Будущие записи остаются активными.

Показать предупреждение:

```text
У услуги есть будущие записи. Они останутся активными.
```

---

### 23.5. Услугу пытаются архивировать, но есть будущие записи

Не разрешать прямое архивирование, пока будущие записи не просмотрены.

---

### 23.6. Мастера убрали из услуги

Существующие записи остаются активными.

Новые записи больше не могут выбрать этого мастера для этой услуги.

---

### 23.7. У услуги нет цены

Разрешить только черновик.

Не показывать клиентам.

---

### 23.8. У услуги нет длительности

Разрешить только черновик.

Не делать услугу доступной для записи.

---

### 23.9. Описание содержит небезопасные обещания

Публикацию нужно заблокировать или отправить на проверку.

Примеры опасных формулировок:

```text
лечит
гарантирует
избавит от
медицинский эффект
диагноз
устраняет заболевание
```

---

### 23.10. DELETE endpoint существует, но UX не должен вести пользователя к hard delete

Даже если backend имеет `DELETE /specialists/me/services/{id}`, основной UX должен использовать:

```text
Скрыть
В архив
Восстановить
```

`Удалить` разрешено только для черновиков без истории.

11. Буфер после услуги учитывается в будущих свободных окнах.
12. Скрытая услуга не видна клиентам.

14. Скрытая услуга может быть доступна для ручной записи администратору/владельцу/solo-мастеру, если роль позволяет.

17. Архивная услуга может быть восстановлена.
18. Hard delete разрешён только для черновика без записей, отзывов и платежей.
19. Изменение цены применяется только к будущим записям.
20. Уже созданные записи сохраняют snapshot цены.
21. Изменение длительности применяется только к будущим свободным окнам.
22. Уже созданные записи сохраняют исходный интервал времени.
23. Если нет `snapshot_duration_minutes`, создаётся follow-up или фиксируется `end_datetime - start_datetime` как source of truth.
24. Удаление мастера из услуги не отменяет существующие записи.
25. Новые записи не могут выбрать удалённого мастера для этой услуги.
26. Публикация небезопасных медицинских обещаний блокируется или требует проверки.
27. AI-описание остаётся черновиком до подтверждения человеком.
28. Права доступа enforced server-side, не только через UI.
29. Offline-состояние отключает действия изменения.
30. Состояние “нет доступа” покрыто.
31. События отправляются при изменении цены, длительности, буфера, видимости и архива.
32. Перед реализацией API draft сверяется с текущей backend OpenAPI schema.

## 31. Follow-up tasks

### FUP-PSP-1 — Service visibility enum

Добавить в backend/spec отдельное поле:

```text
service.visibility = draft | visible | hidden | archived
```

Причина:

`is_active` недостаточно точно описывает продуктовые состояния.

---

### FUP-PSP-2 — Explicit snapshot_duration_minutes

Добавить или задокументировать source of truth для длительности уже созданной записи:

```text
snapshot_duration_minutes
```

или:

```text
end_datetime - start_datetime
```

---

### FUP-PSP-3 — Replace hard delete UX with archive UX

Даже если backend поддерживает `DELETE`, интерфейс должен вести пользователя через:

```text
Скрыть
В архив
Восстановить
```

Hard delete — только для безопасных черновиков.

---

### FUP-PSP-4 — AI description safety gate

Добавить проверку описания услуги на опасные формулировки:

```text
лечит
гарантирует
избавляет
диагноз
медицинский эффект
```

MVP может использовать простой blocklist + ручное подтверждение.

---

### FUP-PSP-5 — OpenAPI validation before implementation

Перед реализацией W1/W2 сверить текущие endpoints с backend OpenAPI schema.

Причина:

В проекте уже были расхождения между Spec v2.0, changelog и реальным кодом.

## 32. Smart Landing / Template service prefill

> Merged from `provider-services-prices-flow.smart-landing-addendum.md` (2026-05-28). Источник UX: `provider-onboarding/provider-landing-enrichment-flow.md`.

### 32.1. Что меняется

Услуги и цены могут быть созданы не только вручную, но и из:

```text
external enrichment draft
uploaded price extraction
template bootstrap
manual input
```

### 32.2. Service draft sources

Каждая созданная услуга должна знать источник:

```text
yclients
website
vk
yandex_maps
2gis
uploaded_price
template
manual
```

Для каждого важного поля хранить provenance:

```text
name
category
price
price_max
duration_minutes
buffer_after_minutes
description
```

### 32.3. Template-generated services

Если услуга пришла из шаблона, она создаётся как draft/requires_review.

Нельзя автоматически публиковать:

```text
шаблонные цены
шаблонные длительности
шаблонное описание
лишние услуги из шаблона
```

UX label:

```text
Создано по шаблону — проверьте перед публикацией.
```

### 32.4. Region price benchmarks

Региональные цены — это подсказки, не финальные цены.

Правильно:

```text
По похожим мастерам в вашем регионе цена обычно в диапазоне 1 500–2 300 ₽.
Какую цену поставить?
```

Неправильно:

```text
Мы поставили цену 1 800 ₽.
```

### 32.5. Acceptance criteria additions

33. Услуга может быть создана из enrichment draft.
34. Услуга может быть создана из uploaded price extraction.
35. Услуга может быть создана из template bootstrap.
36. Template-created услуги имеют статус draft/requires_review.
37. Региональный price benchmark показывается только как рекомендация.
38. Пользователь может accept/edit/reject каждую сгенерированную услугу.
39. Услуга не становится bookable, пока обязательные поля не подтверждены.
40. Field-level provenance сохраняется для сгенерированных услуг.
