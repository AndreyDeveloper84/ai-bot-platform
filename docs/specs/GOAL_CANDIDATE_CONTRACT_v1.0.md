## 0. Как читать

### 0.1 Что этот документ есть и чем не является

Он описывает **один путь**:

```
реплика человека
  → семантическое извлечение
  → GoalCandidate
  → валидация
  → политика подтверждения / продвижения
  → GoalCreateCommand
  → авторитетная Goal
  → жизненный цикл Goal
```

**Non-goals трека B** (не проектируется здесь, ссылки — на соседние треки):

| не здесь | где |
|---|---|
| План и его пересборка | трек D, Plan Engine, канон §15 |
| DecisionReadiness / готовность решения | трек A, канон §8, DRF-1533 |
| Ранжирование кандидатов услуг | трек C, канон §9 |
| **Прогресс цели** | **не проектировать вовсе** — §35 п.13, DRF-1523, DRF-1546 |
| Несколько одновременных измеримых результатов | OD-GOAL-4, сущность `Desired Outcome`, не `ClientGoal` |

### 0.2 Легенда статусов замера

| Статус | Значение |
|---|---|
| `EXISTS` | код/поле/таблица есть, путь вызова прочитан |
| `EXISTS_UNUSED` | объявлено, но ни одного живого писателя не найдено |
| `ABSENT` | искали грепом по трём репозиториям, не нашли |
| `PROSE_ONLY` | существует только как текст канона/политики |
| `STALE` | число взято из документа/докстринга, в этой сессии не переснято (§47.7 правило 2) |

### 0.3 Классификация действий (обязательна по общему брифу)

Каждое действие в разделах 4–9 помечено одним из:
`DETERMINISTIC` · `CONTROLLED_POLICY` · `AUTHORITATIVE_DOMAIN` ·
`LLM_ALLOWED` · `LLM_FORBIDDEN`.

### 0.4 Главное правило неизвестности

```
UNKNOWN ≠ 0 ≠ false ≠ "" ≠ [] ≠ «цели нет»
```

Это не абстракция: она уже стоила дефекта. `active_goals: []` («цели нет») и
отсутствие ключа («слой целей не ответил») были схлопнуты в одно, и человеку,
только что выбравшему «Позаботиться о коже лица», дашборд предложил выбрать
цель (DRF-1476, `apps/miniapp/src/lib/customer-wellness.ts:111-125`).

## 1. Discovery — что существует на самом деле

Все ссылки — `origin/dev` соответствующего репозитория, прочитано 07.09.2026.

### 1.1 Авторитетное хранилище цели

| объект | где | статус |
|---|---|---|
| `ClientGoal` | `djangoproject:goals/models.py` | `EXISTS` |
| `GoalAnketaRun`, `GoalAnketaAnswer` | там же | `EXISTS` |
| `GoalOption` (курируемые чипы) | `djangoproject:services/models.py:738` | `EXISTS` |
| `GoalOptionCategory` (цель → категории) | `djangoproject:services/models.py:775` | `EXISTS` |

**Поля `ClientGoal` целиком:** `id`, `client`, `goal_key`, `goal_text`,
`selected_at`, `source_channel ∈ {bot, miniapp}`, `is_active`, `created_at`,
`updated_at`. Больше ничего.

Инварианты, стоящие в БД:

* `clientgoal_key_or_text_present` — хотя бы одно из `goal_key` / `goal_text`;
* `clientgoal_one_active_per_client` — **ровно одна активная цель на клиента**
  (partial UniqueConstraint).

Салона на цели **нет намеренно**: колонка `tenant` заводилась (миграция `0003`)
и снята (`0005`) решением владельца 04.09 (DRF-1472). Это прямое исполнение
канона §2 «A Goal belongs to the user, not to a salon» и §12.2 «Goal MUST NOT
use salon/service/provider/slot as ownership semantics».

### 1.2 Единственный путь создания цели

`POST /api/v1/internal/me/goals/select/` (`djangoproject:goals/api.py`).
Тело — **ровно одно** из `goal_key` / `goal_text` / `intent` / `answer`
(`GoalSelectSerializer.validate`).

Каждый путь начинается с действия человека:

| действие | что происходит |
|---|---|
| нажат чип | `_create_goal(goal_key=…)` |
| введён свободный текст | `_create_goal(goal_text=…)` |
| `intent=need_guidance` | **цель не создаётся**, возвращается ведущий вопрос |
| `intent=start_anketa` | открывается проход, **активная цель не трогается** |
| `answer` на финальный шаг анкеты | `_create_goal(...)` — завершение анкеты и есть выбор |

**Ни одного пути, где цель создаёт модель, не существует.** Это проверено:
`GoalCandidate` / `goal_candidate` не встречается ни в одном из трёх
репозиториев, кроме двух строк канона и одной строки `OPEN_DECISIONS.md`.
`ayla-ai-core` (24 файла) не содержит слова `goal` вовсе — ни в инструментах,
ни в промптах, ни в памяти.

Смена цели: `_create_goal` в одной транзакции гасит прежнюю
(`is_active=False`) и создаёт новую. **Закрытые ряды и есть история**,
отдельного журнала нет (докстринг `models.py`).

### 1.3 Эфемерный документ состояния

`GET /api/v1/internal/me/decision-context/` → `build_decision_context`
(`djangoproject:goals/decision_context.py`). Документ **в БД не хранится**,
строится поверх `ClientGoal` на каждый запрос. Форма (`version: 2`):

```
version
known:        { goal: {goal_key, goal_text, selected_at, source_channel} | null }
missing:      [ {kind: goal|goal_clarification|goal_guidance|goal_anketa, prompt, …} ]
suggestions:  [ {key, label} ]        — активные GoalOption
intents:      [ {id, label} ]
next:         {id, label} | null
```

Проксируется на платформу **как есть, без трансляции**
(`ai-bot-platform:apps/integrations/ayla/goals_client.py`, таймаут 5 с,
инлайновый брейкер 5 отказов/60 с → 30 с). 4xx брейкер **не** взводит.

### 1.4 Анкета — готовый прецедент QUESTION LOOP

`djangoproject:goals/anketa.py`, два сужающих шага (`area`, `feeling`) плюс
финальный (`goal`). Механика, которую трек B **переиспользует, а не изобретает**:

* `step` — **непрозрачный токен**; экран возвращает его эхом и не толкует;
* устаревшее эхо → **409 `ANKETA_STEP_MISMATCH`**, а не запись не в ту графу;
* нет флага «последний шаг» и нет списка оставшихся — последовательность
  серверная (условие C-1);
* `progress` приходит готовым;
* отклонённый ответ **не создаёт прохода** — иначе каждый 409 оставлял бы
  человеку вечно открытую анкету (исправлено, докстринг `_answer_anketa`).

### 1.5 Экран «Моя цель» — что он читает

Экранов два, и это важно различать.

**(1) `GoalSelectScreen`** (`ai-bot-platform:apps/miniapp/src/screens/GoalSelectScreen.tsx`,
226 строк) — поверхность выбора. Читает документ состояния целиком через
`customer-goals.ts` и **является тупым отрисовщиком**: ни зашитых чипов, ни
локальной логики «что дальше», ни ветвления. Выход с экрана — только по
`next.id`, отображённому через `NEXT_ROUTES`; незнакомый `id` кнопки не даёт.

**(2) Блок «Моя цель» на домашнем экране**
(`CustomerWellnessDashboardScreen.tsx:374`) — то, что владелец разрешил §35 п.13.
Читает поле `active_goals` из `/customer/wellness/today`.

Что кладёт туда сервер — `_active_goals_from_context`
(`ai-bot-platform:apps/miniapp_api/views.py:2559`). Источник — **тот же**
`known.goal` из документа состояния, «так что дашборд и экран цели не могут
разойтись в том, есть ли цель». Заголовок берётся по лестнице:

1. `goal_text` — **собственная формулировка человека**;
2. `suggestions[].label` для его `goal_key` — ярлык едет в том же документе;
3. сам `goal_key` — слаг, «некрасиво, но фактично; выдумать заголовок было бы хуже».

`progress_pct` **отсутствует намеренно**: слой целей прогресса не хранит, и
`0` нарисовал бы 0 % под целью, над которой человек работает.
`week_num` — производная от `selected_at`, счётчик недель, а не оценка.

Три состояния поля различаются: `[{…}]` — цель есть; `[]` — цели нет;
**ключ отсутствует** — слой целей недоступен, и рисовать «Выбери цель» здесь
запрещено (DRF-1476).

### 1.6 Что цель делает дальше (границы, не предмет трека)

* `goals/resolution.py` — цель → набор `category_id` через `GoalOptionCategory`,
  с раскрытием корневых категорий вниз до листьев (DRF-1308).
  Свободный текст разрешается **только точным совпадением с `label`**;
  порога уверенности нет намеренно — калибровать не на чем (OD-2).
* `goals/wiring.py` — единственное чтение флага `GOAL_RESOLUTION_ENABLED`
  (умолчание `False`). При `None` фильтр **не применяется**, выдача прежняя:
  «невыбранная цель не влияет ни на что». Пустая полка при разрешённой цели
  **не** маскируется фолбэком — это дефект курирования и должен быть виден.

### 1.7 Пилотные факты, определяющие поведение

| факт | источник | статус |
|---|---|---|
| `ClientGoal` на пилоте = 0 | докстринг `goals/wiring.py` | `STALE` (дата замера в докстринге не указана) |
| `GOAL_RESOLUTION_ENABLED` = off на пилоте | докстринг `goals/decision_context.py` | `STALE` |
| **Завершённых визитов на пилоте — ноль** (`completed 0`, `completed_by` пусто на всех 30 + 8) | `OPEN_DECISIONS.md` §42, замер 07.09 | `EXISTS`, свеж |
| `ConsentType.HEALTH` объявлен и **не используется нигде** | `apps/consent/models.py:70`, §19 | `EXISTS_UNUSED` |
| `source_channel="bot"` не пишет **ни один** живой вызывающий | греп по `ai-bot-platform`: только `miniapp` в `customer-goals.ts` и тесты | `EXISTS_UNUSED` |

## 3. Модель данных контракта

Три объекта. Границы между ними — и есть контракт.

```
GoalCandidate          эфемерный, ядро/платформа, НЕ авторитетен
      │  (promotion boundary — раздел 6)
GoalCreateCommand      единичная команда, идемпотентная
      │
Goal (ClientGoal)      авторитетный, бэкенд Ayla, durable
```

Правило владения, повторяющее Decision 8 для памяти:

> **Извлечение из разговора никогда не становится авторитетной целью напрямую.
> Между ними всегда стоит явная политика продвижения.**

## 4. `GoalCandidate` — схема

`GoalCandidate` **эфемерен**: живёт в `SemanticConversationState` до истечения
TTL сессии (2 часа бездействия, канон Decision 1) либо до продвижения/отказа.
В авторитетную БД он не пишется. Это тот же приём, что уже применён к
`DecisionContext` — «эфемерный документ, durable-факт отдельно».

```yaml
GoalCandidate:
  candidate_id:            # uuid4, DETERMINISTIC, генерирует платформа
  subject_user_id:

  # ── 1. СЛОВА ЧЕЛОВЕКА. Пишет ТОЛЬКО ingress. См. раздел 5.
  user_wording:
    text:                  # дословно, байт-в-байт, без нормализации
    source_event_ref:      # id входящего события человека (сообщение/клик)
    captured_at:
    origin:                # закрытый allowlist: stated | explicit | click
    channel:               # max | miniapp | ...
    interaction_kind:      # free_text | option_click
    option_ref:            # {decision_id, option_id, state_revision} — только для option_click

  # ── 2. ЧТО ПОНЯЛА МОДЕЛЬ. Пишет извлекатель. Никогда не «слова человека».
  extraction:
    canonical_outcome:     # ОДИН скаляр. Не список. См. раздел 8.
    outcome_vocabulary:    # curated_goal_option | free_form
    goal_option_key:       # GoalOption.key или null
    normalized_text:       # нормализация — ЗДЕСЬ, не в user_wording
    origin: derived        # константа. Иного значения быть не может.
    extractor_version:
    prompt_version:

  # ── 3. НЕОДНОЗНАЧНОСТЬ. Материал для вопроса, НЕ для создания целей.
  ambiguity:
    kind:                  # NONE | MULTI_THEME | UNDERSPECIFIED | NOT_A_GOAL | FORBIDDEN_FRAMING
    discrimination_facets: # [] — грани для различающего вопроса. Продвинуть грань НЕЛЬЗЯ.
    facet_set_hash:        # DETERMINISTIC, входит в question_id

  # ── 4. ГОРИЗОНТ. Только когда назван человеком. См. раздел 9.
  horizon:
    kind:                  # NONE | EVENT_DATED | EVENT_UNDATED
    event_wording:         # дословный фрагмент user_wording.text
    target_date:           # ISO-дата | null
    date_origin:           # stated | click | null  — derived ЗАПРЕЩЁН
    BLOCKED_pending_owner: # см. вопрос Q-B1

  # ── 5. ЧУВСТВИТЕЛЬНОСТЬ. CONTROLLED_POLICY, не модель.
  sensitivity:
    class:                 # NEUTRAL_WELLNESS | HEALTH_SENSITIVE | FORBIDDEN
    rule_id:               # правило, вынесшее класс
    policy_version:
    required_consent:      # [] | [health]
    signals:               # что извлекла модель как СИГНАЛЫ (не решение)

  # ── 6. ОТНОШЕНИЕ К СУЩЕСТВУЮЩЕМУ. DETERMINISTIC.
  relation_to_active:
    kind:                  # NO_ACTIVE_GOAL | IDENTICAL | SIMILAR | DIFFERENT
    active_goal_id:
    dedup_key:             # см. раздел 10
    similarity_rule_id:

  # ── 7. ГОТОВНОСТЬ К ПРОДВИЖЕНИЮ. Считает валидатор, раздел 11.
  validation:
    verdict:               # PROMOTABLE | NEEDS_CONFIRMATION | NEEDS_DISCRIMINATION
                           # | BLOCKED_CONSENT | BLOCKED_SAFETY | REJECTED
    reasons: []            # [rule_id]
  lifecycle:
    created_at:
    expires_at:            # = сессионный TTL; переживать сессию кандидат не вправе
```

### 4.1 Запрещённые поля — список закрыт

Отсутствие этих полей **и есть** структурный запрет раздела 8. Их введение —
нарушение контракта, а не расширение:

```
sub_goals          children        components      parts
parent_goal_id     goal_tree       decomposition   plan_items
goals[]            candidates[]    outcomes[]
```

`GoalCandidate` **скаляр по конструкции**. Массива целей в контракте
не существует, поэтому «породить четыре цели из одной фразы» нечем.

### 4.2 Классификация действий по разделам схемы

| блок | кто пишет | класс |
|---|---|---|
| `user_wording` | ingress-слой канала | `DETERMINISTIC` |
| `extraction` | модель | `LLM_ALLOWED` (канон §21: «parse free text into candidate semantic signals») |
| `ambiguity.discrimination_facets` | модель | `LLM_ALLOWED` |
| `ambiguity.kind` | детерминированный классификатор поверх сигналов | `CONTROLLED_POLICY` |
| `horizon.target_date` | парсер даты из слов человека | `DETERMINISTIC` |
| `sensitivity.class` | политика | `CONTROLLED_POLICY` — **`LLM_FORBIDDEN`** |
| `relation_to_active` | сравнение с БД | `DETERMINISTIC` |
| `validation.verdict` | валидатор | `CONTROLLED_POLICY` |
| создание `Goal` | бэкенд Ayla | `AUTHORITATIVE_DOMAIN` — **`LLM_FORBIDDEN`** |

## 5. Инвариант EVIDENCE ORIGIN — как контракт не даёт подменить слова человека

Требование: `user_wording` обязан хранить **исходную реплику**, а не
нормализацию. Ниже — четыре механизма, каждый из которых работает без доброй
воли извлекателя.

### 5.1 Механизм 1 — раздельные поля с несовместимыми владельцами

`user_wording.text` и `extraction.normalized_text` — **разные поля разных
блоков**. Нормализация физически некуда положить внутрь `user_wording`: поля
для неё там нет. Извлекатель, желающий записать переформулировку, обязан
записать её в `extraction`, где она помечена `origin: derived` константой.

### 5.2 Механизм 2 — сверка с неизменяемым событием, а не доверие

`user_wording.text` **не принимается из вывода модели вообще**. Он копируется
слоем продвижения из журнала входящих событий по `source_event_ref`.

```
promotion_boundary:
    stored = event_store.get(candidate.user_wording.source_event_ref)
    if stored is None:                              → REJECTED (evidence_missing)
    if stored.text != candidate.user_wording.text:  → REJECTED (evidence_tampered)
    if stored.actor != subject_user_id:             → REJECTED (evidence_foreign)
```

Это **проверяемое равенство**, а не соглашение о намерениях. Переформулировка
модели не проходит сверку по построению: она не байт-в-байт.

Прецедент есть: тот же приём стоит в анкете — эхо `step` сверяется с шагом,
который сервер **вычислил заново**, и расхождение даёт 409, а не запись не в ту
графу (`goals/api.py::_answer_anketa`).

### 5.3 Механизм 3 — allowlist закрыт со стороны цитаты

Переиспользуется дословно решение `ayla-ai-core/src/ayla_ai_core/memory.py`
(P0-3, OD_C04_GROUNDED_WHY §1):

```
STATED_ORIGINS = frozenset({"stated", "explicit", "click"})
# ЛЮБОЕ другое значение, включая неизвестное, = derived
```

Обоснование берётся оттуда же и остаётся верным: словарь происхождения ведут
три репозитория, и они его уже разошлись (`stated` в библиотеке, `explicit` в
бэкенде, плюс `behavioral | conversational | transactional | inferred | erased`).
Сравнение на неравенство одному «inferred» пропускало бы все прочие выводы как
прямую речь. **Ошибка несимметрична:** пометить сказанное догадкой — неприятно;
выдать домысел за слова человека — то, чего продукт избегает намеренно.
Поэтому цитатой считается только объявленное, а незнакомое — выводом.

### 5.4 Механизм 4 — происхождение не выводится из позиции в истории

Прямое исполнение инварианта общего брифа. Утверждение, лежащее в истории
диалога, **не становится свидетельством пользователя** оттого, что оно там
лежит. Операционно:

* нет правила «последняя реплика ассистента, не оспоренная человеком,
  считается согласием»;
* `interaction_kind: option_click` требует `option_ref` с
  `{decision_id, option_id, state_revision}`, и сервер проверяет **владение
  опцией** (канон §13); клик по чужому/протухшему решению —
  `CURRENT / REVALIDATABLE / INVALID`, и `INVALID` свидетельством не является;
* молчание, повтор записи, отсутствие возражения — **не** свидетельства.

### 5.5 Что попадает в `Goal.user_wording`

| путь человека | `user_wording.text` | `interaction_kind` |
|---|---|---|
| написал свободным текстом | его текст дословно | `free_text` |
| нажал чип `GoalOption` | **ярлык чипа, который он видел** + `option_ref` | `option_click` |
| ответил на финальный шаг анкеты текстом | его текст дословно | `free_text` |
| ответил на финальный шаг чипом | ярлык варианта шага + `option_ref` | `option_click` |

Клик — свидетельство человека (канон §20 «current click» — вторая строка
приоритета), но **свидетельство о выборе из показанного**, а не авторская
формулировка. Различие хранится в `interaction_kind`, а не додумывается
потребителем.

> **Следствие, ломающее сегодняшнее поведение:** при выборе чипа сервер обязан
> сохранить и `goal_key`, и увиденный человеком ярлык. Сегодня сериализатор
> требует **ровно одно** из `goal_key` / `goal_text`, и при нажатии чипа
> `goal_text = NULL`. См. дефект P1-B1 в разделе 15.

## 6. Граница продвижения

### 6.1 Канонический запрет

Канон §12.1: «Core may extract a `GoalCandidate`, but **cannot create
authoritative Goal by itself**». §21: LLM MUST NOT «create persistent Goals
without controlled user action».

### 6.2 Как этот запрет держится конструкцией, а не намерением

1. **У модели нет инструмента записи.** В `ayla-ai-core/tools.py` пять
   определений: `show_masters`, `show_slots`, `confirm_booking`,
   `show_my_bookings`, `ask_clarification`. Инструмента `create_goal` нет и
   **добавлять его запрещено этим контрактом**. Модель не может вызвать то,
   чего в определениях инструментов не существует.
2. **У записи один вход.** Авторитетная цель создаётся единственным путём —
   `POST /internal/me/goals/select/`, требующим
   `IsBotServiceWithVerifiedClient` (Bearer сервисного токена +
   `X-External-User-ID`). Второй вход не заводить.
3. **Тело команды несёт ссылку на действие человека, а не текст модели.**
   `GoalCreateCommand` (раздел 12) обязателен к `source_event_ref`, и слой
   продвижения сверяет его по 5.2.
4. **Продвижение — не тот же процесс, что извлечение.** Извлекатель отдаёт
   кандидата и на этом заканчивается; команду строит слой продвижения.

### 6.3 Когда Ayla вправе предложить продолжение

Канон §12.1: «Usually Ayla first provides value, then offers continuity: *"I can
take this goal into account going forward"*». Если человек **сам** просит
завести цель — создание может произойти сразу через контролируемое действие.

Триггеры предложения, допустимые **на пилоте** (`CONTROLLED_POLICY`):

| id | триггер | основание |
|---|---|---|
| `T1` | человек явно просит запомнить цель / завести цель | канон §12.1, последний пункт |
| `T2` | человек открыл поверхность цели (`GoalSelectScreen`, кнопка «🎯 Выбрать цель») | существующий путь, `apps/skills/welcome/skill.py:999` |

**`T3` «после визита» на пилоте НЕ СУЩЕСТВУЕТ.** Не «отложено» — не существует:
`OPEN_DECISIONS.md` §42, завершённых визитов ноль, предикат
`apps/booking/completion.py::confirmed_by_human` вернул бы `False` во всех без
исключения случаях. Всё, что гейтится завершением визита, сегодня не
срабатывает ни для кого. Следствие §42 записано прямо: **не строить ничего, что
начинается с «после визита»**.

Иных триггеров контракт не вводит. «Ценность доставлена» вне визита в контуре
не определена — и **выдумывать её здесь запрещено**: это была бы новая
продуктовая семантика ради удобства реализации.

## 7. Что делает извлекатель — и чего не делает

### 7.1 Разрешено (`LLM_ALLOWED`)

* понять свободный текст, синонимы, разговорные формы;
* предложить **одно** `canonical_outcome`;
* предложить сопоставление с `GoalOption.key` — как **кандидата**, не как факт
  (симметрия канону §14: «LLM может предложить кандидата маппинга, но не может
  сделать его VERIFIED»);
* перечислить грани неоднозначности как материал для вопроса;
* извлечь **сигналы** чувствительности (упомянуто здоровье, вес, диагноз);
* отрисовать утверждённые серверные формулировки.

### 7.2 Запрещено (`LLM_FORBIDDEN`)

* создать или изменить `Goal`;
* решить, что цель достигнута;
* объединить похожие цели (канон §12.6 прямым текстом);
* решить класс чувствительности и достаточность согласия;
* назначить целевую дату, не названную человеком;
* переписать `user_wording`;
* инициировать повторный вопрос (`re-ask`) — общий бриф, QUESTION LOOP;
* использовать самооценку уверенности как критерий продвижения (канон §8).

### 7.3 Почему это не «попросим модель решить»

Единственное, что здесь делает модель, — **понимание естественного языка**,
прямо разрешённое каноном §21. Все решения (класс, согласие, дедупликация,
подтверждение, запись) — детерминированные либо политические, и каждое имеет
`rule_id` и `policy_version`. Ни одно из них не читает выход модели как истину:
выход модели читается как **предложение**, требующее подтверждения человеком
или проверки правилом.

## 8. Инвариант: комплексная цель не дробится

### 8.1 Формулировка

> «Хочу подготовиться к свадьбе» остаётся **одной** целью. Лицо, тело, волосы,
> ногти — возможная **декомпозиция плана**, а не автоматические дочерние цели.

### 8.2 Пять механизмов запрета

**(1) Скалярность схемы.** `extraction.canonical_outcome` — одно поле, не
массив. Полей `sub_goals`, `children`, `components`, `parent_goal_id` в
контракте нет (список закрыт в §4.1). Четыре цели физически некуда положить.

**(2) Кардинальность вызова.** `max_candidates_per_event = 1`
(`DETERMINISTIC`). Извлекатель возвращает **не более одного** кандидата на одно
событие человека. Ответ с двумя кандидатами — ошибка контракта, отвергается
целиком (`REJECTED / cardinality_violation`), а не разбирается по частям.

**(3) Многотемье — это вопрос, а не набор целей.** Увидев несколько тем,
извлекатель **обязан** поставить `ambiguity.kind = MULTI_THEME` и перечислить
темы в `discrimination_facets[]`. Грань — материал вопроса. **Продвинуть грань
нельзя технически:** `GoalCreateCommand` принимает `candidate_id`, и команды,
принимающей `facet_id`, в контракте не существует.

**(4) Единичность команды.** `GoalCreateCommand` создаёт **не более одной**
Goal. Пакетной команды нет. Две Goal, созданные в пределах одного
`decision_id` (одного акта подтверждения), — нарушение контракта:
граница подтверждения одноисходная.

**(5) Ограничение БД как последний рубеж.** `clientgoal_one_active_per_client`
физически не позволяет четырём целям быть активными одновременно. Даже при
дефекте всех четырёх механизмов выше Postgres отвергнет вторую.

### 8.3 Где тогда живёт «лицо, тело, волосы, ногти»

В **Плане** (трек D). Канон §12.6: «Goal describes the desired outcome. Plan is
one proposed path and may change without changing Goal».

Решение владельца **OD-GOAL-1 (25.08)** говорит то же самое и раньше:
`ClientGoal` остаётся **semantic framing**; конкретный измеримый результат
моделируется как **Desired Outcome**, связанный с **Personal Plan** и
**Progress Observations**. Прямая цитата последствия, записанная там же:
«Пункт 1 прежней оценки отменён. Я предлагал добавить число и срок в
`ClientGoal` — решение OD-GOAL-1 это отклоняет».

Тот же ответ дал разбор DRF-1523: если состав общей цели задаём **мы** — мы
предписываем программу привычек, нарушая политику §2.3 и §2.6; если состав
собирает **человек** — получаем N уникальных композитов без вычислимой формы.
Рабочая середина: цель **атомарна в формулировке**, система **предлагает**
присоединить крыло, состав выбирает человек.

### 8.4 Проверяемый сценарий (приёмка)

```
Вход:  «хочу подготовиться к свадьбе подруги в июне»

Верно:
  GoalCandidate ×1
  user_wording.text        = «хочу подготовиться к свадьбе подруги в июне»
  canonical_outcome        = «подготовиться к событию»   (одно)
  ambiguity.kind           = NONE
  horizon.kind             = EVENT_DATED | EVENT_UNDATED  (см. Q-B1)
  → Goal ×1

Неверно (нарушение контракта, ловится механизмами 1–5):
  Goal «уход за лицом» + Goal «тело» + Goal «волосы» + Goal «ногти»
```

Категория «🎉 К особому событию» с примером «К свадьбе подруги» уже существует
в политике как **одна** категория целей (`customer-wellness-goal-setting-ux.md`
§3.1, строка 8). Дробление противоречило бы и ей.

## 9. Горизонт и целевая дата

### 9.1 Правило

Целевая дата хранится **только когда она явно обоснована** — то есть названа
человеком и относится к событию. Иначе поля нет: `horizon.kind = NONE`.

Это ровно то, что уже спроектировано в политике:

* §4.4: «Optional target date (only for «Особый случай»)… **For other
  categories: no target date** (goals are open-ended outcomes)»;
* §10.1, ограничение БД:
  `CheckConstraint(Q(category='event_special') | Q(target_date__isnull=True),
  name='ck_target_date_only_for_event')`.

**Переиспользуем это ограничение дословно.** Оно и есть структурный запрет:
дату невозможно записать в цель, не объявив её событийной.

### 9.2 Что дата НЕ означает

Канон §12.3: «Passing a target date does not imply `ACHIEVED`». И «Ayla should
not infer achievement only from indirect evidence such as completed procedures».

Операционно: истечение `target_date` меняет **ровно ничего** в статусе.
Разрешено единственное — событийная цель с прошедшей датой может получить
`freshness = NEEDS_RECONFIRMATION` (раздел 13.3), то есть повод **спросить**,
а не повод **решить**.

Политика §5.3 разрешает «До цели N дней» **только** для событийной категории с
явной датой. Никаких «осталось N дней» у бессрочных целей.

### 9.3 Почему это `BLOCKED`

Между двумя каноническими источниками — прямое противоречие, и разрешать его
самостоятельно общий бриф запрещает. См. вопрос **Q-B1** (раздел 16).

## 10. Дедупликация, похожесть, идентичность

### 10.1 Три ключа, три задачи

| ключ | что решает | класс |
|---|---|---|
| `event_dedup_key = hash(subject_user_id, source_event_ref)` | одно событие человека → не более одного кандидата (ретрай канала не удваивает) | `DETERMINISTIC` |
| `command_idempotency_key = hash(subject_user_id, candidate_id, confirmation_id)` | повтор команды не создаёт вторую Goal | `DETERMINISTIC` |
| `goal_identity_key = (goal_key)` либо `(casefold(strip(goal_text)))` | «это та же цель, что активная?» | `DETERMINISTIC` |

`goal_identity_key` намеренно **тупой**: точное совпадение ключа либо точное
совпадение нормализованного текста. Это та же строгость, что уже стоит в
`goals/resolution.py` — там свободный текст разрешается **только** точным
совпадением с `label`, и порог уверенности не введён сознательно: калибровать
его не на чем (OD-2, корпуса формулировок нет).

### 10.2 Похожесть

`relation_to_active.kind = SIMILAR` вправе предложить модель
(`LLM_ALLOWED` — это семантическое наблюдение). Дальше:

* **слияние запрещено** — канон §12.6: «Similar Goals are not merged
  automatically by LLM»;
* похожесть **не** продвигает и **не** отклоняет кандидата;
* единственное её последствие — вопрос человеку с двумя равноправными
  исходами: «это та же цель» / «это другая цель». Ответ человека —
  свидетельство (`origin: click`), решение — его.

### 10.3 Идентичность

`IDENTICAL` (совпал `goal_identity_key`) → `validation.verdict = REJECTED`
с причиной `already_active`. Повторная запись той же цели **не создаёт нового
ряда**. Сегодня это не так: `_create_goal` гасит прежнюю и пишет новую при
любом повторе, а `_emit_goal_selected` эмитит событие («повторная запись той же
цели = новая строка»). Расхождение зафиксировано в разделе 14.

## 11. Валидация кандидата

Порядок фиксирован. Первое сработавшее правило определяет вердикт —
дальнейшие не выполняются (fail-closed).

| # | Правило | `rule_id` | Вердикт |
|---|---|---|---|
| 1 | Безопасность: состояние `STOP` или `CLARIFY` (канон §7) | `safety_gate` | `BLOCKED_SAFETY` |
| 2 | Свидетельство не сверилось с журналом событий (§5.2) | `evidence_missing` / `evidence_tampered` / `evidence_foreign` | `REJECTED` |
| 3 | Более одного кандидата на событие | `cardinality_violation` | `REJECTED` |
| 4 | `sensitivity.class = FORBIDDEN` (медицинская цель, цифровая мишень) | `forbidden_framing` | `REJECTED` + мягкая переформулировка, политика §3.3 |
| 5 | `sensitivity.class = HEALTH_SENSITIVE` и нет действующего `HEALTH` | `consent_missing` | `BLOCKED_CONSENT` |
| 6 | `relation_to_active.kind = IDENTICAL` | `already_active` | `REJECTED` |
| 7 | `ambiguity.kind = MULTI_THEME \| UNDERSPECIFIED` | `needs_discrimination` | `NEEDS_DISCRIMINATION` |
| 8 | `ambiguity.kind = NOT_A_GOAL` (привычка, услуга, мишень) | `not_a_goal` | `REJECTED` |
| 9 | иначе | — | `NEEDS_CONFIRMATION` |

**`PROMOTABLE` без подтверждения выдаётся ровно в одном случае:** триггер `T1`
(человек сам попросил завести цель) при пройденных правилах 1–8. Это прямое
чтение канона §12.1: «If the user explicitly asks to create/follow a goal,
creation may happen immediately through a controlled action».

### 11.1 Правило 8 — «это не цель»

Переиспользуется различение политики §2.3 и `SYSTEM_GOALS.md` §1: цель — исход,
а не привычка и не мишень.

| реплика | вердикт | почему |
|---|---|---|
| «регулярно ходить на массаж» | `not_a_goal` (привычка) | политика §2.3 |
| «пить 2 л воды в день» | `not_a_goal` (привычка) | политика §2.3 |
| «похудеть на 5 кг к июлю» | `forbidden_framing` | политика §2.1 + §35 п.10 |
| «хочу маникюр» | `not_a_goal` (названа услуга) | ведёт к подбору, не к цели |

Последняя строка — **не** новое решение: `_goal_is_resolved`
(`decision_context.py`) уже признаёт названную услугу готовым исходом и ведёт
человека к подбору, чтобы не уронить его обратно в уточнение (DRF-1451).
Контракт лишь называет это состояние явно.

### 11.2 Правило 4 — переформулировка вместо отказа

Политика §3.3 даёт утверждённое поведение: мягкое перенаправление
«Я не диетолог и не врач. Можем переформулировать как «{{исход}}»?».
Предложенная переформулировка — **предложение модели**, и её принятие
человеком создаёт **новое** `user_wording` с `origin: click` или `stated`.
Она не подшивается к прежнему кандидату задним числом.

## 12. Подтверждение и `GoalCreateCommand`

### 12.1 Стабильный `question_id` (инвариант QUESTION LOOP)

```
подтверждение:  goal_confirm:{candidate_id}
различение:     goal_disambiguate:{candidate_id}:{facet_set_hash}
согласие:       goal_consent:{candidate_id}:{consent_scope}
похожесть:      goal_same_or_new:{candidate_id}:{active_goal_id}
```

`question_id` — `DETERMINISTIC`, вычисляется, а не хранится. Состояние обязано
отвечать на четыре вопроса: задавался / отвечен / остаётся неотвеченным /
политика разрешает повтор.

**Повтор разрешён только по явному правилу с причиной.** Допустимые причины
закрыты списком: `state_revision_advanced` (человек изменил вход),
`consent_state_changed`, `safety_state_changed`. Модель повтор **не
инициирует**.

### 12.2 Устаревшее взаимодействие

Переиспользуется канон §13.4 и уже работающий прецедент анкеты: ответ несёт
эхо `decision_id + option_id + state_revision`; сервер сверяет с тем, что
вычислил заново, и классифицирует `CURRENT / REVALIDATABLE / INVALID`.
«Устарел» **не равно** «недействителен». Расхождение → отказ с кодом,
а не запись не в ту графу (сегодня: HTTP 409 `ANKETA_STEP_MISMATCH`).

### 12.3 `GoalCreateCommand`

```yaml
GoalCreateCommand:
  idempotency_key:        # hash(subject_user_id, candidate_id, confirmation_id)
  subject_user_id:
  candidate_id:
  confirmation:
    question_id:
    decision_id:
    option_id:
    state_revision:
    answered_at:
  goal_key:               # или null
  user_wording:           # копия проверенного блока, целиком
  horizon:                # NONE, либо событийный блок (Q-B1)
  sensitivity:
    class:
    consent_snapshot:     # [{scope, granted_at, document_version}]
  provenance:
    source_channel:       # bot | miniapp
    source_event_ref:
    extractor_version:
    prompt_version:
    policy_version:
```

Свойства (`AUTHORITATIVE_DOMAIN`):

* **идемпотентность** — канон §12.6. Повтор с тем же `idempotency_key`
  возвращает **ту же** Goal, не создаёт ряда и **не эмитит второго события
  воронки**;
* **единичность** — одна команда, не более одной Goal (раздел 8, механизм 4);
* **атомарность** — гашение прежней активной цели, создание новой и закрытие
  открытого прохода анкеты происходят в одной транзакции. Прецедент уже стоит:
  `@transaction.atomic` на `_answer_anketa`, и докстринг объясняет цену
  нарушения — «цель существовала бы при открытом проходе, и человека снова
  тянуло бы в вопросы».

### 12.4 Что произойдёт с существующим API

`POST /internal/me/goals/select/` остаётся единственным входом. Контракт
требует от него трёх изменений (перечислены как требования, не как правки —
код по общему брифу не меняется):

1. принимать `goal_key` **и** ярлык, увиденный человеком, одновременно
   (снятие XOR — дефект P1-B1);
2. принимать `idempotency_key` и вести себя идемпотентно;
3. принимать `source_event_ref` для сверки §5.2.

## 13. Авторитетная `Goal` — жизненный цикл

### 13.1 Статусы

Канон §12.3, дословно:

```
ACTIVE      PAUSED      ACHIEVED      ARCHIVED
```

Правила переходов (`CONTROLLED_POLICY`):

| переход | кто вправе | основание |
|---|---|---|
| `∅ → ACTIVE` | **только явное действие человека** | §12.1 |
| `ACTIVE ↔ PAUSED` | только человек | §12.3 + §2.6 автономия абсолютна |
| `→ ACHIEVED` | **только человек** | §12.3: вывод достижения из косвенных признаков запрещён |
| `→ ARCHIVED` | человек; либо смена цели человеком (сегодняшнее «закрытие ряда») | политика §6.2 |
| любой автоматический | **запрещён** | §12.4: статус не меняется от бездействия, другой записи, отклонённой рекомендации |

**Запрещено выводить `ACHIEVED`:** из прохождения `target_date`, из
завершённых процедур, из числа визитов, из полноты дневника. Первые два —
канон §12.3. Третье и четвёртое — политика §2.4 (`anti-OCD`) и §2.5.

При `→ ACHIEVED` — утверждённое поведение `Q-WG9`: мягкое «отлично, что
получилось», **без конфетти, серий и предложений поделиться**.

### 13.2 Причина закрытия

Политика §6.2 фиксирует три равноправные причины: «достигнута (или почти)»,
«уже не актуально», «просто убираю». Контракт требует хранить причину рядом со
статусом. Сегодня её нет — `is_active=False` без причины (G12), и цель,
которую человек считает достигнутой, неотличима от брошенной.

### 13.3 Свежесть — отдельная ось

Канон §12.3: свежесть **не статус**, а вычисляемая ось
`FRESH | NEEDS_RECONFIRMATION`.

Параметр `goal_freshness_ttl` = **`UNKNOWN`**. Канон числа не даёт, владелец
его не называл, вывести из доменной модели нельзя. По правилу
`UNKNOWN ≠ default` подставлять «90 дней» **запрещено**.

Поведение до назначения параметра — fail-closed **в сторону непонукания**:

```
goal_freshness_ttl is UNKNOWN
  → freshness = FRESH для всех целей
  → вопрос о переподтверждении НЕ ЗАДАЁТСЯ никому
```

Обоснование выбора стороны: обратный fail-closed («считать всех
`NEEDS_RECONFIRMATION`») породил бы вопрос «вы всё ещё хотите …?», а это
буквально запрещённое политикой §2.5 «вы давно не работали над целью».
Молчание безопасно, вопрос — нет.

### 13.4 Сколько целей

| источник | что говорит |
|---|---|
| канон §12.4 | «Multiple ACTIVE Goals are allowed» |
| решение владельца §35 п.13 (06.09) | «**На пилоте — одна текущая цель.** Несколько целей — после проверки реального поведения» |
| решение владельца OD-GOAL-2 (25.08) | «Снятие ограничения «одна активная цель» **до этого не выполнять**» |
| код | `clientgoal_one_active_per_client` — одна |

**Противоречия нет.** Канон описывает семантический потолок, решение владельца
— пилотный профиль. Контракт: **на пилоте ровно одна активная `ClientGoal`**,
ограничение БД остаётся. Многоместность живёт в `Desired Outcome` (OD-GOAL-4:
«схему закладывать многоместной с первого дня»), а это не трек B.

Инструкция исполнителю, которую §19 называет «легко нарушить по аналогии»:
ограничение «одна активная» относится **к `ClientGoal`**, и копировать его на
новые сущности запрещено.

## 14. Исправление и обновление

### 14.1 Что человек вправе изменить

Политика §6.1: переформулировать текст, сменить категорию, поправить дату
событийной цели. §2.6: автономия абсолютна.

### 14.2 Правило неизменности свидетельства

**`user_wording` неизменяем.** Исправление формулировки — это **новое**
свидетельство человека с собственным `source_event_ref` и `captured_at`, а не
правка старого.

Модель хранения — **лента исправлений**, а не перезапись:

```
Goal.user_wording_current   → последнее свидетельство человека
Goal.user_wording_history[] → предыдущие, каждое со своим source_event_ref
```

Причина прямая: перезапись `user_wording` уничтожает **датасет формулировок**,
ради которого поле и заводилось. `ClientGoal.goal_text` документирован как
«будущий корпус формулировок (OD-2: корпуса нет, пилот — механизм его сбора)»
и «не нормализуется». Затирать его правкой — потерять то единственное, что
пилот собирает.

Сегодня лента получается побочно и криво: смена цели закрывает ряд
(`is_active=False`) и создаёт новый, «закрытые ряды и есть история». Этого
достаточно для истории целей и **недостаточно** для истории формулировок одной
цели: правка опечатки неотличима от смены цели.

### 14.3 Исправление, отменяющее свидетельство

Канон §7.2: «Explicit user correction may retract prior signals, but provenance
of original and retraction must remain auditable». Применяется дословно: явное
«я не это имела в виду» ретрактирует прежнее свидетельство, но **обе записи
остаются** в ленте.

### 14.4 Кто исправлять не вправе

Модель — `LLM_FORBIDDEN`. Салон, мастер, оператор — не вправе вовсе (раздел 17).

## 15. Отношение к `CurrentNeed` и к активным целям

### 15.1 `CurrentNeed ≠ Goal`

Канон §2 запрещает схлопывать `CurrentNeed`, `Intent`, `Goal`, `Capability`,
`Recommendation`, `Plan`, `Booking`, `Reaction`, `Outcome`.

Операционные следствия для трека B:

1. **Текущая потребность не создаёт кандидата сама по себе.** «Хочу маникюр
   в субботу» — `CurrentNeed`, и кандидат из неё не порождается
   (правило 8, «названа услуга»).
2. **Явная текущая потребность старше активной цели.** Канон §20, приоритет:
   `явное текущее высказывание → текущий клик → доменная правда → активная
   цель → история/память`. Цель — **четвёртая**, а не первая.
3. **Расхождение потребности с целью цель не меняет.** Канон §12.4: «A current
   need that differs from an Active Goal does not modify the Goal». Ни статуса,
   ни текста, ни свежести.
4. **Отклонённая рекомендация целью не является и цель не меняет** (§12.4,
   плюс §11.2 «Recommendation reactions are not durable memory»).

### 15.2 Активная цель — право на учёт, а не разрешение писать

Канон §12.5, и то же в `OPEN_DECISIONS.md` §40.2 п.3. `ACTIVE` — вход
допустимости; проактивное сообщение всё равно требует: согласия, валидного
триггера, частотной политики, текущей релевантности, безопасности.

Граница допустимого тона зафиксирована политикой §8.3 и переиспользуется без
изменений:

```
✅ «По вашей цели „больше энергии“ — заметила, что бодрее в дни с 7.5+ часов сна»
❌ «Вы делаете прогресс по цели X»        — оценочно
❌ «Чтобы достичь цели X — спите дольше»  — предписывающе
❌ «Не забывайте про цель»                 — понукание, §2.5
❌ «Вы давно не работали над целью»        — понукание, §2.5
```

### 15.3 Как цель входит в решение

Только через **Goal Relevance Resolver** (канон §12.4): в текущее решение
входят лишь релевантные цели. На пилоте цель активна ровно одна, поэтому
резолвер вырождается в проверку релевантности одной цели — но **интерфейс
закладывается многоместным**, иначе он станет вторым местом, где «одна
активная» зашита в код.

Что цель делает в подборе — уже решено и не переоткрывается: она **сужает, но
не ранжирует** (`goals/resolution.py` + `marketplace/discovery.py`);
ранжировать носителей цели друг против друга значило бы рекомендовать.

## 16. Чувствительность, согласия, принадлежность

### 16.1 Почему цель принадлежит человеку, а не салону

Три независимых основания, каждое проверяемо:

1. **Канон.** §2: «A Goal belongs to the user, not to a salon. The current
   salon or marketplace determines which concrete offers can satisfy it now».
   §12.2: Goal MUST NOT использовать салон/услугу/мастера/слот как семантику
   владения.
2. **Решение владельца, исполненное в схеме.** DRF-1455 завёл
   `ClientGoal.tenant`; выяснилось, что цели спрашивает только клиентский
   бот-витрина, у которого салона нет нарочно. Владелец отменил (04.09,
   DRF-1472), **колонка снята миграцией `0005`**. Это не пропуск — это
   решение, доведённое до схемы.
3. **Приватность.** Политика §9.1–9.4: доступ только у клиента; текст цели
   **никогда** не уходит на сторону салона; мастер не видит целевых данных
   вовсе — он видит запись, которую человек сделал, а не цель, которая к ней
   привела; агрегаты по тенанту запрещены даже обезличенные (фаза 2);
   у основателя прямого чтения нет.

Практическое следствие: цель **переживает смену салона** и не является
свойством записи (`SYSTEM_GOALS.md` §1).

### 16.2 Классы чувствительности

| класс | что попадает | требование |
|---|---|---|
| `NEUTRAL_WELLNESS` | «расслабиться», «выглядеть ухоженной», «больше энергии» | базовое `PERSONAL_DATA` |
| `HEALTH_SENSITIVE` | самочувствие, тело, вес, состояние кожи как здоровья | **действующее `HEALTH`**, fail-closed |
| `FORBIDDEN` | диагнозы, лечение, цифровые мишени веса/размеров/калорий | отказ + переформулировка (политика §3.3) |

Классификацию выносит политика (`CONTROLLED_POLICY`), модель поставляет только
сигналы. Это точная копия архитектуры безопасности (канон §7.2: «LLM may
perform signal extraction… LLM MUST NOT decide safety policy»), и каждое
решение атрибутируется `rule_id` + `policy_version` + перечнем сигналов.

Правовое основание, а не UX-предпочтение: самочувствие — медданные, **152-ФЗ
ст. 10** (так же сформулировано в DRF-1546 §2 и в разборе DRF-1523 п.3).

### 16.3 Что происходит при отзыве согласия

Правила ниже — прямое применение **§47.3** (решение владельца 07.09, «шире
§35 п.9») к цели.

1. **Цель не удаляется.** Она принадлежит человеку; отзыв согласия — это
   отзыв разрешения **обрабатывать**, а не отказ от собственной цели.
   Удаление по требованию человека — отдельный путь (политика §9.6).
2. **Чувствительное содержимое перестаёт быть читаемым для всех
   потребителей.** Ни один потребитель (тон, подсказки, подбор, проактив) не
   получает цель класса `HEALTH_SENSITIVE` при отозванном `HEALTH`. Fail-closed.
3. **Ложное состояние «включено» запрещено.** Не серый выключатель, а
   объяснение вместо обычного включения: «Подсказки недоступны, пока согласие
   отозвано» + действие на восстановление, если UX его допускает.
4. **При повторной выдаче согласия ничего не включается автоматически.**
   Возвращается возможность включить, а не само включение.
5. **В аудите причиной блокировки остаётся `consent_revoked`.** Технический
   `opt_out` может быть **дополнительным** эффектом, но **не подменяет
   юридическое основание отзыва**.
6. **Отзыв — не повод спрашивать согласие заново.** Просить согласие ради
   вопроса, которого человек не заказывал, — то самое понукание, что запрещает
   §2.5 (сформулировано в DRF-1546 §2).

`ConsentRecord` (`apps/consent/models.py`) для этого пригоден как есть:
append-only, `withdraw()` ставит `withdrawn_at` и **не удаляет ряд**, история
сохраняется для юридического аудита. Нужного типа согласия заводить не надо —
`HEALTH` объявлен (строка 70) и сегодня не используется нигде.

### 16.4 Цель без крыла — не «цель под замком»

Разбор DRF-1523 п.3, переиспользуется дословно: общая цель у человека без
`HEALTH` — цель **без пищевого крыла**, и точка. Крыло не «закрыто замком»
(это дразнилка), оно **может быть предложено**, и предложение ведёт на честный
запрос согласия. **Ни одно пищевое содержимое без `HEALTH` не показывается
никогда** — 152-ФЗ ст. 10, не UX-вопрос.

| два кандидата на одно событие | `REJECTED / cardinality_violation` целиком | взять «лучшего» |

## 20. Согласованность с соседними контрактами (gate 3)

| граница | правило |
|---|---|
| трек A (DecisionReadiness) | `validation.verdict` трека B — **не** DecisionReadiness. Это готовность **свидетельства к записи**, а не готовность **рекомендации к выдаче**. Общее у них одно: ни то ни другое не читает самооценку модели (канон §8). Сверка происхождений — в 20.1 |
| трек C (ранжирование) | цель входит в подбор как **фильтр**, не как балл. Активная цель — четвёртая строка приоритета §20, ниже текущего высказывания и клика |
| трек D (План) | План читает Goal и **не создаёт** Goal. Декомпозиция «свадьба → лицо/тело/волосы/ногти» живёт в Плане. Смена Плана Goal не меняет (§12.6) |
| Decision 8 (память) | Goal — **отдельная авторитетная сущность**; память вправе ссылаться на неё, но **не дублировать** (§11.2). `MemoryCandidate` и `GoalCandidate` не конвертируются друг в друга |
| Decision 14 (аналитика) | `goal_selected` — evidence, не истина. `shown ≠ engaged ≠ booked ≠ completed ≠ liked`. Событие цели не доказывает ни достижения, ни пользы |
| идентификаторы | `candidate_id` (эфемерный, платформа) ≠ `goal_id` (`ClientGoal.id`, uuid4, бэкенд Ayla). Смешивать запрещено |

### 20.1 Сверка происхождений с треком A

`docs/specs/DECISION_READINESS_ENGINE_v1.0.md` вводит закрытое перечисление
`EvidenceOrigin` и разделяет `ConfirmedEvidence` / `ModelSignal` **типами, а не
значением поля**. Это строже механизма 5.3 (allowlist по значению) и с ним
совместимо. Отображение:

| трек B (`GoalCandidate`) | трек A (`EvidenceOrigin`) |
|---|---|
| `user_wording.origin = stated \| explicit`, `interaction_kind = free_text` | `USER_TEXT`, `source_ref = message_id` |
| `user_wording.origin = click`, `interaction_kind = option_click` | `USER_ACTION`, `source_ref = decision_id + option_id` |
| `extraction.*` (`origin: derived`) | `ModelSignal`, `origin = MODEL_INFERENCE` |
| созданная `Goal` как вход в чужое решение | `PROMOTED_MEMORY` |

**Расхождение, требующее совместного прохода.** Трек A задаёт для
`PROMOTED_MEMORY` ровно один `source_ref` — `memory_entry_id`. Для цели это
неверно: канон §11.2 говорит, что Goal остаётся **отдельной авторитетной
сущностью**, и память «may reference it but **not duplicate** it». Если
единственный допустимый `source_ref` — идентификатор записи памяти, цель
придётся продублировать в память, чтобы она вообще могла служить
свидетельством, — то есть сделать ровно то, что канон запрещает.

**Предложение треку A** (не правка чужого документа): расширить `source_ref`
для `PROMOTED_MEMORY` до `memory_entry_id | goal_id`, либо ввести отдельное
происхождение `ACTIVE_GOAL` с `source_ref = goal_id`. Второе точнее: у цели
свой жизненный цикл, свои статусы и своя ось свежести, и приоритет её в
канонической лестнице §20 (четвёртая строка) **отличается** от приоритета
памяти (пятая).

Смежно: вопрос 1 трека A («может ли `PROMOTED_MEMORY` закрывать безопасностный
слот») трека B не блокирует — цель не является безопасностным свидетельством
ни в одном сценарии этого контракта.

## 21. Найденные дефекты

Документируются отдельно, как требует общий бриф. Ни один не чинился.

### P1-B1 — выбор чипа уничтожает исходную формулировку человека

**Где:** `djangoproject:goals/api.py::GoalSelectSerializer.validate` +
`_create_goal`.

**Что:** сериализатор требует **ровно одно** из
`goal_key / goal_text / intent / answer`. При нажатии чипа записывается
`goal_key`, а `goal_text` остаётся `NULL`.

**Почему это дефект, а не решение:** докстринг самой модели говорит обратное —

> «Дословная формулировка пользователя. **Хранится даже при распознанном
> ключе** — это будущий датасет формулировок (OD-2).»

Модель и API противоречат друг другу; побеждает API, и датасет не собирается
для тех, кто выбрал чип.

**Последствие для канона:** §12.2 требует хранить `user_wording` у Goal.
Сегодня у целей, выбранных чипом, его нет. Обходной путь существует и уже
используется — `_active_goals_from_context` восстанавливает заголовок из
`suggestions[].label` (`views.py:2559`), — но это **восстановление ярлыка по
ключу**, а не сохранённое свидетельство: если `GoalOption` деактивируют,
человеку показывается слаг.

**Почему нашлось:** ровно тот случай, о котором предупреждает общий бриф —
докстринг говорил одно, код делал другое.

### P1-B2 — вариант анкеты «Тело и вес» приглашает запрещённую формулировку

**Где:** `djangoproject:goals/anketa.py`, шаг `area`, вариант
`("body", "Тело и вес")`.

**Что:** ярлык, который человек видит первым в анкете целей, называет **вес**.

**Против чего:** политика §2.1 — «NEVER weight targets… NEVER measurement
specific targets»; §3.3 — «Похудеть на N кг» в списке запрещённых шаблонов;
решение владельца §35 п.10 — «вес и замеры в пилоте не используются», блоки на
весе убрать.

**Последствие:** человек, подведённый ярлыком, формулирует цель весом; она
попадает в `goal_text` дословно (не нормализуется) и становится целью, которую
политика запрещает предлагать. Классификатор `FORBIDDEN` (раздел 11, правило 4)
это отловит — но правильнее не приглашать.

**Предложение (не правка):** «Тело и форма» — формулировка политики §3.1,
категория 4.

### P2-B3 — заголовок цели может выродиться в слаг

**Где:** `ai-bot-platform:apps/miniapp_api/views.py:2559`, третья ступень
лестницы заголовка.

**Что:** при деактивированном `GoalOption` человеку показывается `goal_key`
(например `self_care`).

**Оценка:** поведение осознанное и задокументированное («слаг некрасив, но
фактичен; выдумать заголовок было бы хуже») и **правильное** по приоритету
«не выдумывать». Понижено до P2 и названо здесь только потому, что исчезнет
само при исправлении P1-B1: сохранённый ярлык переживёт деактивацию опции.

## 22. Вопросы владельцу

Формат общего брифа. Один вопрос — одно решение.

### Q-B1. Целевая дата у цели: хранить в Goal или только в Desired Outcome

1. **Что не определено.** Где живёт «к свадьбе 10 июня»: полем цели или
   элементом другой сущности.

2. **Почему канон не даёт ответа — два канонических источника противоречат
   друг другу.**
   * Канон v1.1 §12.2 требует, чтобы Goal хранила «target date/time horizon
     when relevant», и это **Working Canon**, отменяющий v1.0.
   * Решение владельца **OD-GOAL-1 (25.08)** запрещает расширять `ClientGoal`:
     «`ClientGoal` / Transformation Goal остаётся **semantic framing**.
     Конкретный измеримый результат моделируется как **Desired Outcome**».
     Там же дословно: «Пункт 1 прежней оценки отменён. Я предлагал добавить
     число и срок в `ClientGoal` — решение OD-GOAL-1 это отклоняет».

   Общий бриф в такой ситуации предписывает СТОП и вопрос владельцу.

3. **Вариант A — дата в `ClientGoal`.** Два поля (`event_wording`,
   `target_date`) плюс ограничение БД «дата только у событийной цели»
   (готово в политике §10.1 как `ck_target_date_only_for_event`).

4. **Вариант B — даты в `ClientGoal` нет.** Событийная цель живёт как
   свободный текст «подготовиться к свадьбе»; дата появится вместе с
   `Desired Outcome` / `Personal Plan` (порядок OD-GOAL-2).

5. **Последствия.**
   * A: Ayla помнит дату сразу; политика §5.3 разрешает «До события N дней»
     только здесь; цена — 2 поля + миграция + ограничение; риск — прямое
     нарушение буквы OD-GOAL-1 и соблазн доливать в `ClientGoal` дальше.
   * B: OD-GOAL-1 соблюдён; событийные цели на пилоте **безадресны во
     времени** — «к свадьбе» Ayla помнит, «в июне» нет; человеку это заметно.
     Цена — 0 сейчас, вся стоимость переносится в трек D.

6. **Рекомендация — вариант B.** Три довода. (а) Решение OD-GOAL-1 принято
   владельцем и адресовано **именно этому** соблазну, слово в слово.
   (б) На пилоте это ничего не отнимает: `ClientGoal = 0`, событийных целей
   нет ни одной, а среди семи курируемых `GoalOption` событийная — одна
   («Собраться к событию»), и даты у неё нет сегодня. (в) Канон §12.2
   говорит «when relevant» — это разрешение, а не обязанность.

7. **Заблокировано до решения:** блок `horizon` в `GoalCandidate` помечен
   `BLOCKED_pending_owner`; поведение «дата прошла» (раздел 9.2) описано, но
   неисполнимо; событийная формулировка на пилоте хранится без даты.

---

### Q-B2. Разговорный путь создания цели на пилоте: включать или нет

1. **Что не определено.** Может ли цель создаваться из разговора в боте, или
   единственным входом остаётся мини-приложение.

2. **Почему канон не даёт ответа.** Канон §12.1 разрешает создание при явной
   просьбе человека, но не обязывает включать этот путь на конкретной
   поверхности. Схема к нему готова (`source_channel="bot"`), кода нет:
   писателя `bot` не существует, `ayla-ai-core` о целях не знает вовсе.
   Это развилка объёма пилота, а не семантики.

3. **Вариант A — включить.** Извлечение `GoalCandidate` из реплики
   + подтверждающий вопрос + запись с `source_channel="bot"`.

4. **Вариант B — оставить один вход.** В боте — только кнопка
   «🎯 Выбрать цель», ведущая на `GoalSelectScreen` (сегодняшнее поведение).

5. **Последствия.**
   * A: человек, сказавший «хочу привести себя в порядок к отпуску», получает
     цель там же, где сказал; цена — весь конвейер раздела 4–12 плюс новая
     поверхность подтверждения в канале; риск — первый в контуре путь, где
     цель рождается из текста, а не из клика, то есть весь вес инварианта
     EVIDENCE ORIGIN ложится на новый код.
   * B: `EXISTS_UNUSED` остаётся; человек, назвавший цель словами, слышит
     предложение открыть экран — лишний шаг; риск нулевой, но
     `SYSTEM_GOALS.md` §10 продолжает описывать несуществующее поведение
     (расхождение раздела 19 п.1).

6. **Рекомендация — вариант B на пилоте**, с двумя оговорками. (а) Пилотный
   объём и так упирается в единственный настоящий P0 — цепочку доступа
   мастера (§47.6); добавлять новый семантический путь сейчас — расширение
   scope. (б) Разговорный путь имеет смысл, когда есть что подтверждать
   ценностью, а триггер `T3` («после визита») на пилоте невозможен (§42:
   завершённых визитов ноль). Включать A предлагается тогда же, когда
   разрешится §42.

7. **Заблокировано до решения:** раздел 6.3 фиксирует только `T1`/`T2`;
   формулировка `SYSTEM_GOALS.md` §10 остаётся неточной; `source_channel="bot"`
   остаётся объявленным и неиспользуемым.
