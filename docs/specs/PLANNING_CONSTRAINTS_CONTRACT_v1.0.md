## 0. Что это за контракт и чего он не делает

Это **versioned controlled contract для планировочных ограничений**: правила,
по которым утверждение о времени, порядке, совместимости, повторении,
восстановлении или безопасности **получает или не получает право попасть в план**.

**Non-goals, зафиксированные явно.** Контракт не проектирует Plan Engine,
Goal, DecisionReadiness и ранжирование. Он отвечает на вопрос
«из чего Plan Engine можно строить и чего в природе нет».

**Отношение к части 1.** Часть 1 — карта. Часть 2 — правила движения по ней.
Часть 1 установила: из тринадцати типов ограничений один заполнен (длительность),
один частично (булев флаг скрининга), одиннадцать — `UNKNOWN`.
Контракт исходит из этого как из нормального рабочего состояния, а не аварии.

---

## 1. Центральный инвариант

> **Планировочное утверждение без provenance в план не попадает.
> Не «попадает с пометкой», не «попадает и потом уточняется» — не попадает.**

Это структурный запрет, а не рекомендация по стилю. Реализация обязана сделать
попадание утверждения без provenance **невозможным**, а не «нежелательным».
Как — §7.

Канонический источник: v1.1 §15.6 — «Time windows and sequencing claims require
controlled provenance (`rule_id`, policy/catalog version, etc.)»;
§15 итоговый инвариант — «Ayla may present only a plan for which every material
step, restriction, and timing claim has a traceable source.»

---

## 2. `PlanningAssertion` — единица, к которой всё применяется

Планировочное утверждение — **не строка текста**, а объект. Текст порождается
из объекта, никогда наоборот.

```
PlanningAssertion
├── assertion_id          стабильный идентификатор внутри PlanRevision
├── kind                  тип ограничения, см. §3
├── subject               к чему относится: capability_id | canonical_service_id
│                         | tenant_offer_id | plan_step_id | (pair of the above)
├── value                 см. §4 — либо конкретное значение, либо UNKNOWN
└── provenance            см. §5 — ОБЯЗАТЕЛЕН, отсутствие = утверждения нет
```

**Правило нуля.** Объект без `provenance` не является `PlanningAssertion`.
Не «невалидный `PlanningAssertion`» — **не является им вовсе**. Конструктор
обязан отвергать такой ввод, а не создавать объект в дефектном состоянии.

Классификация действия: **`DETERMINISTIC`**. Сборка и валидация
`PlanningAssertion` — чистая функция без участия модели.

## 3. Типы ограничений (`kind`) — закрытый перечень

Перечень **закрыт**. Рантайм не расширяет его — по прямой аналогии с v1.1 §14.4
(«Runtime must not invent new ontology entities»).

| `kind` | Смысл | Состояние данных на 07.09.2026 |
|---|---|---|
| `CAPABILITY_SEMANTICS` | что должно обеспечивать решение | `UNKNOWN` |
| `SERVICE_CAPABILITY_MAPPING` | услуга ↔ способность + статус | `UNKNOWN` |
| `DURATION` | длительность одной процедуры | **известно** (T3) |
| `EVENT_WINDOW` | срок подготовки к дате события | `UNKNOWN` |
| `MIN_INTERVAL` | не раньше чем через | `UNKNOWN` |
| `MAX_INTERVAL` | не позже чем через | `UNKNOWN` |
| `REPETITION` | повторяемость, курс, каденция | `UNKNOWN` + вывод запрещён |
| `SEQUENCE` | порядок шагов | `UNKNOWN` |
| `PRECONDITION` | что должно быть выполнено до | `UNKNOWN` |
| `COMPATIBILITY` | что сочетается | `UNKNOWN` + реестр отклонён |
| `INCOMPATIBILITY` | что не сочетается | `UNKNOWN` + реестр отклонён |
| `RECOVERY_WINDOW` | срок восстановления после | `UNKNOWN` |
| `SAFETY_CONSTRAINT` | ограничение безопасности плана | `UNKNOWN` |

Колонка «состояние данных» — **срез, а не часть контракта**. Она обновляется
замером; форма контракта от неё не зависит. Именно поэтому контракт можно
принять сегодня, когда почти всё `UNKNOWN`.

## 4. Форма `UNKNOWN` — не пустота

Главная ошибка, которую контракт обязан сделать невозможной: `UNKNOWN`,
выраженный отсутствием поля. Отсутствующее поле неотличимо от «поле забыли»,
«поле не доехало», «ограничения нет».

### 4.1 `UNKNOWN` — это значение, а не его отсутствие

```
value := Known(...) | Unknown(reason, asked_source, as_of)
```

`Unknown` несёт:

| Поле | Смысл |
|---|---|
| `reason` | почему неизвестно, из закрытого перечня §4.2 |
| `asked_source` | у какого источника спрашивали (адрес, а не «нигде») |
| `as_of` | когда спрашивали — `UNKNOWN` тоже протухает (§47.7 правило 2) |

Отсутствие поля `value` — **ошибка сборки**, а не `UNKNOWN`.

### 4.2 Закрытый перечень `reason`

| `reason` | Когда |
|---|---|
| `NO_RULE_EXISTS` | правила такого рода не заведено в источнике вообще |
| `RULE_NOT_APPLICABLE` | правила есть, но ни одно не покрывает этот subject |
| `SOURCE_UNREACHABLE` | источник существует, но не ответил |
| `SOURCE_STALE` | ответ есть, но старше допустимого возраста |
| `MAPPING_MISSING` | subject не сопоставлен, спрашивать не о чем |
| `POLICY_WITHHELD` | ответ есть, но этому потребителю не положен |

**`NO_RULE_EXISTS` и `RULE_NOT_APPLICABLE` — разные вещи, и путать их запрещено.**
Первое — «в мире нет такого правила». Второе — «правила есть, это к ним
не относится». Первое требует завести знание, второе — нет.

### 4.3 Три состояния, которые нельзя схлопывать

```
Known(запрещает)     ≠   Known(разрешает)   ≠   Unknown
«правило есть и оно      «правило есть и        «правила нет»
 запрещает»               оно разрешает»
```

Реализация обязана делать эту тройку выразимой **на уровне типа**, а не
соглашения. `bool` для этого непригоден. Двухзначное поле с `NULL` пригодно
только если `NULL` семантически определён как `Unknown` и читатель это соблюдает.

**Существующий образец, который надо повторить:**
`MasterService.resolved_requires_health_check`
(`ai-bot-platform/apps/catalog/models.py:457`) — `null=True, default=None`,
tri-state, и комментарий `:441-456` объясняет ровно эту причину.
Читатель `apps/skills/booking/skill.py:1250-1298` держит гейт закрытым на `None`.

**Существующий контрпример, который повторять запрещено:**
`CatalogService.contraindications` (`:121`) — `default=""`. Пустая строка
означает одновременно «противопоказаний нет» и «поле не заполнено».
Синхронизация его никогда не пишет (`apps/catalog/services/upserter.py:128`),
то есть **все строки находятся в неразличимом состоянии.**

### 4.4 Как `UNKNOWN` доходит до человека

`Unknown` **никогда не рендерится как отсутствие фразы**. Правило уже
сформулировано в коде и распространяется на все планировочные утверждения:

`ai-bot-platform/apps/marketplace/dto.py:77-81` —
«a missing value must render as "not told", never as an invented number».

Форма ответа человеку — **явное называние незнания плюс путь**, по образцу
`apps/skills/faq/prompts.py:242` («Если ответа не нашлось — скажи "уточню
у мастера"»). Дословный текст **не утверждается этим контрактом** — он выносится
владельцу вопросом D-2 (`PLANNING_CONSTRAINTS_INVENTORY.md` §9).

Запрещено при `Unknown`:

* молчание о факте;
* формулировка «обычно», «как правило», «в среднем», «чаще всего» —
  это выдумка с хеджированием, а не незнание;
* диапазон вместо значения («3–4 недели»), если диапазон не пришёл из источника;
* перевод в вопрос человеку, если ответ человека не является допустимым
  источником для этого `kind` (§6.3).

## 5. Provenance — обязательные четыре поля

```
provenance
├── rule_id         стабильный идентификатор правила
├── source          адрес источника (репозиторий/таблица/файл)
├── version         версия источника на момент чтения
└── applicability   к чему правило применимо
```

### 5.1 `rule_id`

Стабильный, неизменяемый, переживающий смену формулировки правила.
Контракт неизменности ID уже сформулирован в каноне для способностей —
`ayla-knowledge/00 Foundation/Ayla Domain Capability Registry.md:319` — и берётся
как образец.

Существующий рабочий пример в коде: `CrossDomainRule.rule_id`
(`djangoproject/nutrition/models.py:724`, `SlugField(unique=True)`).

**Смена `rule_id` = другое правило.** Правка текста правила без смены смысла
`rule_id` не меняет; смена смысла требует нового `rule_id`, а не редактирования
старого.

### 5.2 `source`

Не «канон» и не «каталог» — **адресуемое место**. Форма:
`<repo>:<artifact>[:<node_id>]`.

На 07.09.2026 допустимых адресов для планировочных правил **не существует**
(часть 1 §8). Перечень открывается решением владельца D-1.

### 5.3 `version`

Версия **источника**, не утверждения. Требование канона §14.6
(«Recommendation provenance should include used canonical IDs and
catalog/mapping versions») и §15.6.

Что сегодня может быть версией:

| Источник | Носитель версии | Годен? |
|---|---|---|
| `ayla-knowledge` документ | frontmatter `version` + `.knowledge/schema.yaml` `schema_version` | да, но репозитории разошлись — 1.13 против 1.14 (P1-D5) |
| `intent-registry.yaml` | `registry_version: "1.0"` | да, но статус `draft` и файл ничем не читается (P1-D6) |
| Каталог Ayla | `updated_at` строки | **нет** — это метка времени, а не версия |
| Зеркало бота | `cache_version`, `external_updated_at` | нет — это инвалидация кэша реплики |
| `apps/orchestrator/safety/*` | **отсутствует** | нет |

**Вывод: сегодня ни один источник планировочных правил не имеет годной схемы
версий.** Это фиксируется как требование к реализации D-1, а не обходится.

### 5.4 `applicability`

Область действия правила. Без неё правило про одну услугу может быть применено
ко всему каталогу.

```
applicability
├── scope          GENERAL | TENANT | MARKETPLACE   (v1.1 §15.4)
├── subject_kind   capability | canonical_service | tenant_offer | category
├── subject_ids    к каким конкретно
└── conditions     при каких условиях (может быть пустым — это Known(пусто),
                   а не Unknown)
```

`scope` берётся из канона §15.4 без изменений. **Tenant-scoped правило
не делает Goal tenant-owned** — прямое требование §15.4.

### 5.5 Что provenance НЕ является

* **Не** «модель сказала». Утверждение, порождённое моделью, не становится
  свидетельством оттого, что лежит в истории диалога — инвариант EVIDENCE ORIGIN
  общего брифа.
* **Не** «так написано в описании услуги». Свободный текст `description`
  и `aftercare_text` — контент для человека, не правило. У него нет ни `rule_id`,
  ни `applicability`.
* **Не** «пользователь так сказал». Слова человека — свидетельство о **нём**,
  не о домене. Человек может сообщить «мне делали неделю назад» (факт о нём);
  он не может установить «между процедурами нужно две недели» (правило домена).
* **Не** «так делают на рынке». `docs/catalog/MARKET_PENZA.md` — конкурентная
  разведка. Она может обосновать **задачу завести правило**, но не является
  правилом.

## 6. Классификация действий

Обязательный раздел общего брифа. Каждое действие — ровно один класс.

### 6.1 `DETERMINISTIC`

| Действие |
|---|
| Сборка `PlanningAssertion` из ответа источника |
| Проверка полноты `provenance` (§7.1) |
| Вычисление `PlanValidation` из набора утверждений (§8) |
| Резолв длительности по цепочке specialist → salon → template |
| Сравнение `as_of` с допустимым возрастом → `SOURCE_STALE` |
| Применение `SlotConfig` (шаг сетки, буфер, lead time, горизонт) |

### 6.2 `CONTROLLED_POLICY`

| Действие |
|---|
| Допустимый возраст ответа источника по каждому `kind` |
| Что делать при `Unknown` для каждого `kind`: `INCOMPLETE` или `BLOCKED` (§8.3) |
| Право потребителя видеть правило (`POLICY_WITHHELD`) |
| Судьба старых планов при смене версии правила (§9) |

### 6.3 `AUTHORITATIVE_DOMAIN`

| Действие | Кто авторитет |
|---|---|
| Значение любого планировочного правила | источник по D-1 |
| Длительность услуги | бэкенд Ayla |
| Продаваемость и доступность | бэкенд Ayla |
| Вердикт медицинского скрининга | `SpecialistService.resolved_requires_health_check` |
| Статус маппинга услуга ↔ способность | канонические знания (когда шкала будет заведена) |

### 6.4 `LLM_ALLOWED`

| Действие | Почему это допустимо |
|---|---|
| Понять, что человек спрашивает про сроки/сочетаемость/повторение | понимание естественного языка; результат — **классификация вопроса**, не ответ на него |
| Извлечь из речи факты **о человеке** («делала две недели назад») | семантическое извлечение; результат помечается происхождением `user` и не становится правилом |
| Отрисовать уже собранный `PlanningAssertion` в текст | контролируемая отрисовка; вход — объект, выход — фраза, новых фактов не появляется |
| Объяснить, **почему** шаг в плане (из готового `provenance`) | обоснованное объяснение поверх существующего свидетельства |
| Предложить **кандидата** маппинга услуга ↔ способность | прямо разрешено v1.1 §14.2; кандидат не становится `VERIFIED` |

### 6.5 `LLM_FORBIDDEN` — стена

Модель **не имеет права быть источником истины** ни для одного пункта:

```
время и тайминги планирования
окна восстановления
окна подготовки к событию
минимальные и максимальные интервалы
повторяемость, длина курса, каденция
последовательность шагов
предусловия
совместимость
несовместимость
правила безопасности
статус маппинга (VERIFIED / REVIEW_REQUIRED / UNMAPPED)
```

Это дословно перекрывает список `LLM_FORBIDDEN` общего брифа
(«правила времени в плане, совместимость, решение о безопасности, каноническое
сопоставление каталога») и v1.1 §15.2 («LLM does not invent: timing intervals;
incompatibilities; sequencing requirements; recovery windows; safety planning rules»).

**Формулировка запрета, пригодная для реализации:**

> Никакой текст, порождённый моделью, не может стать `value` объекта
> `PlanningAssertion`. Модель принимает `PlanningAssertion` на вход и производит
> текст на выход. Обратное направление отсутствует в системе — не «запрещено
> политикой», а **не реализовано как путь**.

## 7. Где стоит стена и что происходит при попытке её обойти

Часть 1 §6.3 установила: сегодня стены нет. Сформулированные ниже три рубежа —
то, что должно быть построено. Каждый самодостаточен: обход одного ловится
следующим.

### 7.1 Рубеж 1 — конструктор (структурный запрет)

`PlanningAssertion` невозможно создать без `provenance`. Не «валидатор ругается» —
**конструктор не принимает такой ввод**.

```
build_assertion(kind, subject, value, provenance) -> PlanningAssertion
    provenance отсутствует или неполон  ->  ошибка, объект не создан
    value отсутствует                    ->  ошибка (Unknown — это значение)
```

**Что происходит при обходе.** Обойти нельзя: другого пути создать
`PlanningAssertion` нет. Попытка передать строку вместо объекта не компилируется
в типизированном коде и отвергается на границе в динамическом.

Классификация: `DETERMINISTIC`.

### 7.2 Рубеж 2 — сборка плана (запрет на смешивание)

`PlanRevision` собирается **только** из `PlanningAssertion`. Свободного текста
в плане нет как поля. Любое утверждение о сроке, порядке или сочетаемости,
попавшее в план, по построению несёт `rule_id`.

**Что происходит при обходе.** Разработчик, желающий «просто дописать строчку»,
обнаруживает, что дописать некуда: у `PlanStep` нет поля произвольного текста
про ограничения. Это и есть структурный запрет — отсутствие носителя,
а не проверка носителя.

Классификация: `DETERMINISTIC`.

### 7.3 Рубеж 3 — исходящий фильтр (последняя сеть)

Рубежи 1–2 защищают **план**. Они не защищают **реплику в свободном диалоге**,
где модель может произнести срок, никогда не побывав в планировщике.
Именно это и происходит сегодня (часть 1 §6.3): фраза «между курсами нужно
3–4 недели» не попадает ни в одну из трёх категорий
`apps/orchestrator/safety/outbound.py:70-74` (`medical`, `promise`, `contact`)
и уходит человеку.

**Требование к реализации.** Исходящий фильтр получает четвёртую категорию —
условно `planning_claim` — ловящую утвердительные формы про сроки, интервалы,
курсы, последовательность и сочетаемость. Вердикт при срабатывании
и **отсутствии** соответствующего `PlanningAssertion` в контексте хода — `REVISE`.

**Почему `REVISE`, а не `BLOCK`.** `BLOCK` уничтожает ход целиком, включая
корректную часть ответа. `REVISE` уже существует в `post_check.py:53+`
и предназначен ровно для замены проблемного фрагмента.

**Границы этого рубежа, названные честно.** Регулярка по определению ловит формы,
а не смыслы: перефразированное утверждение пройдёт. Рубеж 3 — сеть, а не стена;
стена — рубежи 1–2. Ставить рубеж 3 **вместо** них было бы той же ошибкой,
против которой предостерегает `apps/orchestrator/safety/gate.py:6`: граница,
которая «rested entirely on the model choosing to obey».

Классификация: `DETERMINISTIC` (регулярка, без LLM — как весь существующий
движок безопасности).

### 7.4 Что происходит при попытке обойти — сводка

| Попытка | Где ловится | Результат |
|---|---|---|
| Собрать утверждение без `provenance` | рубеж 1 | объект не создан, ошибка сборки |
| Дописать срок в план текстом | рубеж 2 | поля не существует |
| Подставить вывод модели как `value` | рубеж 1 + §6.5 | путь не реализован |
| Произнести срок в свободном диалоге | рубеж 3 | `REVISE`, фрагмент заменяется |
| Перефразировать так, что регулярка не поймала | **не ловится** | принимается как остаточный риск; см. §7.3 |
| Впрыснуть клиническое утверждение через `voice_examples` тенанта | **не ловится** (P1-D3) | требует отдельного решения, вне трека D |

Последние две строки — честно названные дыры, а не забытые случаи.

## 8. `PlanValidation` — как незнание превращается в состояние плана

Берётся из канона v1.1 §15.6 без переименования.

```
VALID | INCOMPLETE | BLOCKED
```

### 8.1 Правило вычисления

| Условие | Результат |
|---|---|
| Все существенные утверждения `Known` | `VALID` |
| Есть `Unknown` в существенных, но нет запрещающего `Known` и нет `SAFETY_CONSTRAINT` в `Unknown` | `INCOMPLETE` |
| Есть `Known`, который запрещает | `BLOCKED` |
| `SAFETY_CONSTRAINT` = `Unknown` | `BLOCKED` (fail closed) |
| `SERVICE_CAPABILITY_MAPPING` = `Unknown` для шага, основанного на способности | `INCOMPLETE`, шаг не рекомендуется |

**`INCOMPLETE` предпочтительнее выдуманной точности** — v1.1 §15.6 дословно.
Это не деградация, а нормальный результат при сегодняшнем состоянии данных.

### 8.2 Почему безопасность идёт в `BLOCKED`, а не в `INCOMPLETE`

Асимметрия сознательная и уже реализована в коде для гейта записи:
`apps/skills/booking/skill.py:1268-1270` — «absence of evidence is not evidence
of safety for a medical check». Тот же принцип, что в решении владельца §36:
«при любом сомнении гейт закрыт».

Для всех остальных `kind` `Unknown` даёт `INCOMPLETE`: незнание интервала
делает план неполным, но не опасным.

### 8.3 «Существенное» утверждение

`CONTROLLED_POLICY`, не решение модели. Утверждение существенно, если его
значение может изменить **допустимость**, **порядок** или **обязательные
параметры исполнения** шага.

Формулировка намеренно повторяет критерий допуска вопроса из v1.1 §8
(«Next question is allowed only if its answer can change admissibility, ranking,
or required execution parameters») — чтобы в системе был **один** критерий
существенности, а не два расходящихся.

### 8.4 Отличие «правило есть и запрещает» от «правила нет» — на выходе

Это различие обязано доживать до человека, а не схлопываться в интерфейсе.

| Состояние | Что видит человек | Что записывается в план |
|---|---|---|
| `Known(запрещает)` | почему нельзя, со ссылкой на основание | `BLOCKED` + `rule_id` |
| `Known(разрешает)` | утверждение как факт | `VALID` + `rule_id` |
| `Unknown` | что именно неизвестно и что с этим делать | `INCOMPLETE` + `reason` + `asked_source` |

Схлопывание `Unknown` в «нельзя» так же неверно, как в «можно»:
первое отнимает у человека доступную услугу, второе выдаёт незнание за разрешение.
Исключение ровно одно — `SAFETY_CONSTRAINT` (§8.2), где асимметрия принята
сознательно и обоснована.

## 9. Версионирование правил и судьба старых планов

### 9.1 Что версионируется

Версионируется **источник**, а не отдельное утверждение.
`PlanningAssertion.provenance.version` — снимок версии источника **на момент
построения ревизии**.

### 9.2 Смена версии правила не переписывает существующие ревизии

`PlanRevision` **иммутабельна**. Изменение правила **никогда** не редактирует
уже существующую ревизию: старая ревизия навсегда остаётся записью о том,
что система утверждала тогда и на каком основании.

Это прямое следствие v1.1 §15.5 (durable identity + versioned `PlanRevision`)
и §10.1 (Recommendation как иммутабельный объект).

### 9.3 Что происходит с активным планом при смене версии правила

Смена версии источника делает утверждения активной ревизии **устаревшими**,
но не ложными.

```
версия источника изменилась
        ↓
активная ревизия помечается STALE_RULES (пометка, не правка содержимого)
        ↓
пересчёт: те же subject, новая версия источника
        ↓
результат сравнения                  →  действие
────────────────────────────────────────────────────────────────
утверждения совпали                  →  пометка снята, новой ревизии НЕТ
существенное утверждение изменилось  →  создаётся НОВАЯ PlanRevision
появился запрещающий Known           →  новая ревизия, статус BLOCKED
Known стал Unknown                   →  новая ревизия, статус INCOMPLETE
```

**Новая ревизия создаётся только при материальном изменении** — v1.1 §15.5
перечисляет основания: добавление/удаление/замена шага, материальное изменение
времени, изменение Goal, отказ человека от шага, изменение доступности,
влияющее на стратегию. Смена версии источника **сама по себе не является**
материальным изменением; им является **расхождение утверждений** после пересчёта.

### 9.4 `Known` стал `Unknown` — отдельный случай

Правило удалено из источника, источник недоступен, маппинг отозван. Утверждение
**не сохраняет прежнее значение по инерции**. План уходит в `INCOMPLETE`
с `reason`, соответствующим причине.

Соблазн «оставим как было, оно же работало» — та же ошибка, что дефолт вместо
`UNKNOWN`, только растянутая во времени.

### 9.5 Кто запускает пересчёт

`CONTROLLED_POLICY`. Пересчёт — **не право написать человеку**.
v1.1 §15.7: «Active Plan is not unconditional proactive messaging permission».
Смена статуса плана на `BLOCKED` из-за нового запрещающего правила порождает
**состояние**, а не сообщение; отправка подчиняется отдельным гейтам
проактивности.

### 9.6 Чего эта схема не решает

Пересчёт требует, чтобы источник **умел сообщать свою версию** и чтобы
существовал способ узнать об её изменении. Часть 1 §5.3 установила: ни один
источник планировочных правил сегодня не имеет годной схемы версий.
**До D-1 §9 этого документа неисполним** — форма зафиксирована, механизм
уведомления не существует.

## 10. Границы контракта

### 10.1 Чем `PlanningAssertion` не является

* **Не рекомендация.** Утверждение об ограничении не предлагает услугу.
* **Не Goal.** Ограничение принадлежит домену, цель — человеку (v1.1 §12).
* **Не память.** Утверждение о домене не становится durable memory про человека
  (v1.1 §11, «controlled promotion, never direct extraction»).
* **Не запись.** Наличие плана не создаёт бронь (v1.1 §15.7).

### 10.2 Коллизии имён, которые реализация обязана развести

| Имя | Занято | Чем это грозит |
|---|---|---|
| `Capability` | правами доступа — `apps/identity/services/role_resolver.py:216` `has_capability`, таблица ролей `:150-213` | доменная способность услуги, введённая под тем же именем, столкнётся с RBAC |
| `Capability` (второе) | способностями **подсистем** — `ayla-knowledge` `CAP-001…CAP-027` | это карта ответственности сервисов, **не** свойство услуги из §14 канона |
| `Plan` | `Care Plan` — `docs/SPEC_CARE_CONTRACT.md:269` (домен сопровождения) | канонический `Plan` §15 и `Care Plan` — разные сущности с разными владельцами |
| статусы маппинга | `matched_by ∈ {pair, pair+duration, manual}` — `apps/catalog/services/linking.py:68` | это происхождение **сопоставления строк**, не верификация способности |

**Требование:** реализация обязана либо переиспользовать существующее имя
с его существующим смыслом, либо взять новое. Ввод третьего смысла под старым
именем запрещён.

### 10.3 Сверка с соседним контрактом (`DECISION_READINESS_ENGINE_v1.0.md`)

На момент завершения работы в `docs/specs/` появился документ соседнего трека —
`DECISION_READINESS_ENGINE_v1.0.md`. Сверено:

| Что | Соседний контракт | Этот контракт | Согласовано? |
|---|---|---|---|
| Имя идентификатора правила | `rule_id` (`:273`, `:314`) | `provenance.rule_id` | **да**, одно имя |
| Версия политики | `policy_version` (`:262`, `:273`, `:314`, `:397`) | `provenance.version` | **да** по смыслу; см. замечание ниже |
| Состояния безопасности | `NORMAL / CLARIFY / CAUTION / STOP / UNKNOWN` (`:271`) — имена канона плюс `UNKNOWN` | ссылается на те же имена; фиксирует расхождение с кодом (`ALLOW/CLARIFY/BLOCK/HANDOFF`) | **да**, и оба документа независимо зафиксировали одно и то же расхождение |
| Правило про `null` | «`null` не должен схлопывать `UNKNOWN` и `FLEXIBLE`» (`:244-253`) | §4.1, §4.3 | **да**, один принцип |
| Правила как данные | «Таблица, загружаемая по `policy_version`. **Данные, а не код**» (`:397`) | §5.2, §5.3 | **да** |

**Одна ось, которую нельзя смешивать.** У соседнего контракта состояние слота —
`KNOWN / UNKNOWN / FLEXIBLE` (`:244-253`, из канона §16.2): это про **заполненность
ограничения пользователем**. У этого контракта `Known / Unknown` — про **наличие
правила в домене**. Разные оси: человек может не назвать город (`slot = UNKNOWN`)
при полностью известном правиле, и наоборот. Реализация обязана держать их
раздельными полями, а не одним перечислением.

**Одно замечание к соседнему документу, вынесенное как наблюдение, а не правка:**
`policy_version` там объявлен `int` на `:262` и `str | None` на `:273`.
Для `provenance.version` этого контракта тип обязан быть один. Разрешение —
за владельцем соседнего документа; трек D чужой контракт не правит.
