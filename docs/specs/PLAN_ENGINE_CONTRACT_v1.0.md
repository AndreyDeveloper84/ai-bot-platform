## 1. Назначение и границы

Plan Engine — компонент, строящий **Plan**: контролируемую валидированную
стратегию достижения Goal во времени (канон §15). Его результат на ход —
`PlanDecision`; его durable-результат — `Plan` с версионированными
`PlanRevision`.

Каноническая цепочка (канон §15, без изменений):

```text
Goal → Plan → PlanStep → Recommendation → PendingBookingIntent → Booking
```

### 1.1 Non-goals

- Создание, изменение, достижение Goal — трек B. План читает Goal и **не
  создаёт** Goal (трек B, стр. 1117).
- Правила планирования (13 `kind`) — трек D. Plan Engine **потребляет**
  `PlanningAssertion`, не производит правила.
- Готовность решения и следующий вопрос — трек A. Plan Engine экспортирует
  `execution.required_params`, не вычисляет `readiness_state`.
- Ранжирование услуг/офферов/провайдеров — трек C. Plan Engine не содержит
  ни одной стадии ранжирования.
- Прогресс цели/плана — **решение владельца «не строить»** (трек B, стр. 40;
  DRF-1523 не воскрешён). Ни поля прогресса, ни процента, ни счётчика.
- Повторяемость/курс, совместимость/несовместимость — **принятое решение
  «не делать»** (OD-CI-4, OD-CI-5, ADR-0012 N-04). Не проектировать даже
  как опцию.
- Персональная статистика — на пилоте самообман (§13.3).

### 1.2 Когда Plan уместен (канон §15.1, без расширений)

Plan строится, только когда многошаговая координация материально добавляет
ценность: многошаговый результат; цель с горизонтом; зависимые действия;
явная просьба о плане. Потребность в одной услуге остаётся простой
рекомендацией — Plan Engine обязан уметь ответить `PLAN_NOT_JUSTIFIED`
(§6.4), а не строить план из одного шага ради формы.

## 2. Решённое до этого документа — не переоткрывать

1. **Комплексная цель НЕ дробится на несколько Goal.** «Подготовиться к
   свадьбе» — одна цель; лицо/тело/волосы/ногти — декомпозиция плана, то
   есть `PlanStep`, а не дочерние цели. Трек B закрепил пятью рубежами
   (скалярность схемы, кардинальность вызова, многотемье = вопрос,
   единичность команды, ограничение БД).
2. **Целевая дата живёт не на `ClientGoal`.** Конфликт канона §12.2 и
   OD-GOAL-1 разрешён (`OPEN_DECISIONS` §54): канонический «Goal» —
   составная сущность; дата стоит на `DesiredOutcome`, горизонт — на
   `PlanOutcomeLink` (§4.6).
3. **Прогресс цели не строить.** Честного числа нет.
4. **Совместимость и повторяемость — не пробел, а отказ.** Заполнять нельзя
   без отмены OD-CI-4/OD-CI-5/ADR-0012 N-04.
5. **Порядок построения** (канон §15.3): `Goal/Outcome → Capability →
   PlanStep → CanonicalService/TenantOffer` — последнее только при
   исполнении. Не начинать план со списка услуг.
6. **`INCOMPLETE` предпочтительнее выдуманной точности** (канон §15.6).
7. Слово `REQUIRED` не используется для продуктового пожелания, если это не
   настоящая жёсткая зависимость (общий бриф; goal-care-plan §9).

## 3. Модель: три уровня объектов

Зеркало трёхзвенной модели трека B (стр. 232–247):

```text
PlanCandidate      — эфемерный, результат Plan Engine на ход; НЕ авторитетен
PlanCreateCommand  — единичная идемпотентная команда сохранения
Plan/PlanRevision  — авторитетные, durable, бэкенд Ayla
```

Правило владения: **построенный план никогда не становится авторитетным
напрямую.** Между `PlanDecision` и durable `Plan` всегда стоит явное действие
человека (канон §15.7: «Showing a Plan does not mean it is saved»).

### 3.1 Структурные инварианты (формы, не политики)

- **PE-1 ORDER.** `PlanDecision` собирается строго сверху вниз: Outcome →
  Capability → PlanStep → (CanonicalService/TenantOffer при исполнении).
  Шаг, начатый с услуги, отвергается конструктором — входом шага является
  `capability_ref`, а не `service_id`.
- **PE-2 NO FREE TEXT.** У `PlanStep` нет поля произвольного текста про
  ограничения, тайминги, совместимость, курс (рубеж 2 контракта D, стр.
  369–378). Любое планировочное утверждение — только `PlanningAssertion`.
- **PE-3 FLAT.** У `PlanStep` нет дочерних шагов, подпланов, групп.
  Декомпозиция цели — плоский набор шагов одной ревизии. Поля `sub_steps`,
  `children`, `parts`, `parent_step_id` — в списке запрещённых (§4.8).
- **PE-4 NO PROGRESS.** Ни одно поле ни одной сущности не выражает прогресс:
  запрещены `progress`, `percent`, `completed_count`, `done`, `score`.
- **PE-5 PROVENANCE OR NOTHING.** Утверждение без полного `provenance`
  не существует (правило нуля контракта D, стр. 62–64). План, шаг или
  тайминг без traceable source не попадает в выход — не «с пометкой», а
  не попадает (канон §15, итоговый инвариант).
- **PE-6 CAPABILITY-FIRST.** `PlanStep` может оставаться capability-level
  сколь угодно долго (канон §15.3). Переход к service/offer-level —
  отдельное событие (§9.3), не неявное обогащение.

## 4. Схемы

### 4.1 `PlanDecision` — выход Plan Engine на ход

Неизменяемый объект; резолвером не сохраняется (прецедент
`RecommendationDecision`, трек C, стр. 58).

```text
PlanDecision
├── decision_id              uuid4, генерирует Plan Engine
├── goal_ref                 goal_id | None          (§4.7, Q-PE-2)
├── outcome_refs[]           ссылки на DesiredOutcome (≥1)
├── horizon                  из PlanOutcomeLink-кандидата (§4.6) | NONE
├── steps[]                  PlanStep (§4.2), плоский набор
├── step_validations         step_id → PlanValidation (§6)
├── validation               сводная PlanValidation (§6.2)
├── justification            JUSTIFIED | PLAN_NOT_JUSTIFIED (§6.4)
├── constraint_assertions[]  assertion_id всех использованных PlanningAssertion
├── safety_state             NORMAL | CLARIFY | CAUTION | STOP | UNKNOWN
├── policy_versions          {plan_spec_version, constraint_policy_version,
│                             resolver_spec_version, catalog_mapping_version,
│                             safety_policy_version, reason_code_registry_version}
└── computed_at
```

- Сырых оценок, баллов, «уверенности» в выходе нет — как в треках A и C.
- `PlanDecision` не резервирует услугу, слот, цену, исполнителя — как
  `Recommendation` трека C (стр. 413–414).
- Частично конформный `PlanDecision` отбрасывается целиком
  (`CONTRACT_VIOLATION`) — прецедент §9.4.1 трека C.

### 4.2 `PlanStep` — единица стратегии

```text
PlanStep
├── step_id             стабильный внутри PlanRevision (§9.1)
├── role                CORE | OPTIONAL | ALTERNATIVE (§5)
├── outcome_ref         к какому DesiredOutcome относится
├── capability_ref      ОБЯЗАТЕЛЕН — вход шага (PE-1, PE-6)
├── level               CAPABILITY | SERVICE | OFFER (§4.3)
├── canonical_service_ref   None, пока level = CAPABILITY
├── tenant_offer_ref        None, пока level ≠ OFFER
├── assertions[]        assertion_id всех применимых PlanningAssertion
│                       (запрошены по каждому применимому kind из 13)
├── execution           None | {required_params[], entry_point: PLAN_STEP}
├── alternative_of      step_id | None  (только для role = ALTERNATIVE, §5.3)
└── provenance          {built_at_revision, policy_versions, engine_version}
```

Замечания:

- `capability_ref` — единственный обязательный семантический вход. Шаг без
  способности не существует.
- `execution.required_params[]` — экспорт треку A (терм предиката
  `execution.requires(<param>)`, трек A, стр. 425, 1239). Заполняется
  только на level = OFFER и только из подтверждённых параметров исполнения
  (AUTHORITATIVE_DOMAIN).
- Никаких полей даты/времени у шага нет. Тайминг — только через
  `assertions[]` (kind `EVENT_WINDOW`, `MIN_INTERVAL` и т.д.); при
  отсутствии утверждения тайминга в выводе нет — не «нет ограничений»,
  а отсутствие утверждения.

### 4.3 Уровни шага и переход между ними

```text
CAPABILITY  — знаем способность; услуга не выбрана; BookingIntent невозможен
SERVICE     — CanonicalService разрешён резолвером (трек C); оффер не выбран
OFFER       — TenantOffer разрешён; шаг исполним через Recommendation →
              PendingBookingIntent (канон §16.4, entry_point = PLAN_STEP)
```

Переход вниз — только через вызов резолвера трека C (§8.2) и только по
событию §9.3. Переход вверх не определён: исполненный уровень не
«откатывается», изменение стратегии — новая ревизия (§9).

### 4.4 `Plan` и `PlanRevision` — durable

```text
Plan
├── plan_id             uuid4, бэкенд Ayla
├── subject_user_id
├── goal_ref            goal_id | None (Q-PE-2)
├── status              ACTIVE | PAUSED | SUPERSEDED | ARCHIVED (§4.5)
├── created_via         confirmation (§4.9)
└── current_revision_id

PlanRevision                        — ИММУТАБЕЛЬНА (канон §15.5)
├── plan_revision_id
├── plan_id
├── revision_no           монотонный, в рамках plan_id
├── steps_snapshot[]    PlanStep целиком (снимок, не ссылки)
├── validation          PlanValidation на момент сборки
├── assertions_snapshot[]  PlanningAssertion целиком (воспроизводимость)
├── staleness           NONE | STALE_RULES (контракт D §9)
├── policy_versions
├── created_from        {decision_id | recompute_event}
└── created_at
```

- `PlanRevision` никогда не правится. Изменение — новая ревизия (§9).
- Снимки, а не ссылки: пересчёт и аудит обязаны воспроизводить ревизию без
  обращения к текущему состоянию каталога (прецедент `context_snapshot_ref`
  трека C; `DecisionEvidence` трека A).
- PII-дисциплина трека A: план не копирует транскрипт; ссылки
  (`goal_id`, `decision_id`, `assertion_id`) вместо текстов.

### 4.5 Статусы Plan

```text
ACTIVE      — текущий действующий план; не более одного ACTIVE на Goal (§4.7)
PAUSED      — приостановлен человеком или статусом Goal (канон §15.7)
SUPERSEDED  — замещён другим планом той же цели (§4.7)
ARCHIVED    — закрыт человеком или архивацией Goal
```

- Переходы `∅ → ACTIVE` и `ACTIVE ↔ PAUSED` — только явное действие
  человека; `→ SUPERSEDED` — при сохранении нового плана той же цели;
  `→ ARCHIVED` — человек или `Goal → ARCHIVED`.
- Автоматические переходы запрещены (зеркало канона §12.4): статус плана не
  меняется от бездействия, прохождения даты, отклонённой рекомендации,
  другой записи. Пересчёт `STALE_RULES` статуса не меняет (контракт D §9.5).
- Изменение статуса Goal влияет на **использование** плана (канон §15.7:
  «Goal status changes may pause or invalidate active plan usage»):
  `Goal → PAUSED` ставит план в `PAUSED`; `Goal → ARCHIVED` — в `ARCHIVED`;
  `Goal → ACHIEVED` — поведение «план больше не предлагается», статус плана
  `ARCHIVED` по подтверждению человека, не автоматически (достижение цели
  само по себе решено только человеком, трек B стр. 823–825).

### 4.6 `PlanOutcomeLink` — связка плана с результатом и горизонтом

Место жизни горизонта по решению владельца (`OPEN_DECISIONS` §54).

```text
PlanOutcomeLink
├── plan_id
├── outcome_ref         DesiredOutcome (носитель даты — НЕ этот объект)
├── horizon_kind        NONE | EVENT_DATED | EVENT_UNDATED (трек B, стр. 289–295)
└── horizon_origin      stated | click   — derived ЗАПРЕЩЁН (трек B, стр. 293)
```

- Дата здесь не хранится и не дублируется: читается из `DesiredOutcome`.
- `PlanOutcomeLink` не вычисляет окна: утверждение «за N дней до события»
  — `PlanningAssertion` kind `EVENT_WINDOW`, которого на 07.09.2026 не
  существует (инвентарь D, T4 = ABSENT). Связка с горизонтом без окон —
  честный `INCOMPLETE`, а не повод выдумать сроки.

### 4.7 Кардинальность Goal ↔ Plan

- Один Goal — не более одного `ACTIVE` Plan. Основание: канон §12.6 «Plan is
  one proposed path»; второй сохранённый план той же цели переводит прежний
  в `SUPERSEDED`. Это вывод из канона, не новое продуктовое решение;
  многоместность закладывается схемой (`goal_ref` — поле, а не
  ограничение «ровно одна цель» на клиента — ограничение пилота не
  копируется, трек B, стр. 859–875).
- Один Plan относится ровно к одному Goal (`goal_ref` скалярен). План,
  обслуживающий две цели, не существует — как и две цели из одного
  кандидата (рубежи трека B).
- План без Goal — открытый вопрос Q-PE-2 (§16.2); схема допускает
  `goal_ref = None`, чтобы вопрос не блокировал форму.

### 4.8 Запрещённые поля — список закрыт

По прецеденту трека B (стр. 322–334): `sub_steps, children, parts,
parent_step_id, progress, percent, completed_count, done, score,
confidence, next_visit_date, course, sessions_total, sessions_done,
compatible_with, incompatible_with, repeat_every, recovery_days`.
Введение любого — нарушение контракта. Основание каждого запрета: §1.1
(прогресс, курс, совместимость) и PE-3/PE-4.

### 4.9 `PlanCreateCommand` — граница сохранения

```text
PlanCreateCommand
├── idempotency_key = hash(subject_user_id, decision_id, confirmation_id)
├── subject_user_id
├── decision_id            PlanDecision, который человек видел
├── confirmation           {question_id, decision_id(quick reply), option_id,
│                           state_revision, answered_at}   (канон §13.4)
├── mode                   SAVE | FOLLOW (§10.2)
├── goal_ref               goal_id | None
└── provenance             {source_channel, policy_versions}
```

Свойства — зеркало `GoalCreateCommand` (трек B, стр. 778–788):

- **Идемпотентность:** повтор команды возвращает тот же `Plan`, не создаёт
  второй ревизии и не эмитит второго события аналитики.
- **Единичность:** одна команда — не более одного `Plan`.
- **Атомарность:** создание `Plan` + первой `PlanRevision` + гашение
  прежнего `ACTIVE` плана той же цели (→ `SUPERSEDED`) — одна транзакция.
- Команда принимает `decision_id` целиком: сохранить «часть плана» или
  «план с правками» нельзя — правки человека сначала порождают новый
  `PlanDecision` (пересборка, §9.3), затем новую команду.

## 5. Семантика CORE / OPTIONAL / ALTERNATIVE

Критерий существенности один на систему (совпадает с §8.3 контракта D и
критерием допуска вопроса канона §8): утверждение/шаг существен, если меняет
допустимость, порядок или обязательные параметры исполнения.

### 5.1 CORE

Шаг, без которого `Outcome` не достигается по курируемой декомпозиции
(источник — каноническое знание владельца: связи Outcome → Capability),
или шаг с существенным `Known`-утверждением обязательности. Присвоение
`CORE` — `CONTROLLED_POLICY` над курируемыми данными, **не вывод модели**.
Если курируемой декомпозиции нет — все шаги `OPTIONAL` по умолчанию, и это
честное состояние, а не дефект.

### 5.2 OPTIONAL

Шаг, усиливающий результат, но не обязательный для него. Умолчание при
отсутствии знания — сюда, не в `CORE` (асимметрия: ложный `CORE`
навязывает, ложный `OPTIONAL` только недопредлагает).

### 5.3 ALTERNATIVE

Шаг-замена другого шага **той же способности**: `alternative_of` указывает
на шаг с тем же `capability_ref`. Конструкция структурная, а не
выведенная: альтернативность определяется совпадением способности, а не
знанием о сочетаемости (которого нет и не будет — OD-CI-4/5). Два шага с
разными `capability_ref` не могут быть альтернативами друг другу.
Альтернативы показываются как равноправные — прецедент `tier` трека C
(стр. 328–332).

### 5.4 Чем роль НЕ является

Роль не выражает важность «вообще», не ранжирует шаги между собой (Plan
Engine не содержит ранжирования), не является порядком исполнения. Порядок —
только из `PlanningAssertion` kind `SEQUENCE`, которого нет (инвентарь D,
T8): сегодня шаги — **неупорядоченный набор**, и вывод обязан это честно
показывать (§12), а не сортировать молча.

## 6. Валидация

### 6.1 `PlanValidation` шага

Из канона §15.6 и контракта D §8 без переименования: `VALID | INCOMPLETE |
BLOCKED`. Вычисление по шагу — правило контракта D (стр. 432–438):

- все существенные утверждения `Known` → `VALID`;
- есть `Unknown` в существенных, нет запрещающего `Known`, и
  `SAFETY_CONSTRAINT` не `Unknown` → `INCOMPLETE`;
- есть запрещающий `Known` → `BLOCKED`;
- `SAFETY_CONSTRAINT = Unknown` → **`BLOCKED` (fail-closed)** — асимметрия
  сознательная: «absence of evidence is not evidence of safety»
  (`skill.py:1268-1270`; решение владельца §36);
- `SERVICE_CAPABILITY_MAPPING = Unknown` для capability-шага → `INCOMPLETE`,
  шаг не рекомендуется (контракт D §8; трек C стр. 770–787).

### 6.2 Сводная валидация плана

```text
любой CORE-шаг BLOCKED            → план BLOCKED
любой CORE-шаг INCOMPLETE         → план INCOMPLETE
BLOCKED только OPTIONAL/ALT       → план INCOMPLETE (шаг исключается из вывода)
иначе                             → VALID
```

`BLOCKED`-шаг не показывается как предложение никогда; человеку — почему
нельзя + `rule_id` (§8.4 контракта D). Пустой набор шагов после исключений
— честный «плана нет» (§12), не пустой массив без пояснения.

### 6.3 `INCOMPLETE` — первоклассный результат

На пилоте почти каждый план будет `INCOMPLETE` (11 из 13 типов ограничений
`UNKNOWN`). Документ фиксирует это как **ожидаемое поведение, а не
деградацию**: `INCOMPLETE`-план отдаётся с явным перечнем `Unknown(reason,
asked_source, as_of)` по каждому существенному пробелу. Рендер пробела —
«не сказано», никогда выдуманное число (`dto.py:77-81`, распространено на
все утверждения контрактом D, стр. 159–179). Дословный текст — D-2.

### 6.4 `PLAN_NOT_JUSTIFIED`

Если потребность сводится к одной услуге без многошаговой координации
(§1.2), Plan Engine возвращает `justification = PLAN_NOT_JUSTIFIED` и не
строит шагов. Это отказ вида «задача не моя», а не ошибка; потребность
уходит обычному пути рекомендации (трек C).

## 7. Provenance

- Материал — только `PlanningAssertion` контракта D: `kind` (закрытых 13),
  `value = Known | Unknown(reason, asked_source, as_of)`, обязательный
  `provenance {rule_id, source, version, applicability}`. Plan Engine не
  вводит ни четырнадцатого `kind`, ни иного носителя утверждений (канон
  §14.4: рантайм не изобретает сущностей онтологии).
- Каждый шаг несёт `assertions[]`; каждая ревизия — `assertions_snapshot[]`.
- Происхождение свидетельств о человеке — по трекам A/B: слова человека,
  клик, доменная правда, подтверждённая память/цель. Слова модели — не
  свидетельство; самооценка модели не используется нигде (инвариант NO
  MODEL CONFIDENCE трека A).
- `policy_versions` на `PlanDecision` и `PlanRevision` — шесть версий
  (§4.1), по образцу трека C (стр. 435–443): воспроизводимость решения по
  версиям, а не по «тогда так было настроено».

## 8. Связи

### 8.1 Goal ↔ Plan

- Plan **читает** Goal через Goal Relevance Resolver (канон §12.4): в
  текущее решение входят только релевантные цели; на пилоте это вырождается
  в проверку одной цели, интерфейс многоместен.
- Plan не создаёт, не изменяет, не закрывает Goal (трек B, стр. 1117).
- Смена плана цель не меняет; смена цели — основание новой ревизии или
  `SUPERSEDED` (канон §15.5, §12.6).
- Явная текущая потребность сильнее активной цели (канон §12.4): конфликт
  «человек просит другое» разрешается в пользу просимого, план при этом не
  правится молча — фиксируется расхождение, пересборка только по §9.3.
- Идентификаторы не смешиваются: `plan_id`, `plan_revision_id`, `goal_id`,
  `candidate_id`, `decision_id`, `recommendation_id` — шесть разных
  пространств (прецедент трека B, стр. 1120).

### 8.2 PlanStep ↔ Recommendation

- Переход шага `CAPABILITY → SERVICE/OFFER` выполняется **только** вызовом
  резолвера трека C: `RecommendationRequest` с `need.capability_refs[] =
  [step.capability_ref]`, `need.origin = GOAL` (трек C, стр. 279) и
  plan/step-ссылками в provenance.
- Результат — `RecommendationDecision` → персистентная `Recommendation` с
  `recommendation_id`; шаг хранит ссылку на неё. Шаг никогда не получает
  кандидата в обход резолвера — третий авторитет запрещён (PATHS_AUDIT:
  сегодня три расходящихся авторитета, `RecommendationDecision` не
  принадлежит никому; Plan Engine не имеет права стать четвёртым).
- WHY шага — только `reason_codes + evidence` резолвера (S2/S3 на пилоте;
  S5 пусто по решению владельца). Plan Engine не добавляет своих причин и
  не переформулирует силу свидетельства (LLM_FORBIDDEN трека C, стр.
  542–546).
- Шаг на уровне `CAPABILITY` рекомендации не имеет и не нуждается в ней.
- `recommendation_eligible ≠ catalog_visible` (канон §14.3): неразрешённый
  шаг остаётся capability-level, человеку доступен прямой выбор из
  каталога — это не рекомендация и не порождает `Recommendation`.

### 8.3 PlanStep ↔ BookingIntent

- Цепочка единственная (канон §15): `PlanStep (OFFER) → Recommendation →
  PendingBookingIntent → Booking`. Шаг не создаёт `PendingBookingIntent`
  напрямую.
- Handoff от плана несёт `entry_point = PLAN_STEP`, provenance `PLAN` и
  plan/step-ссылки (канон §16.4); `recommendation_id` присутствует только
  при реальной цепочке (§16.4).
- Транзакционная правда перепроверяется перед записью всегда (канон §16.8):
  план не резервирует цену/слот/исполнителя; `MATERIAL_CHANGE` не
  применяется молча; явно запрошенное не подменяется.
- Исполнение шага (факт записи) не меняет ни статус плана, ни статус цели
  автоматически (§4.5); «после визита»-триггеров не существует (§13.2).

### 8.4 Экспорт треку A

- `execution.required_params[]` с OFFER-шага — вход предиката
  `execution.requires(<param>)` (трек A, стр. 425, 1239).
- Plan Engine потребляет `safety.forbidden_capabilities[]` (трек A, стр.
  275): способность из списка не становится шагом — отсек конструктором,
  а не фильтром вывода.
- Оси не смешиваются (сверка трека D §10.3): состояние ограничения
  **пользователя** (`KNOWN/UNKNOWN/FLEXIBLE`, канон §16.2) и наличие
  **правила домена** (`Known/Unknown` контракта D) — раздельные поля на
  шаге; обе оси могут быть независимо пусты.

## 9. Ревизии и перепланирование

### 9.1 Идентичность

`Plan` имеет durable identity; `PlanRevision` иммутабельна; `step_id`
стабилен внутри ревизии и не переиспользуется в следующей (удалённый шаг
не воскресает с тем же id — иначе невозможен аудит «что именно отклонил
человек»).

### 9.2 Основания новой ревизии (канон §15.5, исчерпывающе)

1. добавление/удаление/замена шага;
2. существенное изменение тайминга (только через новое `PlanningAssertion`
   после D-1);
3. изменение Goal (смена формулировки человеком; не автособытия);
4. отклонение шага человеком (явное, через `SemanticOption`);
5. стратегически значимое изменение доступности (level OFFER: оффер
   снят/недоступен — по данным AUTHORITATIVE_DOMAIN);
6. пересчёт `STALE_RULES`, изменивший существенное утверждение (контракт D
   §9; `Known → Unknown` — тоже новая ревизия, значение по инерции не
   сохраняется).

### 9.3 Триггеры перепланирования — честный список на пилоте

| Триггер | Существует сегодня? | Действие |
|---|---|---|
| Явное действие человека (правка, отклонение шага, «собери иначе») | да | пересборка → новый `PlanDecision` |
| Смена статуса Goal | да (только вручную, трек B) | §4.5 |
| `STALE_RULES` (смена версии правил) | **нет — после D-1** | пересчёт контракта D §9 |
| Снятие оффера/недоступность (OFFER-шаги) | частично (данные бэкенда есть, подписки нет) | новая ревизия, §9.2.5 |
| Изменение safety_state | да (движок `apps/orchestrator/safety/*`) | `BLOCKED` fail-closed |
| «После визита» | **нет, класс отсутствует** (0 завершённых, трек B стр. 476–481) | не проектировать |
| Прохождение target_date | событие есть, права нет | **НЕ триггер** (канон §12.3) |
| Отклонённая рекомендация | есть | **НЕ триггер** (канон §12.4; не меняет ни цель, ни план) |
| Бездействие | — | **НЕ триггер** (§4.5) |

### 9.4 Пересборка

Пересборка — `CONTROLLED_POLICY`: тот же набор subject, те же версии
политик либо явно новые; результат — новый `PlanDecision`, durable-изменение
только через `PlanCreateCommand` или пересчёт `STALE_RULES`. Пересчёт не
даёт права написать человеку (канон §15.7; контракт D §9.5).

## 10. Граница хранения; «сохранить / следовать»; проактив

### 10.1 Где что живёт

- `PlanDecision` — не сохраняется резолвером; аудит-след — по дисциплине
  `DecisionEvidence` трека A (AUTHORITATIVE_DOMAIN, PII только ссылками).
- `PlanCandidate`-состояние — в `SemanticConversationState`, TTL сессии
  (2 часа, канон Decision 1); переживать сессию не вправе — как
  `GoalCandidate` (трек B, стр. 253–256).
- `Plan`/`PlanRevision` — бэкенд Ayla (канон §15.7: «durable
  Plan/PlanRevision/lifecycle → Ayla backend»).
- Композиция и семантическая валидация — `ayla-ai-core` (канон §15.7).
  Пилотная поправка: место резолвера трека C — модуль внутри бэкенда за
  границей §9.4 (решение §53); Plan Engine следует тому же решению о месте,
  не заводя второго шаблона размещения.
- Представление — `ai-bot-platform`, только доставка (DETERMINISTIC).

### 10.2 SAVE и FOLLOW — два разных действия

- **SAVE** («Сохранить план»): durable `Plan` + первая `PlanRevision`.
  Никаких последствий для будущих решений, кроме существования объекта.
- **FOLLOW** («Следовать плану»): SAVE + план становится входом
  допустимости для будущих решений (контекст подбора, напоминание о
  существовании при релевантном разговоре).
- Оба — только явные действия человека через подтверждение §4.9. LLM не
  сохраняет и не активирует план сам — как не создаёт Goal (трек B,
  LLM_FORBIDDEN, стр. 502–511).
- Ни SAVE, ни FOLLOW **не создают**: бронь (канон §15.7), разрешение на
  проактив (канон §15.7, §12.5), durable-память (отклонение шага — не
  память, канон §15.7), изменение Goal.

### 10.3 Граница проактивных сообщений

`ACTIVE` план — «право на учёт, а не разрешение писать» (зеркало трека B,
стр. 944–948). Проактив требует независимо: согласия, валидного триггера,
частотной политики, текущей релевантности, безопасности (канон §12.5).
Триггеров проактива от плана на пилоте **не существует**: единственные
планировочные кандидаты («пора к следующему шагу») требуют окон и
интервалов, которые `UNKNOWN`, и триггера «после визита», которого нет.
Документ не проектирует проактив плана даже опционально до D-1 и матрицы
безопасности.

параметра, принимающего свободный текст модели.

## 13. Реальность контура, которую документ учитывает

### 13.1 Пилотные нули

- 0 завершённых визитов (30 зеркал: 17 отменено, 10 подтверждено, 3 ждут
  оплаты) — «после визита» не срабатывает ни для кого; триггер T3 не
  существует.
- `contraindications` пуст на всех 265 услугах; синхронизация поле никогда
  не пишет (`upserter.py:128`) — «нет противопоказаний» неотличимо от
  «не знаем».
- Связи услуг с шаблонами — **206 из 265 (78 %)**; машина подтверждения
  человеком (`DraftSalonService`) отработала на 58 записях (замер §61 от
  07.09, отменяет «0 из 58» от 23.08 — STALE, другая выборка). Чего нет —
  **шкалы** `VERIFIED/REVIEW_REQUIRED/UNMAPPED`: связь есть, признака
  доверия к ней нет. Это **поле, а не работа**.
- `ClientGoal = 0`; `GoalCandidate` нет ни в одном репозитории;
  `ayla-ai-core` не содержит слова `goal`.
- Durable-память — **одна запись `MemoryEntry` на весь пилот** (замер §61 от
  07.09; 26 людей, 13 связанных с Ayla). Любой механизм, читающий память,
  на пилоте неотличим от выключенного.

Следствие: на пилоте у Plan Engine **нет входа** (Q-PE-2), нет правил (D-1),
нет шкалы доверия к маппингу (§6.1), нет триггеров исполнения (§9.3), нет
памяти для персонализации (§13.3). При этом стадия смыслового соответствия
**имеет на что опереться** — 78 % каталога размечено, остаток конечен и
назван числом: 59 услуг. Документ это не «чинит» — он спроектирован так,
чтобы каждый из этих нулей давал честный `INCOMPLETE`/`BLOCKED`/«входа
нет», а не выдумку.

### 13.2 Что работает уже сегодня (переиспользуется)

- Детерминированный safety-движок реплики (`apps/orchestrator/safety/*`,
  регулярки без LLM) — вход `safety_state`.
- Tri-state fail-closed: `MasterService.resolved_requires_health_check`
  (`models.py:457`) + читатель `skill.py:1250-1298` — эталон.
- Резолв с честным `None`: `resolved_duration()`
  (`djangoproject-catalog/services/models.py:466`) — единственный
  заполненный `kind` (DURATION). Пять точек молчаливого `NULL → 60`
  (дефект P1-D2) план обязан обходить: длительность только через резолв.
- Курируемые знания владельца: 7 целей → ~20 категорий

### 13.3 Пороги осмысленности — сказано прямо

При 31 мастере / 265 услугах / 13 людях статистическая персонализация плана
— самообман (GAP_RESEARCH, стр. 582–590): рейтинг как свидетельство — от

курируемое знание владельца и слова человека в этом разговоре.

## 14. Коллизии имён — разведены явно

- **`Capability`**: RBAC-право в `ai-bot-platform` (97 вхождений,
  `role_resolver.py`) ≠ доменная способность услуг (этот документ, канон
  §14) ≠ способность подсистем `CAP-001…CAP-027` (реестр ayla-knowledge —
  про подсистемы, не про услуги). В коде Plan Engine имя —
  `ServiceCapability` или `DomainCapability`, третий смысл под старым
  именем запрещён (инвентарь D §10.2).
- **`Plan`**: этот документ (канон §15) ≠ `Care Plan` из
  `SPEC_CARE_CONTRACT.md:269`. Пересечений схем нет; ссылаться по полному
  имени.
- **`goal`**: `goals.ClientGoal` ≠ `nutrition.NutritionProfile.goal` —
  не связаны ничем (GAP_RESEARCH, стр. 640–643); Plan Engine знает только
  первое.
- **`decision_id`**: у треков A, C и этого документа — три пространства;
  полные имена в ссылках.

## 16. Вопросы владельцу

D-1, D-2, матрица сигналов безопасности, §6.1 (VERIFIED при нуле) — **не
дублируются**: стоят, блокируют gate 5 (§17), здесь только наследуются.

### 16.1 Q-PE-1. Показ `INCOMPLETE`-плана человеку

1. **Что не определено.** Что видит человек, когда план собран, но существенные
   утверждения `Unknown` (на пилоте — почти всегда): весь план с честными
   прорехами или только ближайший исполнимый шаг.
2. **Почему канон не даёт ответа.** §15.6 требует «INCOMPLETE предпочтительнее
   выдуманной точности» и §15 — «план stays incomplete», но ни §15, ни §9.3
   не говорят, как incomplete-план **предъявляется**: оба варианта канону не
   противоречат.
3. **Вариант A.** Показывать весь план: шаги + явный перечень «чего мы не
   знаем» по каждому пробелу (`Unknown(reason, asked_source)`), рендер
   «не сказано» вместо чисел.
4. **Вариант B.** Показывать только ближайший исполнимый шаг; остальное
   раскрывать по мере появления данных. План как видимая структура не
   предъявляется, пока не `VALID`.
5. **Последствия.** A: человек видит стратегию и ценность многошаговости, но
   и масштаб незнания; риск ощущения «план из заглушек» на пустых данных.
   B: чище экран, но на пилоте почти всегда означает «плана нет» — продукт
   теряет главную демонстрацию ценности Goal→Plan; многошаговость не
   продаётся.
6. **Рекомендация — A.** Стоимость ошибки асимметрична: скрытый план
   невозможно оценить и отклонить (отклонение шага — законный триггер §9.2.4,
   ему нужна видимость шага); честные прорехи уже спроектированы как
   первоклассный вывод (§6.3), прятать их — платить сложностью за иллюзию
   полноты.
7. **Заблокировано до решения:** поведение поверхности при `INCOMPLETE`
   (тексты — по D-2 отдельно). НЕ блокировано: схемы, валидация, ревизии,
   связи — весь остальной документ.

### 16.2 Q-PE-2. Существует ли план без активной Goal

1. **Что не определено.** Может ли Plan Engine строить (эфемерный) план из
   `CurrentNeed`/явной просьбы при отсутствии активной Goal — и может ли
   такой план быть сохранён.
2. **Почему канон не даёт ответа.** Цепочка §15 начинается с Goal; но §15.1
   называет достаточным «explicit request for a plan» без требования
   durable-цели. Обе трактовки канону не противоречат.
3. **Вариант A.** План строится только от активной Goal. Следствие на пилоте:
   `ClientGoal = 0` → у Plan Engine нет входа вообще, механизм не срабатывает
   ни разу до появления целей (Q-B2 держит и разговорный путь их создания).
4. **Вариант B.** Эфемерный `PlanDecision` допускается от явной просьбы или
   многошаговой потребности (`goal_ref = None`); durable `Plan` — только
   привязанным к Goal (сохранение плана без цели предлагает сначала
   оформить цель — через границу трека B, не мимо неё).
5. **Последствия.** A: чистая онтология, ноль риска «планов-сирот»; цена —
   фича мертва на пилоте и недемонстрируема. B: живой путь «попробуй план»
   и естественная воронка в создание цели; риск — люди копят эфемерные
   планы без целей, размывая смысл Goal; гасится TTL сессии и запретом
   durable без цели.
6. **Рекомендация — B.** Сессионный TTL уже делает эфемерный план дешёвым и
   самоочищающимся; durable-граница сохраняет онтологию (§15.7); иначе
   вся цепочка Goal→Plan не проверяема на пилоте в принципе, а «построить
   машинерию, которой нет входа» — повтор ошибки S4 (GAP_RESEARCH, стр.
   664–672).
7. **Заблокировано до решения:** допустимость `goal_ref = None` в проде
   (схема уже допускает — вопрос не блокирует форму); сценарий «сохранить
   план без цели». НЕ блокировано: всё остальное.
