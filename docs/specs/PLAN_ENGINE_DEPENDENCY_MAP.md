# Plan Engine — карта зависимостей (шаг 1 по HANDOFF_PLAN_ENGINE)

Составлено 07.09.2026 по первому шагу `docs/HANDOFF_PLAN_ENGINE.md`.
Это **не** контракт Plan Engine. Это карта: что реализуемо на сегодняшних
данных, что упирается в `UNKNOWN`, что упирается в нерешённое владельцем.
Прочитаны целиком: трек A (1317 стр.), трек B (1351 стр.), трек C — контракт
(1140 стр.) + план границы (379 стр.), трек D — инвентарь (1061 стр.) +
контракт (632 стр.), GAP_RESEARCH (1097 стр.), PATHS_AUDIT (643 стр.),
`goal-care-plan.md` (905 стр.), `BRIEF_TRACKS_COMMON.md`.

## 1. Что Plan Engine обязан определить (рамка, не перечитывать промпт)

Из `goal-care-plan.md` §9 (стр. 570–586) и хендофа: `PlanDecision` и
`PlanStep` — схемы; `CORE / OPTIONAL / ALTERNATIVE`; валидация; неполные и
заблокированные планы; `PlanRevision`; триггеры перепланирования; provenance;
`Goal ↔ Plan`; `PlanStep ↔ Recommendation`; `PlanStep ↔ BookingIntent`;
граница хранения; «сохранить / следовать»; граница проактивных сообщений.
Классификация каждого действия: `DETERMINISTIC / CONTROLLED_POLICY /
AUTHORITATIVE_DOMAIN / LLM_ALLOWED / LLM_FORBIDDEN`.

## 3. Упирается в UNKNOWN (данные — честная карта отказов)

Из инвентаря D: **заполнен 1 тип из 13 (DURATION), частично 1
(SAFETY_CONSTRAINT булев флаг), одиннадцать — UNKNOWN.**

- **`SERVICE_CAPABILITY_MAPPING` — ABSENT.** Шкалы `VERIFIED /
  REVIEW_REQUIRED / UNMAPPED` не существует нигде; VERIFIED-маппинга — ноль.
  Следствие для плана: шаг на уровне способности не рекомендуется, пока
  маппинг Unknown (контракт D §8) — это `INCOMPLETE`, не дефект.
- **`EVENT_WINDOW`, `MIN_INTERVAL`, `MAX_INTERVAL`, `SEQUENCE`,
  `PRECONDITION`, `RECOVERY_WINDOW` — ABSENT.** Окон подготовки к событию не
  существует (таблица в Killer PRD — окна атрибуции маркетинга, не сроки).
  `aftercare_text` — свободный текст, не срок; читается только пушами;
  дефолт пустой строки схлопывает UNKNOWN.
- **`REPETITION`, `COMPATIBILITY`, `INCOMPATIBILITY` — не пробел, а решение
  «не делать»** (OD-CI-4 / OD-CI-5; ADR-0012 N-04 запрещает курс из вывода
  модели). План не имеет права утверждать ни сочетаемость, ни курс. Заполнять
  — только после отмены прежних решений владельцем.
- **`DURATION` — единственный заполненный, но:** канонический каталог знает
  0 из 1223 длительностей; пять точек кода молча превращают NULL в 60 минут
  (дефект P1-D2, `bookings/tasks.py:428-432` — комментарий буквально
  «NULL means "unknown, assume 60"»). План обязан брать длительность только
  через `resolved_duration()` и честный `None`.
- **Всё, что начинается «после визита», не срабатывает ни для кого:** ноль
  завершённых визитов (30 зеркал: 17 отменено, 10 подтверждено, 3 ждут
  оплаты). Триггер T3 не существует (трек B стр. 476–481).
- **`contraindications` пуст на всех 265 услугах, синхронизация поле никогда
  не пишет** (`upserter.py:128`): «противопоказаний нет» неотличимо от
  «не знаем». Безопасность **плана** сегодня — UNKNOWN.
- **Прогресс цели не строить** — решение владельца, честного числа нет.
- **Персонализация — сказать прямо, с какого объёма она что-то значит**
  (GAP_RESEARCH стр. 582–590): рейтинг — ≈10 отзывов на мастера (на контур
  150–310, есть 0); «был у этого мастера» — ≥2 завершённых визита пары
  (есть 0); «люди как вы» — порядок 10⁴ взаимодействий (покрытие 0,9 %).
  При 31 мастере / 265 услугах / 13 людях любая статистическая
  персонализация плана — самообман. Работают ровно два источника:
  курируемое знание владельца и слова человека в этом разговоре.

Проектное следствие: **на пилоте почти каждый план будет `INCOMPLETE`, а при
затронутой безопасности — `BLOCKED`. Это ожидаемое поведение, не деградация.**
Документ Plan Engine обязан спроектировать честный `INCOMPLETE`-план как
первоклассный результат, а не как ошибку.

## 4. Упирается в нерешённое владельцем (уже стоит — не дублировать)

1. **D-1 — владелец и носитель планировочных правил.** Канон §15.7 назначает
   `ayla-knowledge`, у назначенного владельца нет носителя и пути в рантайм.
   Без ответа неисполнимы §5.2 и §9 контракта D → у Plan Engine нет источника
   правил → **ни одного `PlanningAssertion` с полным provenance не построить**
   → gate 5 не пройден, документ Plan Engine останется `DRAFT`. Рекомендация
   трека D: носитель — бэкенд (образец `CrossDomainRule`), строка несёт
   `source`/`source_version` на документ в ayla-knowledge.
2. **D-2 — дословный текст ответа на планировочный вопрос без данных.**
   Рекомендация трека D: честный отказ по умолчанию, передача салону при
   поднятом гейте здоровья.
3. **Матрица сигналов безопасности** (`OPEN_DECISIONS` §40.4 п.3): канон
   требует четыре состояния, матрицы нет → `SAFETY_CONSTRAINT` для плана
   в основном UNKNOWN → `BLOCKED` fail-closed.
4. **§6.1 / §40.4 п.1 — рекомендации при нулевом VERIFIED.** Удешевлено
   дважды: размечать подкатегории (десятки решений), не 265 услуг; замер
   §61 (07.09) назвал остаток числом — **59 услуг из 265** (78 % уже
   сопоставлены шаблонам). Чего нет — шкалы доверия
   `VERIFIED/REVIEW_REQUIRED/UNMAPPED`: поле, а не работа. Вопрос
   удешевлен, но **не решён** — он про правило, не про объём.
5. Сопутствующее, влияющее на Plan Engine: `tau_separation` / `N_broad`
   (DRF-1519, трек A); `goal_freshness_ttl = UNKNOWN` (fail-closed в сторону
   непонукания — все цели FRESH); Q-B2 — разговорный путь создания цели на
   пилоте (рекомендация B: пока только мини-приложение).

## 5. Что Plan Engine должен решить сам (свой scope, не выносить без нужды)

- Схемы `PlanDecision` / `PlanStep`; семантика `CORE / OPTIONAL / ALTERNATIVE`
  (кандидат на вывод из канона: существенность из контракта D §8.3 — «меняет
  допустимость, порядок или обязательные параметры исполнения»).
- **Триггеры перепланирования.** Честный список на пилоте короткий: явное
  действие человека; `STALE_RULES` (после D-1); смена существенного
  ограничения; отклонённая рекомендация — НЕ триггер (трек B: не меняет ни
  цель, ни план автоматически). «После визита» — отсутствует как класс.
- **Граница проактивных сообщений:** канон §15.7 — «Active Plan is not
  unconditional proactive messaging permission»; `ACTIVE` цель — «право на
  учёт, а не разрешение писать» (трек B стр. 944–948).
- **«Сохранить / следовать»:** по аналогии с продвижением Goal — создание
  авторитетного плана только через явное действие человека; LLM-план —
  кандидат, эфемерный, как `GoalCandidate`.
- **`PlanStep ↔ BookingIntent`:** через `Recommendation` (атрибуционная
  цепочка трека C); шаг на уровне способности BookingIntent не порождает.
- **Граница хранения:** план-кандидат эфемерен (сессионный TTL), авторитетный
  план — бэкенд Ayla; идентификаторы `plan_id / plan_revision_id` не
  смешивать с `recommendation_id` и `goal_id`.
- **Коллизии имён, развести в документе** (инвентарь D §10.2): `Capability`
  (RBAC в ai-bot-platform ≠ доменная способность ≠ CAP-* подсистем);
  `Plan` (канон §15 ≠ Care Plan из SPEC_CARE_CONTRACT).

## 6. Кандидаты в вопросы владельцу от этого трека

D-1, D-2, матрица, §6.1 — **не дублируем**. Предварительно (проверить при
написании документа, что это настоящие развилки, а не выводимое из канона):

- **Q-PE-1. Показ `INCOMPLETE`-плана человеку.** Вариант A: показывать план
  с честными прорехами («этого мы не знаем — вот что сказать мастеру»).
  Вариант B: не показывать план, пока он не `VALID`, при неполноте — только
  ближайший шаг. Асимметрия: A создаёт ощущение плана на пустых данных,
  B на пилоте почти всегда означает «плана нет».
- **Q-PE-2. Существует ли план без цели.** Вариант A: план строится только
  от активной Goal (на пилоте ClientGoal = 0 → планов нет вообще).
  Вариант B: допускается разовый «путь к событию» из CurrentNeed без
  сохранения. Влияет на то, есть ли у Plan Engine вообще вход на пилоте.

## 8. Явный итог для главного окна

- **Зависимость подтверждена и усилена: C → потом D.** Контракт C нормативен;
  WHY шага рождается только в S2/S3; S5 пусто по решению владельца.
- **Реализуема форма, не содержимое.** Все схемы, валидация, provenance,
  связи и жизненный цикл спроектировать можно уже сейчас — на готовых
  входах из раздела 2.
- **Содержательно план на пилоте почти всегда `INCOMPLETE`/`BLOCKED`** —
  11 из 13 типов ограничений UNKNOWN, и это проектируется как честное
  поведение, а не как недостаток.
- **Gate 5 упрётся в D-1** — как и у трека D. Это не обходится изнутри
  трека: без владельца и носителя правил ни одно утверждение плана не имеет
  допустимого `source`.
