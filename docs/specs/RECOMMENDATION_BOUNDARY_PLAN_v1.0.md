## 1. Где проходит граница

### 1.1 Граница — не сетевой хоп

Соблазн прочитать «границу» как эндпоинт. Так нельзя: два из трёх авторитетов
(B и C) живут **в одном процессе** с будущим резолвером (аудит §5.2), и
граница, состоящая из HTTP, для них не существует вовсе. Она была бы границей
для одного бота и декорацией для двоих — то самое «выглядит как решение».

> **Граница — это типизированный контракт `RecommendationRequest →
> RecommendationDecision` и единственная публичная точка входа, одинаково
> обязательная для внутрипроцессного и межпроцессного потребителя.
> HTTP — одна из двух проекций этой границы, а не сама граница.**

### 1.2 Топология

```
   бот (BOT_CHAT)          Mini App home            LLM-контекст
   ai-bot-platform         ai-bot-platform          ai/ (тот же процесс)
        |                        |                        |
        | HTTP-проекция          | HTTP-проекция          | внутрипроцессная
        | + валидация схемы      | + валидация схемы      | проекция
        +------------+-----------+------------+-----------+
                     v                        v
        POST /api/v1/internal/recommendation/resolve/
                     |           resolve(request) -> Decision
        +------------+------------------------------------+
        |  recommendation/  — новое Django-приложение      |
        |  ЕДИНСТВЕННЫЙ публичный модуль: api.py           |
        |    resolve(), типы, реестр кодов, схемы          |
        |  приватно: _stages/S0..S6, _evidence, _tiers     |
        +------------+------------------------------------+
                     v  четыре резолвера (контракт §5)
        бэкенд Ayla — авторитетная правда домена
```

**Почему `recommendation/` — отдельное приложение, а не пакет внутри `ai/`.**
Соглашение репозитория: домены — приложения верхнего уровня (`users`,
`services`, `goals`, `ai`, `appointments`, `tenants`, `wellness`). Внутри `ai/`
резолвер оказался бы под тем же владельцем, что и потребитель C, и первый же
рефакторинг стёр бы границу изнутри. Маршрут — `api/v1/internal/...`, как все
внутренние (`djangoProject/urls.py:32-113`).

### 1.3 Четыре стены границы. У каждой — свой сторож

Граница считается **введённой**, когда стоят все четыре. Три из четырёх —
не документ, а красный билд.

| | стена | формулировка | сторож |
|---|---|---|---|
| **W1** | **форма** | границу пересекает только `RecommendationDecision`. В нём нет строки для показа и нет сырого балла (контракт §4.3, канон §8) | тест схемы: полей `reasoning_text`/`reason_text`/`why_text`/`score` в ответе нет; `EvidenceItem(kind=RATING)` без `review_count` не собирается (§8.4 E1–E2) |
| **W2** | **порядок** | ни одна поверхность и ни один потребитель не содержит собственного упорядочивания множества кандидатов (контракт §2.1 C1) | тест-гард по **обоим** репозиториям: сортировка кандидатов по качеству/близости/рейтингу вне `recommendation/` — красный билд. Список разрешений — сам модуль резолвера |
| **W3** | **происхождение WHY** | потребитель отрисовывает утверждённые `reason_codes`, не изобретает причину (§53 п.2, §7.3) | тест: подмена LLM заглушкой «код → шаблон» не меняет ни одного семантического утверждения; во фронте нет ветки, порождающей текст причины при пустых кодах |
| **W4** | **отказ** | три различимых исхода `OK / UNAVAILABLE / CONTRACT_VIOLATION`; **ответ конформен целиком или не конформен** (§53.1) | тест: частично конформный ответ даёт `CONTRACT_VIOLATION` и пустую выдачу целиком, а не «годные элементы» |

W2 — это и есть та стена, отсутствие которой превращает вариант B в «оставили
как было». Она вводится **в первом же срезе работ**, до миграции хоть одного
потребителя: с этого момента любое **новое** место ранжирования — красный
билд, независимо от того, сколько старых ещё не мигрировали.

### 1.4 Что остаётся снаружи границы и почему это не дыра

* **Полки `layer_1/2/3`** — представление (контракт §16). Полка 1 «твои
  салоны» — не ранжирование, а **scope**: отдельный `resolve` с
  `scope.tenant_refs = тенанты из истории`. Полка 2 — `resolve` с
  исключением этих тенантов. Полка 3 — счётчики категорий, агрегат каталога,
  не рекомендация; остаётся как есть и **явно объявляется не рекомендацией**.
* **Выбор `k`** и форма карточки — поверхность (контракт §9.1).
* **Перевод кода в фразу** — единственная зона `LLM_ALLOWED` (§7.3).

## 2. Что становится потребителем первым

Порядок: **B → C → A**. Он выводится, а не выбирается.

### 2.1 Первый — B, домашний экран Mini App

`users/catalog_recommendations_api.py` → прокси `apps/miniapp_api/views.py`
(`customer_recommendations`) → `apps/miniapp/src/lib/customer-booking.ts`.

Четыре причины, по убыванию веса:

1. **Это P0 (C-02), и §53 предписывает чинить его введением границы, а не
   заплаткой на поле.** Иначе мы сведём два контракта, оставив три авторитета.
2. **Единственный потребитель, у которого ранжирование упраздняется, а не
   переносится.** `_compute_layer_2_score` (:205), `_build_reasoning_text`
   (:261), `RATING_REASONING_FLOOR` (:103) — по контракту §16 **удаляются**.
   Ничего не нужно сперва построить, чтобы забрать у него авторитет.
3. **Внутрипроцессный** — миграция не добавляет сетевого хопа и проверяет
   ровно ту проекцию границы, которая иначе останется непроверенной.
4. **Именно здесь ложное свидетельство выходило человеку как причина.**
   Сегодня оно не видно только из-за C-02 (аудит §4) и выйдет наружу в момент
   стыковки форм — то есть в момент этой самой миграции. Чинить надо **до**
   стыковки, а не после.

**Условие, без которого миграция B вредна.** Снятие рейтинга с WHY (C-03)
в одиночку даёт не хорошую рекомендацию, а пустую: «Принимает записи»
(`RECOMMENDER_GAP_RESEARCH` §1). Поэтому B мигрирует **в паре** с оживлением
курируемой связи «цель → категории» (`_apply_goal_category_filter`, :363) как
первого честного свидетельства S2 с `origin: CURATED_KNOWLEDGE`. Актив уже
оплачен и синхронизирован; сегодня он применяется только при пустом `goal`
(P2-R3). Это единственный пункт плана, взятый из чужого трека, и взят он
потому, что без него первая же миграция обменивает ложь на молчание.

### 2.2 Второй — C, движок LLM-контекста

`ai/application/services/recommendation_engine.py`. Тот же процесс, тот же
репозиторий, наружу человеку напрямую не смотрит — значит цена ошибки ниже,
чем у B и A. И он **отдаёт больше всех**: `_score_rating` (:494, насыщение по
отзывам), `_split_by_review_evidence` (:411), `_load_history_specialist_ids`
(:465) переезжают в резолвер как **реализации** S5 и S4 и не переписываются
(контракт §16). Упраздняется единая сумма 30/25/20/15/10 (:57-61), `score=`
в промпте (`to_prompt_summary`, :200) и `top_reasons` строками (:164).

C идёт вторым, а не первым, потому что до миграции B он остаётся вторым
авторитетом в том же процессе — и порядок B→C гарантирует, что расхождение
`_score_rating` против `_compute_layer_2_score` (DEFECT-C-04) закрывается
**первой** миграцией, а не последней.

### 2.3 Третий — A, бот. И это не удобство, а необходимость

Бот сегодня — **лучшая из трёх поверхностей** по сверке с каноном (аудит §6):
город как фильтр, fail-closed, рейтинг вне ранжирования, точность совпадения,
ротация. Перевести его в потребители **до** переноса S2 означало бы посадить
лучшую поверхность на семантику ILIKE, которая живёт на стороне Ayla
(`_apply_goal_filter`, :349) — то есть **ухудшить продукт границей**.

Поэтому у A два прямых предусловия:

* **PRE-A1 — замер моста идентификаторов.** Резолвер ранжирует над правдой
  Ayla; бот показывает зеркало (`apps/catalog/models.py`: `ayla_service_id`
  :131, `ayla_user_id` :292 — оба **nullable**, у инвайт-строк пусты по
  устройству, :419-432). Доля бронируемых зеркальных строк с непустым ключом
  **не измерена**. Пока не измерена — срок миграции A неизвестен, и это надо
  говорить числом, а не намерением.
* **PRE-A2 — перенос S2** (точность совпадения, стемминг, курируемые ключи
  цели) из `discovery.py:1216-1245` в резолвер над каноническим каталогом.
  Это работа трека наполнения, не моя; план от неё зависит и её не забирает.

**Названная цена, которую нельзя спрятать.** Сегодня бот выдаёт мастеров, даже
когда Ayla недоступна. После миграции — не выдаёт: контракт §14 запрещает
частичное множество, а §10.2 запрещает называть каталог рекомендацией.
Выводимое поведение: при `UNAVAILABLE` бот показывает **поиск по каталогу**,
честно не названный подбором, без выбора «лучшего» (§12.3: нет seed — ярус
показывается равноправным). Это следует из контракта, а не изобретается,
**но человек в этот момент видит другой продукт**, и владелец вправе это
переиграть. Внесено как названная цена в `OPEN_DECISIONS` §58, не как блокер.

### 2.4 Почему поэтапная миграция не противоречит «границе сразу и полностью»

Владелец запретил вырождение B в «оставили как было». Вырождение — это
**резолвер без границы**. План даёт обратное: **граница встаёт первой**, до
единого мигрированного потребителя (срез E0), и с этого момента W2 делает
любое новое место ранжирования красным билдом. Три сегодняшних авторитета
перечислены поимённо в реестре §4.5, и эпик не закрывается, пока хоть одна
строка реестра говорит «авторитет». Ни одна миграция не отложена «на потом
после пилота» — отложен только **вынос в `ayla-ai-core`**, как и решил
владелец.

## 4. Чем доказывается, что авторитет остался один

Пять доказательств. Ни одно не опирается на намерение или на чтение кода
глазами; каждое либо красный билд, либо число с before/after.

### 4.1 Cross-surface тест (§9.5) — доказывает тождество политики

Один `RecommendationRequest`, поданный с `surface = BOT_CHAT` и
`surface = MINIAPP_HOME`, обязан дать **идентичные** `ordered[]`, `tier`,
`reason_codes`. Различаться вправе только `k`. Плюс структурная проверка:
обращений к `request.surface` внутри стадий S0–S6 нет. Пока поверхностей
две и более, а тест зелёный, вторая политика невозможна **по построению**.

### 4.2 Гард W2 — доказывает отсутствие второго места решения

Тест по обоим репозиториям: упорядочивание множества кандидатов по
качеству/близости/рейтингу вне `recommendation/` — красный билд. Это ровно та
проверка, которую контракт назвал сам (§2.1 C1: «не должно остаться ни одного
`order_by` по признаку качества над множеством кандидатов»). Ценность гарда
не в том, что он вычистит старое (это делают миграции), а в том, что он
**делает невозможным появление нового** с первого дня, включая период, когда
не все три потребителя мигрировали.

### 4.3 Измеритель DRF-1556 — доказывает, что расхождение видно и что оно ушло

`recommendationsContractViolation` (`api.ts:244-298`) — уже стоящий детектор,
ложных срабатываний в нём не может быть **структурно**: `try` накрывает ровно
транспорт, проверка формы стоит после и видит только доставленные ответы.
Из этого делается targeted proof в три шага:

1. **до** — тот же детектор на сегодняшнем ответе даёт `diverged`
   (источник отдаёт `{data: {layer_1..}}`, потребитель ждёт
   `{recommendations: [{service_id, score}]}`);
2. **после T7** — новый контракт даёт `ok`;
3. **и остаётся строгим** — подложенный старый ответ по-прежнему даёт
   `diverged`, а частично конформный (§53.1) — `CONTRACT_VIOLATION` целиком.

Шаг 3 обязателен: без него «зелено» доказывает только, что проверку ослабили.

### 4.4 Аналитическая достижимость — доказывает, что авторитет один по следствиям

Функция ранжирования чиста и детерминирована, поэтому множество кандидатов,
которые **не могут** попасть в top-k ни при каком seed, вычисляется без логов
и без трафика (обход P1-R1). Снимается baseline до миграций (T5) и после
каждой.

Утверждение, которое это доказывает, сильнее структурного:
**если две поверхности на один и тот же запрос дают разные множества
недостижимых, авторитета всё ещё два** — сколько бы общих модулей они ни
импортировали. После миграции всех трёх множество обязано быть одно.

## 5. Названные цены и риски

1. **Бот при недоступности резолвера** (§2.3) — человек видит другой продукт.
   Поведение выводимо из контракта, но цена реальная; выносится владельцу как
   названная цена.
2. **Мост идентификаторов** может оказаться дырявым (T10). Тогда срок E3
   определяется не резолвером, а заполнением ключей — и это выяснится
   **до** начала работ, а не в середине.
3. **T11 — чужой трек.** Если он не сделан, E3 не начинается. План этого не
   скрывает и не забирает работу себе.
4. **Пилот и `VERIFIED`-маппинг.** По букве §14.3 рекомендовать нельзя
   ничего; вопрос уже висит у владельца (OD §40.4 п.1), контракт описывает
   оба ответа (§10.4). План не дублирует вопрос, но **E1 нельзя выкатывать
   людям, не получив ответа**: иначе первая же честная выдача будет пустой.
   Удешевление ответа уже найдено: размечать надо подкатегории, а не 265
   услуг — десятки решений, не сотни.
5. **Дев красный** (#1449). Ни одна задача плана не мержится раньше него;
   ребейз до слияния бессмыслен.

## 6. Что в план не входит

* Чем наполнять стадии — `RECOMMENDER_GAP_RESEARCH`, отдельный трек
  (кроме T8 и T11, взятых по названным причинам).
* Вынос в `ayla-ai-core` — после пилота, решение владельца §53.

  не содержит; после E0–E3 вынос — замена реализации за стоящим контрактом.
* Пороги `N_substantiated`, `tau_separation`, 80% расписания — уже висят
  у владельца в существующих задачах, не переспрашиваются.
* P2-R2 (инициатор отмены) и P2-R3 — вне границы; P2-R3 частично закрывается
  T8 как побочный эффект.
