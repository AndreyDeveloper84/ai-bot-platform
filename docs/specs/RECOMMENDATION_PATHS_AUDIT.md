## 1. Резюме: авторитетов не один и не два, а ТРИ

Вопрос трека — кто владеет `RecommendationDecision`. Ответ по коду:
**никто, потому что решение принимают три независимые реализации, ни одна
из которых не знает о существовании остальных двух как о своём источнике.**

| # | авторитет | поверхность | файл (origin/dev) | формула |
|---|---|---|---|---|
| **A** | бот | чат Telegram/MAX | `ai-bot-platform` `apps/marketplace/discovery.py` | точность совпадения услуги → ротация ничьих |
| **B** | домашний экран Mini App | карточки «Ayla подобрала тебе» | `djangoproject` `users/catalog_recommendations_api.py` | `rating*10 + 100/(km+1) + 5·available` |
| **C** | LLM-контекст Ayla | подбор кандидатов в промпт | `djangoproject` `ai/application/services/recommendation_engine.py` | взвешенная сумма 30/25/20/15/10 |

Три формулы. Три разных множества полей. Три разных ответа на один и тот же
вопрос «кто подходит этому человеку». Ни одна не порождает
`recommendation_id`, альтернативы, reason codes или снимок контекста.

**Это и есть cross-system semantic divergence в чистом виде,**
причём (B) и (C) живут в ОДНОМ репозитории и в одном процессе.

## 2. Путь A — бот. Доказан построчно

### 2.1 Фактический путь вызова

```
apps/orchestrator/discovery.py:1071      discover_masters(..., rotation_seed=rotation_seed(conversation))
apps/orchestrator/concierge.py:1870,2316 discover_masters(..., rotation_seed=...)
        |
apps/marketplace/discovery.py:1490       discover_masters  -> тонкая обёртка
apps/marketplace/discovery.py:1583       discover_masters_window   <- НАСТОЯЩЕЕ место решения
        | _bookable_qs (:1347) -> _match_precision (:1216) -> _rotate_ties (:1561)
```

`discover_masters` (`:1490`) сам ничего не решает — он вызывает
`discover_masters_window` и выбрасывает счётчик найденного (`:1521-1529`).
Имя функции обманывает: точка решения — `_window`.

### 2.2 География — жёсткий фильтр, не балл. ПОДТВЕРЖДЕНО

`_bookable_qs`, `discovery.py:1413-1414`:

```python
if city:
    qs = qs.filter(tenant__city__iexact=city)
```

Плюс `:1443-1444` — токен, назвавший город, уходит в `tenant__city__in`, а не
в имя услуги. Ни одного слагаемого от географии в `_match_precision` нет.
**Соответствует канону §9.1 и §29.1.**

### 2.3 Набор кандидатов и отсечение

`discovery.py:1617-1622`:

```python
candidates = list(qs[:_CANDIDATE_SCAN_CAP])   # 200
if rotation_seed:
    candidates = _rotate_ties(candidates, rotation_seed)
total = len(candidates)
masters = candidates[offset : offset + limit]
```

Срез **в Python, после ранжирования и ротации**, а не `qs[:limit]` в SQL.
`total` возвращается наружу — на нём стоит «Показать ещё». Кандидат за
позицией 5 больше не «не запрошен», а «на следующей странице».
**Соответствует §29.6.**

### 2.4 Ранжирование — точность, а не счётчик

`_match_precision` (`:1216-1245`) — `COALESCE(MAX(_row_precision(...)), 0.0)`.
`MAX`, а не `SUM`: счёт даёт **лучшая одна строка услуги** мастера, а не сумма
по всему прейскуранту. `COALESCE(...,0)` load-bearing: без него мастер,
совпавший только по свободному тексту `specialization`, шёл бы NULL, а Postgres
под `DESC` ставит NULL первыми — «не совпал ни с чем» оказалось бы выше
реального совпадения.

Рейтинг в ранжирование бота **не входит вовсе** — в `_match_precision`,
`_bookable_qs` и `_rotate_ties` поля `rating`/`review_count` не читаются.
**Соответствует §29.4** («в сортировку рейтинг пока не включать»).

Цена в ранжирование не входит. Доступность (расписание) не входит.
**Соответствует §29.1 и §29.5** (включается позже, по условию 80%).

### 2.5 Ничьи — стабильная контролируемая ротация. ПОДТВЕРЖДЕНО

`_rotation_key` (`:1542`): `blake2b(seed || master_id)`, где `seed` — id разговора
(`apps/orchestrator/discovery.py:967-979`). Чистая функция пары. Ни часов,
ни `random`.

`_rotate_ties` (`:1561`): сортировка по `(-match_score, _rotation_key(...))`.
Ключ ротации — **вторичный**: где точность различает, её вердикт стоит, ротация
сдвинуть не может. Внутри одного диалога порядок стабилен; между диалогами
первое место распределено равномерно.
**Соответствует §29.6 и канону §9.1** («стабильно для одного, различно между людьми»).

### 2.6 Отказ закрыт, а не открыт

`:1425-1435`: если запрос не разбирается в один токен («я», эмодзи) —
`return qs.none()`, а не «фильтр не применился». Комментарий прямо называет
альтернативу «confidently wrong». Хорошее поведение, редкое: fail-closed.

### 2.7 WHY в боте: его нет, и это честно

`apps/orchestrator/discovery.py:1166-1193` — рендер карточки:

```python
has_rating = card.rating is not None and card.rating >= 1
rating = f" · ★ {card.rating}" if has_rating else ""
lines.append(f"• {card.name}{spec}{service}{rating}{city_suffix}")
```

Бот **не формирует обоснование вообще**. Он печатает имя, специализацию,
услугу, звёздочку и город. Никакого «почему именно этот» не выдаётся.
`review_count` при рендере не читается (гейт только по `rating >= 1`, DRF-1224).

**Следствие:** бот показывает рейтинг 4.9 без единого отзыва — но как
украшение карточки, не как ОСНОВАНИЕ. Это существенно слабее нарушения на
поверхности B, но по инварианту EVIDENCE STRENGTH это всё равно
недоказанное свидетельство на экране человека.

### 2.8 ГДЕ ЛЕЧЕНИЕ НЕ ДОЕХАЛО — три точки сортировки, вылечена одна

DRF-1529 прямо перечисляет три места, которые наследуют решение владельца.

```python
...
```

**Конец потребителя.** `api.ts:217`:


Тела нет. `views.py:2472-2478`: без `Content-Type: application/json` тело

**Конец источника.** `catalog_recommendations_api.py:168-181`:

`_compute_layer_2_score` (`:204-224`) слагаемое расстояния тогда просто не
добавляет. Это ровно `distance_km: None` из замера §41 — но замер снят с

**Города нет вообще.** В `_base_pool` (`:395-410`) фильтр по городу

Отсюда межтенантная выдача `pylca-i-lyon` из замера §41.

> **Канон §9.1: «City/search scope is a filter, not an ordinary ranking score.»**
> Здесь география не фильтр и не балл — её нет. Хуже обоих вариантов.
> А если бы координаты пришли, она стала бы **баллом** (`100/(km+1)`, вес до
> 100 из ~155) — то есть прямо запрещённой формой.

### 3.4 Ранжирование: рейтинг — единственный различитель. ДОКАЗАНО

`_compute_layer_2_score` (`catalog_recommendations_api.py:204-224`):

```python
score = 0.0
if specialist.rating is not None:
    score += float(specialist.rating) * 10.0      # 0..50
distance = _specialist_distance_km(...)
if distance is not None:
    score += 100.0 / (distance + 1.0)             # НИКОГДА не срабатывает (3.3)
if specialist.is_available:
    score += 5.0                                  # константа: is_available — предусловие пула
return score
```

`is_available=True` — уже условие `_base_pool`, значит `+5` получают **все**
и различить никого не может. Расстояние всегда `None`. **Остаётся `rating*10`
и ничего больше.** Ранжирование поверхности B есть сортировка по рейтингу.

Канон §9.1: «Rating is a **secondary** quality/tie-break signal after relevance
and execution viability». Здесь рейтинг — **единственный первичный** сигнал.

### 3.5 Ничьи: `str(id)` под отсечением до трёх

`:424-427`:

```python
scored.sort(key=lambda pair: (-pair[1], str(pair[0].id)))
top_n = scored[:LAYER_2_LIMIT]      # LAYER_2_LIMIT = 3
```

Ничья разводится лексикографикой UUID. Это тот же класс, что алфавит: чистая
функция идентификатора, одинаковая для всех людей и на все времена, под
отсечением в три. Мастер с «неудачным» UUID при равенстве не показывается
**никому и никогда**. Контролируемой ротации нет.
**Нарушение канона §9.1** (запрет лексикографического fallback при top-N
и требование распределять экспозицию между людьми).

Слой 1 — `order_by("-rating","id")[:5]` (`:400-404`) — то же самое.

### 3.6 WHY: строка для показа, собранная источником. И она лжёт

`_build_reasoning_text` (`:261-297`) и константа `:105`:

```python
RATING_REASONING_FLOOR = Decimal("4.5")
...
if specialist.rating is not None and specialist.rating >= RATING_REASONING_FLOOR:
    parts.append(f"Рейтинг {format(specialist.rating,'g')}")
```

**`reviews_count` в этом условии не проверяется.** Комментарий у константы
говорит «Below this we omit it to avoid surfacing weak signals as
endorsements» — то есть автор ДУМАЛ про силу свидетельства и защитился не от
того: порог поставлен на значение оценки, а не на её обоснованность.

Порядок фактов: цель → расстояние → рейтинг → фолбэк «Принимает записи».
Цель не приходит (пустой payload). Расстояние не приходит. Остаётся рейтинг.
**Отсюда дословное «Рейтинг 4.9» у всех строк замера §41** — не совпадение,
а единственная достижимая ветка.

Отдаётся **строка `reasoning_text`**, а не `reason_codes` + `evidence`.
Потребителю передан готовый текст для показа человеку.

`djangoproject services/management/commands/seed_demo_salons.py:379-383`:

Настоящий пересчёт — `reviews/views.py:29-52`, `Avg(rating)`/`Count(id)` по

Отзывов на контуре ноль (DRF-1527: 31 бронируемый мастер, отзывов > 0 — **ни у

**Полная цепочка происхождения числа «4.9»:**

```

   поставлен, чтобы пройти порог AI_SPECIALIST_MIN_RATING=4.0 движка (C)
   прочитан ЧУЖОЙ поверхностью (B), про порог движка не знающей

```

Автор сида честно отказался выдумывать отзывы. Число, поставленное как
техническая заглушка порога, вышло на экран как свидетельство.
**Это точный механизм нарушения EVIDENCE STRENGTH — и он не про небрежность,
а про отсутствие границы: у поля `rating` нет владельца, объявившего его
семантику.**

### 3.8 Семантика услуги: ILIKE по названию, канонического слоя нет

Исключение в лучшую сторону: `_apply_goal_category_filter` (`:363-390`) ходит

### Что это меняет

## 5. Путь C — движок LLM-контекста. Третий авторитет

`ai/application/services/recommendation_engine.py` → `SpecialistContextBuilder`
(`ai/application/services/specialist_context_builder.py:95`) →
`ai/concierge_factory.py:118`, `ai/tools_handlers.py` → системный промпт.

### 5.1 Одна глобальная формула — ровно то, что канон запрещает

`recommendation_engine.py:57-69`:

```python
WEIGHT_RATING = 0.30
WEIGHT_DISTANCE = 0.25
WEIGHT_AVAILABILITY = 0.20
WEIGHT_SERVICE_MATCH = 0.15
WEIGHT_HISTORY = 0.10
```

Канон §9: «**Ayla does not use one global ranking formula.** Candidate
resolution is staged». Здесь — одна взвешенная сумма, где семантическое
совпадение услуги весит 0.15, а рейтинг 0.30, вдвое больше. Стадий нет:
жёсткие ограничения и качество смешаны в одном числе, то есть
**жёсткое ограничение компенсируется баллом** — прямой запрет §9.1.

Докстринг `:14-16` заявляет: «Designed to be **the** ranker. The recommendation
API endpoint (Phase 6, when added) **will also call this**». Эндпоинт (B)
написан и **не зовёт** движок — он реализовал свою формулу. Доказательство
того, что «единый ранкер» существовал только в комментарии.

### 5.2 И при этом ЭТОТ авторитет вопрос отзывов решил ПРАВИЛЬНО

`_score_rating` (`:494-517`):

```python
pure = max(0.0, (float(s.rating) - 1.0) / 4.0)
saturation = s.reviews_count / (s.reviews_count + REVIEWS_SATURATION)   # 10
return pure * saturation
```

При `reviews_count == 0` насыщение = 0, весь 30%-й вклад рейтинга обнуляется
**независимо от значения поля**. Плюс `_split_by_review_evidence` (`:411-463`,
DRF-1433): порог `min_rating` — защита от плохих оценок, а не от их
отсутствия; неоценённые берутся отдельной выборкой и сортируются по `id`,
потому что «у группы без отзывов `rating` ничего не значит».

> **Это самое дорогое наблюдение аудита.** Один и тот же репозиторий, один
> процесс, одно поле `SpecialistProfile.rating`, один и тот же вопрос — «можно
> ли считать рейтинг без отзывов свидетельством». Движок (C) ответил «нет» и
> написал два механизма защиты. Эндпоинт (B) ответил «да» и печатает
> «Рейтинг 4.9» человеку. DRF-1433 вылечил одного носителя политики и не мог
> вылечить второго — потому что политики нет, есть две реализации.
>
> **Расхождение бота и мини-приложения — не единственное. Оно есть и ВНУТРИ
> бэкенда.** Любой контракт, который разведёт только бота и Mini App,
> оставит этот разрыв нетронутым.

### 5.3 Сырой балл и готовые строки уходят в LLM

`to_prompt_summary` (`:200-222`):

```python
f"- {c.id} | {c.display_name} | ★{c.rating} ({c.reviews_count} отз.){distance}{services} | score={c.score:.2f}"
```

`top_reasons` (`:164-176`) отдаёт готовые русские строки «Высокий рейтинг»,
«Близко», «Свободные слоты», отфильтрованные по вкладу > 0.05.

Два нарушения:

* канон §8: «Numerical internal ranking scores… are not a public semantic
  API». `score=0.72` кладётся в промпт, то есть становится входом для того,
  кто пишет текст человеку;
* **EVIDENCE ORIGIN**: обоснование, которое увидит человек, дальше сочиняет
  модель по этой строке. Порождение WHY моделью — `LLM_FORBIDDEN`
  (происхождение свидетельств). В плюс: `★{rating} ({reviews_count} отз.)` —
  единственное место во всей системе, где рейтинг и число отзывов идут
  **рядом**; но решение, что с этим делать, оставлено модели.

### 5.4 Доступность — заявленная и фактическая

`_score_availability` весит 0.20, но докстринг `:23-29` признаёт: это
«cheap proxy» — `is_booking_enabled` + наличие строк `working_hours`.
Замер §29.5: `WorkingHours` у 4 из 31, `SlotConfig` — 0 строк.
То есть 20% веса стоят на признаке, который у 27 мастеров из 31 не заполнен,
и **отсутствие расписания складывается с занятостью** — запрещённое схлопывание
UNKNOWN (общий бриф: `UNKNOWN ≠ 0 ≠ false`). §29.5 требует третьего состояния.

`_score_distance` (`:519-531`) при `None` возвращает **0.5** — «нейтрально».
Это тоже подстановка значения вместо UNKNOWN: неизвестная география получает
половину балла и участвует в ранжировании наравне с измеренной.

## 8. Дефекты, найденные попутно

**DEFECT-C-01 (P1)** — алфавитный fallback под отсечением жив на двух из трёх
точек сортировки бота: `apps/orchestrator/handoff.py:456-465`,
`apps/marketplace/discovery.py:2240,2249`. Нарушает канон §9.1 и решение
владельца §29.6. Лекарство (`_rotate_ties`, `rotation_seed`) уже написано и
покрыто тестами — его просто не позвали. DRF-1529 закрытой считаться не может.

**DEFECT-C-02 (P0)** — см. §4. Расхождение форм ответа между
`catalog_recommendations_api` и `customer-booking.ts`, проглоченное пустым
`catch`, с нулевой наблюдаемостью.

**DEFECT-C-03 (P1)** — `RATING_REASONING_FLOOR` защищает от низкой оценки и не
защищает от отсутствия оценки (`catalog_recommendations_api.py:105,286-292`).
Прямое нарушение EVIDENCE STRENGTH. Не проявляется наружу только из-за
DEFECT-C-02; чинить надо раньше, чем C-02.

**DEFECT-C-04 (P1)** — две противоречащие политики по одному полю в одном
процессе: `_score_rating` (обнуляет вклад при `reviews_count=0`) против
`_compute_layer_2_score` (использует сырой `rating`). DRF-1433 вылечил один
носитель из двух.

**DEFECT-C-05 (P2)** — `_score_distance` подставляет `0.5` при неизвестной
географии, `_score_availability` считает незаполненное расписание отсутствием
слотов. Оба — схлопывание UNKNOWN в число.

**DEFECT-C-06 (P2)** — сырой `score` и готовые строки-обоснования уходят в
системный промпт (`to_prompt_summary`, `top_reasons`), после чего WHY для
человека сочиняет модель.
