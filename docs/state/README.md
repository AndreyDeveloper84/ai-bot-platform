# `docs/state/` — состояние, которое можно проверить одной командой

## Зачем это заведено

Файлов состояния у проекта и без того много: `docs/OPEN_DECISIONS.md` (~5900
строк), `docs/OPEN_QUESTIONS_OWNER.md`, `docs/CLIENT_QUEUE_AUDIT.md`,
`docs/ORPHANED_DEFECTS_AUDIT.md`, `docs/HANDOFF_*.md`, планы в `docs/specs/`,
контрольные точки окон на шине. **Беда не в том, что файлов нет. Беда в том, что
ни один из них нельзя проверить на свежесть.** Они записывают вывод, но не
записывают, чем он снят и как его перепроверить.

Только за 08.09.2026 протухшими оказались:

* план дневника, слитый в `dev` — описывает как открытые строки 1.1–1.4,
  которые слиты в PR #1482;
* строка §33 в `OPEN_DECISIONS` — дефект уже починен;
* две трети очереди клиентского окна (аудит 07.09: 32 строки из 63 держались
  открытыми на работе, которая уже сделана);
* три слитые задачи, лежащие в Linear в `Backlog`;
* комментарий в `config/settings/base.py:861` про три ручки `customer/food/*`,
  которых не существует ни одной.

Этот каталог — **не одиннадцатый пересказ**. Это слой поверх остальных, в
котором каждый факт несёт команду своей перепроверки. Развёрнутые разборы
остаются там, где они были: сюда идёт утверждение, место, команда и ссылка на §.

## Главное правило

> **Строка без поля `проверка` в этот файл не кладётся.**

Не «желательно», не «по возможности». Факт, у которого нет способа
перепроверки, — это мнение, а мнение через полгода неотличимо от протухшего
факта. Проверялка отдельно печатает такие блоки списком «БЕЗ ПОЛЯ проверка» и
возвращает ненулевой код: файл с ними считается сломанным.

Если команду придумать **нельзя** — так и пишется: `проверка: нечем`, и
обязательно `почему:` с объяснением. Таких блоков должно быть мало, и они сразу
видны. Честно перечисленная дыра замера дороже придуманного факта.

## Формат блока

```
### Блок «Ayla подобрала» рисует услуги, а решено — мастеров
статус:   СЛОМАНО
где:      apps/miniapp/src/screens/CustomerCatalogScreen.tsx:203
проверка: git grep -c "ServiceCard" origin/dev -- apps/miniapp/src/screens/CustomerCatalogScreen.tsx
ожидание: >0
снято:    2026-09-08 @ 8c276fa (ai-bot-platform)
задача:   §81 / T6
```

| поле | обязательно | что значит |
|---|---|---|
| `### заголовок` | да | утверждение одной строкой, читаемое без контекста |
| `статус` | да | `РАБОТАЕТ` / `СЛОМАНО` / `В РАБОТЕ` / `ЖДЁТ ВЛАДЕЛЬЦА` / `НЕ ЗАМЕРЕНО` |
| `где` | да, кроме `нечем` | путь и строка — где смотреть глазами |
| `проверка` | **да, всегда** | команда перепроверки либо слово `нечем` |
| `ожидание` | да, кроме `нечем` | что она обязана вернуть |
| `снято` | да | `ДАТА @ SHA (репозиторий)` — когда и на чём снималось |
| `задача` | нет | DRF-номер или § решения владельца |
| `почему` | только при `нечем` | почему команду придумать нельзя |

Блок начинается заголовком `###` и кончается следующим заголовком любого уровня.
Разделы файла (`## Работает`, `## Сломано или отсутствует`, `## В работе`,
`## Ждёт владельца`, `## Замер не снят`) — заголовки `##`.

**Раздел «Замер не снят» обязателен и не должен быть пустым ради красоты.**

## Требования к полю `проверка`

* **Только чтение и только эти команды:** `git grep`, `git show`, `git ls-tree`,
  `git log`, `git merge-base`; плюс `gh run list` и `gh pr list` / `gh pr view`
  там, где факт про прогон CI или PR. Всё остальное проверялка не исполняет, а
  печатает как «проверка отклонена» и возвращает ненулевой код.
* **Команда воспроизводится из корня репозитория** и ссылается на `origin/dev`,
  а не на рабочее дерево. Рабочее дерево у каждого своё; `origin/dev` — общее.
* Репозиторий берётся из скобок в поле `снято`: `(ai-bot-platform)` — этот
  чекаут, `(djangoproject-catalog)` или `(beautygo_backend)` — соседний
  Ayla-бэкенд, который проверялка ищет рядом с главным чекаутом. Другой путь
  задаётся флагом `--repo ИМЯ=ПУТЬ`.
* Перед запуском нужен свежий `git fetch origin dev` в обоих репозиториях —
  проверялка сама в сеть за ветками не ходит. Поэтому она **не подключена к
  CI**: `actions/checkout` тянет только голову PR, ссылки `origin/dev` там нет,
  и все проверки покраснели бы на упавшей команде. Это запуск для человека и
  для окна, а не гейт прогона.

### Как читается `ожидание`

* `есть` / `нет` — вывод непустой / пустой. Так проверяется присутствие или
  отсутствие файла через `git ls-tree`.
* Число или сравнение: `0`, `>0`, `=3`, `>=2`, `<10`, `!=1`. Число из вывода
  добывается так:
  1. если **каждая** непустая строка кончается на `:<цифры>` — берётся сумма
     (это формат `git grep -c`);
  2. иначе, если весь вывод — одно целое число, берётся оно;
  3. иначе берётся количество непустых строк (`git ls-tree`, `git grep -l`,
     `git log --oneline`).
* Любая другая строка — подстрока, которая обязана встретиться в выводе. Если
  важны пробелы по краям, возьмите её в двойные кавычки.

### Чего команда делать не должна

Никаких конвейеров и редиректов: команда исполняется списком аргументов **без
шелла**, поэтому `|` внутри `git grep "a\|b"` — это просто символ регулярного
выражения, а `foo | bar` без кавычек станет тремя аргументами git и упадёт
громко. Ничего, что пишет, ставит, качает или ходит в сеть, кроме `gh`.

## Как запускать

```bash
git fetch origin dev                  # и то же самое в соседнем репозитории
python tools/state_check.py           # все направления
python tools/state_check.py --file client
python tools/state_check.py --timeout 30
python tools/state_check.py --repo djangoproject-catalog=/путь/к/ayla
```

Проверялка печатает три списка — **держится**, **ПРОТУХЛО**, **не проверено** —
и, если формат нарушен, ещё два: «проверка отклонена» и «без поля проверка».

Коды возврата: `0` — всё держится; `1` — есть протухшее; `2` — нарушен формат
(команда не из белого списка, блок без `проверка`, каталог не найден).

## Правило добавления факта

**Пересказ источника — не источник.** Перенося факт из чужого отчёта, прогоните
его сами той командой, которую для него пишете. Если команда даёт не то —
неверен либо факт, либо команда, и то и другое чинится ДО записи. Это половина
ценности формата: при первом сборе этого каталога так вскрылись, например,
восстановленная клавиатура у повтора отказа (`concierge.py`, DRF-1576),
выложенный на пилот `8c276fa` и открытый PR #1487 — все три отчёта разведки
описывали их иначе.

Отсюда следствие, которое не надо пугаться увидеть: **на первом прогоне
протухшего быть не должно** — всё, что не подтвердилось, исправлено до записи.
Польза начинается со ВТОРОГО прогона, через день или неделю, когда код уехал, а
файл остался.

## Границы

Этот слой **добавляется, а не заменяет**. `OPEN_DECISIONS.md`, `HANDOFF_*`,
аудиты и планы не переписываются и не сокращаются. Здесь — только то, у чего
есть проверяемое следствие, примерно 15–40 фактов на направление; разбор
остаётся в источнике, сюда идёт ссылка на § или DRF-номер.
