## 4. Куда ушли силы 14–16 августа

Ни одна задача этих трёх дней не входит в восемнадцать экранов P0. Работа шла на **стороне предложения**:

- салонный бот и онбординг сотрудников по коду;
- кабинет мастера — день, записи, расписание, клиенты, услуги, биллинг;
- салонная админка — одиннадцать экранов, команда, услуги, деактивация, внутренний чат;
- операционка — закрытие визита, автозакрытие, день салона.

Это не ошибка сама по себе: кто-то должен исполнять запись, и без исполнителя клиентский цикл упирается в пустоту. Но **как P0-стратегия это другой продукт**: доказывается гипотеза «салон может работать через Ayla», а не гипотеза «пользователь достигает цели, и Ayla ведёт его к ней».

## 5. Что это значит для гипотезы

P0 в этом документе поставлен так, что доказывает **цикл трансформации**. Текущий контур не может его доказать даже теоретически: нет ни цели, от которой считать прогресс, ни baseline, ни повторного замера.

При этом **Food Scanner — единственная построенная часть верхнего контура**, и построена целиком. Это единственное место, где Ayla фиксирует состояние пользователя, а не его запись к мастеру.

**INFERRED, но твёрдо:** если гипотезу трансформации решено доказывать, дешёвый путь начинается не с нуля, а с Food Scanner — там уже есть регулярный контакт с пользователем и данные о нём. Не хватает цели, к которой эти данные привязать.

## 6. Решение, которое обязан принять владелец

Промпт ниже нельзя запускать, пока не выбрано одно из трёх:

1. **P0 остаётся как написан** — тогда весь текущий контур это подготовка стороны предложения, и клиентский цикл надо строить с нуля, начиная с Goal Creation. Двенадцать отсутствующих экранов.
2. **P0 переопределяется под пилот** — тогда этот документ устарел целиком, и §12 больше не действует: booking-архитектура становится намеренной, а не нарушением.
3. **P0 сужается до одной вертикали** — например «питание → цель → еженедельный замер → прогресс», где booking пока не участвует. Тогда достраивается верх над Food Scanner, а салонная часть живёт отдельной дорожкой.

## Роль

Ты работаешь над проектом **Ayla**.

Твоя задача --- провести точную ревизию клиентского **P0 MVP** и
сформировать/проверить реестр экранов клиентского приложения.

Не проектируй весь будущий продукт и не расширяй scope по собственной
инициативе. Сейчас нас интересует именно **P0 MVP** --- минимальный
vertical slice, который должен доказать основную продуктовую гипотезу
Ayla.

## Главная цель P0 MVP

P0 должен доказать полный пользовательский цикл:

> **пользователь формулирует Transformation Goal → Ayla формирует
> baseline → показывает желаемый результат и прогноз → создаёт
> персональный план → пользователь выполняет действия → получает
> релевантную рекомендацию → при необходимости записывается к
> специалисту → возвращается на check-in → видит прогресс → план
> корректируется.**

Это важнее количества функций.

Ayla нельзя сводить к обычному каталогу специалистов или системе
онлайн-записи.

Раздели найденные проблемы:

## P0 Blockers

Без них MVP journey невозможно пройти.

## P0 Gaps

Journey работает, но нарушен обязательный контракт или acceptance
criterion.

## P1

Нужно вскоре после MVP, но не блокирует доказательство основной
гипотезы.

## Later

Не требуется для текущего MVP.

Не повышай severity только потому, что функция выглядит полезной.

# 17. Owner Decisions

Все места, где нельзя получить однозначный ответ из канона или кода,
вынеси отдельно:

  OD   Вопрос   Варианты   Рекомендация   Что блокирует
  ---- -------- ---------- -------------- ---------------

Не принимай product decision за владельца.

------------------------------------------------------------------------

# 18. Проверка фактической реализации

Не доверяй:

-   названию файла;
-   README;
-   старому roadmap;
-   TODO;
-   комментариям;
-   заявлению другого агента.

Проверяй фактический код.

Для каждой важной функции различай:

``` text
documented
implemented
wired
tested
production-ready
```

Это пять разных состояний.

# 20. Definition of Done

Работа считается завершённой только если можно однозначно ответить:

1.  Какие экраны действительно входят в P0?
2.  Какие из исходных 18 экранов подтверждены актуальным каноном?
3.  Нужно ли добавить Chat/Conversation как отдельный P0 surface?
4.  Какие экраны являются самостоятельными screens, а какие лучше
    реализовать как state/modal/bottom sheet?
5.  Какие экраны уже реализованы?
6.  Какие реализованы частично?
7.  Какие отсутствуют?
8.  Какие backend API уже существуют?
9.  Где отсутствует связка mobile ↔ backend?
10. Какие P0 blockers существуют?
11. Какие owner decisions необходимы?
12. Можно ли сегодня пройти P0 journey end-to-end?
13. Если нельзя --- какой минимальный набор работ делает его проходимым?

# Формат финального отчёта

Верни результат строго в следующем порядке:

1.  **Executive Summary**
2.  **Canonical P0 Scope**
3.  **P0 Screen Registry**
4.  **End-to-End Journey Matrix**
5.  **Architecture / Domain Dependencies**
6.  **Backend Readiness**
7.  **Mobile Readiness**
8.  **P0 Blockers**
9.  **P0 Gaps**
10. **P1 / Later**
11. **Canonical Conflicts**
12. **Owner Decisions**
13. **Minimal Implementation Plan**
14. **Recommended execution order**
15. **Final GO / NO-GO assessment**

В конце дай краткий ответ:

> **Можно ли прямо сейчас реализовывать P0 клиентского приложения без
> дополнительных архитектурных решений?**

Ответ должен быть одним из:

-   `GO`
-   `GO WITH BLOCKERS`
-   `NO-GO`

И перечисли конкретные причины.

Главный принцип: **не проектируй желаемую Ayla вместо существующей Ayla.
Сначала установи canonical truth, затем фактическую реализацию, затем
gap между ними.**
